# SWCraft 0.19.0

Released 2026-10-23. The release of an assistant that asks the server instead of reading the model.
The assistant profile carries the model's schema, so the agent knows it before its first call. A
question that used to take a walk through the model is now one call: find an element by a
half-remembered name, count the components rated B, list the ports nothing connects, remove a
component with everything that hangs on it, see what a change touches, ask whether 40 KB still fit
into a memory, ask who realises a requirement and which links need confirming. On the same architect
tasks an agent needs about a third of the calls it needed with 0.18.1, and the requirement tasks
take about two calls each and are all answered right, where before this release's requirement work
they took seven to ten and about half went wrong.
Two MCP tools leave the server, and three answers change their default form; *What upgrading takes*
at the end is the recipe, and its one step every project needs is copying the new assistant profile.
The model's format is unchanged.

## The assistant knows the schema before its first call

The assistant profile that *SWCraft: Onboard Project* writes now carries the model's schema: every
layer, its fields and which of them are required, generated from the model's contract. The agent no
longer spends its first calls on `discover`, its views and one read per layer to learn what a
component or a task looks like; it writes a change straight away, and the server checks it when it is
staged.

Three things support that:

- **A project-wide `discover` answers the `baseline` form** by default: the server's passport, the
  `reads` block (the read forms and the computed values the server offers) and the baseline token,
  with an empty `layers`, because the profile carries the layers. A client that wants them asks for
  `form: "summary"` or `"full"`, as before.
- **`read` takes several addresses** in one call (up to 16), and **a `read` with no address answers
  the model's map**: every layer's element count, and the names of each layer of at most fifty
  elements. On a large model the map stays a few kilobytes, because a long layer is counted, not
  listed.
- **`change_set` with `complete: true`** lets the server finish a new or edited component whose
  application data types are not mapped yet: it adds the mapping the model needs, and the review shows
  which rows the server added and which the client sent.

The profile's rules changed with it: change without reading first, never check again after a commit
that succeeded, read a component's dependents before removing it, and answer a long list with its
number and the first twenty names (the rest by a list request), never with a pattern or a range.

## Questions in one call

- **`find`, a new MCP tool**, resolves up to 16 names at once across every layer and the ports,
  runnables and other members: exact first, then ignoring case, then by whole words or their
  beginnings (`brake temp` finds `BrakeTemperatureSensor`), then the nearest spellings. Each name
  gets up to five candidates, each with the address to send back unchanged.
- **A misspelled reference names the nearest candidates.** When a `change_set` names an element or
  member that does not exist, the refusal lists what it probably meant, so a typo costs one short
  answer instead of a search.
- **`remove` with `with_dependents: true`** removes a component together with what would be left
  pointing at it: its connectors, the composition members of its type with their delegations, the
  task entries and sequence steps that name it (a sequence left with no step goes whole). A referrer
  your own operations in the same change set moved elsewhere is left alone, and the review lists
  every row the server added. It applies to the removal of a whole component only, and a
  requirement's `derived_from` is not unlinked.
- **New computed values:** `unconnected` (the ports no connector and no delegation reaches, with
  their direction and interface), `core` (a task's partition and its core), and a `rating` on
  `effective_level` (the plain level, `B` for `B(D)`).
- **`where` over computed values, and `count`.** A read can now filter on a computed value it asks
  for, and `form: "count"` answers just the number:

  ```json
  {"address": {"layer": "swc"}, "form": "count", "derived": ["effective_level"],
   "where": [{"field": "derived.effective_level.rating", "equals": "B"}]}
  ```

  "How many components are rated B" is one call and one number, however large the model. A `where`
  over a computed value the request does not ask for is refused.

`swcraft query --request` accepts the same `where` over computed values; it refuses `count`, which on
the command line is the row count of an `index` request.

## Answers bounded by the question

- **`impact_of` counts first.** `form: "count"` answers, per layer, how many elements a change would
  reach and of which kinds, in about two hundred bytes on any model. `summary`, still the default,
  and `full` stay, paged as before.
- **`resource_report` answers a resource and a fit.** With no arguments it gives one row per core and
  per memory (usage, limit, headroom, status), the findings and the topology. With `core` or `memory`
  it answers that resource with its consumers, and with `fits` (`{"memory": "RAM2", "bytes": 40960}`,
  or `{"core": "CORE2", "utilization": "0.05"}`) whether the amount fits, by the report's own
  arithmetic and threshold. The answer is yes, no, or unknown when a strict budget has a consumer
  without a declared figure. The MCP tool answers structured data instead of the rendered text;
  `swcraft resource-report` prints its text as before.
- **`model_diff` summarises first.** By default it answers per layer the counts of added, removed
  and changed elements and up to fifty names per kind of change, the rest counted; `form: "full"` is
  the old text. Either form is now refused, not cut, when it is over the answer budget, and the
  refusal names `swcraft diff`. The Change Report stays the form for a person.
- **A removed element is shown as its summary** in the `change_set` response and the review: its
  identity, its required fields and references, and each collection's count, marked
  `before_form: "summary"`, with what was left out counted. The server's own safety checks still read
  the whole element; the full value is a `read` away before you approve, and in git after.

## Two MCP tools withdrawn

`check_port_compatibility` and `check_connector_consistency` are no longer MCP tools. The server
checks a connector's two ends when the change set is staged, and the refusal names both interfaces;
the whole-model connector check is part of `swcraft check-model` and `swcraft validate`, where it
stays. Neither command changes. With `find` added, the MCP server has twelve tools.

## Requirements

The assistant can now answer requirement questions in one call:

- **Who realises a requirement, whether it is allocated, which links need confirming:** three
  computed values on the requirements layer. `realised_by` lists every component, port, runnable and
  other element whose `satisfies` names the requirement, with the version it states; `allocation`
  says whether anything realises it; `stale_links` lists the links stated at an older version. They
  are classified exactly as `check-model`'s trace warnings classify them, and can be filtered and
  counted like the others.
- **Requirements about a topic:** `find` with `text` answers the requirements whose id, title and
  description hold every word of the phrase, as a whole word or its beginning, up to sixteen with
  the rest counted.
- **Candidates for a requirement:** `find` with `for_requirement` answers the trace link search's
  ranking for that requirement, the same as `swcraft experiment trace` ranks it, with the shared
  terms as the reasons and the links it already has. The assistant explains them; you decide, as in
  the Trace Links view.
- **Confirming links at a new version:** an `update` of a requirement's `version` with
  `confirm_links: true` moves every link stated at another version, or at none, onto the new one;
  the review shows each link removed and added. It also works with the version unchanged, after a
  requirements import has raised it.
- A `change_set` operation refused for a missing or an extra `value` now says what to send instead.

`find` for a requirement lists at most sixteen existing links; past that, `existing_links_more`
counts the rest and `existing_links_read` is a `read` request to send back as is (then with `after`)
that pages every link.

Every integer field of the editing protocol now reads a number with no fractional part as the
integer, as the published schema always did: `candidates: 2.0` is `2`, `limit: 50.0` is `50`. A
fraction, `true` or a string is still refused, now also over MCP for `read`'s `limit` and `find`'s
`candidates` (before, a boolean or a numeric string was accepted there).

## The calls an agent needs

Seventeen architect tasks (nine questions about the model, eight changes) on a small model of about
120 elements and on a generated large one of about 150 components, 1 200 interfaces and 1 450 connectors
around a 550-port hub, with Copilot. Each row adds to the one above it; the figures are calls per
task run and the tasks answered right.

| | Small model | Large model |
|---|---|---|
| 0.18.1 | about 9, all | not measured |
| schema in the profile, the map, batched reads | about 4, 33 of 34 | about 5.5, 31 of 34 |
| + `find`, nearest names, remove with dependents, computed values with `where` and `count` | about 3, all | about 3, all |
| + answers bounded by the question, two tools withdrawn | about 2.5, all | about 4, 16 of 17 |
| 0.19.0, with the requirement questions | about 3, all | the row above stands |

The large model's seventeen tasks were not measured again on the release's own build; the row above
it, the build without the requirement work, stands for them. Seven requirement tasks, measured on
the second row's build and on 0.19.0: on the small model about 7 calls a task with 2 to 4 of 7 right,
then about 2 with all 7 right; on the large model about 10 with 4 or 5 of 7 right, then about 2 with
all 7 right.

What these figures do not show:

- **"Does 40 KB fit into the memory a core reaches" is answered wrong on the large model.** The agent
  asks for the core's resources, reads a headroom of about 27 KB and answers "yes" without asking
  `fits`; a profile sentence telling it to ask did not change that. On the small model it asks and
  answers right. Until the answer itself carries the verdict, read a fit from `fits`, not from a
  headroom.
- **The large model costs more calls than the small one once answers are bounded:** about 4 against
  2.5. With the forms before it the two were even.
- **One question regressed with Codex** on the small model at the release's build (which components
  sit in a partition); it passed on the build before. Codex otherwise answered 7 to 8 of the 9
  questions on either model.
- Each figure from the third row on is one run per task, not a median.

`contractVersion` stays `12.0.0`. No model file needs an edit.

python-build-standalone build of 2026-09-01), `elkjs` 0.12.0 inside the `swcraft-tools` package, and
the two extensions of the pack, Red Hat XML 0.29.3 and Red Hat YAML 2.0.0, which is still the
Marketplace's newest release. The archive carries the same packages as 0.18.1. The Linux archive measures
**197 995 524 bytes** (SHA-256 `cd26c304…8116084`) and the Windows archive **202 045 641 bytes**

more than 0.18.1's.

## What upgrading takes

1. **Install the 0.19.0 archive, then set `toolchain_version: "0.19.0"`** in each project's
   `swcraft.yaml`. Until you do, every command that writes or gates refuses a project pinned to
   0.18.x with the pin sentence. The read-only commands (`diff`, `impact`, `list`, `query`,
   `resource-report`) and `swcraft guard` only print a warning, so Copilot keeps working meanwhile.

2. **Run *SWCraft: Onboard Project* again, in every project.** This is the step that matters this
   time. The MCP server's project-wide `discover` now answers the `baseline` form by default, to
   every MCP client, and the schema it no longer sends is in the new profile. A project keeps its old
   profile until it copies the new one, and an old profile still sends the agent to `discover` for
   the schema, where a bare `discover` now answers an empty `layers`. Onboarding overwrites the
   profile, the Copilot instructions and the model guard, so keep a copy of anything you edited in
   them. A client of your own that reads the schema from `discover` asks for `form: "summary"`
   explicitly.

3. **A client that calls `check_port_compatibility` or `check_connector_consistency`** over MCP gets
   an unknown-tool error. Stage the connector instead (the refusal names both interfaces), or run
   `swcraft check-model` for the whole model.

4. **Three answers change their default form** for an MCP client that reads them:
   - `model_diff` answers the summary; ask `form: "full"` for the old text, which is now refused
     rather than returned when it is over the answer budget;
   - `resource_report` answers structured data instead of the rendered text; `swcraft
     resource-report` is unchanged;
   - a `remove`'s `before` in the `change_set` response and the review is the element's summary
     (`before_form: "summary"`); `read` the element before approving if you need all of it.

5. **A client that parses `find`'s candidates answer strictly** will meet two new optional keys,
   `existing_links_more` and `existing_links_read`, when a requirement has more than sixteen links;
   and over MCP `true` or `"2"` is no longer accepted as an integer for `read`'s `limit` or `find`'s
   `candidates`.

The model's files, the hook file `.github/hooks/swcraft.json` and the generated ARXML are unchanged
from 0.18.1. A project on 0.17.x or earlier follows [0.18.0's note](0.18.0.md) first.
