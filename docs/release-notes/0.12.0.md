# SWCraft 0.12.0

**Released 2026-09-17** (the bump commit; the tag follows the `verify` gate on both self-hosted
runners, Linux and Windows, on this commit, and the tag's own run publishes the release archives to
the NAS). This note was written with each change rather than after it, so every figure below was
measured on the host and at the commit that produced it.

## The diagrams are drawn by SWCraft, as UML/SysML views, and open as files

0.11.0 was withdrawn because of its diagrams: the viewer they needed was 7 535 files that took over
thirty minutes to install under an anti-virus scan, and one connector from a component to itself
emptied every diagram it drew. This release replaces that whole stack. **`swcraft generate c4`,
the `.c4` file, the LikeC4 extension, the diagram viewer the installation started and the files it
ran on are gone.** In their place `swcraft generate diagrams` draws the model the way an AUTOSAR
architect reads it and writes plain files into the manifest's `views_root` (`views/` by default):

- **An internal block diagram per composition**, `ibd-<composition>.svg`: every member with every
  port of its type — connected or not, since a port that hangs unconnected is information — the
  connectors port to port, and the composition's own boundary ports on its frame with their
  delegations drawn as lines to the member ports. Ports carry the AUTOSAR glyphs: a square on the
  border, a ball on a stem for a providing port and an open socket for a requiring one, the ball
  filled and a dot in the socket for client-server. A member that is itself a composition is drawn
  as a box you can click into.
- **An overview per composition**, `overview-<composition>.svg`: one line per connected pair of
  members, labelled with the number of connectors it stands for.
- **One nesting view**, `nesting.svg`: the composition tree as boxes in boxes, framed by the root
  composition and its `title`. A model with no root composition has no nesting view.
- **One sequence diagram per scenario**, `sequence-<scenario>.svg`: the task and the components as
  lifelines, an activation per step labelled with its runnable (and its note), and a data message
  per connector the step's component provides.
- **A page per view**, the same name with `.html`, **and `index.html`**, titled with the project's
  `name`, listing every view with the report beneath. A page pans (drag), zooms (the wheel, the `+`,
  `−` and *Fit* buttons, the `+`, `-` and `0` keys), searches every port, component, connector and
  message by name — highlighting each hit and moving to it, *Enter* and *Shift+Enter* to step — and
  a click on a member composition opens its own page. *Reload* shows a regenerated diagram; nothing
  reloads by itself.
- **`report.txt`**: every element that could not be drawn, grouped by why and counted, the size of
  every view, and — separately — each connector from a component to itself, which is drawn as a
  loop rather than left out. The report carries no timing, so it changes only when the model does.

**Nothing is served and nothing listens on a port.** The pages are files: they load nothing from
the network and nothing from beside them, so they open from a file manager, a mail attachment or a
shared folder. The `.svg` files are the ones to paste into a wiki page or a document; each page
carries its own copy of its picture, because a page opened from a file cannot search a picture it
loads.

**What `generate diagrams` prints** — on `examples/basic`, measured on macOS:

```text
Diagram ibd-Root: written
Diagram overview-Root: written
Diagram nesting: written
Diagram sequence-task10ms_consumer_cycle: written
Layout: 0.10 s
Report: …/views/report.txt
Generated diagrams: …/views (4 views)
```

A view whose files already hold exactly what would be written says `kept` and is not rewritten. A
diagram file the model no longer produces — a scenario you deleted — is removed and named on a
`Removed:` line; anything else in the directory, a README or an older `model.c4`, is left alone.
**Nothing is written until every file is ready**, so a run that fails leaves the previous diagrams
as they were. A failure while the files are being written — a full disk, a file another program
holds open on Windows — can still leave some files new and some old.

**The layout needs Node.js.** Placing the boxes and routing the lines is Eclipse ELK's work, run
through its JavaScript build `elkjs`, which ships inside SWCraft; SWCraft draws everything you see.
`generate diagrams` uses the Node.js the installation carries and otherwise the one on `PATH`. With
none, or with one older than 14.8.0, it says so in one sentence and writes nothing — the floor is the
one this release measured on macOS; no older Node.js was tried on Linux or Windows. A composition
whose name cannot be a file name, or a composition or sequence name declared twice, stops the command
before anything is drawn, with a sentence naming `swcraft check-model`, which reports such a name.
Two names that differ only in case are drawn both, the second into files suffixed `~1`, so a
case-insensitive disk does not make them one file.

**In VS Code**, *Diagrams* runs `swcraft generate diagrams` and opens `index.html` in your default
browser — a new tab on each press, which is how a browser opens a file. From that press on, saving a
model file regenerates the diagrams; reload the page to see the change. *Build* runs `generate
diagrams` as its fourth step, where it ran `generate c4`. A *Build* whose `check-model` fails leaves
`views/` absent, as every output of a failed build is; the next *Diagrams* press writes it again,
because there is no longer a running viewer to be left pointing at a removed directory. The
extension pack is now two extensions, Red Hat YAML and Red Hat XML: nothing in SWCraft uninstalls the
LikeC4 extension from a machine that has it, and SWCraft no longer uses it.

**What this does not reach.** The pages were measured in Chrome on macOS; Safari, Linux and Windows
have not been measured opening them, nor the regeneration on save outside macOS. In a VS Code window
connected to another machine (SSH, WSL, a container), *Diagrams* opens a path on that machine, which
a browser on yours cannot open; not measured. Like the diagrams before them, no picture is evidence
that a model is valid — `swcraft validate` is the gate. Requirements documents still embed no
diagram.

## Two ports are joined when their interfaces fit, not only when they are the same

Until this release a connector was refused unless its two ports named **the same** interface, and a
delegation likewise. That is stricter than AUTOSAR, which asks whether the interface the *requiring*
side needs is satisfied by the one the *providing* side offers. A connector whose two ends name two
interfaces that differ only in their **name** — identical content element for element, type for type —
or a client-server pair where the providing port offers more operations than the requiring port asks
for, failed `check-model`.

That was not only a reporting problem. The assistant refuses to commit any edit to a model that has
outstanding findings, so on such a project **no** change could be made through it at all: asked to
add a single data element, it declined and named the twelve connectors as the reason. From this
release those models pass the gate with no hand edit, and the assistant works on them.

**What "fits" means.** For a connector, every data element — or operation — the *requiring* port's
interface declares must have a counterpart of the **same name** in the *providing* port's, and the
two counterparts must have compatible types. For a delegation, the direction of the composition's own
boundary port decides: a `require` port needs every member of the inner interface to have a
counterpart in the outer one, and a `provide` port needs **at least one** shared member, which is the
standard's own condition rather than a relaxation SWCraft invented.

Types are compared **after references are resolved** and by structure, never by name: a reference
type is followed to the value type it rests on and that to its base type, and two types fit when
their kind and structure agree — a record field for field in order, an array by length and element
type, an enumeration by its literals and their values, a base type by its size, encoding and native
declaration. So two types spelled differently and built identically are interchangeable, which is
a shape a tool export can carry. Arguments are matched by position and direction; an
argument's *name* takes no part, because the standard does not compare it either.

**Nothing you have written changes.** No file changes shape, no field is added, and every model the
gate accepted before this release is accepted after it — the new condition is strictly more
permissive, so findings can only disappear. Every diagram, requirements document and ARXML file
SWCraft generated for a model it already accepted is byte-for-byte what it was.

**What is not checked, and is worth knowing.** SWCraft judges compatibility on member names,
argument direction and resolved type structure only. It does **not** compare queueing
(`swImplPolicy`), the service flag, conversion methods, byte order, memory alignment, optionality,
or invalidation policy — none of which the model carries — nor a value type's `unit` and its
`value_min`/`value_max` range, which the model **does** carry and the comparison passes over by
design, as they describe a type rather than decide it and reach no generated file. And where the
standard offers an interface *mapping* as an alternative way to make two interfaces fit, SWCraft
has no mapping to consult and reports the mismatch instead. Each of those is a case SWCraft may accept that a
downstream RTE generator could still reject, so they stay a matter for review. The user guide's
*Working with the model* page lists them where it describes connectors, so the list is in the
documentation the release ships rather than only in the sources.

**Two things you may see change.** `check-model`'s one-line description of the two rules is reworded,
and both messages now end by naming *what* is incompatible — the missing element or operation, the
argument whose direction differs, the type whose structure differs and where. The message keeps its
opening words, so a script matching the prefix still matches; one reading the whole line sees a
longer sentence.

## The model's contract is `6.0.0`

`contractVersion` moves from `5.0.0` to `6.0.0`, a major, in two steps. `5.0.0` is 0.11.0's, which
was withdrawn: a project coming from 0.10.1 moves from `4.6.0`, and takes 0.11.0's major as well —
its data types are reorganised, and the first step of *Upgrading a project* below is that recipe.

The first step, a minor on its own, is the compatibility change above. No identifier is added,
removed or renamed by it: the two rules keep their ids, their bindings and the places they report at,
and what changed is the condition each one judges. Their two summaries are reworded, and the list of model
fields each rule declares that it reads grows to cover the interface and data type fields the new
comparison consults.

Six field, kind and layer descriptions are reworded in the same version, because each still said a
connector's — or a delegation's — two ports must name one interface. They are what the editor shows
on hover and what the reference pages of the user guide print, so they would otherwise have
contradicted this note.

The second step is what makes the release a major. The diagrams are no longer drawn by LikeC4, and
the contract drops what existed only for it:

- The rule that checks a sequence's name is renamed from
  `rule:sequences.sequence.name.likec4-identifier` to `rule:sequences.sequence.name.identifier`. What
  it checks is unchanged — a sequence's name is non-blank and made of letters, digits and underscores,
  not starting with a digit — and a script that matches the old identifier must use the new one.
- The `systems` layer is removed, with its one element kind and its three fields. Nothing but the
  LikeC4 diagrams ever read it, and no ARXML, requirements document or check used it.
- The descriptions that said a component, a composition or a sequence is drawn in LikeC4, or as a
  *dynamic view*, are reworded; they are what the editor shows on hover and what the reference
  pages of the user guide print.

**What you do.** Delete the empty `model/systems/` directory from your project. If it is not empty,
the files in it described nothing any generated file carried, and they can be deleted too.

## The import report is short and names no product

`swcraft import model` wrote a report headed *"Rhapsody import report"* and a baseline requirement
`REQ-RHAPSODY-IMPORT` titled after that tool, although the reader is a generic AUTOSAR reader and
0.11.0 had already removed the name from the command. And its skipped list was one line per
element: on a large export, a very long list, most of it one explanation repeated.

- The report opens with `Import report: <source>`.
- The baseline requirement is **`REQ-ARXML-IMPORT`**, titled *Imported architecture baseline*, with
  a description that names no tool and names the check a component without a requirement link would
  be reported by.
- The skipped list is **one line per distinct reason**, `N × TAG: reason`, most frequent first. A
  report is a fraction of its former length. `--verbose` lists the skipped elements again,
  each under its reason; `import component` has no such list and refuses `--verbose`.

**A project imported before this release** keeps `model/requirements/REQ-RHAPSODY-IMPORT.yaml`.
Nothing renames it: `import model` refuses a project that is not empty unless you pass `--force`,
and a forced re-import writes `REQ-ARXML-IMPORT.yaml` **beside** the old file. Delete the old one
after such a re-import, or the model carries two baseline requirements linked to the same
components. A script that matched the old heading or the old id must match the new ones.

## `impact` names every port, and takes a depth and a JSON form

`swcraft impact`, `swcraft query --dependents` and `--deps`, and the assistant's `impact_of` in its
`full` form printed each dependent once with **one** port beside it, the first one the walk met. A
component with three ports on an interface read `swc BrakeController (via port pBrakeRequest)`,
which looks like the whole answer and was a sample of it: the lines
under one interface — components and compositions — named one port each where the components and
the compositions can carry several on it. And a connector's line named no port at all, so
the connectors that really carry an interface could not be told from the ones merely attached to
the same components.

- **Every line names every detail of every edge that reached it**, in the order the walk met them:
  `swc BrakeController (via ports pBrakeRequest, pBrakeRequestAux, pBrakeRequestDiag)`. The same
  holds for a task reaching a component through several runnables (`runnables R1, R2`), a sequence
  through several steps (`steps: R1, R2`) and a composition placing several reached components
  (`members A, B`); an element reached through edges of two kinds names both, separated by `;`. A
  line reached through one edge reads exactly as before, unless it is a connector's, which gains its
  endpoints (below). Two edges carrying the same value are
  never merged into one: when two components each map a runnable `Run` into one task, or charge
  the same budget to one memory, the line names each after its component — `runnables SwcA.Run,
  SwcB.Run`, `memory budgets SwcA.2048, SwcB.2048 bytes`. Where those two elements also share a
  name — a component and a composition both called `X` — each is named with its layer too:
  `via ports swc X.p, composition X.p`.
- **A connector's line names its endpoints, owner first**: `connector Brake_link (via ports
  BrakeController.pBrakeRequestAux, BrakeConsumer.rBrakeRequest)` — each endpoint whose component
  or composition the report reached. A connector carries the interface when one of its endpoints is
  a port that its owner's own line names, on the plain report as on `--depth 2`.
- **`swcraft impact --depth N`** stops after N steps and ends the report with a `(depth: N)` line —
  the same text the assistant's `impact_of` returns in its `full` form for that depth. `--depth 1`
  is the first look that fits a console on a large model. A depth below 1 is refused as a usage
  error (exit 2), where `query --dependents NAME --depth 0` exits 1.
- **`swcraft impact --format json`** prints exactly the document `swcraft query --dependents NAME
  --format json` prints. Each row of that document keeps its `detail` text and gains `details`, a
  list of `{"kind", "value"}` pairs. `kind` is one of `port`, `endpoint`, `runnable`, `member`,
  `step`, `budget`, `core` and `access`; `value` is always a string — an `endpoint` is `Owner.port`
  and a memory budget is its byte count, `"512"`. A detail named after its component also
  carries `owner`, and its `value` stays the plain value; one named with its layer too also
  carries `ownerLayer`.

**What changes in output you may have kept.** `swcraft impact` without the new options prints the
lines it printed before, except where a line gains further details or a connector gains its
endpoints; no line is added, removed or reordered. The query JSON documents' **`schemaVersion` is now `2`**.
One version number covers both of `query`'s documents: the walk document's rows gained `details`,
and the layer slice document (`swcraft query LAYER … --format json`) moved to `2` with it although
its shape is unchanged. `impact_of`'s summary form, the default, is unchanged byte for byte; its
`full` form is wider, and on a very large model a `full` answer that was already refused as too
large is still refused, with the same hints.

**What this does not reach.** With `--depth N`, an element N steps out is listed and not walked
further, so an edge leading out of it is on no line: a connector is two steps from an interface, so
its endpoints are named from `--depth 2` on, and a line one step out can gain details at a larger
depth. A connector the report reaches only through the composition it is drawn inside names no
port. A line names the element a detail came from only when another element reached it with the
same value; otherwise it does not say which of several elements each detail came from. And finding the
connectors that carry an interface is still a read of the lines, not a single query.

## A smaller archive, and a Windows install that cleans up after itself

The workstation archive no longer carries the diagram viewer, its 7 535 files or the LikeC4
extension. The macOS archive built for this release measures **141 971 676 bytes**, against
0.11.0's 170 025 078. It still carries Python 3.11, Node.js — now for one purpose, the diagram
layout — and the two extensions of the pack, and `elkjs` travels inside the `swcraft-tools` package
rather than beside it. `THIRD-PARTY-NOTICES.md` names `elkjs` with its declared licence,
`EPL-2.0 OR GPL-3.0-or-later`, and says SWCraft distributes it under EPL-2.0, the licence whose text
the package ships. The Linux and Windows archives are built on their own hosts by the tag's run:
`swcraft-0.12.0-linux-x64.zip` is **143 727 511 bytes** and `swcraft-0.12.0-windows-x64.zip`
**150 616 097 bytes**, each with its `SHA256SUMS-<platform>` beside it.

**On Windows the installer's temporary copy of Python is removed.** Every Windows install used to
end with *"delete that directory yourself"*, because the installer cannot remove the Python it is
running on. The `.cmd` wrapper now removes that copy once the installer has exited, and the
installer says so instead. This is checked against the wrapper's text only; it has not yet been run
on a Windows machine. On macOS and Linux nothing changes.

**An anti-virus exclusion.** An installation is still thousands of small files — Python, its packages
and Node.js come to about 12 900 in the macOS archive. The user guide's install page now says that an exclusion for the
installation directory shortens an install under an anti-virus scanner, and why.

## Upgrading a project

**From 0.10.1** — the last release that was not withdrawn — first follow
[0.11.0's *Upgrading a project's data types*](0.11.0.md#upgrading-a-projects-data-types): a
`primitive` or an `alias` data type is refused by `check-model` in this release exactly as in
0.11.0, and 0.12.0 is the first release that delivers that change to most projects. Then the steps
below, which are this release's own.

1. Delete the `c4:` line under `outputs:` in `swcraft.yaml`. A stale line is ignored rather than
   refused, so nothing fails if you forget, but nothing reads it either.
2. Delete the `model/systems/` directory. It is empty in every project SWCraft has seen; if yours is
   not, nothing SWCraft generated ever carried what the files in it held.
3. Replace `swcraft generate c4` with `swcraft generate diagrams` wherever a script or a build calls
   it. In a moon project the template's task is now `generate-diagrams`, with `views/` as its output
   where `generate-c4` had `views/model.c4`, and `build` depends on it by that name. The
   `swcraft-generate-c4` command and the Python functions `swcraft_tools.writer.generate_c4` and
   `generate_c4_cli` are gone with it and have no namesake: call `swcraft generate diagrams
   --project PATH`, or from Python `swcraft_tools.writer.generate_diagrams(model_root, views_root,
   project_name)`.
4. If a script matches the check rule `rule:sequences.sequence.name.likec4-identifier`, match
   `rule:sequences.sequence.name.identifier`.
5. After a forced re-import, delete `model/requirements/REQ-RHAPSODY-IMPORT.yaml`.
6. Delete `views/model.c4` if it is still there, and the `.likec4/` line from `.gitignore` if you
   like; neither is read any more.
7. If a script reads `swcraft query --format json` and checks `schemaVersion` for `1`, accept `2`:
   a layer slice has the same shape as before, and a walk's rows carry `details` beside `detail`.
