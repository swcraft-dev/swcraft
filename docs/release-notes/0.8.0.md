# SWCraft 0.8.0

**Released 2026-09-06** (the bump commit; the tag follows the `verify` gate on both self-hosted
runners, Linux and Windows, on this commit, and the tag's own run is the first to publish the
release archives to the NAS by itself). This note was written with each change rather
than after it, so everything below was measured on the host and at the commit that made it —
macOS, CPython 3.14.7, 2026-09-06.

**The exported AUTOSAR file now carries a signal's initial value.** `0.7.0` put a sender-receiver
data element's `init` **in the model and nowhere else** and said so in as many words; this release
is the other half. `swcraft generate arxml` and `swcraft validate` emit one
`CONSTANT-SPECIFICATION` per data element that declares a value and reference it from the element
and from every port that uses it, at `--arxml-version` **4.2.2 and 4.3.0** alike. An RTE generator
reading the export now sees what each signal starts from.

**And it carries what every runnable reads, writes and calls.** `0.7.0` put a runnable's `reads`,
`writes` and `calls` **in the model and nowhere else** and said so in as many words; this release is
the other half of that pair too. Every entry of the three lists becomes one access point under the
runnable's own `RUNNABLE-ENTITY` — a `VARIABLE-ACCESS` inside `DATA-RECEIVE-POINT-BY-ARGUMENTS`,
`DATA-RECEIVE-POINT-BY-VALUES` or `DATA-SEND-POINTS`, or a `SYNCHRONOUS-SERVER-CALL-POINT` inside
`SERVER-CALL-POINTS` — at `--arxml-version` **4.2.2 and 4.3.0** alike. Those are the declarations
an RTE generator derives a runnable's `Rte_Read` / `Rte_Write` / `Rte_Call` API from: until this
release an exported model carried no runnable API at all.

**Both halves ride this one minor, and this is one note rather than two.** The initial values
and the access points were built one after the other, on branches of
their own and never beside each other, because both edit the same writer; the first wrote this note and
the second extended it. Everything below is stated once for whichever half it belongs to, and where the
two meet — the joint name budgets, the contract, the upgrade checklist — they are stated together.

## What an existing project must change

**Nothing to your model's content, and — for almost every project — nothing at all.** A project
that declares no initial value and no runnable access generates **exactly** the bytes it generated
on `0.7.0`, at both versions, and that is a gate rather than a promise: `examples/basic` hashes to
the digests it hashed to before, the three committed writer goldens are byte-identical, and — the
part that actually witnesses the claim — two copies of one project, one with the declarations and
one without, generate documents that become byte-identical the moment the added nodes are stripped
out of the first. There is one such pair per half: the added constants and `INIT-VALUE` subtrees
for the values, and the four access containers plus the capability marker for the access points.
The delta is exactly the new nodes; nothing else moved.

Seven things can now refuse a model that `0.7.0` accepted. **Four of them are about an initial
value**, and they **do not all wait for you to declare one**. The first two are about the *name*
`{Interface}_{Element}_Init`, which every
sender-receiver interface reserves once per data element whether or not that element carries an
`init` today — a conditional reservation would mean that adding the first value to one interface
starts failing generation on an interface file nobody touched, so both checks are **unconditional**
and a project that declares no value at all can meet them. The last two are about a *value* the
exporter cannot write, so they can only fire where a value is declared. Each of the four is
reported by `swcraft check-model` and refused by the writer and by every write path, so the two
surfaces agree:

1. **The joint name budget: 122 characters.** *(Unconditional.)* The constant is named
   `{Interface}_{Element}_Init`, which is the first generated AUTOSAR name SWCraft derives from
   **two** names you wrote. The `_` and the `_Init` spend 6 of the 128-character `Identifier`
   limit, so an interface name and each of its data element names get **122 characters between
   them** — the interface has no allowance of its own, and neither does the element. The message
   names both declared names, the constant it would emit, its length and which of the two to
   shorten. No measured project comes within forty characters of the limit.
2. **Two pairs deriving one constant name.** *(Unconditional.)* The derivation is not injective,
   because both names may contain an underscore: interface `A_B` with element `C` and interface `A`
   with element `B_C` both give `A_B_C_Init`. Two such pairs in one model would emit two constants
   under one `SHORT-NAME`. `rule:interface.init-constant-name-collision` reports it — naming both
   pairs and the shared name — and also reports the other half, a declared interface whose own name
   is a pair's constant. There is no counter and no rename: neither declared name is SWCraft's to
   change, so the repair is to rename one of them.
3. **A text `init` on a numeric type.** *(Needs a declared value.)* Every scalar is exported as a
   `NUMERICAL-VALUE-SPECIFICATION` and this release emits no text value specification, so a `str`
   under a `primitive` or an `alias` has no spelling and is refused as
   `rule:interface.init-string-scalar` — whatever the base `encoding`, and whether or not the alias
   declares a bound. **This supersedes one line of the `0.7.0` note**, which told you to spell "a
   string value that reads as a number" as `init: '010'`: on a `uint8` that is a finding now. Write
   the number unquoted. The quoting rule still holds where it was always needed — an **enum
   literal** named `ON` is still `init: 'ON'`, because YAML 1.1 would otherwise load it as `True`.
4. **An integer too wide to write out.** *(Needs a declared value.)* The exporter converts an
   integer with `str(value)`, which CPython bounds by `sys.get_int_max_str_digits()`. A value above
   that limit — reachable from a hand-authored `init: 0x…`, because `int(v, 16)` is exempt from the
   same limit — is `rule:interface.init-unwritable-integer`. The bound is the interpreter's, read
   at run time, and a limit of `0` means *no limit*, so with the limit disabled nothing is
   reported. The message names the value's **bit length**, never a digit count: counting the digits
   of such a value is the very conversion that raises. Nothing engineering-sized comes near it — a
   64-bit mask is 20 decimal digits — and the scope is `init` alone: `enum_literal.value` and
   `core.hw_id` stay unbounded, as `0.7.0` said they would.

**The other three are about a runnable's `reads`, `writes` and `calls`**, and all three need a
declared entry: an empty list reserves nothing, names nothing and refuses nothing, so a project
whose runnables declare no access meets all three by having nothing to check.

5. **Two more joint name budgets: 125 and 122 characters.** Each entry is exported as an access
   point whose `SHORT-NAME` is derived from the entry's own two strings — `R_<port>_<element>` for
   a read, `W_<port>_<element>` for a write, `Call_<port>_<operation>` for a call. `R_` and `W_`
   spend the prefix and the separating `_`, so a port name and each data element name a runnable
   reads or writes through it get **125 characters between them**; `Call_` spends six, so a port
   name and each operation name get **122**. These are the third and fourth joint budgets in the
   tool, and the only ones joining names declared in **two different files** — the port on the
   component, the member on the interface the port names. The message names both declared names,
   the access point it would emit, its length and which of the two to shorten.
6. **Two entries of one runnable deriving one access point name.** The derivation is not injective
   for the same reason the constant's is not: a port named `pA_B` with member `C` and a port named
   `pA` with member `B_C` both give `R_pA_B_C`. Two such entries under one runnable would emit two
   access points with one `SHORT-NAME` under one parent.
   `rule:swc.access.name-collision` reports it — naming the derived name and **every** entry that
   claims it, by list, port and member — and the writer refuses the same model. There is no counter
   and no rename: neither declared name is SWCraft's to change, and a `_0`/`_1` suffix would make
   the exported name a function of the order the entries happen to sit in the file. The repair is
   to rename one of the two.
   The rule is reported per runnable, and it fires whether or not the two entries would otherwise
   resolve.
7. **`swcraft generate arxml` now refuses a model `swcraft check-model` already reported.** This is
   the one refusal that is not about a name. On `0.7.0` the writer ignored the three lists
   entirely, so a project whose access entries name an unknown port, an unknown element or
   operation, a port facing the wrong way or a port of the wrong interface kind — every one of them
   a `rule:swc.access.*` finding since `0.7.0` — still produced an ARXML file, because generation
   never looked. From this release the writer resolves every entry before it creates the component,
   and refuses the whole run when one does not resolve. `generate arxml` has no `check-model` gate
   in front of it, so for a project carrying such a finding this is a command that used to succeed
   and now exits non-zero, with no partial file written. Running `swcraft check-model` first is how
   you see the full list rather than the first refusal.

**If you re-import a component ARXML with `--update`, its access lists now follow a regime.**
Because a SWCraft export can finally *say* that a runnable accesses nothing, and an ARXML with no
access container is written just as well by `0.7.0` and by a tool that cannot express access points
at all, the exporter marks the exports it can vouch for. `swcraft import component --update` decides
what happens to a target runnable's `reads`/`writes`/`calls` by that signal, names the regime it
chose in the import report, and never merges silently:

| What the incoming file says | Regime | What happens to the target runnable's lists |
|---|---|---|
| It carries the SWCraft capability marker (a `0.8.0`-or-later SWCraft export of a component that has at least one access point) | `marked` | The export is the truth for its runnables: its lists **replace** the target's, through the same diff preview as the rest of the runnable |
| No marker, and you passed `--replace-access-lists` (MCP: `replace_access_lists=True`) | `replace-flag` | The same replacement, through the same preview, on your explicit word — and the report says the flag did it |
| No marker and no flag — a `0.7.0`-era export, a third-party ARXML, or a SWCraft export of a component whose lists are all empty | `carried` | The target's lists are **kept**, the report says what was preserved per runnable and per list, and it names the flag that would replace them |
| The component was not updated | `none` | Nothing decided anything: a newly created component takes the export's lists, an unchanged one changes nothing |

`--replace-access-lists` is refused without `--update` and refused beside `import rhapsody`, so it
can never be a flag that quietly does nothing. **The residual, stated rather than left to be
found:** on the non-`--dry-run` path the diff preview is rendered into the report *after* the
write, so under `marked` and `replace-flag` a removed entry is visible in the report and not before
it — `--dry-run` is where you see it first, and `check-model` will not tell you afterwards, because
a runnable that declares no access is not a finding. And a foreign export that carries access
points for *some* of its runnables and none for others is unmarked as a whole, so the empty ones
are `carried`; the flag is the answer, and the report's regime line is what tells you to consider
it.

## What the exporter writes for an initial value

For each data element that declares an `init`, one `CONSTANT-SPECIFICATION` in the
`PortInterfaces` package, emitted **immediately before its own interface** and in data-element
order. It is a sibling of the interfaces rather than a package of its own, deliberately: a fourth
`AR-PACKAGE` would appear in every document and move the bytes of every model that declares no
value at all.

The `SHORT-NAME` is the **eighth generated name form**, `{Interface}_{Element}_Init` — joining
`_impl`, `_CompuMethod`, `_AppView`, `_Implementation`, `_InternalBehavior`, `TMT_` and `IT_`, and
the first derived from two declared names. That is where the 122-character budget above comes from.
The access points below are the ninth, tenth and eleventh forms, and three more of that kind, so
this release takes the tool from seven generated forms to **eleven**, four of them joint.

The value is referenced, never repeated, from three places, always as an
`INIT-VALUE` → `CONSTANT-REFERENCE` with `DEST="CONSTANT-SPECIFICATION"`:

- the element's own `VARIABLE-DATA-PROTOTYPE`, after `TYPE-TREF`;
- every `NONQUEUED-RECEIVER-COM-SPEC` naming that element, after `HANDLE-NEVER-RECEIVED`;
- every `NONQUEUED-SENDER-COM-SPEC` naming it, after `USES-END-TO-END-PROTECTION`.

A port never carries a value of its own — the port-side override AUTOSAR admits is not modelled — so a
port repeats the element's constant. A
client-server port, and an element without `init`, emit exactly what they emitted before.

The shape of the value follows the element's **declared type**, recursively:

| Declared type | What is emitted |
|---|---|
| `primitive`, `alias` | `NUMERICAL-VALUE-SPECIFICATION` with the number in `VALUE` |
| `enum` | the same, carrying the literal's declared **number** (the model spells the literal's name; the file carries its value) |
| `record` | `RECORD-VALUE-SPECIFICATION` / `FIELDS`, one member per declared field **in declaration order**, each with a `SHORT-LABEL` naming the field |
| `array` | `ARRAY-VALUE-SPECIFICATION` / `ELEMENTS`, exactly `length` members, unlabelled |

Both composites nest as deep as the declared type graph does.

**Where the XSD evidence is.** Both licensed schemas accept the emitted subset at 4.2.2 and 4.3.0
— `python scripts/dev.py test-xsd` is 131 passed with 0 skipped — and the position of `INIT-VALUE`
is a measurement rather than a reading: the same document with the receiver's `INIT-VALUE` one
position earlier is **refused** by both schemas, and that negative control is a committed test.

## What the round trip does not restore

Re-importing SWCraft's own export gives you the values back **by value and by type**, and the three
places it cannot are named here rather than discovered later:

- a **`bool`** is written as `1` / `0` and comes back as the integer `1` / `0`. The reader does not
  resolve the base type, so it cannot know a boolean was meant. The values compare equal; the YAML
  re-spelling differs.
- a **hexadecimal** source spelling is never restored. `0x10` was read as the integer 16 on the way
  in — `0.7.0` decided that — and nothing re-spells it on the way out.
- a **float**'s fixed-point width is **unbounded**. `1e-300` emits 302 characters and validates. No
  bound is added, because no project measured needs one and a number nothing measured would be a
  guess. What *is* guaranteed is the type: a float comes back a float, at every depth, including
  the integral ones — `100.0` is written `100.0` and not `100`, and `1e20` is written
  `100000000000000000000.0`.

**One asymmetry is kept rather than closed**, and it is not a lossiness: a `bool` is accepted on a
bare `primitive` and on an alias with no bound, and refused under an alias that **declares** a
bound, as `rule:interface.init-shape-mismatch`. That refusal is about the bound — a numeric range
cannot be applied to a boolean, and YAML 1.1's `init: ON` loading as `True` is why booleans are
excluded from the numeric test in the first place — not about whether the exporter can write it.
Making it uniform would have been a second refusal surface with no exporter behind it.

## Runnable data access is in the exported file

`0.7.0`'s note said, in as many words, that the exporter ignores a runnable's `reads`, `writes` and
`calls`. **That sentence is superseded by this section.** Every entry now becomes exactly one
access point, emitted under the runnable's own `RUNNABLE-ENTITY` between
`CAN-BE-INVOKED-CONCURRENTLY` and `SYMBOL`, in the order AUTOSAR fixes:

| The declaration | The container | The element and its `SHORT-NAME` |
|---|---|---|
| a `reads` entry without `by: value` | `DATA-RECEIVE-POINT-BY-ARGUMENTS` | `VARIABLE-ACCESS`, `R_<port>_<element>` |
| a `reads` entry with `by: value` | `DATA-RECEIVE-POINT-BY-VALUES` | `VARIABLE-ACCESS`, `R_<port>_<element>` |
| a `writes` entry | `DATA-SEND-POINTS` | `VARIABLE-ACCESS`, `W_<port>_<element>` |
| a `calls` entry | `SERVER-CALL-POINTS` | `SYNCHRONOUS-SERVER-CALL-POINT`, `Call_<port>_<operation>` |

A `VARIABLE-ACCESS` carries an `ACCESSED-VARIABLE` / `AUTOSAR-VARIABLE-IREF` naming the port
(`PORT-PROTOTYPE-REF`, `DEST` `R-PORT-PROTOTYPE` for a read and `P-PORT-PROTOTYPE` for a write) and
the interface member (`TARGET-DATA-PROTOTYPE-REF`, `DEST` `VARIABLE-DATA-PROTOTYPE`), by the same
paths the exported file already uses for a port and for a data element. A call point carries an
`OPERATION-IREF` with `CONTEXT-R-PORT-REF` and `TARGET-REQUIRED-OPERATION-REF`, and a `TIMEOUT` of
`0` — the value an RTE generator reads as *no timeout*. A container is emitted only when its list has an entry, so a runnable
that declares nothing carries the three children it carried on `0.7.0` and no more.

`by: value` is a real distinction and is preserved. A read declared `by: value` becomes an
`Rte_IRead`-style by-value point and a plain one an `Rte_Read`-style by-argument point; flattening
the two would silently change the API an RTE generator produces.

**The capability marker.** A component whose runnables carry at least one access point gets one
extra node: an `ADMIN-DATA` / `SDGS` / `SDG GID="SWCRAFT"` / `SD GID="ACCESS-POINTS"` with the value
`explicit`, immediately after the `SWC-INTERNAL-BEHAVIOR`'s `SHORT-NAME`. It is a **capability**
token and never a version string — it says the exporter can speak about access points, not that
this component has any particular one — and it is what `import component --update` reads to decide
the regime above. It is per component and per export, never per runnable: an export of a component
with **no** access point carries no marker and no `ADMIN-DATA` at all, which is exactly why such an
export is treated as silent rather than as authoritative. Re-importing a marked export does not
report the marker as vendor metadata it had to skip — and that exemption is exactly the marker on
the behaviour: the same block on the component, on an interface, or a `SWCRAFT` group of any other
shape is vendor metadata SWCraft does not read, so a component import still refuses it rather than
dropping it in silence. Only the value `explicit` is trusted; a marker carrying anything else is
treated as unmarked (the conservative regime, never a refusal) and the import report names the
value it found.

**Where the XSD evidence is.** Both licensed schemas accept the emitted subset at 4.2.2 and 4.3.0 —
`python scripts/dev.py test-xsd` is 157 passed with 0 skipped — and the *position* of the four
containers is a measurement rather than a reading: the same document with them placed after
`SYMBOL`, and with `DATA-SEND-POINTS` before `DATA-RECEIVE-POINT-BY-ARGUMENTS`, is refused by both
schemas, and those negative controls are committed tests. Checked against real tool exports the maintainer holds privately.

**What is deliberately still not emitted**, so it is not discovered later: *implicit* access
(`DATA-READ-ACCESSS` / `DATA-WRITE-ACCESSS` — unmodelled, and an export's empty
containers are not reproduced), *mode* access (`MODE-ACCESS-POINT`s), asynchronous calls and their result points, `TIMEOUT` values other than `0`,
`SCOPE`, local variables, parameter access, wait points, triggering points, exclusive areas and
per-instance memory. The three lists also say *what* a runnable accesses and never in what order:
entries are emitted in declaration order and compared as sets, and no check compares a sequence
against them.

## Exchanging a component now carries its values and its access points

`swcraft generate arxml --component NAME` runs the same writer, so a component export carries the
constants of every interface in its closure. Importing one into a project that does **not** declare
the interface creates it **with** its initial values — nothing is lost on the way out any more, and
no lossiness channel in `export-summary.json` was needed; that file is byte-identical with and
without the values. Importing into a project that already declares the interface is unchanged: an
equal value is reused, a contradicting one is a conflict naming both.

One asymmetry there is deliberate and stays. An incoming export that carries **no** value is not
evidence that the design has none — a third-party export, or one written by `0.7.0`, carries none
either — so the target project's authored value is kept rather than blanked. `0.7.0`'s note said
this would be revisited "when 27.2 emits them"; it was, and the reason is now the true one rather
than "the writer emits none". The access points show what closing it would take: a signal in the
file that distinguishes *this exporter said nothing* from *this exporter cannot speak*. The access
lists have one; initial values do not, and nothing in this release invents one for them.

**The same export also carries its access points**, and importing it is where the regime table in
§ *What an existing project must change* applies. A component exported from a `0.8.0` project with
at least one access point is marked, so re-importing it with `--update` replaces the target's lists
through the preview; anything else is `carried` unless `--replace-access-lists` says otherwise.
Creating a component from such an export writes its `reads`, `writes` and `calls` into the new YAML.

## The model contract is `3.4.0`

`contractVersion` moves from `3.2.0` to `3.4.0`, a minor: four rule identifiers added, nothing
removed and nothing renamed. A consumer authored against `3.0.0` reads a `3.4.0` document without
noticing, and `SUPPORTED_CONTRACT_MAJORS` stays `{3}`. Two releases of the contract are folded in
here, `3.3.0` and `3.4.0`, because both halves of this note ship together.

`3.3.0` is the first minor on the `3.x` line that **opened with no new identifier at all**.
`rule:identifier.generated` — a legal declared name whose emitted `SHORT-NAME` is not legal —
already existed and already said what it says; what changed is where it can fire. The seven earlier
generated forms are all derived from an `swc` or a `data_types` name, so the rule's `appliesTo`
named those two layers; the eighth is derived from an interface name and a data element name, so it
is reported at the **interfaces** layer and the declaration has to say so. A rule that applies to
one more layer is *additive* — nothing is removed and nothing renamed — so it is a minor, which
the contract's versioning rule now writes down as a rule of its own, the three-way rule having
had no case for it before.

Three of the four identifiers added are the ones described above:
`rule:interface.init-constant-name-collision`, `rule:interface.init-string-scalar` and
`rule:interface.init-unwritable-integer`. The fourth is `3.4.0`'s and belongs to the other half of
this release: `rule:swc.access.name-collision`, which reports two entries of one runnable deriving
one generated access point name. All four are in the **cross-element** family and all four are
mapped to `consistency-violation` in the editing protocol. The inventory goes from 10 layers, 32
kinds, 125 fields and 125 rules to 10 layers, 32 kinds, 125 fields and **129** rules (cross-element
71 → **75**). No field, no kind and no key moved.

The `interface.init-` prefix now holds **eight** identifiers, of which `check_init_conformance`
mints seven — the collision rule is `check_name_uniqueness`'s, because it judges a *name* and not a
value, and it fires whether or not any element in the model declares an `init`.

## What the editing protocol and the MCP surface publish differently

**No tool was added or removed** — the surface is the same thirteen tools — and no read answers
differently. One tool gains one keyword: `import_component` takes `replace_access_lists` (default
`False`), the MCP spelling of the CLI's `--replace-access-lists`, threaded into the same planner so
the two surfaces decide the regime identically. The width of an answer and the shape of a request
have been parameters rather than tools since `0.4`, and this follows that.

What else changes is what is **accepted**: a staged change set that writes an `init` the exporter
could not spell, that creates an interface or a data element whose derived constant overflows the
joint budget or collides with another pair's, or that writes a runnable whose access entries
overflow their joint budget or derive one access point name twice, is now refused in pass D with a
`consistency-violation` naming the offending value, pair or entries. The four new rules run in the
same composed check `swcraft check-model` runs, which is why the two surfaces cannot drift.

## What the editor does not check

Unchanged, and worth restating because this release adds refusals the editor is silent about. The
generated YAML schemas still render `init` permissively — every JSON type there is — because the
value's shape is a property of the *other* file the element's `type` names. They also cannot see
any of the four joint name budgets: neither of the two declared names has a length a schema
validating one document could check on its own, and for the three access forms the two names are
not even in the same file. Nor can a schema see two access entries of one runnable deriving one
name: that is a derivation *across* entries, which no JSON Schema expresses.
`swcraft check-model` is the authority, as it is for every cross-file rule.

## Upgrade checklist

1. Install all four artifacts at this version, the extension included.
2. Run `swcraft check-model --project swcraft.yaml`. If your model declares no `init` and no
   runnable access, it reports exactly what `0.7.0` reported. If it declares either, read § *What
   an existing project must change* — the seven refusals there are the only ways a model that
   passed can stop passing.
3. Replace any `init: '010'`-style quoted number with the number itself. Quoted **enum literal
   names** stay quoted.
4. **If `check-model` reports any `swc.access.*` finding, fix it before you generate.** On `0.7.0`
   such a project still produced an ARXML file, because the writer ignored the lists; from this
   release `swcraft generate arxml` refuses it, and refuses it whole.
5. Run `swcraft validate --project swcraft.yaml` and compare the generated ARXML with what you had.
   Without `init` and without access declarations it is byte-identical; with them, the difference is
   exactly the added constants and `INIT-VALUE` references, the four access containers and the
   capability marker, and nothing else.
6. If you re-import a Rhapsody export, the values now survive an export–import round trip by value
   and by type; read § *What the round trip does not restore* for the three places it does not. The
   access points survive it as sets per runnable, with every derived name the export's own.
7. If you `swcraft import component --update` from an ARXML written by `0.7.0`, by another tool, or
   by a SWCraft project whose access lists are empty, your target's `reads`/`writes`/`calls` are
   **kept** and the report says so. Pass `--replace-access-lists` — with `--dry-run` first — when
   the incoming file really is the truth for them.
