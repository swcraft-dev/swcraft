# SWCraft 0.7.0

**Released 2026-09-05** (the bump commit; the tag follows the `verify` gate on both self-hosted
runners, Linux and Windows, on this commit — since this release that gate runs on every push to
`main`, so the release needs no seated sitting). Everything stated here was measured on the host
that built it, at the commit it describes.

**Three changes ride this release.** Two are model-only and additive — a signal's initial value
(this section and the ones that follow it) and a runnable's data access (§ *Runnable data
access*) — and the third is how SWCraft reaches a workstation at all: the **workstation
archive**, one file per platform that installs the toolchain and the VS Code extension once per
machine (§ *SWCraft is installed once per machine*). The two ARXML halves, Phases 27.2 and 28.2,
are deliberately **not** here; they ship together in the next minor.

**A signal now knows what it starts from.** A sender-receiver data element takes an optional
`init` — the value an RTE returns before anything has written to it — typed by the element's own
declared data type and checked by `check-model`. `swcraft import rhapsody` reads it out of the
export's `CONSTANT-SPECIFICATION` / `INIT-VALUE` pairs, which until now were reported as skipped
and lost.

**Read this before you expect it in the ARXML.** This release puts the value **in the model and
nowhere else**. The exporter does not emit `CONSTANT-SPECIFICATION` and does not emit
`INIT-VALUE`; a model that declares `init` and a model that does not generate byte-identical
documents at both `--arxml-version`s, and that identity is a gate rather than a promise. The
emission — the constants, the port COM-SPECs, the goldens and the XSD evidence at 4.2.2 and
4.3.0 — comes in a later release, planned only now that the field's name and value shape are fixed. Until it
ships, an `init` in the model is a declaration your team can review, diff, query and hand to a
downstream tool through the model, and it is not something an RTE generator reading the exported
ARXML will see.

**All four artifacts move together, as always — but 0.7.0 is the release where *how* they move
changes.** Installing them as four pinned packages is retired by the third section of this note,
§ *SWCraft is installed once per machine, and a project installs nothing*: from this release on
you are handed one file, `swcraft-0.7.0-<platform>.zip`, and you run the installer inside it.
That one run replaces the three `pip install swcraft-*==0.7.0` lines and the separate
`.vsix` install, and it is also how you *upgrade* — there is no per-project environment left to
raise a pin in. Read that section before you install anything; `docs/guide/upgrading.md` is the
procedure.

## What an existing project must change

**Nothing.** `init` is optional and defaults to absent, so every model that loads under 0.6.0
loads unchanged, `check-model` reports the same findings on it, and `swcraft validate` writes the
same ARXML bytes. There is no migration and no new mandatory key.

What changes is what you *may* write:

```yaml
# model/interfaces/IVehicleSpeed.yaml
name: IVehicleSpeed
kind: sender_receiver
data_elements:
  - name: speed
    type: SpeedKph          # an alias with value_min: 0, value_max: 300
    init: 0
  - name: gear
    type: GearPosition      # an enum
    init: GEAR_NEUTRAL      # the LITERAL's name, never its number
  - name: calibration
    type: CalibrationBlock  # a record with fields `offset` and `gain`
    init:
      offset: 0
      gain: 1
  - name: history
    type: SpeedHistory      # an array of length 3
    init: [0, 0, 0]
```

The shape follows the element's own `type`, recursively, and both composites may nest — as deep as
the declared type graph does, which `rule:data-type.cycle` keeps acyclic and therefore finite:

| Declared type | What `init` takes |
|---|---|
| `primitive` | a plain scalar |
| `alias` | a plain scalar, bounded by the alias' `value_min` / `value_max` where it declares them |
| `enum` | the **name** of one of the type's literals — `GEAR_NEUTRAL`, not `0` |
| `record` | a map keyed by **exactly** the declared field names: none missing, none extra |
| `array` | a list of **exactly** the declared `length` |

**One YAML rule worth reading before you hand-author.** A value or key that YAML 1.1 resolves to
a non-string has to be quoted: an enum literal named `ON` is `init: 'ON'`, and a string value that
reads like a number is `init: '010'`. Unquoted they load as `True` and as the integer `8`, and the
model is silently a different one. Files SWCraft writes are already safe — the writer quotes
automatically — so this is a hand-authoring rule. What it does *not* reach: a literal name YAML resolves to a **number** has to begin with a
digit, which an AUTOSAR `Identifier` may not, so that half of the rule is unreachable for an enum
literal and the boolean/null family is where it actually bites.

## What `check-model` refuses

Five new rules, all in the cross-element family — they resolve the element's `type` across
`data_types/` and judge the value against what they find:

| Rule | Refuses |
|---|---|
| `rule:interface.init-shape-mismatch` | an init value whose shape the declared type cannot hold — a list where a scalar is declared, a map where an array is |
| `rule:interface.init-unknown-enum-literal` | an init value naming no literal of its declared enum type |
| `rule:interface.init-record-field-mismatch` | an init map whose keys are not exactly its record type's fields |
| `rule:interface.init-array-length-mismatch` | an init list whose length is not its array type's declared length |
| `rule:interface.init-out-of-range` | an init value outside the range its alias type declares |

**What they do not check**, stated rather than left to be found. A `primitive` declares `size` and
`encoding` and **no value domain**, so `init: 999` on a `uint8` is accepted — only an `alias`'
declared bounds are checked, and only where the alias declares them. Nor is a scalar's *type*
checked uniformly: a **non-numeric** scalar (`init: abc`) is refused only under an alias that
declares a bound — the refusal says why the bound could not be applied — and is accepted on a bare
`primitive` and on an unbounded alias. Making that uniform is left to the release that adds the
exporter, which is the reason to do it. An element whose `type` names
no declared type keeps producing exactly the broken-reference finding it produced before, with no
init finding stacked on top: there is no resolved type to judge the value against. And the editor
is silent about all five — see *What the editor does not check* below.

`.nan`, `.inf` and `-.inf` are refused inside an `init` at every depth, by the same
`allow_inf_nan=False` on the model base that has always refused them in a `period` or a
`value_min`. No new validator was needed for it, and a regression test now pins that.

One limit is neither a finding nor a load error: **an integer in an `init` has no bound at the
model boundary.** YAML resolves `0x…` through `int(v, 16)`, which CPython exempts from
`sys.get_int_max_str_digits()`, so a hand-authored value above that limit — roughly 3 570
hexadecimal digits at the 4 300-digit default — loads and then raises in the next
re-serialization (`yaml.safe_dump` in a writer, `json.dumps` in `swcraft diff --format json`).
Every command that *describes* such a value describes it rather than aborting on it —
`check-model`, `swcraft diff --format text`, the conflict line `swcraft import component` refuses
with, and the delta summary the editing protocol stages for review all render a model value
through one policy, `rendering.render_model_scalar`, which substitutes
`<an integer of N bits, too wide to render>` for the one integer Python refuses to print,
**inside a `record` or `array` `init` as well as at the top level** — but that is a message, not a
bound: nothing writes the value out. `swcraft query --where init=…` and the editing protocol's
member matching are the third case, neither message nor serialization: both reduce a value to a
canonical comparison key, and a `float()` in that key made a wide integer an `OverflowError`
rather than an answer. Each now keys such an integer as itself, so the read succeeds; the value
still cannot be written.

`init` is **not** the first model field to take an integer with no bound of its own. No model
field bounds an integer's magnitude at all: `enum_literal.value` and `core.hw_id` carry no
validator either, and the ones on `size`, `length`, `wcet_us` and `priority` bound the sign
rather than the width. The importer *does* bound it and skips such a value with a reason; a file
you write by hand goes through neither reader. Closing it is a contract change rather than a code
change — a validator in `schema.py` mints a rule identifier the model contract has to declare —
so it is left to the release that adds the emitter that would have to write the value out, and it is
scoped to `init`: the two other unbounded fields and the four sign-bounded ones are pre-existing
and remain unowned. Nothing engineering-sized comes near the limit: a 64-bit mask is 20 decimal
digits.

## What `swcraft import rhapsody` now reads

For each sender-receiver data element the importer follows `INIT-VALUE` → `CONSTANT-REFERENCE` →
`CONSTANT-SPECIFICATION` → value, in the four value-specification shapes AUTOSAR uses for it
(`APPLICATION-VALUE-SPECIFICATION`, `NUMERICAL-VALUE-SPECIFICATION`, `ARRAY-VALUE-SPECIFICATION`,
`RECORD-VALUE-SPECIFICATION`, the last two recursing), and writes the value onto the element's
`init`.

Checked against real tool exports the maintainer holds privately:

- **Every init value lands** but those of interfaces the importer already skipped whole — that
  behaviour is unchanged.
- **No element-level refusal**: no port-side override, no dangling reference, no shape the
  declared type could not hold. Not no refusal *of any kind* — the import also emits
  **port-level lines**, one per `NONQUEUED-SENDER`/`RECEIVER-COM-SPEC` whose `DATA-ELEMENT-REF`
  names one of the elements lost with their interfaces above, so the port's init is reported
  rather than dropped with it. They name only those element paths and no element that imported.
- **Hexadecimal spellings normalize to their decimal value.** `0xFF`
  imports as `255`. The source radix is **not preserved** — a recorded loss of the import, so a round
  trip compares values and not spellings. The import report says so rather than leaving it to be
  discovered: a section of its own, *Init values re-spelled from hexadecimal to decimal*, beside
  the type-name reductions and the flattened delegation chains, with one line per element naming
  the spelling the export wrote.
- `check-model` on an imported project reports no `interface.init-*` finding of the import's making.

**The port level is read as a consistency check, not as a second place to store a value.** AUTOSAR
admits an init override on a port's COM-SPEC; SWCraft expects every `NONQUEUED-SENDER`/`RECEIVER-COM-SPEC`
that carries an `INIT-VALUE` to point at the same constant the element itself does. So the
model has one place for the value, and the importer verifies the ports agree. A port naming a
*different* constant, or a reference the reader could not follow, lands the element **without** its
init plus one skip line against **the element** naming what it saw; so does a value the declared
type cannot hold, which is the element's own refusal rather than a port comparison. The field is
optional; a wrong init is not. If a future export does carry a genuine override, that skip line is
what will say so.

Two more refusals have no element to be reported against, so they are reported against **the
port** — its path and the COM-SPEC tag — and the element keeps its own init: a COM-SPEC whose
`DATA-ELEMENT-REF` is missing or blank binds to nothing, and one whose reference names an element
this import mapped none for (its interface was skipped, or the reference is unresolvable) has
nothing to compare against.

**What is read at the port at all** is the two COM-SPEC kinds that initialize a *data element*.
AUTOSAR puts an `INIT-VALUE` on three other kinds — `PARAMETER-PROVIDE`/`REQUIRE-COM-SPEC`
carries a `PARAMETER-REF`, `NV-REQUIRE-COM-SPEC` a `VARIABLE-REF`, neither a
`DATA-ELEMENT-REF` — and those belong to interface kinds SWCraft does not model, so they are not
read and the port that carries one is reported once, against its own unmappable interface
reference. `NV-PROVIDE-COM-SPEC` is dropped with them although it carries no `INIT-VALUE` at all:
it names a `VARIABLE-REF` beside a `RAM-BLOCK-INIT-VALUE` / `ROM-BLOCK-INIT-VALUE`, so the kind
filter — not the `INIT-VALUE` one — is what excludes it.
What that filter
buys is a calibration-heavy export not being told that every one of its parameter COM-SPECs is
missing a reference AUTOSAR never puts there.

**`CONSTANT-SPECIFICATION` is still reported as skipped, and its reason now says why that is not a
loss.** There is no constants layer in the model and there will not be one — a constant's name is
derivable from the interface and element it belongs to, and it is ARXML's storage for a value
rather than a fact about the design. The line now reads:

```
CONSTANT-SPECIFICATION is not an SWCraft element; where a data element's INIT-VALUE
references it, its value is imported onto that element's `init`
```

**`swcraft import component` keeps working**, which needed a deliberate change: it compares a
projected form of the interface it is about to reuse, the incoming side is rebuilt from ARXML and
a SWCraft-produced export carries no init at all, and without this any target project whose
interface declared one would have failed **every** component import with a non-overridable
conflict. An init value the incoming side does **not** declare is now projected out of that
comparison beside `description`, and the note the command prints about what the projection cannot
see names it. The projection is deliberately one-directional: an incoming *value* — which only a
third-party ARXML carries today — is evidence the reader took from the file, so where the target
contradicts it the interface is a conflict rather than a silent reuse, with both values in the
message.

**What that leaves, stated rather than left to be found.** A component export carries no init
value at all — the exported ARXML is produced by the same writer, which emits none — so an
`import component` of a SWCraft export that **creates** an interface in the target project creates
it without `init`, and neither report says so: `ComponentExportReport` and `ComponentImportReport` have no lossiness
channel, and adding one would change `export-summary.json`, whose key order and bytes are a fixed
schema. So a component handoff between two teams does not carry recorded initial values in either
direction. Nothing is silently *overwritten* — a target interface that already declares an `init`
is reused, not rewritten, which is what the projection above buys — but a newly created one starts
empty. A **third-party** component ARXML that does carry `INIT-VALUE` is the one case that differs:
the importer reads those values, a created interface keeps them (the dialect normalization carries
`init` through rather than rebuilding the data element without it), and a *reused* one whose target
definition declares a different value — or none — is refused as a conflict naming both sides
instead of being reused with the incoming value dropped. A later release revisits the projection when
the SWCraft export itself carries values.

## The ARXML is unchanged, and this is what that means

No byte moves. The claim is held two ways rather than asserted: `examples/basic` generates
byte-identical documents at 4.2.2 and 4.3.0 — but that project declares no `init` at all, so on
its own it witnesses only that a model *without* values is unchanged. Beside it, two copies of
that project gain the same data types and data elements and only one of them gains the values, one
per shape the field admits; the two generated documents are compared at both versions and are
byte-identical. A source-level scan sits beside the digests: the two ARXML writer modules name no
`INIT-VALUE` tag and make no attribute access called `init`.

**What the values are worth is worth stating honestly, because an early draft of this work got it
wrong.** Scalar init values in a tool export are real engineering content — distinct values,
hexadecimal spellings among them — and a first measurement mis-read them out of the neighbouring
array-size element. They are worth importing. And until 27.2 emits them, the exporter ignores the
field: a downstream RTE generator reading SWCraft's ARXML sees no initial value, exactly as before
this release.

**Checked against real tool exports the maintainer holds privately.** No init story is claimed for
mode-switch, non-volatile or parameter interfaces. Client-server interfaces are untouched.

## The model contract is `3.2.0`

`contractVersion` moves from `3.0.0` to `3.2.0`, across this release, in **two** minors and no
major: `3.1.0` is this change — one optional field and five rule identifiers added, nothing removed
or renamed — and `3.2.0` is the runnable-data-access change described further down, which was
written as `3.1.0` on its own branch and renumbered when it merged second. A consumer authored
against `3.0.0` reads a `3.2.0` document without noticing, and
`SUPPORTED_CONTRACT_MAJORS` stays `{3}`.

This change's own step of the inventory goes from 10 layers, 29 kinds, 114 fields and 109 rules to
10 layers, 29 kinds, **115** fields and **114** rules. The new declarations are
`field:interfaces.data_element.init` and the five `rule:interface.init-*` ids listed above. What
the release installs is the second step's totals — 10 layers, **32** kinds, **125** fields and
**125** rules — stated where that change's own § reports them.

`field:interfaces.data_element.init` declares a type the vocabulary did not carry before:
**`value`** — a scalar, a list, or a mapping, which may nest. It is what the schema spells as one
named recursive alias, and any consumer that switches on the published type name needs a case for
it. *Which may nest*, and not "to any depth": every walk over the value tree — the reader's, the
validator's, and Pydantic's own — recurses with no depth bound of its own, so a value nested past
CPython's recursion limit raises rather than loading. The real bound is unmeasured and no number
is invented for one.
`contractVersion` is deliberately not one of the five product lockstep sites; this release
moves both, and they move independently.

## What the editing protocol and the MCP surface publish differently

Nothing a client sends changes — no tool, no request shape, no argument. What comes back does,
and so does what is **accepted**:

- A `read` of an interfaces address at `form: "full"` now carries `init` on any data element that
  declares one, and `discover` publishes the field with its `type: "value"` and, at
  `form: "full"`, its description.
- **A staged change set that writes a non-conforming `init` is now refused.** The five rules run
  in the editing protocol's pass D as well as in `check-model` — it is the same composed
  `check_cross_layer_consistency` — and all five map to `consistency-violation` (not
  `broken-reference`, because the check abstains wherever the declared type does not resolve, so
  by the time one fires every reference it read has resolved). The refusal names two addresses:
  the value's own, three steps deep at `data_elements` → the member → `init`, and the data type
  that refused it. This is the one way an edit that succeeded before this release can start
  failing after it.
- **`sender_receiver.data_elements` stops being a collection whose `summary` is its full answer.**
  It has always been one, because a `data_element` had no field the summary rules drop; it now has
  one. Concretely: the over-budget hint chain from a default-form read of that collection used to
  read `["full", "index"]` and now reads `["index"]`, and `data_element` leaves the published set
  of member kinds whose summary is their full answer (eight, now seven). The prose in `discover`'s
  `reads` block that counts both sets is re-derived, not reworded to fit.

## What the editor does not check

The generated YAML schemas render `init` **permissively** — `["boolean", "integer", "number",
"string", "array", "object", "null"]`, every JSON type there is — and that is deliberate rather
than a gap left open. The value's shape is not a property of the field; it is a property of the
*other file* the element's `type` names, which a schema validating one document has no way to
reach, and a narrowing that guessed would be wrong in the accepting direction the moment the type
changed. What the editor does give you is the field's hover text, which states the shape rule.

The authority is `swcraft check-model` — as it is for every cross-file rule, now recorded with a fixture of its
own.

## Python API

- `schema.DataElement` gains `init: InitValue | None = None`, and `schema.InitValue` is a new
  public name: a named recursive type alias over `bool | int | float | str | list[InitValue] |
  dict[str, InitValue]`. It is spelled as a `TypeAliasType` rather than a bare union because the
  bare union does not build — schema generation recurses without bound.
- `writer.mutations.create_interface` accepts an optional `init` key per data-element dict and
  writes it out. Whether the value conforms to the declared type is `check-model`'s question, the
  same division that already applies to a `type` naming no declared data type.
- **`typing-extensions>=4.6` becomes a declared dependency of `swcraft-tools`.** It supplies
  `TypeAliasType` on the declared Python floor of 3.11 (PEP 695's own syntax needs 3.12). It was
  already installed transitively through Pydantic; it is now declared directly, because every
  direct use is declared directly.

## Upgrade checklist

1. Install all four artifacts at `0.7.0`, the extension included.
2. Run `swcraft check-model --project swcraft.yaml`. It should report exactly what 0.6.0 reported:
   nothing in this release refuses a model that loaded before it.
3. Run `swcraft validate --project swcraft.yaml` and compare the generated ARXML with what you had.
   It is byte-identical.
4. Add `init` where your design fixes an initial value, running `check-model` as you go.
5. If you re-import a Rhapsody export, expect the init values to arrive and the
   `CONSTANT-SPECIFICATION` skip lines to stay — read one of them, it now says where the value
   went.
6. Run **SWCraft: Onboard Project** once so the editor picks up the regenerated schema bindings.

## Runnable data access: what a runnable `reads`, `writes` and `calls`

*A second change rides this release, from a branch cut beside the one above. Its section is
appended here so the note stays one document; the merge that brings both together is what makes
the contract number in § **The model contract** above the one a user installs (see § *The
contract, from this change's side* below).*

**A runnable now says what it touches.** Each runnable of a software component may declare three
optional lists — `reads` and `writes` of `(port, element)` pairs, `calls` of `(port, operation)`
pairs — naming a port of its **own** component and a member of that port's interface. They are the
declarations an RTE generator derives `Rte_Read` / `Rte_Write` / `Rte_Call` from, and they were the
largest single gap between the model and a tool export: **the access points**, of which the model
could hold none. `check-model` validates
them, `swcraft import rhapsody` reads them, the assistant's `read` answers over them, and `swcraft
diff` reports a member added or removed by its pair. The command-line `swcraft query` reaches them in
no form — it filters and slices a layer's declared top-level fields, and the lists sit two levels
down (see *What the assistant's `read` answers* below).

**Read this before you expect it in the ARXML.** This release puts the lists **in the model and
nowhere else**. The exporter emits no `DATA-RECEIVE-POINT-BY-ARGUMENT`, no `DATA-SEND-POINT` and no
`SYNCHRONOUS-SERVER-CALL-POINT`; a model that declares the lists and a model that does not generate
byte-identical documents at both `--arxml-version`s, and that identity is a gate rather than a
promise. The emission — the three generated name forms with their identifier checks, the goldens
and the XSD evidence at 4.2.2 and 4.3.0 — comes in a later release, planned only now that the shape is fixed.
Until it ships, an access declaration is something your team can review, diff, read through the
assistant and hand to a downstream tool through the model, **and an RTE generator reading the exported ARXML does not see
it**.

### What an existing project must change

**Nothing.** All three lists are optional and default to empty, and an empty list is **not written**
— a runnable file without them is byte-identical to what 0.6.0 wrote, which the writers' own digests
pin. `check-model` reports the same findings on a model that declares none, and `swcraft validate`
writes the same ARXML bytes.

What changes is what you *may* write:

```yaml
# model/swc/chassis/SpeedControl.yaml
name: SpeedControl
ports:
  - {name: rSpeed, direction: require, interface: IVehicleSpeed}
  - {name: pTorque, direction: provide, interface: ITorqueRequest}
  - {name: rDiag, direction: require, interface: IDiagnostics}   # client_server
runnables:
  - name: Control10ms
    events:
      - {type: timing, period: 0.01}
    reads:
      - {port: rSpeed, element: speed}
      - {port: rSpeed, element: gear, by: value}   # received by value; absent = by argument
    writes:
      - {port: pTorque, element: torque}
    calls:
      - {port: rDiag, operation: ReportFault}
```

Three rules of the shape are worth knowing before you hand-author:

- **The identity of an entry is its pair.** The same `(port, element)` twice in one list is refused
  when the file loads, whatever the receive form — `by: value` is a *form*, not a second identity,
  so one pair may not appear once by argument and once by value. A blank `port`, `element` or
  `operation` is refused the same way.
- **`by` belongs to `reads` alone.** `writes` and `calls` have no receive form; a stray `by` key on
  one of them is ignored when the file loads, as every stray key on every element is, and the
  editor's schema is where it is flagged.
- **The lists say *what*, never *when*.** The order of entries carries no meaning, and nothing
  compares a sequence's steps against a runnable's lists — a sequence owns ordering.

### What `check-model` refuses

Five new rules in the cross-element family, resolved against the component's own ports and the
interfaces they name, with the maps built **once** per run:

| Rule | Refuses |
|---|---|
| `rule:swc.access.unknown-port` | an entry naming a port the component does not declare — **one finding per `(component, port)`**, listing every runnable and entry that names it, and nothing further for those entries |
| `rule:swc.access.unknown-element` | an entry naming no data element of the port's sender-receiver interface |
| `rule:swc.access.unknown-operation` | an entry naming no operation of the port's client-server interface |
| `rule:swc.access.direction-mismatch` | a read or a call through a `provide` port, a write through a `require` port |
| `rule:swc.access.interface-kind-mismatch` | a read or write through a client-server port, a call through a sender-receiver port — reported instead of, never beside, an element or operation finding |

A direction mismatch is decided *beside* the member check, so a write through a require port whose
element also does not exist is two findings, each a repair of its own. A port whose `interface` is
undeclared keeps producing exactly the finding it produced before, and its accesses are not reported
a second time under a rule about something else. And the six element-local rules — a pair listed
twice, a blank name — refuse at load, before `check-model` runs at all.

### What `swcraft import rhapsody` now reads

For every runnable the importer reads the four access containers — `DATA-RECEIVE-POINT-BY-ARGUMENTS`
and `DATA-RECEIVE-POINT-BY-VALUES` onto `reads` (the second with `by: value`), `DATA-SEND-POINTS` onto
`writes`, `SERVER-CALL-POINTS` onto `calls` — resolving each point's port and target through the
component's own ports and the interface the port was imported with.

Checked against real tool exports the maintainer holds privately:

- **The access points land** — reads (some by value), writes and calls. The rest of a file's points
  are three named classes, each a skip line with its
  reason: those that name a port the component never declares (the class the `unknown-port` rule
  would otherwise report on the imported project), those that sit on one of the ports the import
  already skipped and carry that port's reason verbatim, and those that are the same `SHORT-NAME`
  twice in one runnable, which the reader drops as it always has (an *empty* `SHORT-NAME` counts as
  a name there, as it does to the path index that reports the drop; only an access with no
  `SHORT-NAME` element at all has no path to collide on). The landed points and the three classes
  add up to every point in the file — one identity — and a closed gated test holds it.
- **A collapse is not a skip.** A duplicated `(port, element)` under two *different* names
  collapses to one entry and is reported under a section of its own, *Collapsed duplicate access
  points*, rather than as a skip — a collapse loses no model content. The section lists the components the import **writes** — after
  `--packages` selection and the reserved-name pass — and each line names its component by the
  export's own `SHORT-NAME`, as every skip line cites the export's path; when that pass renames the
  component, the same report's rename section maps the name.
- **Access names are not model content.** Data accesses and call points usually
  follow `R_<port>_<element>` / `W_<port>_<element>` / `Call_<port>_<operation>`; the importer
  keeps none of them, and a later release's writer derives them. A call point whose name diverges
  (a numeric suffix) lands under its pair like every other.
- `check-model` on an imported project takes longer from the command line than before the lists
  existed, and the difference is not the new walk (a small part of it): the component layer grew on
  disk and the composed check parses it several times over — eleven layer reads across its
  constituent checks — as it did before this change.
- Components with no access point re-import byte-identically.

### The ARXML is unchanged, and this is what that means

No byte moves. `examples/basic` generates byte-identical documents at 4.2.2 and 4.3.0 against the
digests taken before the first line of this change, and the writer's own source names no access
container: `grep -r 'VARIABLE-ACCESS\|DATA-SEND-POINT\|DATA-RECEIVE-POINT\|SERVER-CALL-POINT'
tools/src/swcraft_tools/writer/` returns nothing. Over the whole package the same grep returns
exactly two modules, `tools/src/swcraft_tools/arxml_reader.py` and
`tools/src/swcraft_tools/arxml_import/swc_mapping.py` — the reader and the mapper this release
taught the four names to. Both halves of that sentence have an oracle now, a source scan in
`tools/tests/test_arxml_components_writer.py` that pins the writer's tree at none and the package's
inventory at those two, so the first emitting module fails a test rather than staling a sentence
— **superseded by the release that emits them, on 2026-09-06, which deleted the scan on purpose** because its subject
now emits, and put the additive-delta gate
`tools/tests/test_arxml_components_writer.py`'s `TestTheDeltaOfAnAccessIsExactlyTheNodesThatCarryIt`
in its place. Until a later release emits them, the exporter ignores the
lists: a downstream RTE generator reading SWCraft's ARXML sees no access point, exactly as before.

**`swcraft import component` keeps working on SWCraft's own exports**, which needed a
deliberate change. The comparison that decides whether a component already in the target project
is *unchanged* or *diverges* now projects the three lists out on both sides — a SWCraft-produced
export carries no access point, and without the projection every component import into a project
whose runnables declare accesses would have conflicted, and `--update` would have silently
overwritten the declarations. The note the command prints about what its comparison cannot see
names the lists. Three things that leaves, stated rather than left to be found:

- a component handoff between two teams does **not** carry access declarations in either direction
  until 28.2 emits them — and an export that *does* carry access points (a hand-built one, or one
  from a tool that emits them) imported onto a component the project already has is `unchanged`,
  its points neither compared nor landed, with no line in the report, because the lists are no part
  of the comparison at all;
- `--update` on a *real* divergence **keeps the target's `reads`, `writes` and `calls`** — the
  rule the same path already applies to the `memory` budget, one level down. The export's runnables
  carry no access point until 28.2 emits them, so an imported runnable whose three lists are empty
  is silent about them, not declaring none; the target runnable's lists are carried across the
  replacement, matched by runnable name, *before* the mandatory diff preview is rendered (so it
  advertises no removal that is not happening), and the report states what was carried, per
  runnable and per list (`ACCESS LISTS preserved from the target project`), on the real run and on
  `--dry-run` alike. The other half of the rule answers "two sources of truth": an export that
  *does* carry a point for a runnable — a hand-built one today, every SWCraft export once 28.2
  emits them — is the truth for that runnable, and the target's lists are replaced by its through
  the preview, as the rest of the runnable is. A target runnable the export no longer declares is
  removed with its lists. The carried entries are the target's own and `check-model` re-checks them
  after the import as it checks every declaration: an update that removes a port a carried entry
  names leaves a finding there, not a silent drop. This reverses an earlier design
  ("replace the whole definition, lists included, through the preview"):
  the preview is an insufficient guard for content the source cannot express — it is
  shown before the write only on `--dry-run` — which is exactly the case the `memory` rule was
  written for. The preservation and the comparison's nulling of the lists are one decision and
  leave together in a later release;
- **an export from another tool can now be refused where 0.6.0 imported it.** The reader reads the
  four access containers, so every point it cannot place is a skip entry with a reason — and a
  component import refuses over any skip that is not deferred content, because a component export
  holds nothing but the component's own closure and importing without part of it would be lossy.
  The classes, each a sentence in the refusal: a point naming a port the component does not
  declare; a target reference that does not resolve (or is no path at all); a read or a call
  through a `provide` port, a write through a `require` port; a data access through a client-server
  port or a call through a sender-receiver port; a point with no port or no target reference; a
  second point under a `SHORT-NAME` the runnable already used; and an
  `ASYNCHRONOUS-SERVER-CALL-POINT`, which the model does not carry. A duplicated `(port, element)`
  under two names is the one non-refusal: it collapses to one entry with a report line. Whole-model
  `import rhapsody` reports the same classes as skip lines and keeps going, as it always has.

### What the assistant's `read` answers, and what it cannot

The lists are three more collections on a runnable, so everything the editing protocol already does
for a collection applies: `create` and `remove` at a member's own address, `read` in the three
forms, `where` over `port`, `element`, `operation` and `by`, the keyset page, `discover`
publishing the fields. None of that is the command line's: `swcraft query` filters and slices the
declared top-level fields of a layer, so `--where`/`--exists reads` is refused as an undeclared
field and `--members runnables` answers runnable identities only — from the shell, `swcraft diff`
is the one window onto a pair, and the YAML file is the other. Three facts are specific to the
lists:

- **A hub's lists are visible as counts at one address.** `read` of a component's `runnables`
  collection in `summary` form answers one row per runnable — `{name, events, reads, writes,
  calls}` as counts — a small fraction of
  the 80 000-byte response budget even for a large component. The component's own summary is
  unchanged.
- **The lists themselves can exceed the budget, in every form, and the page is the answer.** The
  identity of a write or a call is the whole entry, so `summary` and `index` narrow those lists not
  at all; a read's identity is everything but its optional `by`, so `summary` drops exactly that.
  A hub runnable with many accesses, read through the live engine, can **refuse at `full`** on its
  `reads` (`full` publishes `by` on every entry, `null` where it is absent) and still **answer at
  `summary` and `index`**; its `writes` can refuse in every form, and the runnable itself at
  `full`. A page of fifty reads fits easily; the longer the port and element names, the sooner
  `reads` cross the budget.
- **An `update` that replaces a runnable and omits its lists resets them.** This is not new — it is
  the shipped behaviour for every collection on a member, recorded as a negative vector for `events` — but a runnable now has four collections it can happen to instead of one. An omitted
  key is not "leave this alone": the replacement is re-validated through its class, the collection
  comes back at its default `[]`, and the delta the reviewer sees carries a `remove` the client
  never wrote. Address the entry, not the runnable.

Two consequences reach every project, not only those declaring accesses:

- **`discover` at `form: "full"` for the whole project is now a refusal.** The descriptors this
  change adds push the project-wide `full` answer to 88 530 wire bytes on the seed project (111 %
  of the budget) — the regime the response budget was designed for — so it answers `over-budget`
  with a hint chain: the default `summary` form (34 050 bytes, 43 %) or `full` one layer at a time,
  the widest of which (`swc`) is 22 848 bytes. A client that walks the hints gets everything it got
  before. The recorded protocol vectors say so: the project-wide `full` is a negative vector now,
  and ten per-layer `full` vectors carry the prose it used to.
- **The `reads` block of `discover` re-counts its own sentences.** `runnable.writes` and
  `runnable.calls` join the collections whose `summary` is their full answer, `data_write` and
  `operation_call` join the member kinds selected whole, and both collections join the `index`
  exceptions; `data_read` joins none of the three, because its optional `by` is what a summary
  drops. The prose is re-derived from the contract, not reworded to fit, and the merged counts after
  the change above are what a client reads.

### What the editor does not check

The generated YAML schemas render the three lists with their closed member objects, the pair
required, and `by` as the one-value enum it is — completion and hover for all of it. What they
**cannot** check is anything that lives in another file: that the port is declared on this
component, that the element is on that port's interface, that the direction agrees. Two shapes the
schema accepts and `check-model` refuses are recorded in the editor limitation map: one pair read
by argument and by value (even whole-item uniqueness would pass it), and an entry naming a port the
component does not declare. The authority is `swcraft check-model`, as it is for every cross-file
rule.

### Python API

- `schema.Runnable` gains `reads: list[DataReadRef] = []`, `writes: list[DataWriteRef] = []` and
  `calls: list[OperationCallRef] = []`; the three reference classes are new public names.
  `DataReadRef.by` is `Literal["value"] | None`, so an argument-read serializes with no `by` key.
- `writer.mutations.add_runnable` accepts `reads`, `writes` and `calls` as **appended** keyword
  parameters (each an iterable of the YAML's own mappings, default `None`); every existing
  positional caller is untouched. The runnable is built through the same validation a file goes
  through, so a duplicated pair is refused with the file unchanged and no audit entry. The
  cross-element rules stay `check-model`'s — `add_runnable` reads no interface file, as `add_port`
  never has.
- `validator.check_runnable_access` is the new pass, composed into `check_cross_layer_consistency`
  after the port-interface check; `validator.CONSISTENCY_RULES` carries the five rules.
- `arxml_reader.SwcRunnableInfo` gains `accesses: list[SwcAccessInfo]`, a new public class.
  `map_swcs`'s signature is unchanged: `arxml_import.swc_mapping.ImportedSwc` gains
  `access_collapses: list[str]`, the collapse lines of that component, which `run_import` and
  `plan_component_import` gather into `ImportReport.access_collapse_lines` and
  `ComponentImportReport.access_collapse_lines`, each with a `render()` section of its own.
- `component_exchange` projects the three lists out of the reuse comparison (`_projected_runnable`);
  `_UNREPRESENTABLE_NOTE` names them.

### The contract, from this change's side

This change moves `contractVersion` to `3.2.0` — a **minor** over the `3.1.0` of the section
above, by the same rule as that section: three fields, three member kinds, seven member fields and
eleven rule identifiers are added, `omitAtDefault` is declared on three more fields (the exception
table that held `min_start_interval` alone holds four, all on the runnable), and nothing is removed
or renamed. `SUPPORTED_CONTRACT_MAJORS` stays `{3}`. On its own branch, cut from the same `3.0.0`
as the change above, it was written as `3.1.0`; it merged second, so it was renumbered — the
identifiers and this section with it. The shipped
inventory it leaves is 10 layers, **32** kinds, **125** fields and **125** rules (71 cross-element,
53 element-local, 1 `schema-config`), and it is what an installed `discover` reports.

### Upgrade checklist

1. Install all four artifacts at `0.7.0`, the extension included.
2. Run `swcraft check-model --project swcraft.yaml`. It should report exactly what 0.6.0 reported:
   nothing in this change refuses a model that loaded before it.
3. Run `swcraft validate --project swcraft.yaml` and compare the generated ARXML with what you had.
   It is byte-identical.
4. Declare `reads`, `writes` and `calls` where your design fixes them, running `check-model` as you
   go; address a single entry, never the whole runnable, when you edit through the assistant.
5. If you re-import a Rhapsody export, expect the access points to arrive, one skip line per point
   the import could not place, and — where a component export carried the same pair under two
   names — a *Collapsed duplicate access points* section in the report.
6. If a client of the assistant requested `discover` at `form: "full"` for the whole project,
   teach it the hint chain: the default form, or `full` one layer at a time.
7. Run **SWCraft: Onboard Project** once so the editor picks up the regenerated schema bindings.

## SWCraft is installed once per machine, and a project installs nothing

*A third change rides this release, from a branch cut beside the two above. Its section is
appended here for the same reason: the note stays one document. It touches no model file, no
check and no generated byte — what it changes is how the program that writes them is
installed, found and invoked.*

**One archive, one file, one installation.** SWCraft is delivered as
`swcraft-<version>-<platform>.zip`: the installer, its two wrappers, the three wheels with their
whole third-party closure and the VS Code extension. A colleague with Python 3.11 unpacks it and
runs `swcraft_install.cmd` (`swcraft_install.sh` elsewhere). Afterwards the machine carries one
installation under the user profile — `%LOCALAPPDATA%\SWCraft` on Windows, `~/.swcraft` elsewhere
— holding one directory per release with a `current` link, and one directory that has to be on
the user `PATH`: the installer adds it there itself on Windows and, on macOS and Linux, prints
the one `export PATH=…` line for a shell profile and edits no file.
There is no compiler, no Node, no network and nothing built on that machine.

**A project stops owning a toolchain.** `swcraft init --integration moon` writes fourteen files
and none of them installs anything: no `.venv`, no `bootstrap.py`, no `requirements-swcraft.txt`,
no `clean_outputs.py` and no `.vscode/mcp.json`. Every build task runs the bare `swcraft` from
`PATH`, the clean step is the new `swcraft clean-outputs`, and the SWCraft VS Code extension
registers the MCP server with the editor itself. What the project keeps is the *statement* the
retired files made: `toolchain_version` in `swcraft.yaml`, the release it is built with.

### What an existing project must change

Unlike the two changes above, this one is **not** "nothing" — but it is short, and none of it
touches the model.

1. **Add the pin.** In `swcraft.yaml`:

   ```yaml
   toolchain_version: "0.7.0"
   ```

   One exact release, never a range: `>=0.7`, `==0.7.*` and `~=0.7.0` are refused at load,
   because a range would pin nothing. A manifest without the field pins nothing either, and is
   accepted — the field is optional.

2. **Delete what the toolchain no longer reads**: `.venv/`, `bootstrap.py`,
   `requirements-swcraft.txt`, `clean_outputs.py`, and `.vscode/mcp.json` with the
   `.vscode/mcp.json.example` beside it (and the `.gitignore` entry that hid the first;
   `git rm --cached` whichever of them was committed). A leftover `.venv` is worse than
   untidy — activated in a terminal it shadows the installation for everything you type there.
   The editor's health check cannot see that: it reads the `PATH` VS Code itself was started
   with, and a venv activated inside the integrated terminal changes that shell and not the
   extension host.

3. **Update the build graph** if you hand-edited it. The scaffolded `moon.yml` now runs
   `command: 'swcraft'` with `options.shell: false` on every task, its `toolchain:` input group is
   gone (`swcraft.yaml` is already in the `model` group, so raising the pin still invalidates
   every cached task), and `validate-arxml` gained `@group(model)` in its `inputs:` — without it
   an upgrade would be served from moon's cache. Re-scaffolding into a copy and diffing is the
   quickest way to see the whole shape.

4. **Drop the `python` pin from `.prototools`** if you have one. The project builds no
   environment, so it needs no interpreter; the moon pin stays.

5. **Make `dist_root` and `views_root` relative**, if either is written as an absolute path.
   *An absolute `dist_root` or `views_root` is now refused at load* — and that is a **breaking
   manifest change**, the only one in this release. 0.6.0 accepted such a manifest everywhere
   except `clean-outputs`; 0.7.0 refuses it in `project.require_project`, which every command and
   the MCP server load through, so `check-model`, `generate`, `validate`, an agent session **and
   the five read-only commands** all exit 1 on it. Those five otherwise promise exit 0 whenever
   the project could be read, and this is consistent with that promise rather than an exception
   to it: a manifest the loader refuses is a project that could not be read. The refusal names the
   field, and the fix is one line — write the root relative to the project directory, which is
   also the only spelling that means the same thing on the next machine. "Absolute" is judged
   under **both** platforms' rules, so `C:/dist` is refused on macOS and Linux too rather than
   creating a directory called `C:` inside the project.

### What a workstation must do once

Unpack the archive and run the one file. Then get `swcraft` on `PATH`, which is the one step
that is not the same on both platforms: on Windows the installer has already edited the user
`PATH`, so open a **new** terminal; on macOS and Linux it printed one `export PATH=…` line and
edited no shell file, so add that line to your profile first. Then `swcraft --version`. That is
the whole of it, and it replaces: a SWCraft checkout on the target platform to build a
wheelhouse, a project scaffold, a bootstrap per project, a `code --install-extension` and a
hand-maintained chat configuration.

Afterwards:

- **Updating** is the next archive's installer. The new release is installed beside the old one,
  `current` moves to it, the `.vsix` is handed to VS Code, and only then is the previous version
  removed — so an interrupted update leaves the previous release working. A directory Windows
  will not delete because VS Code still has it open is reported in one sentence and is **not** a
  failure: the new release is already current.
- **Repair** is the same archive again — it reinstalls in place.
- **Rollback** is the previous archive's installer. There is no rollback command; the archive is
  the version.
- **Uninstall** is `--uninstall`: the home and the extension, plus — on Windows — the `PATH`
  entry. On macOS and Linux it prints the line to remove from your shell profile and edits no
  file, the mirror of what the install does there.
- The installer's other flags: `--home DIR` (absolute — a relative one is refused, because the
  `current` link would be written with a target that resolves against itself), `--source DIR` or
  `--index-url URL` for where the
  wheels come from (exclusive; an index skips the platform check because pip then resolves for
  the running interpreter), `--no-path`, `--no-vsix` — the flag a **build agent** uses, since it
  has no editor — and `--python PATH`.

### What the extension no longer does

- It no longer writes, repairs or opens a chat configuration. `SWCraft: Repair MCP Config` and
  `SWCraft: Open MCP Config` are **gone**, and so is the `.vscode/mcp.json` they maintained: the
  extension registers one MCP server per workspace folder whose root holds a `swcraft.yaml`,
  running `swcraft mcp-serve --project <that manifest>` with `SWCRAFT_REVIEW=elicit`. A manifest
  *nested* inside the folder registers no server — the workspace root is what is read. Another
  chat client is configured by hand with the same command line, which the user guide's *In VS
  Code* page carries.
- It no longer looks for a Python. It runs the workstation installation's own `swcraft` by
  absolute path — neither a project `.venv` nor the proto shim is a candidate any more — and the
  one override is the new `swcraft.executable` setting, which exists for developing the extension
  against a SWCraft checkout.
- Two commands replace what went: **SWCraft: Install Toolchain** and **SWCraft: Update
  Toolchain**, which run the archive's *own* installer on an archive you point them at (the
  `.zip` or an unpacked directory). *Update* refuses an older archive; rollback stays the older
  archive's installer, deliberately outside the editor. The command count is unchanged at
  thirteen.
- `SWCraft: Check Editor Tooling` reports the installation in six cases, each with its own
  repair: missing; present but `swcraft --version` will not start (the installation is built over
  an absolute base interpreter, and a workstation may upgrade or remove the Python it was built
  on); running and printing no version this can read; a version that is not the extension's; a
  bare `swcraft` resolving **nowhere** in the window; and a bare `swcraft` resolving **somewhere
  else** there. The last two are warnings rather than faults — the extension spawns the
  installation by its full path — and the first of them is what every healthy macOS and Linux
  install reports until the `export PATH=` line the installer prints is in a shell profile.

### What the pin does not reach

**A 0.6.x install reads `toolchain_version` and ignores it.** `SwcraftProject` declares no
`model_config`, so pydantic's `extra="ignore"` applies and an older toolchain accepts the field
without seeing it. The check therefore works **forward only**: from 0.7.0 on, a project pinned to
a release the machine does not carry is refused by every `swcraft` command that writes or gates and
reported by the read-only five, and nothing protects a project from a toolchain that predates the
field. `schema_version` is deliberately **not** bumped for an added optional field — the
`arxml_version` precedent.

Three further limits, stated rather than implied: the check is an **equality on one release** and
not an ordering, so it says which two versions disagree and never which is newer; it reads the
**manifest**, never the shell, so a second `swcraft` ahead of the installation on `PATH` is
caught only when the versions differ; and a manifest without the field pins nothing at all.

**And a fourth: the pin lives in `swcraft` alone.** Neither `swcraft-mcp` nor `swcraft-agent`
reads `toolchain_version` — the check is written once, in the `swcraft` CLI, and every path that
does not go through it bypasses it entirely. Three do, and all three are supported: the
`swcraft-mcp` and `swcraft-agent` console scripts, which stay installed; and
`python -m swcraft_mcp.server`, the documented invocation for a host that runs the server itself.
A project pinned to another release opens normally in all three. What `swcraft mcp-serve` and
`swcraft agent` exec is the **module** and not the console script — `sys.executable -m
swcraft_mcp.server` and `-m swcraft_agent.cli` (`cli._hand_over`) — and both check the pin before
handing over, so the exec is not a fourth bypass; the console scripts are a separate entry point
that nothing routes through. This is a deliberate boundary rather than an omission — the pin is a
statement about the *toolchain a project is built with*, and those three are entered by a program
that has already chosen its interpreter — but it means "every command checks the pin" is true of
`swcraft` and of nothing else. `tools/tests/test_cli.py::TestToolchainPin` states the boundary in
both directions so that a future check added to either server is a deliberate act.

### The read-only commands still exit 0

A pin mismatch is one sentence and two consequences. `generate`, `validate`, `check-model`,
`import`, `clean-outputs`, `mcp-serve` and `agent` stop with it on stderr and exit 1, before
anything is written or announced. `diff`, `impact`, `list`, `query` and `resource-report` print
the same sentence and **answer anyway**, exiting 0: their committed guide sentence promises a
successful run whenever the project could be *read*, and a pin mismatch is not a failure to read
one. Only the prefix differs — `Error:` against `Warning:`.

### Two new subcommands

- `swcraft agent ARGS...` hands its arguments to the assistant unchanged, so `swcraft agent chat
  --project PATH` is the old `swcraft-agent chat --project PATH`. It is an exec of the same
  interpreter's `swcraft_agent.cli`, never an import. The `swcraft-agent` console script stays
  installed.
- `swcraft clean-outputs --project PATH` removes the two directories the **manifest** declares as
  output (`dist_root`, `views_root`) and nothing else, preserving `dist/audit.jsonl`. It takes no
  directory argument, which is how the template script's second source of truth disappeared; what
  it keeps is a check on the fields, so a root that is the project directory or escapes the
  project through `..` is refused by name before anything is deleted. The third of those rules —
  **an absolute root** — is no longer this command's: it belongs to the **loader**, so every
  command answers the same way rather than the graph's first task refusing a manifest every other
  command accepted. See *An absolute `dist_root` or `views_root` is now refused at load* below,
  because that move is the one thing here an existing project can notice. It is a write command,
  and the build graph's first task.

### Where this is measured, and where it is not

Everything above is built and tested on macOS. **Windows is unmeasured**: the directory junction,
the `PATH` edit through `HKCU\Environment`, the settings broadcast, the `code.cmd` lookup, whether
SmartScreen interposes on a downloaded `.cmd`, and whether moon resolves a bare `swcraft` from
`PATH` with `options.shell: false` are written from documentation and tested with injected I/O.
The seated Windows gate that observes them is owed. macOS and Linux archives are built by
the same command and installed by the test suites; nothing here is evidence about Windows.

### Upgrade checklist

0. Check `swcraft.yaml` for an absolute `dist_root` or `views_root` and make it relative: 0.7.0
   refuses one at load, in **every** command. It is the release's one breaking manifest change and
   the only step here that can stop a project dead.
1. Install the `0.7.0` archive: unpack it and run its one file. On Windows the installer edits
   the user `PATH`; on macOS and Linux it **prints** an `export PATH=…/current/bin:$PATH` line and

2. In each project, set `toolchain_version: "0.7.0"` in `swcraft.yaml`.

   `.vscode/mcp.json*` from the project, un-tracking whichever of them git holds.
4. Re-scaffold into a copy and diff `moon.yml` and `.prototools` against yours, or apply the four
