# SWCraft 0.17.0

Released 2026-10-19. The release of requirements traceability: a requirement is versioned and
says who owns it, the trace link moves from the requirement into the architecture element that
satisfies it, requirements are imported from a requirements tool and exported to Sphinx-Needs, and
a finding can be a warning that lets a model build. Two changes need an edit in an existing project
— the requirement files and one line of `swcraft.yaml` — and *What upgrading takes* at the end is
the recipe. The archive's sizes are the tag run's, recorded under *The archive*.

## A finding is an error or a warning

A model finding now has a class. An **error** refuses as every finding did before; a **warning**
is listed and lets the model check, generate and build. `swcraft check-model` and
`swcraft validate` print every `ERROR:` line, then every `WARNING:` line, both on stderr, and exit
0 when there are warnings alone, with the success line unchanged. After the findings, one line on
stderr counts both classes, the way a compiler closes its diagnostics:

```text
  WARNING: SWC 'SpeedSensor' satisfies no requirement — add `satisfies: [<id>@<version>]` on the component, one of its ports or one of its runnables.
0 error(s), 1 warning(s).
```

The line is printed only when there is a finding, so a clean run's output is unchanged, and the
document `check-model --format json` prints is unchanged too. The rules page of the guide's
reference says which class each check has.

**A component that satisfies no requirement is a warning**, where it was the error that stopped a
build. A model whose only finding was that one now builds. A release pipeline that wants the old
strictness adds **`--warnings-as-errors`** to `check-model` or `validate`: the warnings keep their
`WARNING:` prefix, one line `Error: N warning(s) treated as errors (--warnings-as-errors).` follows
the count, and the command exits 1 before anything is generated. The flag is declared on those two commands
only; every other command refuses it as an unknown option.

The assistant's `validate` and `build` answers carry a `warnings` list beside `errors`, and a
change set whose only finding is a warning is committed: the assistant reports the warning after
the commit instead of being refused.

## The trace link lives in the element that satisfies the requirement

A requirement no longer lists the components that realize it. The **element** names the
requirement it satisfies, in a `satisfies` list, together with the requirement's version the link
was confirmed for:

```yaml
# model/swc/chassis/BrakeController.yaml (an excerpt)
name: BrakeController
type: application
satisfies: [REQ-BRK-001@2]
```

Twelve kinds of element can carry `satisfies`: a component, each of its ports and runnables, a
composition, the three kinds of interface, a task, and a processor, core, memory or partition. A
component is judged against the safety levels of the requirements it, its ports and its runnables
satisfy; a link on a composition, an interface, a task or a hardware element is recorded,
checked and reported, and allocates no level.

Why the move: a requirement that comes from a requirements tool belongs to that tool, and
importing it again overwrites its file. A link kept in the requirement would be lost on every
import; a link kept in the architecture is the architect's and stays.

A requirement now states three things:

```yaml
# model/requirements/REQ-BRK-012.yaml
id: REQ-BRK-012
title: Brake temperature derating
description: The controller reduces the brake torque request above the temperature limit.
version: 1
source: architecture
derived_from: [REQ-BRK-001@2, hardware:BrakeEcu]
asil: B
```

- **`version`** (required): SWCraft's own change counter for the requirement, a positive whole
  number. The requirements import raises it for an external requirement whose text, type, level or
  parents change; the author raises it for an architecture requirement. No edit raises it on its
  own.
- **`source`** (required): `external` when a requirements tool owns the file and an import
  writes it, `architecture` when it is written in the project.
- **`derived_from`** (optional): the requirements this one is derived from (`REQ-BRK-001@2`), or a
  top-level element (`hardware:BrakeEcu`).

`status` is gone — the requirements tool owns a requirement's lifecycle — and so is `links`. A
requirement `id` may no longer contain `@` or `:`, which now separate a link's version and an
element reference.

**What `check-model` and `validate` report.** Errors: a `satisfies` member naming no requirement, a
`derived_from` member naming nothing, requirements deriving from each other in a cycle, two files
declaring one requirement `id`, and a decomposed level (`B(D)`) whose bracket disagrees with the
level of the requirement it derives from. The check that a component is rated at least as high as
its requirements now counts the links on its ports and runnables too. Warnings: a link whose version
is not the requirement's current one (the link needs confirming), a link with no version at all, a
requirement nothing satisfies, and — new with the import below — a placeholder requirement.

`swcraft impact <requirement>` lists the elements that satisfy it.

**`swcraft import model` writes no placeholder requirement any more.** An imported model has no
requirement until you add or import one, and each imported component is listed as a warning until
it is linked; the import report says so in one sentence. `swcraft import component` carries no link
either — an AUTOSAR export has no place for one — and `--update` keeps the links the project's
component, its ports and its runnables already have.

## In VS Code: the Problems panel and two quick fixes

**Check Model** and **Build** fill the Problems panel with the model's findings, errors in red and
warnings in yellow, each at the line of the element it names. They describe the saved model at the
last run and are refreshed by the next one; saving a file runs nothing, and the panel is not the
gate — `swcraft validate` is.

On a trace link the panel offers **two quick fixes**: confirm a link to the requirement's current
version, or write the version a bare link lacks. Each edits the open file and leaves it for you to
save. Go to Definition follows a `derived_from` element reference, and Find All References on a
requirement lands on the lines that satisfy it.

`swcraft check-model --format json` is what the panel reads: one document on stdout with each
finding's rule, class, message and the elements it names. The text output is unchanged.

## Where a requirement came from, and the placeholder for a missing parent

A requirement may record its provenance in three optional fields: **`document`** (the source
document, as the requirements tool names it), **`baseline`** (that document's baseline) and
**`revision`** (the tool's own revision of the requirement, exactly as the tool writes it). No check
reads them, and a change of one never moves `version`: `revision` is the number a reader outside
SWCraft knows, `version` is SWCraft's counter.

A requirement may be a **stub** (`stub: true`): the placeholder the import writes for a parent
that a requirement derives from and that has not arrived yet, with a placeholder title and text.
Every stub is a warning, so a model holding one fails under `--warnings-as-errors`; a stub is not
also reported as a requirement nothing satisfies. When the real requirement is imported it replaces
the stub. `stub` takes only `true` or `false`.

## Import requirements from a requirements tool

```sh
swcraft import requirements --source requirements.json --project swcraft.yaml --dry-run
swcraft import requirements --source requirements.json --project swcraft.yaml
```

The file is a strict profile of Sphinx-Needs' `needs.json`; its JSON Schema is published in the
guide's reference (*Requirements interchange*) for whoever writes a converter from a requirements
tool. The import compares by `id` and has one behaviour, with no modes and no `--force`:

- a new requirement is written at version 1;
- a requirement whose title, description, type, level or set of parents changed gets the next
  version, and the links that name the old one become warnings to confirm;
- `document`, `baseline` and `revision` are updated without a new version;
- a requirement the file marks `rejected` is removed;
- a parent found neither in the file nor in the project becomes a stub;
- an `id` the project holds as an architecture requirement, or one id in two files, refuses the
  import.

The report opens with a fixed `Summary:` line — added, changed, removed, stubs created, source
updates — then lists each change and the links that need confirming; `No change.` follows the
summary when nothing is written. `--dry-run` prints the report and writes nothing; `--report PATH`
also writes it to a file. Every file is written, or none: an apply that fails part-way restores
the files it touched. A file the import refuses is reported as `Error: FILE: <where>: <why>`,
naming the first problem only. The import runs no model check: run `swcraft check-model` after it.

In VS Code, **SWCraft: Import Requirements…** (the command palette and the panel's *Model*
section) does the same through the same command: pick a `.json` file, read the dry run's report in
an editor tab, then choose *Apply…* and confirm. Nothing is written unless you confirm; the applied
run's report opens in a tab of its own, and *Check Model* is offered, not run.

## `generate rst` writes a Sphinx-Needs export

`swcraft generate rst` now writes a folder, `dist/needs` unless `outputs.rst` names another,
holding four files:

| File | What it holds |
|---|---|
| `requirements.rst` | every requirement as a `req` or `spec` need, with `source`, `asil`, `revision`, `document`, `baseline`, `stub` where set, and its `derived_from` as a link |
| `architecture.rst` | every element that satisfies a requirement or that a requirement derives from, as a need of its own kind, with its `satisfies` as a link |
| `swcraft-needs.toml` | the Sphinx-Needs configuration the two files need: the types, the fields, the two link types and the id rule |
| `swcraft_needs.py` | the same configuration as Python data, for a documentation project with a configuration of its own |

**Sphinx-Needs 7.0 or newer** is required. A documentation project with no Sphinx-Needs
configuration of its own reads the toml with two lines in `conf.py`; one that has its own adds
`swcraft_needs.py`'s types, fields, links and id rule to it. The guide's *Command line* page,
section *The Sphinx-Needs export*, has both recipes, the `include` lines, and a table and a graph
of the trace to start from.

A requirement id holding a character Sphinx-Needs cannot link (`SR.3.1`) is written with `_`
(`SR_3_1`), with the original in `source_id`. The command builds all four files in memory first and
writes nothing, exiting 1 with one `Error:` line, when two needs would share an id, when a value it
writes on one line holds a line break, when a link's written id would be another need's, or when a
title or description holds `[[`, which Sphinx-Needs would evaluate as a dynamic function. A link is
shown and never judged: whether it needs confirming is `check-model`'s finding.

**The Resource Utilization section is no longer in the RST.** `swcraft resource-report` prints it,
as before.

**A requirement's multi-line description stays inside its directive.** Every line of it is now
indented; before, only the first was, and the rest of the text fell out of the need.

## The Windows installer waits for the antivirus

On a Windows machine with an on-access scanner, the installer could stop at *unpacking Python* on
its first run, because the scanner still held the files it had just written; a second run passed.
The installer now retries such a directory rename for up to about eight seconds before it refuses,
and the refusal names the wait.

## The model's contract is `11.1.0`

`contractVersion` moves from `10.1.1` — the contract 0.16.2 shipped — to `11.1.0`, a major: an
identifier is removed. Removed: `field:requirements.requirement.links`,
`field:requirements.requirement.status` and `rule:cross-layer.requirement-link-unknown-swc`. Added
on the requirement: `version`, `source`, `derived_from`, `document`, `baseline`, `revision` and
`stub`; `satisfies` on the twelve kinds above. Twelve rules are new: `rule:trace.link-unknown-requirement`,
`rule:trace.link-needs-confirmation`, `rule:trace.link-version-not-stated`,
`rule:trace.derived-from-unknown-target`, `rule:trace.derived-from-cycle`,
`rule:trace.decomposition-context-mismatch`, `rule:trace.requirement-unallocated`,
`rule:trace.requirement-stub`, `rule:name.duplicate-requirement`,
`rule:requirements.requirement.version.positive`, `rule:requirements.requirement.retired-links` and
`rule:requirements.requirement.retired-status`. A rule may now declare `severity: warning`; five do —
`rule:cross-layer.swc-without-requirement-link`, `rule:trace.link-needs-confirmation`,
`rule:trace.link-version-not-stated`, `rule:trace.requirement-unallocated` and
`rule:trace.requirement-stub` — and every other rule is an error. A project's own tooling that reads
a requirement's `links` or `status` has to follow the move.

## The archive

The runtime payloads are 0.16.2's, unchanged: Node.js 22.23.2, CPython 3.11.16 (the
python-build-standalone build of 2026-09-01), `elkjs` 0.12.0 inside the `swcraft-tools` package, and
the two extensions of the pack, Red Hat XML 0.29.3 and Red Hat YAML 1.25.0. The archive carries the
same packages as 0.16.2. The Linux archive measures **197 636 913 bytes**
(SHA-256 `9be1eb72…0f8a3e88`) and the Windows archive **201 698 859 bytes** (`9c448698…0f54ad6e`),
as the tag run of 2026-10-19 published them: 178 204 and 178 203 bytes more than 0.16.2's.

## What upgrading takes

1. **Install the 0.17.0 archive, then set `toolchain_version: "0.17.0"`** in each project's
   `swcraft.yaml`. Until you do, every command that writes or gates refuses a project pinned to an
   earlier release with the pin sentence and never reaches the model.

2. **Change one line of `swcraft.yaml`, together with the pin.** Under `outputs:`, replace
   `rst: dist/requirements.rst` by `rst: dist/needs`, or delete the line to take that default. A
   manifest still naming a `.rst` file is refused — by the `swcraft` commands, the assistant, the
   Copilot guard and the VS Code panel alike — with

   ```text
   outputs.rst names the folder generate rst writes (default dist/needs), not a .rst file
   ```

   A project still pinned to an earlier release is reported on its pin first, so change both lines
   in one edit. In a project scaffolded with a build graph, replace the `generate-rst` task's output
   `dist/requirements.rst` in `moon.yml` by the four files `dist/needs/swcraft-needs.toml`,
   `dist/needs/swcraft_needs.py`, `dist/needs/requirements.rst` and
   `dist/needs/architecture.rst`. A documentation build that set `needs_extra_options = ["asil"]`
   and included `dist/requirements.rst` takes one of the two recipes in the guide's section *The
   Sphinx-Needs export* and includes `dist/needs/requirements.rst` and
   `dist/needs/architecture.rst`.

3. **Move each requirement's links into the elements.** For every requirement file:

   1. for each name under `links`, add `REQ-…@1` (the requirement's `id` and `@1`) to the
      `satisfies` list of that component;
   2. delete `links` and `status`;
   3. write `version: 1` and `source: architecture` — or `source: external` for a requirement a
      requirements tool owns, which the next import then manages.

   A file still carrying `links` is refused, never converted, with a sentence naming the move:

   ```text
   'links' moved to the elements by contract 11.0.0: write 'satisfies: [REQ-12@N]' on the component, port, runnable, composition, interface, task or hardware element that realizes it
   ```

   with the file's own `id` in place of `REQ-12`; a file with `status` alone is refused with
   `'status' is retired by contract 11.0.0: an external tool owns the lifecycle; delete the key`.
   Every command that reads the model refuses such a file, and `swcraft diff` refuses a revision
   committed before the move like any revision it cannot read — **commit the move on its own**.

4. **A project imported from an AUTOSAR export** deletes its `requirements/REQ-ARXML-IMPORT.yaml`
   (or `REQ-RHAPSODY-IMPORT.yaml`), the placeholder the import used to write, and links each
   component to a real requirement; until then each is a warning, not an error.

5. **Run *SWCraft: Onboard Project* again** to bring the assistant profile and the Copilot
   instructions to this release: they now tell the assistant to write a component's `satisfies`
   link, and that a warning blocks no commit. It overwrites both files, so keep a copy of anything
   you edited in them.

6. **Check the model.** `swcraft check-model` lists the warnings of the new checks — links to
   confirm, requirements nothing satisfies — which build anyway. A release pipeline that relied on
   an unlinked component stopping the build adds `--warnings-as-errors`.

A model with no requirement and no `outputs.rst` line needs only steps 1 and 5. The generated
ARXML does not change: no requirement, link or provenance field reaches it. A 0.15.0 project upgrading straight
to 0.17.0 reads [0.16.0's note](0.16.0.md) first.
