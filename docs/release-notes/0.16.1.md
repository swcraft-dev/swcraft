# SWCraft 0.16.1

Released 2026-10-14. A patch release of the 0.16 line: five fixes found in the first day's use of
0.16.0, on Windows and on a large project. The model's format, the commands' options, the
set of MCP tools and their arguments, and the ARXML SWCraft generates are unchanged from 0.16.0;
`impact_of`'s paged answer gains one part (below). The archive's sizes are the tag
run's, recorded under *The archive*.

## Windows install: no more `.bootstrap` line

On Windows every install ended with a line saying `.bootstrap` could not be removed. That was not a
failure: on Windows the installer runs from inside `.bootstrap`, so it cannot delete that folder
while it is running, and `swcraft_install.cmd` removes it as soon as the installer has finished. The
line is gone; the folder is still removed, as before. On macOS and Linux nothing changes: if the
folder cannot be removed there, one sentence still says so and asks you to delete it yourself.

## The *diagram* link opens a current page straight away

The `diagram` link above a composition's or a sequence's `name:` line regenerated every diagram on
every click — on a large model that is a wait of many seconds before the page opens. It now opens
the page **straight away** when both of these hold:

- the diagrams were generated **in this VS Code window** — by a click on the link, by the panel's
  **Diagrams** or by **Build** — and
- nothing in the model folder or in `swcraft.yaml` has changed since that generation started.

Otherwise the click regenerates the diagrams first and then opens the page, as in 0.16.0. That
includes the first click after VS Code starts or the window reloads, a click while another
generation or build is running, and any saved change to the model. The panel's **Diagrams** always
regenerates: it is the way to renew the pages when you want to, after installing a new toolchain
for instance.

**What it does not see.** The window notices changes to the model, not to the generated pages: if
you regenerate or delete the diagrams from a terminal or another window after a click here, the
link opens whatever page is there now, or regenerates when the page is gone. A change VS Code
reports late or never — a folder your settings exclude from watching, a network drive, or a click
that comes a moment after a save, before VS Code has reported it — is not noticed either, as the
panel's out-of-date mark does not notice it.

## A large impact answer says how many of each kind there are in all

When an assistant asked `impact_of` for the elements that depend on a much-used interface and the
answer was longer than one page, the page showed only its own rows. An assistant reading the first
page could take it for a sample and estimate the rest — and the estimate could be far off, with a
whole kind of element missing from it. A page that is not the whole answer now ends with the count
of every kind in the whole answer, for example:

```text
(page: 50 of 1200, truncated; in all: requirement 1, composition 9, swc 40, connector 1150; next: after="…")
```

The kinds are listed in the order the summary form uses, and the counts add up to the total. A
complete page carries no such part — every row is there. The `swcraft impact` command, which does
not page, prints exactly what it printed before. `query`'s pages need nothing of the kind: a page of
one layer already counts that layer, and a `where` filter counts any kind of a mixed layer.

## The guide's reference pages speak to you

Each page under *Reference* opened by saying it is not edited by hand and naming a command to run
instead — a sentence for the people who build SWCraft, not for you. A page now opens with one
sentence only: it is generated from SWCraft's own definitions and describes the version you have
installed.

## The Copilot guard: a guard that cannot run blocks every Copilot tool

0.16.0's note said that what Copilot does when the guard's hook cannot run had not been measured,
and that it "suggests it allows the call". That is wrong. Observed in VS Code 1.141.1: when the hook
cannot run — no `swcraft` on your path (*"hook errored"*), or an `swcraft` older than 0.16.0, which
has no `guard` command (*"hook exited with code 2"*) — Copilot **denies every tool call** in the
project, SWCraft's own tools included. The same session also showed what the guard sees: a read
arrives as `Read`, a search as `Grep`, SWCraft's tools as `SWCraft-<tool>`, and a denial is shown to
you with SWCraft's reason.

- **Check Editor Tooling says what it costs.** The *Copilot model guard* row now says, when a bare
  `swcraft` resolves nowhere or is a release from before the guard, that Copilot can call no tool in
  this project — SWCraft's included — until this release's `swcraft` is on your path. It says so as
  a possibility when the version cannot be read or your hook file differs from this release's, and
  not at all when the project has no hook file, because then nothing runs. When the `swcraft` found
  is another release that has the guard, the row says that release's guard is the one deciding — if
  your hook file differs, provided it still runs the guard, and with no hook file, only that no hook
  runs it. The row stays a warning and is not counted: the panel, the command line and SWCraft's
  server outside Copilot keep working.
- **A `Grep` is judged by its folders.** Copilot's Agent mode names a search's folders as a list.
  The guard now judges each folder in it: a search of `docs/` is allowed, a search of the model
  folder, or of a folder above it, is denied. In 0.16.0 the list was not read, so every `Grep` in a
  guarded project was denied as a search of the whole project. An entry the guard cannot read as a
  path is denied, and so is a read whose path arrives as a list naming the model folder.
- **To get Copilot working again** after one of the blocks above: put this release's `swcraft` on
  your path and restart VS Code so that it sees the new path.

## The archive

The runtime payloads are re-checked against the publishers' own digests for this release and none
moved: Node.js 22.23.2, CPython 3.11.16 (the python-build-standalone build of 2026-09-01), `elkjs`
0.12.0 inside the `swcraft-tools` package, and the two extensions of the pack, Red Hat XML 0.29.3 and
Red Hat YAML 1.25.0, each still the newest Marketplace release (`dev.py update-pins` rewrote nothing).
The archive carries the same packages as 0.16.0. The Linux archive measures **197 366 618 bytes**
(SHA-256 `d3704457…8a799bff`) and the Windows archive **201 435 763 bytes** (`4fdb7c8d…23bc9104`),
as the tag run of 2026-10-14 published them: 17 615 and 24 810 bytes more than 0.16.0's.

## What upgrading takes

Install the 0.16.1 archive, then set `toolchain_version: "0.16.1"` in each project's `swcraft.yaml`.
Until you do, every command that writes or gates refuses a project pinned to 0.16.0 with the pin
sentence and never reaches the model. The read-only commands (`diff`, `impact`, `list`, `query`,
`resource-report`) and `swcraft guard` only print a warning, so Copilot keeps working meanwhile.

Nothing else in a project moves: the model, its format, the hook file `.github/hooks/swcraft.json`
and the agent files are the same as 0.16.0's, so *Onboard Project* has nothing to replace and
*Check Editor Tooling* reports them as this release's. A 0.15.0 project upgrading straight to
0.16.1 reads [0.16.0's note](0.16.0.md) for what changed there.
