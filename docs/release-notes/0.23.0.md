# SWCraft 0.23.0

Released 2026-11-10. The release where the diagrams open in VS Code and lead to the model and back.
What is generated looks the same: the same files, and the same SVG pictures to share. Beside them,
**`swcraft generate test-tables`** writes tables for the test team, Codex and Claude Code work with a
project in VS Code the way Copilot does, Kiro joins them as a fourth chat client, and a runnable's reads and writes can be **implicit** and its
calls **asynchronous**. *What upgrading takes* at the end has, beyond the pin, moving an `outputs.needs`
that points into the test tables' folder.

## The diagrams open in VS Code, and lead to the model and back

**Diagrams** now opens the diagrams in a tab of VS Code instead of your browser.

- **From a diagram to the model:** Ctrl+click (Cmd+click on macOS) an element — a component, a port, a
  connector, a task — or click it and press **Open in model**: its YAML file opens beside the diagram,
  at the element's line.
- **From the model to a diagram:** the `diagram` link above an element's name, or **Show in Diagram**
  in the editor's context menu, opens the diagram with the element selected and centred, as if you had
  clicked it; the search box is left for your own searches. An element drawn on several diagrams asks
  which one, and one drawn twice on a diagram offers **Next** to go to the other.
- The links between the pages, the way up and the index stay in the same tab, with **Back** and
  **Forward**.
- The tab follows VS Code's colour theme, in colours of its own (*Fixes found before the release*
  has them). The files, and a page opened in a browser, stay white.
- A requirements page built from `needs.json` can link each element into the project open in VS Code:
  `vscode://swcraft-local.swcraft-vscode/model?path={{need.swcraft_path | urlencode}}`.

Nothing changed in what the generated files show: the SVG files are the same pictures to share, and
the HTML pages still open from the file in a browser. Their text gains marks the tab reads, without
moving anything drawn (*Fixes found before the release*). Saving a model file still regenerates nothing; the open tab says
when its diagrams are out of date, with a **Generate** button.

**One change reaches the page in a browser too:** a port, a line and a sequence diagram's message no
longer have to be hit exactly — the pointer only needs to be within a few pixels of it, at every zoom,
and near a port the port wins over the edge of its box. Before, a message had to be hit on the line
itself, and a port drawn across its box's edge was easily missed.

**Pages generated by an earlier release are not shown in the tab**: it says they were generated by
another release, with a **Generate** button; one press writes them again. If the pages that press
writes are still another release's, the `swcraft` the window runs is not the extension's release, and
the tab says so instead of asking for **Generate** again. **Show in Diagram** on diagrams an earlier
release generated says that no diagrams list the model's elements yet, with **Generate Diagrams**.

## Test tables for the test team

- **`swcraft generate test-tables`** writes the component list, the component placement (each
  occurrence's tasks, partitions and cores) and the runnable scheduling (task, period, events, budget)
  as CSV files with a `manifest.json` into `dist/test-tables/`. The test team keeps its own columns —
  how a row is verified, a comment, accepted or not — in a folder of its own; `--annotations <folder>`
  joins them by a stable row id, so regenerating keeps them, an acceptance whose facts changed shows as
  `stale`, and an annotation whose row is gone is kept in `orphaned-annotations.csv`. A model
  `swcraft check-model` refuses gets no tables. The tables describe the model; they are no verification
  evidence.
- **Test Tables in VS Code.** A new panel item after *Diagrams* regenerates the tables and opens them
  in a read-only tab: one sub-tab per table, rows coloured by review state, nothing editable, and the
  CSV files never changed. The first press asks for the test team's folder (or *none yet*) and
  remembers the answer in the workspace folder's setting `swcraft.testTables.annotations`;
  **Change…** asks again.

## Fixed: a missing or broken `swcraft.yaml` is named in the chat, never its values

When the MCP server cannot open the project, every tool that needs it now answers one sentence the
assistant reads in the chat: which manifest, what is wrong with it, and what to do. Before, the reply
said only *Error calling tool* and the reason was in the server's log.

- **Not there:** a client started outside the project folder answers *No SWCraft project here:
  `swcraft.yaml` was not found in the folder the server was started in; start the client in the project
  folder.* A manifest given with a full path is named by its file name alone.
- **There and unusable:** *The SWCraft project cannot be opened: swcraft.yaml* followed by the kind of
  failure — *is not valid YAML (line 2, column 1)*, *is empty*, *is not a mapping of manifest fields*,
  *is not UTF-8 text*, *cannot be read (Permission denied)*, *in swcraft.yaml, field `name` is invalid
  (string_type)*, a root written as an absolute path, or the field that resolves outside the project
  or into the model — then *correct the manifest, then call the tool again*. `build`, `validate`,
  `export_component` and `import_component` give the same sentence as their one error message.

**Fixed defect, since 0.1.0:** a manifest value the schema refused was quoted back in the reply of
every tool — pydantic's own text, input value included — so a `model_root` written as a list of
folders put those folders, the project's location among them, into the chat. Since 0.7.0 a `dist_root`
or `views_root` written as an absolute path was quoted the same way by `build`, `validate`,
`export_component` and `import_component`. The sentences above name the field and the kind of error,
never the value; you find the value in your own `swcraft.yaml`.

What this does not reach: which value was refused, and any file other than the manifest. A model file
that cannot be read keeps its own answer, which names the file inside the model and the field, not the
value.

## Fixed: Onboard Project never writes Copilot's files through a link

**Fixed defect, since 0.3.0:** **Onboard Project** copied the Copilot instructions and the SWCraft
Architect agent — and later Copilot's model-guard hook — into `.github/` by a plain copy, which
follows a symbolic link: a repository you cloned that commits `.github/copilot-instructions.md` as a
link to a file of yours, or `.github` or its `hooks` folder as a link to a folder outside the project,
had that file overwritten or the folder written into. Since 0.16.0 the **Add the SWCraft Architect
agent** notice, which never overwrote a file, still wrote into a linked `.github` folder. Both now
keep such a link as it is, write nothing through it, and **Onboard Project** names it in one line; a
regular file of Copilot's is still replaced, as before.

What this does not reach: another program swapping a folder for a link in the instant between the
last check and the write.

## Fixed: a project set up without Copilot is not asked about Copilot

**Check Editor Tooling** reported the Copilot agent profile as missing and the Copilot model guard
as a warning in every project, and the activation notice offered the SWCraft Architect agent every
time — also in a project set up for Codex or Claude Code alone, where neither could ever clear. A
project that holds another client's files and none of Copilot's now gets both rows as *not checked*
and no notice; a project with Copilot's files, or with no client's files at all, is checked as
before.

## Codex and Claude Code in VS Code

OpenAI's Codex and Anthropic's Claude Code, opened in VS Code on a SWCraft project, now work with
it the way Copilot does: they ask SWCraft's tools, and a change they propose opens the SWCraft
review tab.

- **You choose the clients.** Onboard Project asks which chat clients the project is for —
  GitHub Copilot, Codex, Claude Code, several at once — and `swcraft init --integration moon` takes
  `--client copilot`, `--client codex` and `--client claude`, once per client. Only the chosen
  clients' files are written, and the default is **Copilot alone**: a project made without a choice
  gets no Codex or Claude Code file. Codex's model guard, `.codex/hooks.json`, now comes with the
  Codex choice, and the *Add the SWCraft Architect agent* notice no longer writes it. A client left
  out gets nothing, and none of its files already in the project is removed.
- **Onboard Project writes their files**, and so does `swcraft init --integration moon`, for the
  chosen clients: `.mcp.json` and `.claude/settings.json` for Claude Code, `.codex/config.toml` for
  Codex, and `AGENTS.md` (with `CLAUDE.md` for Claude Code) for the instructions both read. The server line names `swcraft` on
  your path and the project's `swcraft.yaml` relative to it, with `SWCRAFT_REVIEW=panel`, so nothing
  in them is per-machine. A file of that name you wrote yourself is kept and named in the
  onboarding output; nothing is merged and nothing is written outside the project. The guide's
  *Codex and Claude Code in VS Code* section (In VS Code) has the one-time steps for each client.
- **Copilot with Codex or Claude Code.** Copilot attaches a project's `AGENTS.md` and `CLAUDE.md`
  to every request in its chat by default, so with that choice the project also gets
  `.vscode/settings.json` holding `"chat.useAgentsMdFile": false` and `"chat.useClaudeMdFile":
  false` — only where it has no settings file. An existing settings file is never edited: the
  onboarding output names the two settings, to add by hand.
- **Copilot with Claude Code shows one warning**, and asks nothing: *Copilot also reads .mcp.json,
  so it may list the SWCraft server twice; see the guide's "Codex and Claude Code in VS Code"
  section (In VS Code).* `swcraft init` prints it after `Warning:`. Copilot may then run the
  project's `swcraft` server instead of the extension's; this has not been observed yet, and the
  guide says what is known.
- **Claude Code is guarded.** `swcraft guard --host claude`, the hook `.claude/settings.json`
  declares, denies Claude Code's own reads, edits, searches and shell commands on the model
  directory — `Bash` and `Monitor` commands alike — its edits of the guard's files, its `PowerShell`
  tool, and a literal path into the review's own folder or a folder above it. A call is judged
  against the project the command runs in and the one the session was started in, so a `cd` out of
  the project leaves it guarded. It does not block when `swcraft` is missing, and it does not run in
  a session started in a subfolder of the project.
- **A broken `swcraft.yaml` is yours to fix.** When the project's `swcraft.yaml` cannot be read or is
  not valid, Codex's and Claude Code's guards deny every edit and shell command — an edit, a `Read` or
  a `cat` of `swcraft.yaml` itself included — and tell the assistant to ask you to fix the file by hand
  in the editor. Since 0.20.0 Codex's guard let the assistant patch and `cat` a broken `swcraft.yaml`
  to repair it; that is withdrawn, because a file linked to `swcraft.yaml` could let such a "repair"
  rewrite a guard's own settings. Once the file reads again, the assistant works as before.
- **The guards share their files.** Codex's guard now protects the same set as Claude Code's —
  `swcraft.yaml`, `.mcp.json`, the `.codex/` and `.claude/` folders and Copilot's hook folder — so
  neither assistant can switch off the other's guard. An assistant's edit of the project's own
  Claude Code commands, a skill or `.mcp.json` is denied with them: make those edits by hand. The
  folders holding those files count too: a command or an edit naming `.github` or `.kiro` itself,
  such as `rm -rf .github`, is denied, while a path inside it that is no guard file, such as the
  folder of your workflows under `.github`, is not. So does a folder holding the model directory inside the project —
  `arch` for a model directory `arch/model`: `rm -rf arch` is denied, `ls arch` and `rm -rf
  arch/other` are not. A command other than the reading ones (`cat`, `ls`, `grep` and the like)
  that names one of these folders is denied even when it writes nothing, such as `git add .github`.
  The project folder itself is not judged this way, so `rm -rf .` is not stopped by this rule.
- **`swcraft init` never writes through a link.** A template file, or a folder on the way to one,
  that is a link in the project — even one pointing nowhere — is left as it is and reported as
  *Skipped*, so a linked `.claude` folder of your own is never written into.
- **A warning when the chats would run another `swcraft`.** The extension warns when the bare
  `swcraft` on the path VS Code was started with is missing or is not the one SWCraft uses. The
  check is the warning not coming back after VS Code is started again from the Dock or Finder.
- **Codex reads all of `AGENTS.md`.** Codex reads 32 KiB of it by default, and SWCraft's
  instructions are longer: the project's `.codex/config.toml` sets `project_doc_max_bytes` to
  131072.
- **`import_component`'s description is shorter.** Claude Code cuts a tool's description at 4 096
  characters, and this one was 7 982; it is now 3 188, and the rules it dropped are in the guide's
  *Import a component* how-to, under *What the plan decides*.

What this does not reach: the clients were tried once, on macOS, with the releases the guide names;
Windows and Linux were not tried, and a client release may change how it reads these files. Which
`swcraft` a guard hook finds — the path VS Code was started with or the one your login shell's
profile sets — is not told apart, and SWCraft's warning sees only the first.

## Kiro, a fourth chat client

Kiro — an editor built on the same base as VS Code, and its command-line client `kiro-cli` — now
works with a SWCraft project as Codex and Claude Code do: its chat asks SWCraft's tools, and a change
it proposes opens the SWCraft review tab in Kiro. The guide has a new page, *In Kiro*.

- **Its own three files.** Onboard Project and `swcraft init --integration moon --client kiro` write
  `.kiro/settings/mcp.json` (SWCraft's server, `SWCRAFT_REVIEW=panel`, the project's `swcraft.yaml`
  named relative to the project folder Kiro starts it in), `.kiro/steering/swcraft.md` (SWCraft's instructions, whole, with a few opening
  lines for Kiro) and `.kiro/hooks/swcraft-guard.json` (the model guard's hook). A file of that name
  you wrote yourself is kept and named in the onboarding output, as for the other clients. Kiro's
  chat does not see the server SWCraft's extension registers, so these files are how it finds SWCraft.
- **Onboard Project starts with Kiro ticked inside Kiro**, and with Copilot ticked in VS Code, as
  before; `swcraft init` keeps Copilot as its default.
- **Kiro is guarded.** `swcraft guard --host kiro` runs before every one of Kiro's tool calls and
  denies its reads, searches, edits, deletions and shell commands on the model directory, its edits
  of the guard's own files and the folders holding them or the model, its Windows shell, a web fetch
  of anything but an `http:` or `https:` address, a command started in the background through its
  process tool, and any tool it does not know — Kiro updates itself, so a new file tool is denied
  until SWCraft's guard knows it. A denial
  is exit code 2 and one line on standard error, which is how Kiro reads a hook; the other clients'
  guards still answer on standard output and exit 0. A search over the whole project is denied: narrow
  it with an include pattern.
- **Your SWCraft folder is protected from Claude Code and Kiro.** Their guards deny an edit, a
  write, a deletion or a shell command that changes, removes or moves your SWCraft folder,
  `$HOME/.swcraft`, anything in it or a folder holding it, because the `swcraft` the guard runs is
  installed there; reading it stays allowed, except the review's own folder. So neither assistant
  can update or reinstall SWCraft: you do. A path written with `~`, `$HOME` or a variable is not
  judged, and a `swcraft` installed elsewhere is not protected. Codex's guard is unchanged: Codex's
  own sandbox keeps its writes inside the project.
- **Trust the folder, then reload the window once.** Until Kiro's window is reloaded after the first
  **Trust**, Kiro loads none of the three files.
- **Kiro with Codex or Claude Code shows one warning**: *Kiro also reads AGENTS.md, so it reads
  SWCraft's instructions twice, the second time cut short; see the guide's "In Kiro" page.* Kiro reads
  a project's `AGENTS.md` on its own and cuts it at 50 000 characters. The choice stands.
- **Content collection.** On its free tier and for individual subscribers, Kiro collects content for
  service improvement by default; the guide says where to turn it off.

What this does not reach: Kiro was tried on macOS only, with Kiro 1.4.121 and `kiro-cli` 3.0.0 and
3.1.0; the editor's write tools have not yet been seen reaching the guard, a hook that runs past its
time limit lets the tool run, and `autoApprove` and `elicit` in Kiro's editor chat were not tried. The
guard mirrors how `kiro-cli` 3.1.0 and Kiro 1.4.121 find a file from a written path; `kiro-cli` updates
itself, and under a later Kiro the guard's protection is not established until it is checked again. The
guide's *In Kiro* page lists the rest.

## Kiro's guard files are guarded by the Codex, Claude Code and Kiro guards

`.kiro/hooks/`, `.kiro/settings/` and `.kiro/agents/` join the guard's own files in the Codex, Claude
Code and Kiro guards, so no one of the three assistants can switch off Kiro's guard, or its server,
or give a Kiro agent tools of its own. An assistant's edit of another MCP server in
`.kiro/settings/mcp.json`, or of a Kiro agent, is therefore denied: make those edits by hand. Kiro's
`.kiro/steering/` and `.kiro/specs/` are not guarded. Copilot's own edit and terminal tools are not
judged by its guard, as before, so they can still change these folders.

## Every client's instructions: never switch off the guard

When the guard refused a direct change, an assistant was seen suggesting that the user switch the
model guard off. The instructions every client reads — Copilot's assistant profile, `AGENTS.md` and
Kiro's instructions file — now say: never propose disabling, editing or bypassing the model guard or
its hook files; when a direct change is refused, use the SWCraft tools, or tell the user what the
tools cannot do. Running Onboard Project again brings the new text into a project.

## Implicit access and asynchronous calls

A runnable's reads and writes can now be **implicit**, and its calls **asynchronous**.

- **`by: implicit`** on a `reads` or `writes` entry: the runnable works on a copy that does not change while it
  runs. A read is by argument (no `by`), `by: value` or `by: implicit`; a write is a send (no `by`) or
  `by: implicit`. `swcraft check-model` reports an implicit read of a queued element and one of an element whose
  port's communication specification enables the update flag.
- **`asynchronous: true`** on a `calls` entry: the call returns at once. Its result is fetched by the calling
  runnable itself with **`poll: true`**, or a runnable is started when it returns by the new **`call_returned`**
  event (`{type: call_returned, port, operation}`). `result` and `name` state the names written to the file; an
  optional **`timeout`**, in seconds, is written only when you state it.
- **One rule depends on the project's AUTOSAR version:** an asynchronous call with no result is reported in a
  4.2.2 project only (AUTOSAR 4.3.0 allows it). `check-model`, the assistant's change sets and
  `import component` read the version from `arxml_version` in `swcraft.yaml`; `generate arxml` uses the version it writes, so `--arxml-version 4.2.2` on a 4.3.0 project can
  refuse what `check-model` passed. Six more findings cover mixed synchrony, differing timeouts, two results, an
  event naming no call or an ambiguous one, and a start-up runnable fetching a result.
- **Generated ARXML.** Implicit reads and writes go to their own containers; an asynchronous call is an
  asynchronous call point; a poll and a `call_returned` event each write a result point, the event an
  asynchronous-call-returns event. An asynchronous call with no stated `timeout` is written without one: the file
  is valid against the schema and partial under the standard's own reading, never given an invented value. A model
  that uses none of the new forms generates the same file as before.
- **Import.** `swcraft import model` and `swcraft import component` read the implicit containers, asynchronous
  call points with their timeout, result points (as a poll on the calling runnable, or with a returns event as a
  `call_returned` event) and returns events; what cannot be carried is one line with its reason. Two of those
  lines are new kinds: a returns event of a call that two or more runnables of the component make
  asynchronously (a `call_returned` event names the port and the operation, not the runnable that calls it),
  and a second result point that reaches one call only because two call points of one operation on one
  runnable were collapsed into one call. `import component` refuses a file holding either, as it refuses every
  such line. A `SCOPE` on a port access is dropped without a line, and a result point of a call through a port
  whose interface the file declares nowhere is a line rather than bound.
- **`import model` names what the file itself states that `swcraft check-model` refuses**, each imported as the
  file states it and listed under *Defects of the export* with its rule and the finding as `check-model` words
  it: an implicit read of a queued element (`[constr_2020]`) or of an element whose communication specification
  states an update flag (`[constr_1103]`); one operation of one port called both synchronously and
  asynchronously (`[constr_2022]`); asynchronous calls of one operation stating different timeouts
  (`[constr_2023]`); a result point on a runnable an init event starts (`[constr_1259]`); two result points of
  one call point (`[constr_2006]`); and, for a file that declares AUTOSAR 4.2.2, an asynchronous call with no
  result point (`[constr_2006]`). A file that declares neither release SWCraft writes has no rule of its own to
  cite, so in a 4.2.2 project such a call is a line under *Not supported by SWCraft* saying that the project's
  4.2.2 rules apply and how to answer it: `poll: true` on the call, a `call_returned` event naming it, or
  `arxml_version: 4.3.0` in `swcraft.yaml`.
- **`import model` says when the file's AUTOSAR version differs from the project's.** It never changes
  `swcraft.yaml`; the report gains one line under its title — for example *ARXML version: the file declares AUTOSAR
  4.3.0 (AUTOSAR_4-3-0.xsd); this project's arxml_version is 4.2.2, and import model does not change it -- set
  arxml_version: 4.3.0 in swcraft.yaml, or check-model applies 4.2.2's rules.*
- **Component exchange.** A component file now says that it carries implicit accesses and asynchronous calls;
  `import component --update` with a file from an earlier release keeps the project's `by: implicit`,
  asynchronous calls and `call_returned` events and lists them. An earlier release refuses every component file
  this release writes. `import component` writes a component whose asynchronous calls or implicit reads
  `check-model` then refuses, and names each finding the import introduces, on `--dry-run` and in the
  assistant's import plan too: in a 4.2.2 project each asynchronous call left with no result under
  *ASYNCHRONOUS CALLS WITHOUT A RESULT* (the runnable, the port and the operation, the rule, `[constr_2006]`
  and the repair); any other asynchronous call finding under *ASYNCHRONOUS CALL FINDINGS*; and an implicit read
  kept from the project onto a read the file has since changed — its communication specification now states
  an update flag, or its element is now queued — under *IMPLICIT ACCESS FINDINGS*, each the rule and the
  finding as `check-model` words it. A finding the project's component already held is not listed.
- **`swcraft resource-report`** adds an `IMPLICIT ACCESS` section — two tables, the implicit reads and writes
  per task and the runnables with one in no task — in the text, the report file, `--format json` and the
  assistant's answer; the VS Code Resources view does not show it. It gives no time or memory figure on purpose:
  when the RTE copies the values, and what that costs, is not in the model.
- **Allocation experiment and metrics.** A runnable that only a `call_returned` event starts is a sixth kind,
  *call-returned*: never moved and never costed. Cohesion counts the event's port among the ports such a runnable
  touches.
- **Trace link search.** The new fields, left at their defaults, change no proposal: a field at its default is
  left out of what the search compares (*Fixes found before the release*).
- **Test tables.** The test tables now show a `call_returned` event with its port, its operation and, when stated,
  its result, and judge the model at the project's `arxml_version`, as `check-model` does, so a 4.3.0 project's
  asynchronous call with no result no longer refuses them. The VS Code Test Tables tab draws such an event as
  `call_returned Port.Operation`.

## Enumeration values given as numbers

`swcraft import model` and `swcraft import component` now read a number given as the initial value of an
enumeration, or under an implementation type that references a table, through the table: a whole number that
exactly one single-value entry gives is carried as that entry's literal, and the report says so. A number no
single entry gives, a fraction, and a number under a bit-field table, a table with a symbol, a table an entry of
which was dropped, or a type collapsed into its implementation twin, is still not carried, with its line. Earlier
releases did not read any such number.

## Fixes found before the release

- **The Trace Apply Report is a report, and Apply asks the way Import Requirements does.**
  **Apply…** in the Trace Links view now opens the preview's report in the same tab as the
  requirements import's report: the report on top, **Write** and **Cancel** under it, and no question
  in a dialog. The report is a document with tables — the result counts, the links to write and to
  confirm, the rejections to record, what is already done, what is stale and why, the links you must
  add by hand, the allocated levels the links raise — and says when it was made and that nothing was
  written. **Write** writes exactly what the preview showed and shows its report in the same tab;
  **Cancel**, or closing the tab, writes nothing. A preview with nothing to write offers no **Write**.
  Before, the report opened as an unsaved text document you could type into, which asked to be saved
  when closed, and Apply asked in a dialog. On the command line, `swcraft experiment trace --apply`
  takes **`--report PATH`**, as the imports do: a path ending in `.md` gets that document with its
  tables, any other path what the run printed — the text, or with `--format json` the JSON document.
- **The requirements import's report names the mapping file relative to the project.** Its
  `Mapping:` line — in VS Code, in the terminal and in `--report` — shows `conf/team.needs-mapping.yaml`
  for a mapping file inside the project, where VS Code showed its full path. A mapping file outside the
  project is still named as you gave it, and so are the `Error:` lines about a mapping file.
- **The diagram tab's colours.** In VS Code's light and dark themes the tab now draws in LikeC4's
  published palette with two changes of ours: blue components with light labels, compositions as a
  light blue tint with a solid blue border — on every view, so a composition inside another stands
  apart from a component — and grey lines, on a white or a near-black canvas. Before, in a dark theme
  the boxes took almost the canvas's own colour and vanished into it. A port is one colour, its line's
  grey, filled with the tint of the composition around it. The selection and what you point at are
  outlined in amber, the current search match in red and the other matches in light red; a port you
  point at, pin or select turns amber, square and arrow. A high-contrast theme is unchanged. **The
  SVG files and the pages opened in a browser keep their colours.** What changes in them is their
  text: each label carries `data-kind` with the kind of the element it names, and the label of a port
  drawn inside a box carries the class `in-member` and its box's kind; nothing drawn moves. A script
  that compares the SVG files byte for byte sees them change once.
- **A new file is never created through a link, on Windows too.** `swcraft init`, a new model file and the
  files **Onboard Project** writes refuse a link found at the file's name — one pointing nowhere
  included — on Windows as on macOS and Linux; so do the temporary files written on the way to the
  build report, the diagrams, `needs.json`, the experiment and other report files, the requirements
  import and the review hand-off. Before, on Windows, a link put there in the instant
  after SWCraft's own check was followed and the file it named was created. What this does not reach:
  **Onboard Project** on a drive without hard links (FAT, exFAT, some network shares), and another
  program swapping a folder on the way for a link.
- **A trace-link proposal is compared without the fields left at their defaults.** A field a later
  release adds with a default, or one you write out at its default value where it was absent, no longer
  makes a saved proposal stale; a field changed from another value to its default still does.
  This changes what is compared **once**: in a proposals file written by 0.22.0, the proposals you
  decided and did not apply yet — a tick, a rejection, a choice, a confirm — report themselves stale
  under 0.23.0, *changed since the search*; run the search again. Undecided proposals, confirmed
  links, and proposals already applied or already stale are not affected.
- **A rejection already recorded is *already done*.** Apply counted a rejection that
  `trace-decisions.yaml` already held, for the same requirement version, as *rejected* again; it now
  counts it under *already done*, *already rejected*, as it does a link that is already there. What is
  written does not change.
- **A clearer refusal for the assistant.** When an assistant updates one entry of a list — a
  runnable's read, for example — and sends only the field it changes, the refusal now says that such
  an update replaces the whole entry, and gives the field's own address to send instead. Changing a
  field that names the entry — the element of a write, for example — says that it is a removal and a
  creation in one change. Before, the refusal said the entry's identity was a different one and
  suggested a removal and a creation, which was then refused as well, and the assistant stopped.

## Carchetype in the delivery

The workstation archive installs Carchetype 0.2.2 beside `swcraft`. `carchetype specimen passport.json
--out <dir>` writes a project of the shape a `swcraft passport` file describes, and `carchetype generate
small --out <dir>` writes one from a packaged preset; either project's `swcraft.yaml` names this release
(`carchetype --help` lists the presets and the commands). It is installed into the same environment as
SWCraft and was checked against this SWCraft release before publication; installing a newer SWCraft
replaces it. Nothing is downloaded separately. Unchanged since 0.22.0.

## The model's contract is `12.7.0`

`contractVersion` moves from `12.6.0` to `12.7.0`, by one minor: one kind, ten fields and twelve rules
are added — the `call_returned` event with its five fields, a write's `by`, a call's `asynchronous`,
`poll`, `result` and `timeout`, nine checks across elements and three on one element — and a read's `by`
and a runnable's `events` accept the new values; seven earlier rules apply to more fields than before.
Nothing is removed or renamed, and none of the new rules is a warning. The inventory goes from 15
layers, 66 kinds, 349 fields and 340 rules to 15 layers, **67** kinds, **359** fields and **352** rules.
A `12.6.0` model is a valid `12.7.0` one.

## For contributors

The runtime pins did not move: `update-pins` rewrote nothing, so Node.js, CPython, `elkjs` and the
companion extensions are 0.22.0's.

## What this release does not reach

- A page opened in a browser does not open the model; only the tab does.
- The tab shows what the last generation drew: an element added since is not on it until a press.
- Interfaces, data types and requirements are drawn on no diagram, so they have no `diagram` link.
- The tab was tried by hand on a Mac only; on Windows and in a remote window (SSH, WSL, a container) it
  has not been tried.
- A window reload closes the tab; the next **Diagrams** press opens it again.
- A diagram page changed by hand, or written by another tool, is not shown in the tab: it says the page
  is not one SWCraft generated, with **Generate**.
- On Windows, the model guard refuses every Kiro or Claude Code search pattern that starts with the
  home-folder `~`, whatever folder it names: narrow the search with a folder of the project instead.

## What upgrading takes

- **A project used with Codex, Claude Code or Kiro:** run Onboard Project again and choose the
  clients you use, then trust the project once in each — in Kiro, trust it and reload the window once
  (the guide's *Upgrading* page has the steps). Running it again also brings the new instruction
  about the guard into every client's files, Copilot's included.
- **`outputs.needs` may no longer point at or below `dist/test-tables/`**; every command that reads
  the project refuses it. Move it before upgrading (the guide's *Upgrading* page has the step).
- Nothing for a model that states no `by: implicit`, no asynchronous call and no `call_returned` event: it
  loads, checks and generates exactly as before; its component exports gain two marker lines.
- A project that imports again from an export holding enumeration values given as numbers gains those values.
- A trace-link proposals file written by 0.22.0: the proposals you decided and did not apply yet report
  themselves stale once; run the search again (*Fixes found before the release*).
