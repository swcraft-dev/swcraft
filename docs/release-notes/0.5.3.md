# SWCraft 0.5.3

**The guide server stops talking over every other command.** A one-defect patch release from
`release/0.5`, for the demonstration track. The model contract, the editing protocol, the 13-tool
MCP surface and the emitted ARXML bytes are unchanged from 0.5.2 — not by assertion but by
construction: **no Python source changed at all** between the two releases, and the whole diff is
the VS Code extension plus its concept documents.

```
swcraft-tools==0.5.3
swcraft-mcp==0.5.3
swcraft-agent==0.5.3
```

plus `swcraft-vscode-0.5.3.vsix`.

---

## The defect: one channel, two lifetimes

0.5.2 shipped `SWCraft: Open Guide`, the panel item that starts `swcraft docs` and opens the served
address. `swcraft docs` logs **one line per HTTP request** to stderr, deliberately, for as long as
the server is up — and the extension streamed that stderr into the **shared** `SWCraft` output
channel, the one every other panel command writes its answer to.

Found on a **native Windows host during the 0.5.2 acceptance run, 2026-08-27**. The report is now
the fixture the TypeScript oracle drives, verbatim:

```
127.0.0.1 - - [27/Aug/2026 13:02:22] "GET /reference/ HTTP/1.1" 304 -
127.0.0.1 - - [27/Aug/2026 13:02:25] "GET /reference/model/interfaces/ HTTP/1.1" 200 -
$ c:\...\.venv\Scripts\python.exe -m swcraft_tools.cli check-model --project swcraft.yaml
Validation passed (no artifacts generated).
127.0.0.1 - - [27/Aug/2026 13:03:44] "GET /reference/model/connectors/ HTTP/1.1" 200 -
```

`check-model`'s entire answer, one line long, sandwiched between two request lines — and every
later command's answer the same, for as long as the guide window stayed open. On the surface whose
whole purpose is that a click produces a **findable** answer, that is demo-blocking rather than
cosmetic: on stage the presenter clicks *Check Model* and cannot find the result. That is why it is
a release and not a note.

The two channels differ by **lifetime**, not by command. Every other command this extension spawns
writes an answer and its child exits, so one channel reads as a transcript. The guide server does
not exit; it is the only one that keeps writing.

## The fix: the guide gets `SWCraft Guide`

The extension now creates a second output channel, `SWCraft Guide`, and the whole of one guide run
goes there and nowhere else: the `$ <command>` echo, the child's stdout, and the child's stderr —
the request log. The shared `SWCraft` channel is unreachable from the guide command.

- **The failure notifications name the new channel by name.** Both of them — the CLI that cannot be
  spawned, and the CLI that exits before announcing, whose five-line refusal (the directory it
  searched, a rejected `SWCRAFT_GUIDE_SITE`, the release archive to unpack) a notification cannot
  carry. Pointing a reader at the channel the text is *not* in would have been a quieter version of
  the same defect.
- **The reveal behaviour is unchanged in kind**: `SWCraft Guide` is shown on a failing outcome only,
  and the happy path reveals neither channel, because it ends in a browser window.
- **The CLI is untouched.** `cmd_docs` logs to stderr exactly as it did in 0.5.2; that is a
  deliberate, documented decision and the request log keeps its diagnostic value. Only the
  extension's routing moved.

`guideServer.ts` states why there are two channels.

## What this does not reach, stated rather than implied

- **This fixes where the log appears, not what is logged.** The request log still exists, it is
  still one line per request, and it still arrives for as long as the server is up — in
  `SWCraft Guide` instead of `SWCraft`. A reader who wants it quiet does not get that here.
- **Nothing else about the guide command changed.** One server per window, no `Stop Guide`, the
  20 s announcement timeout, the loopback bind, `vscode.env.openExternal` — all as 0.5.2 shipped
  them.
- **The oracles are two source-level tests, not a UI test.** Both channels exist only in the file
  that imports `vscode`, so `guideServer.test.ts` drives the routing against a recording channel and
  asserts a stand-in for the shared channel stays empty and unshown, while `commandCore.test.ts`
  scans `commands.ts` for the wiring. Both fail against the pre-fix adapter, which is the check that
  they witness the defect. Neither runs VS Code, and no test in this repository observes the real
  channel picker.
- **This is one Windows host, one date.** The defect was found there and the fix is verified by the
  two oracles on Linux; the Windows re-run of `SWCraft: Open Guide` against 0.5.3 has not happened
  and stays on the standing Windows checklist. 0.5.2's notes said Windows was unmeasured for this
  command — this release is what that measurement found.
- **No qualification claim moves.** Where an extension writes its log text is not evidence about a
  model or a generated artifact. `swcraft validate` remains the sole authoritative model and
  ARXML/XSD gate.

## Upgrading

**Reinstall the VS Code extension** (`swcraft-vscode-0.5.3.vsix`) and reload the window. That is the
whole upgrade for this defect: the fix is entirely in the extension.

The two Python distributions carry **no behavioural change** in 0.5.3 — they move because the four
artifacts are released in lockstep and a project pins one version string. A project that keeps its
own pinned `requirements-swcraft.txt` raises the three `==` pins; installing them is otherwise
optional for this release.

**Nothing in a project changes**: no manifest key, no model file, no generated output, no MCP
configuration, no migration. After reloading, `SWCraft Guide` is in VS Code's output-channel
picker beside `SWCraft` — the extension creates both when it activates, not when the guide starts.
