# SWCraft 0.9.0

**Released 2026-09-07** (the bump commit; the tag follows the `verify` gate on both self-hosted
runners, Linux and Windows, on this commit, and the tag's own run publishes the release archives to
the NAS). This note was written with the change rather than after it, so every figure
below was measured on the host and at the commit that produced it — macOS, CPython 3.11.13,
2026-09-07.

**The architecture now has a shape.** Until this release a SWCraft model was a flat list of
components and one composition the *writer invented* — `SwCraftComposition`, a name no model file
ever contained, holding every component the project declared, side by side, at one level. AUTOSAR's
own answer to "what contains what" is the `COMPOSITION-SW-COMPONENT-TYPE`: a component that has
ports of its own, holds instances of other components and delegates its ports to theirs. This
release puts that in the model. A new mandatory layer, `compositions/`, holds composition **types**, one
file each; a member instantiates a declared component or another composition; a delegation wires a
boundary port through to a member's; and the exported ARXML carries all of it, including
`DELEGATION-SW-CONNECTOR` — a tag SWCraft has never written.

**`containers/` is retired to make room for it**, with its kind and its four fields. It was a
grouping label with no AUTOSAR counterpart, no ARXML emission and one reference (`system`);
`compositions/` is the real hierarchy, and keeping both would have meant two answers to the same
question. `systems/` is untouched.

**Read *"What an existing project must change"* below before you install this.** Every project
needs **one new hand-written file**, and there is no `swcraft migrate` command — that is a
decision, not an omission, and the reasoning is in that section. The recipe is short, it is written
out step by step, and every error message quoted in it is from a real run.

**The importer stops throwing the hierarchy away.** `swcraft import rhapsody` used to resolve every
delegation chain down to leaf-to-leaf connectors and report the result as lost. It now maps them: compositions, prototypes and
delegations land in the model or are skipped and reported, and a re-export puts them back where the source had them.

Upgrade all four artifacts together, as always — one workstation archive,
`swcraft-0.9.0-<platform>.zip`, and the installer inside it.

---

## What an existing project must change

**A model written for 0.8.0 does not load under 0.9.0** — strictly, it loads and then
`swcraft check-model` refuses it, because the layer's first rule is that some composition has to be
the root. Nothing migrates it for you.

**There is no migration command, and that is deliberate.** A migration that wrote the file for you
would have to guess two things it cannot: what your top-level composition is *called*, and which of
your components belong in it directly rather than one level down. Both are architecture decisions,
and the whole point of this release is that the model now records them. What the tool does instead
is refuse clearly and name the repair — and `swcraft init` writes the file for a *new* project, so
only projects that already exist do this by hand. It is one file.

The recipe below is the whole of it for a flat project — which every 0.8.0 project is, since 0.8.0
had no way to express anything else.

**0. Move the `toolchain_version` pin first, if your manifest carries one.** `swcraft init
--integration moon` has written one since 0.7.0, and the check is an **equality on one release**:
while `swcraft.yaml` says `toolchain_version: 0.8.0` and this install is 0.9.0, every command that
writes or gates — `check-model`, `validate`, `generate`, `import`, `clean-outputs` — stops with

```
Error: this project's swcraft.yaml pins toolchain_version 0.8.0 and this is SWCraft 0.9.0 — install
the 0.8.0 workstation archive (its swcraft_install.cmd on Windows, swcraft_install.sh elsewhere), or
edit the pin if this project is meant to move to this release.
```

and **not** the composition errors quoted below. The five read-only commands (`diff`, `impact`,
`list`, `query`, `resource-report`) print the same sentence as a `Warning:` and still answer. So
edit the pin to this release before step 4, or the gate never gets far enough to tell you what is wrong
with the model. A manifest without the field pins nothing and needs no step.

**1. Write the root composition.** Create `model/compositions/` and put one file in it. Its `name`
is your filename and its `SHORT-NAME` in the exported ARXML, so it must be a legal AUTOSAR
`Identifier`; `title` is required (the C4 diagram renders it); `root: true` says it is the top.
Every component the project declares goes in `members`, as a `{name, type}` pair. This is
`examples/basic`'s own file, and it is the worked example for the rest of this note:

```yaml
# model/compositions/Root.yaml
name: Root
title: Root composition
root: true
description: >-
  The top of the hierarchy: every component this project declares stands in it
  once, and the connector between them is drawn inside it. A connector that
  names no composition belongs to the root, which is why Example_to_Consumer
  carries no `composition:` key.

members:
  - name: ExampleSWC
    type: ExampleSWC
    description: The provider of IExample.
  - name: ExampleConsumerSWC
    type: ExampleConsumerSWC
    description: The consumer of IExample.
```

**`name` and `type` are both written, always, even when they are equal.** That is AUTOSAR's
`SW-COMPONENT-PROTOTYPE` shape — the instance and the type it instantiates are two different
things — and it is the reserve that lets one type be placed in several compositions later. There is
no one-word form.

Until the file exists, `check-model` says so and nothing else:

```
  ERROR: No composition declares 'root: true'; exactly one must, because it is the top of the
  emitted hierarchy and the composition a connector that names none belongs to.
```

**2. Make every wired component a member.** A connector's endpoints still name **types**, exactly as
they did on 0.8.0 — nothing in `model/connectors/` changes — but the writer now has to find the
*instance* those types stand for, and it looks inside the connector's own composition. A component
that is wired and is not placed is the second error you will see, one line per endpoint:

```
  ERROR: Connector 'Example_to_Consumer' from endpoint names type 'ExampleSWC', which is not a
  member of composition 'Root' the connector is drawn inside.
  ERROR: Connector 'Example_to_Consumer' to endpoint names type 'ExampleConsumerSWC', which is not
  a member of composition 'Root' the connector is drawn inside.
```

The repair is to add the member. A connector that names no composition belongs to the **root**, so
for a flat project every connected component is a member of the file you wrote in step 1.

**3. Delete `model/containers/`.** The layer is no longer read at all. A leftover directory is
**silently ignored** — nothing reports it, nothing removes it, and `swcraft list` simply does not
mention it — which is exactly why this step is on the list rather than left to be noticed. It is the
same trap `model/resources/` set on 0.6.0, and it is on the list for the same reason.

**A script that named the layer breaks loudly, though, and that is the one place it is not silent.**
`swcraft list containers` and `swcraft query containers` take their accepted layer set from the
contract, so `containers` is no longer a choice and both exit **2** with an `argparse` usage error:

```
swcraft list: error: argument LAYER: invalid choice: 'containers' (choose from 'requirements',
'systems', 'compositions', 'swc', 'interfaces', 'data_types', 'connectors', 'tasks', 'sequences',
'hardware')
```

A moon task or a CI step that ran either one stops the build. `compositions` is the name to use.

If your containers carried real grouping information, the successor is a composition per container:
give it a `title`, put the components it grouped in its `members`, and make it a member of the root
in turn. Nothing forces you to — a single flat root is a complete migration — but it is the reason
the layer exists.

**4. Run the gate.** `swcraft check-model --project swcraft.yaml` exits 0 when steps 1 to 3 are
done, and names what is missing until then. Running it after each step is the fastest way through.

**5. Re-generate and expect the ARXML to move.** The output changes for every project, and this is
the whole of the change for a flat one:

```diff
-          <SHORT-NAME>SwCraftComposition</SHORT-NAME>
+          <SHORT-NAME>Root</SHORT-NAME>
...
-                <CONTEXT-COMPONENT-REF DEST="SW-COMPONENT-PROTOTYPE">/ComponentTypes/SwCraftComposition/ExampleSWC</CONTEXT-COMPONENT-REF>
+                <CONTEXT-COMPONENT-REF DEST="SW-COMPONENT-PROTOTYPE">/ComponentTypes/Root/ExampleSWC</CONTEXT-COMPONENT-REF>
```

plus one reordering: the prototypes are now emitted in your **declared member order** instead of the
`swc/` layer's read order. For a project that declares at least one connector, no element is added
and none is removed, and on `examples/basic` the document loses exactly 42 bytes —
`SwCraftComposition` is eighteen characters, `Root` is four, and the name occurs three times.

**A project with components and no connectors is the exception, and it gains elements.** On 0.8.0
one `if connectors:` gated the whole composition, so such a model emitted **no**
`COMPOSITION-SW-COMPONENT-TYPE` at all — not an empty one. On 0.9.0 the composition is an element of
the model rather than a by-product of the connector list, so the document gains the
`COMPOSITION-SW-COMPONENT-TYPE` and one `SW-COMPONENT-PROTOTYPE` per member. Nothing is lost; the
diff is simply larger than the two-line one above, and a byte-comparison against a stored 0.8.0
artifact will not be a two-line diff.

**Anything downstream that resolves a path through `/ComponentTypes/SwCraftComposition/…` has to be
re-pointed at your root's name.** That is the one hard external break in this release: an RTE
configuration, a hand-written reference, or a script that grepped for the invented name will not
find it any more. There is no compatibility spelling, because the invented name was never a fact
about your design.

**6. Check the name you chose against your component names.** A composition and a component are
siblings in the `ComponentTypes` package, so two of them may not share a `SHORT-NAME` — and neither
may a composition share one with a component's generated `{swc}_Implementation`. **Both ends refuse
it**: `check-model` reports it as `rule:name.duplicate-component-type` (or
`rule:name.composition-implementation-collision`) and `generate arxml` refuses before it emits
anything:

```
$ swcraft check-model --project swcraft.yaml
  ERROR: Composition name 'ExampleSWC' is also declared as an SWC; a composition and a component
  are siblings in the ComponentTypes package and cannot share one SHORT-NAME.
$ swcraft generate arxml --project swcraft.yaml
Error: Colliding /ComponentTypes SHORT-NAME(s) declared in …/model/compositions/: composition
'ExampleSWC' and the component of that name in …/model/swc/. A composition, a component and a
component's generated SWC-IMPLEMENTATION are siblings in one AR-PACKAGE and cannot share a name.
```

(The `…` stands for the project's absolute path: the writer prints the resolved model root, not the
relative one, whatever `--project` was given.)

Exit 1 from both, and no file is written. The repair is to rename one of the two. `Root` is
a safe choice in every project measured; the check is one word long and worth doing once.

**7. If you keep a generated `.c4` under version control, expect it to move too.** Every component
you placed as a member is reparented under its composition — a component no composition places stays
where it was — a `composition` element joins the specification block, and one new static view,
`view compositions`, is added. See § *The C4 diagram gains a level*.

**8. If your assistant or your editor talks to the model over MCP, its `containers` addresses are
gone.** One other wire-observable change: a `read` of a `connector_endpoint` now has a `summary`
step in its `over-budget` hint chain, because contract `4.0.0` made `swc` optional and a summary of
that kind now drops a field. **No tool was added or removed.** See § *What the editing protocol and
the MCP surface publish differently*.

**What does not change, so you do not go looking:** connector files, component files, interfaces,
data types, tasks, sequences, requirements, hardware, `systems/`, every budget and every task
mapping. Step 1 writes one file, step 3 deletes one directory, and that is the migration.

**Going back is not symmetric, and it is silent.** A 0.8.0 install opening a migrated project finds
no `containers/` — which it does not need, because that layer was never mandatory — and **never
looks at `compositions/` at all**: it is not a layer that install knows, so the hierarchy is not
read, not reported and not refused. `check-model` passes, and `generate arxml` regenerates the
invented `SwCraftComposition` holding every component flat, discarding the hierarchy the newer
release wrote. Nothing warns you: the `toolchain_version` pin works **forward only** (a 0.8.x
install accepts the field and ignores it, pydantic's `extra="ignore"`), so a pin of `0.9.0` does not
stop a 0.8.0 toolchain. If you have to go back, go back to a commit rather than to a re-generated
artifact.

## The `compositions/` layer

One file per composition **type**, named after the element, under `model/compositions/`. The
directory is flat however deep the instantiation goes, because the hierarchy is by *reference* —
a member names a type, it does not nest one — which is exactly how AUTOSAR spells it and how a
reader follows it.

| Field | Required | What it is |
|---|---|---|
| `name` | yes | The identity and the filename; emitted as the `COMPOSITION-SW-COMPONENT-TYPE`'s `SHORT-NAME`, so it must be a legal AUTOSAR `Identifier`. Unique across the layer, immutable — renaming is a remove and a create. |
| `title` | yes | The human-readable title, rendered on the C4 diagram. |
| `description` | no | Free text; rendered into the diagram, deliberately not emitted into ARXML. |
| `root` | no, default `false` | Whether this composition is the top of the hierarchy. **Exactly one** in a project declares `true`. Omitted from the file at its default, so only the root carries the key. |
| `ports` | no, default `[]` | The composition's own boundary ports: `name`, `direction`, `interface`, `description` — the same four fields a component's port has. |
| `members` | no, default `[]` | The instances it contains. |
| `delegations` | no, default `[]` | The wiring from a boundary port to a member's port. |

**A member is `{name, type-or-composition, description}`**, and **exactly one** of `type` and
`composition` is set. That is not a stylistic split: it is the model's spelling of AUTOSAR's `DEST`
on the `TYPE-TREF`, which says `APPLICATION-SW-COMPONENT-TYPE` or `COMPOSITION-SW-COMPONENT-TYPE`.
`type` resolves into `swc/`, `composition` into `compositions/`, and each is a declared reference,
so `swcraft impact` walks both with no composition-specific traversal code — the three rows of
detail-suffix data in `query.py` are the whole of it (§ *Python API*). Neither or both is
refused when the file is read:

```
Error: Invalid composition YAML in model/compositions/Bad.yaml: 1 validation error for Composition
members.0
  Value error, a composition member must declare exactly one of 'type' and 'composition'
```

**A delegation is `{name, port, member, member_port, description}`** — its `name` becomes the
`DELEGATION-SW-CONNECTOR`'s `SHORT-NAME`, so it is a legal `Identifier` too; `port` is one of this
composition's own, `member` one of its members, and `member_port` a port of that member's type. The
two ports must declare the same direction **and name the same interface**, and no two delegations
of one composition may wire the same `(port, member, member_port)` triple.

**A connector now says which composition it is drawn inside**, with one optional field, and
**`composition:` absent means the root**:

```yaml
# model/connectors/sub_link.yaml
name: sub_link
composition: Sub          # omit this key and the connector belongs to the root
from:
  swc: Beta               # the TYPE; the writer finds the member of that type inside `Sub`
  port: pInner
to:
  swc: Gamma
  port: rInner
```

The root's name is a property of *your model*, not a constant, so `None` is resolved where the model
is in hand — in the writer, in the rules, in the importer — and never written into a file as a
default. An endpoint gains the same second field, `composition`, for a sub-composition's boundary
port, again exactly one of the two:

```yaml
name: root_link           # no `composition:` — this one is the root's
from:
  composition: Sub
  port: pSignalOut
to:
  composition: Sink
  port: rSignalIn
```

**A type may be placed in several compositions, and at most once in any one of them.** That
restriction is what keeps an endpoint naming a type unambiguous: the writer resolves the type to the
member of that type inside the connector's own composition, so a second member of one type in one
composition would leave it with two candidates. Placing a type twice in *one* composition is refused
by `rule:composition.member-type-repeated`; placing it in two different compositions is legal.

**A member's `name` may differ from its `type`, and it is emitted that way.** The prototype's
`SHORT-NAME` is the member's name and the `TYPE-TREF` is the type's, and the two references an
assembly connector emits then differ by more than a prefix: `CONTEXT-COMPONENT-REF` ends at the
prototype, `TARGET-*-PORT-REF` at the type's port. Where such names differ by case only, that is the kind a
byte comparison catches and a person reading a diff does not.

`swcraft init` scaffolds `model/compositions/Root.yaml` beside the two hardware elements, so a fresh
project passes the gate it is told to run. It is withheld by **content**, not only by path: a
project that already declares a root, or already declares an element named `Root`, keeps what it
has.

## What `check-model` refuses that it did not before

**Twenty-five cross-element rules** — the rules contract `4.3.0` adds against `0.8.0`'s `3.4.0`,
which is this release's own delta; counting instead every rule whose `appliesTo` names
`layer:compositions` or a `field:compositions.*` entry gives 27, because that picks up older rules
that gained an entry and drops the two `rule:name.*` ones, whose `appliesTo` is `layer:swc`. All
reported before any generation runs and all listed on the
guide's checks page (`docs/guide/reference/model/compositions.md` describes the fields; the rules
page lists every identifier):

| Rule | What it refuses |
|---|---|
| `rule:composition.no-root` | No composition declares `root: true`; exactly one is required. |
| `rule:composition.multiple-roots` | More than one declares it. |
| `rule:composition.duplicate-name` | The same composition name declared in more than one file. |
| `rule:composition.duplicate-port` | One composition declaring a boundary port name twice. |
| `rule:composition.duplicate-member` | One composition declaring a member name twice. |
| `rule:composition.duplicate-delegation` | One composition declaring a delegation name twice. |
| `rule:composition.duplicate-delegation-link` | Two delegations of one composition joining the same boundary port to the same member port. |
| `rule:composition.cycle` | A dependency cycle in the hierarchy — a composition that contains itself, at any depth. |
| `rule:composition.member-unknown-type` | A member naming no declared SWC. |
| `rule:composition.member-unknown-composition` | A member naming no declared composition. |
| `rule:composition.member-type-repeated` | One composition placing the same type in more than one member. |
| `rule:composition.delegation-unknown-member` | A delegation naming no member of its composition. |
| `rule:composition.delegation-unknown-port` | A delegation naming a port its composition, or its member's type, does not declare. |
| `rule:composition.delegation-port-direction-mismatch` | A delegation whose two ports declare different directions. |
| `rule:composition.delegation-interface-mismatch` | A delegation whose two ports name different interfaces. |
| `rule:composition.connector-endpoint-not-a-member` | A connector endpoint naming a type that is not a member of the connector's composition — step 2 of the migration. |
| `rule:composition.delegation-connector-name-collision` | A delegation with the name of a connector drawn inside the same composition — they are siblings in one `CONNECTORS` block. |
| `rule:composition.port-undeclared-interface` | A boundary port naming no declared interface. |
| `rule:connector.unknown-composition` | A connector naming no declared composition. |
| `rule:connector.endpoint-unknown-composition` | An endpoint naming no declared composition. |
| `rule:name.duplicate-component-type` | A composition name also declared as an SWC — a composition and a component are siblings in `ComponentTypes`. |
| `rule:name.composition-implementation-collision` | A composition name colliding with a component's generated `_Implementation`. |
| `rule:swc.external-with-ports` | An external stub declaring ports, runnables or a memory budget (§ *External stubs*). |
| `rule:swc.external-incomplete-reference` | An external stub whose `external_ref` or `external_dest` is blank, or whose `external_dest` is no AUTOSAR reference `DEST`. |
| `rule:swc.external-reference-without-stub` | A component declaring `external_ref` or `external_dest` without `external: true`. |

Six more are **element-local** — refused when the file is read rather than reported as findings —
one per validator the new classes carry: a blank composition `name` or one containing a path
separator; a boundary port with a blank `name` or `interface`; a member with a blank `name`, `type`
or `composition`; a member that does not declare exactly one type field; a delegation with a blank
`name`, `port`, `member` or `member_port`; and the endpoint's own exactly-one rule.

The two `*-type-form` rules a first draft of this note listed as cross-element are **not** there:
the loader refuses their shape before any check reads the layer, so the element-local pair above is
the whole of that answer.

`rule:name.composition-reserved` is **deleted**. `SwCraftComposition` was reserved because the
writer minted it; it does not any more, so a component *or* a composition may now carry that name.
What replaces the reservation is the AUTOSAR invariant underneath it — a `SHORT-NAME` is unique
among its siblings — which is model-dependent rather than a fixed word, and is stated as the two
rules the table above carries: `rule:name.duplicate-component-type` and
`rule:name.composition-implementation-collision`. Both ends refuse it, `check-model` and
`generate arxml`, as § *What an existing project must change* step 6 records.

**Composition, member, delegation and boundary-port names are all covered by the identifier check.**
`layer:compositions` is ARXML-bound, so every name it emits is held to `[a-zA-Z][a-zA-Z0-9_]*` and
128 characters, `check-model` reports each offender, and the writer and every write path refuse the
same model. No new *generated* name form is introduced by this release: the count stays at eleven,
and the four joint budgets of 0.8.0 are unchanged.

## What the exported ARXML carries now

One `COMPOSITION-SW-COMPONENT-TYPE` per **declared** composition, in read order, emitted into the
`ComponentTypes` package after every component type, with the children AUTOSAR fixes:
`SHORT-NAME`, `PORTS`, `COMPONENTS`, `CONNECTORS`.

| Element | What the writer emits |
|---|---|
| `PORTS` | always present, empty when the composition declares no boundary port; each port through the same emitter a component's port uses, in **declaration order** |
| `COMPONENTS` | one `SW-COMPONENT-PROTOTYPE` per member, in declared member order, `SHORT-NAME` = the member's `name`; omitted entirely when the composition has no member — which a freshly scaffolded root has |
| its `TYPE-TREF` | `/ComponentTypes/{type}` with `DEST` `APPLICATION-SW-COMPONENT-TYPE`, or `/ComponentTypes/{composition}` with `DEST` `COMPOSITION-SW-COMPONENT-TYPE`, or a stub's own two strings verbatim |
| `CONNECTORS` | the assembly connectors whose `composition` names this one, then its delegations; omitted entirely when there are neither |
| `DELEGATION-SW-CONNECTOR` | `SHORT-NAME`; an `INNER-PORT-IREF` holding one `P-`/`R-PORT-IN-COMPOSITION-INSTANCE-REF` with `CONTEXT-COMPONENT-REF` at the prototype and `TARGET-P-`/`TARGET-R-PORT-REF` at the member's type's port; then `OUTER-PORT-REF` at the composition's own port, its `DEST` matching the inner side |

**`DELEGATION-SW-CONNECTOR` is a tag SWCraft has never written before.** Its exact shape was
measured rather than read off a specification: the two licensed schemas are identical in every
composition group, and a
hand-built probe validates at both versions. The two AUTOSAR versions emit **the same composition
bytes** — the generated documents differ only in their `xsi:schemaLocation` line.

**The change to the goldens is asserted, not eyeballed.** Every committed ARXML golden and the `.c4`
fixture move in this release, which is the first time that has happened since the writer became
first-party — so an expected-difference list was hand-derived from the design and committed
*before* anything was regenerated, and a test asserts that the observed difference between the old
golden and the new one equals the list. It matched on the first run. For the two populated goldens
the whole difference is one rename and one reorder; for the empty one there is none at all, and
that entry says so in as many words: before this release an empty model emitted no composition
because it declared no *connector*, and after it because it declares no *composition*. The gate
moved and the degenerate output did not.

**Where the XSD evidence is.** Both licensed schemas accept the emitted hierarchy at 4.2.2 and
4.3.0 — `python scripts/dev.py test-xsd` is 164 passed and 0 skipped on a host with both licensed schemas
installed, re-measured 2026-09-07 — and the check is
non-vacuous: the *validated* document is re-read and asserted to carry three compositions, six
prototypes, three delegations, two assembly connectors and both `INNER-PORT-IREF` variants, because
every one of those elements is optional in both schemas and a writer emitting none would pass a
conformance test alone. What the XSD **cannot** answer is also asserted: a `TYPE-TREF` pointing
outside the document validates at both versions, which is why the round trip below is the oracle for
external stubs and not the schema.

## What `swcraft import rhapsody` no longer throws away

The importer used to resolve every delegation chain down to leaf-to-leaf connectors, rename
prototypes into components and record the result as lost. It maps the hierarchy now, checked against real tool exports the maintainer holds privately:

| | Before | After |
|---|---|---|
| compositions | none | imported |
| prototypes | flattened away | imported, some as external stubs |
| delegations | chain records in the *lossy* list | imported, or skipped and reported — a pair an export declares twice, wiring one `(boundary port, member, member port)` triple under two names, is refused by `rule:composition.duplicate-delegation-link` |
| assembly connectors | renamed and re-parented | imported, each keeping the export's own `SHORT-NAME` and the composition it was drawn inside, or skipped and reported |
| components | the export's own | the same, plus the stubs |

A re-export puts every
composition back with the same member, delegation and connector names the source declared — the
comparison is set equality per composition, not a count, so a document that lost one delegation and
invented another would fail it.

**What is skipped, and why — stated as classes rather than as a number.** The delegations and
connectors that do not survive divide five ways: they reach an **external stub**, which
has no port to wire to; they reference a prototype of **another** composition, a wiring an
export can declare and the model cannot carry because a connector belongs to exactly one composition;
they reach a port an earlier pass already skipped, because its interface is in a package the
export does not contain; a connector has both ends facing the same direction; or it is a
**second** connector for an endpoint pair the export already wired under a different `SHORT-NAME` —
a duplicated wiring an export can declare, which the model's identity for a connector
cannot hold. Every one of them is reported with its reason and its ARXML path.

**The root is derived, never guessed:** the composition no prototype instantiates is the root. Zero
or two such compositions is an import error naming them, tested on hand-built models.

**One thing the importer now deletes, which it never did before.** `swcraft init` writes an empty
root composition, and an import that brings a root of its own would leave the project with two —
which `rule:composition.multiple-roots` refuses. So the import removes that scaffolded root before
writing its own, and reports each removal.

**The predicate is narrow, and both halves matter.** A composition is removed only when it declares
`root: true` **and** no boundary port, no member and no delegation — which is exactly what
`swcraft init` scaffolds. It is deliberately *not* "declares nothing": an empty **non-root**
composition is a placeholder a person wrote, it collides with nothing this import writes, and the
wider predicate deleted it and reported it as scaffolding the person never wrote. The file is
located by **reading the layer for the declared identity**, never by composing `{name}.yaml`, so a
root whose filename was changed by hand is found rather than left in place unreported. And the step
runs only when this import actually marks a composition `root: true`.

**What it does not reach:** a root that carries a port, a member or a delegation is never removed,
so a `--force` import into a project holding a hand-authored hierarchy writes its own root beside it
and the two roots are `check-model`'s to report. Without `--force` the emptiness guard refuses that
project first.

`SYSTEM` is still a deferred tag, and the root prototype under it is still not emitted. That is the
node the hierarchy mapping leaves out, and it is a question about `systems/`, deliberately not decided by side
effect here.

## External stubs, and what may connect to them

A tool export's prototypes may reference types the export does not carry — packages
of basic software and of other projects. Dropping them would have left every
composition that places one incomplete, and the round trip could not close. They are imported as
**stub** components instead: `external: true`, plus the source's `TYPE-TREF` and its `DEST` carried
**verbatim** in `external_ref` and `external_dest`, stored under `swc/external/`, with no ports and
no runnables.

```yaml
# model/swc/external/ExternalStub.yaml
name: ExternalStub
type: application
external: true
external_ref: /Other/Project/SupplierPlatforms/Bsw/ExternalStub
external_dest: APPLICATION-SW-COMPONENT-TYPE
```

The writer emits no `APPLICATION-SW-COMPONENT-TYPE` and no implementation for a stub — the one place
it appears is its prototype's reference, written back with those two strings unchanged, so the
target toolchain resolves it where the original did. The `DEST` is carried beside the path rather
than inferred from it, because a path alone does not say what kind of element it names, and a wrong
`DEST` validates against the XSD while dangling downstream. A stub may
carry `COMPOSITION-SW-COMPONENT-TYPE`.

**What connects to a stub: nothing — and that is measured, not an assumption.** A stub declares no
ports, so a connector or a delegation that reaches one cannot resolve. On import such a connector is
**skipped and reported**, one line each; on generation such a model is **refused**.
A stub is not a placeholder you can wire to later by hand either: `rule:swc.external-with-ports`
reports a stub that has grown ports, so the two paths agree. If you need the wiring, the answer is to
import the package the type lives in.

Stubs are components the project declares, so they are linked to the import's umbrella requirement
like every other component rather than exempted from
traceability. Budgets and task mappings ignore them.

## The C4 diagram gains a level

A composition is a real LikeC4 element containing its members, not a label:

```
model {
  Root = composition {
    title "Root composition"
    ExampleSWC = component { title "ExampleSWC" … }
    ExampleConsumerSWC = component { title "ExampleConsumerSWC" … }
  }
  Task_10ms = task { … }
  Root.ExampleSWC -> Root.ExampleConsumerSWC "pOut -> rIn: IExample"
}
```

The nested element is the **instance**, named by the member — a type may stand in several
compositions and a LikeC4 id is unique. Its title is the member name, and `"<member> : <type>"`
where the two differ, which is UML instance notation. A component **no** composition places stays
flat, exactly where it stood before, so a partial hierarchy is a drawable project rather than a
refusal. Delegations are not drawn: containment already says what a delegation says, and an edge
from a composition to its own child would draw it twice. A connector *between* two compositions is
drawn — that is a relation between siblings.

One new refusal comes with the level: a composition **no member places** is a top-level LikeC4 id, a
namespace systems, flat components and tasks already claim, so `generate c4` refuses a model in which
two of them collide rather than emitting a document the renderer rejects. A *placed* composition's
members are namespaced by their parent and are never in that namespace.

One new static view, `view compositions`, is claimed — conditionally, exactly as `components` and
`tasks` are, so a project that declares no composition neither draws it nor reserves the name. When
the layer has content, `compositions` joins the static view names a `sequence` may not collide with.

**What a project that used `containers/` loses from the diagram**, said plainly because a
regenerated `.c4` is where it shows up: every `container` node is gone, `element container` leaves
the specification block, and `view index` moves — its title is `"Systems"` instead of
`"Systems and containers"` and its predicate is `element.kind = system` alone. A project that
declared containers but **no** system had an `index` showing those containers; it now falls back to
`"Model overview"` over the components, which is what a project with neither has always got. The
successor is a composition per container (§ *What an existing project must change*, step 3): a
composition is a real containing element, so what a container drew as a flat box is drawn as a
nesting one.

**The flat views survive as projections — with one qualification, because "unchanged" unqualified
would be false.** Node sets, edge sets and every existing view body are equal once identifiers are
projected to their leaf segment; that is asserted in the test suite and confirmed once with the
renderer itself. What *does* change on screen is `view tasks`: it gains a `Root` box. LikeC4 elides
only the ancestors common to **every** node in a view, and the task sits outside the root, so the
root is drawn as a compound there and elided in `components` and `group_example`. No node is lost, no
edge is added or lost, and no other view moves.

## Budgets and task mappings stay per type

A core's load and a memory's consumption are still charged **per component type**, and a
`{swc, runnable}` pair is still mapped to at most one task — not per instance. `swcraft
resource-report` answers exactly what it answered on 0.8.0.

That is a decision checked against real tool exports the maintainer holds privately: per-instance
figures would today be per-type figures with more bookkeeping. It is written
down here rather than left implicit because it is the one place where the model can now say
something the analysis does not yet read: place one type in two compositions and both instances
share one budget line. If a project ever needs them separated, that is a change to the resource
layer and not to this one.

## The model's contract is `4.3.0`

`contractVersion` moves from `3.4.0` to `4.3.0`, a **major** with a prose-only patch and then three minors on top — `4.0.0` is the break, the third, and the first
one against a contract that has actually shipped. The grounds are removals alone: `layer:containers`,
`kind:containers.container`, its four fields (`name`, `title`, `system`, `description`) and
`rule:name.composition-reserved` — **seven identifiers**. **`4.0.0` puts fifty-two in their
place**, and the three minors below add nine rules more, so the whole move from `3.4.0` adds
**sixty-one** identifiers and removes seven:
`layer:compositions`, its four kinds, twenty-five fields (the four kinds' own twenty, plus the
connector's `composition`, the endpoint's `composition` and the three external-stub fields on
`kind:swc.swc`) and twenty-two rules.

| Inventory | `3.4.0` | `4.3.0` |
|---|---|---|
| layers | 10 | 10 — `containers` out, `compositions` in at its display slot |
| kinds | 32 | **35** |
| fields | 125 | **146** |
| reference fields | 12 | **16** |
| collections | 16 | **19** |
| rules | 129 | **159** (cross-element 75 → 99, element-local 53 → 59, `schema-config` 1 → 1) |
| ARXML-bound layers | 4 | **5** |

`SUPPORTED_CONTRACT_MAJORS` becomes `frozenset({4})`, so a consumer authored against a `3.x`
document is refused with the loader's existing message rather than misreading one.

`4.0.1` is the patch on top: `kind:systems.system`'s description still read *"a C4 context-level
element that containers are assigned to"* — the one place in the contract where the retired layer
survived, and a sentence shipped into the editor's hover, this guide's own reference page and every
`discover` answer. It now says the system names a boundary of the architecture and is what the
landscape view draws. No identifier moved, so it is a patch and not a second break.

`4.1.0` is the **minor** added on top of that, and it is where
`check-model` caught up with what the ARXML writer already refused. **Nine** rules arrive, seven of
them cross-element:
`rule:composition.duplicate-port`, `rule:composition.delegation-connector-name-collision` and
`rule:composition.port-undeclared-interface` — the three sibling scopes and the one declared
reference the layer owed; `rule:swc.external-incomplete-reference` and
`rule:swc.external-reference-without-stub` — an external stub's `external_ref`/`external_dest` pair,
which nothing checked on any path; and `rule:name.duplicate-component-type` and
`rule:name.composition-implementation-collision` — the `swc` layer and the `compositions` layer are
one `/ComponentTypes` `SHORT-NAME` namespace, which `swcraft import rhapsody` had already said
and `check-model` had not. Two more are **element-local**, the not-blank guards the loader owed:
`rule:compositions.composition_port.reference-not-blank` and
`rule:compositions.composition_member.reference-not-blank`. Two go:
`rule:composition.member-type-form` and
`rule:connector.endpoint-type-form`, whose shape the Pydantic loader refuses first, so no
`check-model`, no `generate *` and no editing-protocol pass could reach either — the element-local
`rule:compositions.composition_member.type-form` and `rule:connectors.connector_endpoint.type-form`
are the whole answer. Removing an identifier is a major by the contract's own three-way versioning rule, and it is not
one here for the reason that rule turns on: both were declared inside this same **unreleased** `4.x`
line, so no consumer has ever seen them.

**No identifier changes meaning**, which is the part worth stating because the design expected
otherwise. `field:connectors.connector_endpoint.swc` still resolves into `layer:swc` and still names
a component *type*; what changed is only that it stopped being required, since an endpoint may now
name a composition instead. Resolving the type to an instance is the writer's job and not the
declaration's — which is why the impact graph's connector → component edge is exactly as precise as
it was, and why the contract's decision record needed no new clause for a field whose referent did **not** move. It records that
decision rather than leaving it to be re-derived.

`4.2.0` is the **second minor**, and it
closes the last shape of the layer that nothing gated at all:
`rule:composition.delegation-interface-mismatch`. A delegation's two ports had to face the same
way; they did not have to name the same interface. A `CLIENT-SERVER` boundary port delegated onto a
`SENDER-RECEIVER` member port therefore passed `check-model`, passed `generate arxml` **and** passed
the licensed XSD at 4.2.2 and at 4.3.0 — AUTOSAR requires the two ports of a
`DELEGATION-SW-CONNECTOR` to reference compatible port interfaces and the schema cannot express it.
The connector path has had `rule:connector.interface-mismatch` for many releases; this is the
delegation path's half, with the fail-closed writer refusal beside it. The same bump widens two `appliesTo`
lists — `rule:name.swc-implementation-collision` and
`rule:name.composition-implementation-collision` each gain `field:swc.swc.external`, a field both
conditions have read since `4.1.0` and neither declared. One identifier added, none removed, none
renamed.

`4.3.0` is the **third minor**, and it is the same shape
of hole once more: `rule:composition.duplicate-delegation-link`. The duplicate-delegation
check keyed on the delegation's **name**, so two delegations wiring the identical
`(port, member, member_port)` triple under different names passed `check-model`, passed
`generate arxml` and passed the licensed XSD at both versions, emitting two
`DELEGATION-SW-CONNECTOR`s byte-identical but for their `SHORT-NAME`. A link is identified by what
it wires — which is what `rule:connector.duplicate-link` has long said about an assembly connector. `swcraft import rhapsody` mirrors the new key and skips such a pair with the rule named in
the skip line, because a tool export can carry such pairs. Delegation **multiplicity** is
deliberately *not* gated: several delegations onto one boundary port and different member ports
stay legal, and a tool export's `(composition, outer port)` pairs can be that
shape. One identifier added, none removed, none renamed.

## What the editing protocol and the MCP surface publish differently

**No tool was added or removed** — the surface is the same thirteen tools, and the decision table
that pins them is byte-untouched. The layer arrives over the wire with **no projection module
moving**, in the sense that matters to a client — no **addressing** projection changed;
`editing/diagnosis.py` grew, because the new rules need protocol error codes. `discover` publishes
`compositions`, its four element kinds (`composition`,
`composition_port`, `composition_member`, `delegation`), its three collections and its three
references from the contract, and every published kind is addressable because the protocol derives
addresses from the same declarations. The `containers` address vocabulary is gone with the layer.

Two things follow that a client should know. A change set that stages a second root, a type placed
twice in one composition, or an endpoint that is not a member of its composition is refused in pass D
with a `consistency-violation` naming the rule; one whose member, delegation or boundary port names
something the model does not declare is refused as a **`broken-reference`** instead, carrying the
group a client repairs it in. Either way it is the same composed check `swcraft check-model` runs,
which is why the two surfaces cannot drift. And **a composition is the natural second shape for the
`over-budget` refusal**: the response budget is 80 000 wire bytes, and a composition with hundreds of
boundary ports or delegations exceeds it. A hand-built element of such a wide
shape measures well over the budget at its element address. The refusal carries a hint
chain as it always has, and walking it reaches an answer; a hint is a narrower *form*, never a
promise that the narrower form fits, so the first step of a long chain can itself be refused, with a
shorter chain of its own.

**Removing a member, removing a delegation and retargeting a member's `type` are not weakening
directions.** All three narrow what is wired and none widens a permission, so the safety-relevant
set stays at five and the review boundary does not put the second question for them. The reasoning
is written down rather than left as a bare classification.
Deleting a whole composition needs `delete` authority, like any element.

## What the editor does not check

The generated JSON Schemas cover the new layer — `vscode_extension/schemas/compositions.schema.json`
is written by the same generator as the other ten, and hover and completion work on a composition
file as they do on any other. What a schema validating one document cannot see is every cross-file
rule in the table above: whether a member's `type` names a declared component, whether exactly one
composition claims `root`, whether the hierarchy has a cycle, whether a delegation's two ports agree
on direction **and on interface**, whether two delegations wire the same triple, and whether a
connector's endpoints are members of its composition. It also cannot see
the `Identifier` limits on the four emitted name sites. `swcraft check-model` is the authority, as it
is for every cross-file rule, and no editor diagnostic is qualification evidence.

## Python API

Names that moved with the layer. Nothing here is deprecated with a compatibility spelling: the
retired layer's names are gone in one step, for the reason § *What an existing project must change*
gives.

- **Removed.** `schema.ContainerElement`, `reader.read_containers`, `writer.create_container` and
  `writer.arxml_generation.COMPOSITION_NAME` — the last being the invented `SwCraftComposition` the
  writer no longer mints.
- **Arrived.** `schema.Composition`, `schema.CompositionPort`, `schema.CompositionMember`,
  `schema.Delegation`, `reader.read_compositions` and `writer.create_composition`, which is
  `create_container`'s successor in shape as well as in name: `(model_root, name, title,
  description="", root=False, auditor=None)`, where `create_container` took a required `system`
  and no `root`. It writes an empty composition; members, ports and delegations are added by
  editing the file or through the editing protocol.
- **Changed.** `schema.ConnectorEndpoint.swc` is now `str | None` with a default of `None`, because
  an endpoint may name a composition's boundary port instead: exactly one of `swc` and `composition`
  is set. Code that read `endpoint.swc` as a `str` has to handle `None`.
- **The audit trail's action name moves with the function.** `dist/audit.jsonl` records
  `create_composition` where it recorded `create_container`. A reader that filtered on the old
  action matches nothing; historical lines keep the name they were written with, because the audit
  log is history and nothing rewrites it.
- **`swcraft impact` prints more edges.** The reference model gains five composition-touching
  references, three of which render a detail suffix — `member <name>` for a member's `type` or
  `composition`, `via port <name>` for a boundary port's `interface`. A script parsing the impact
  report's lines sees rows it has not seen before; the report's *format* is unchanged.

## Known gaps, recorded on purpose

- **Placing one type twice in one composition is refused.** Lifting it means an endpoint that names
  a *member* rather than a type, which is a change to the reference model underneath `impact` — a
  relation with state, or member kinds as graph nodes. The same type in several compositions is
  legal now.
- **`systems/` is untouched**, and whether it should become ARXML-bound is a separate question. The
  `SYSTEM` element and its root prototype are still not emitted.
- **Per-instance budgets and task mappings** are out of scope, as § *Budgets and task mappings stay
  per type* records.
- **A `read` of a large composition is an `over-budget` refusal by design**, not a defect.
- **A composition whose bare name collides with an imported component's is skipped on import**, not
  renamed: renaming a composition would be a name-minting policy for a case nothing has yet
  called for.
- **The showcase project migrates in its own repository**, after this release is tagged, and is
  pinned to `0.9.0` there.
- **Windows is measured by the `main` run after the merge**, per the release gate; the branch's own
  runs measured Linux and macOS only.
- **The round trip's oracle is real tool exports the maintainer holds privately**, on one host; a project whose export nests
  differently may skip a different set, and the report is what names it.

## What two Windows workstations taught the install guide

Not a change to any artifact of this release — the archive, the installer and the extension are
the 0.8.0 ones with the version raised — but four things learned on 2026-09-07, when the 0.8.0
archives were installed on two corporate Windows workstations by the guide alone, and which a
reader of this release meets before any composition does. Each is recorded with its evidence; the
showcase's install guide is corrected in its own repository.

- **The diagram preview needs a Node.js the guide said you did not need.** The LikeC4 extension
  runs its language server on an external Node.js 22.22 or later — `node` from `PATH`, or the
  `likec4.node.path` setting — and without one every *open preview* fails with *"Language server
  failed to start"*. Every host that had been measured carried a Node, so the requirement was
  invisible; the 0.7.0 note's "no Node" and the guide's "Not needed: Node.js" are true of `swcraft`
  and false of the preview. No administrator is needed: unpack the portable Node.js 22 LTS zip and
  point `likec4.node.path` at its `node.exe`. `swcraft generate c4` needs nothing of this.
- **VS Code below 1.110 refuses the extension**, because the pack's floor is LikeC4's. One host on
  1.108 met that dialog; updating the editor resolved it. The floor has been in the guide's
  prerequisites since 0.7.0 — it was the first time a host was under it.
- **The installer's extension step can fail and the toolchain still be installed.** On that host
  VS Code's CLI died on start (an ICU error, exit code `2147483651`) and the installer said so in
  one sentence and named the `.vsix` to install from the Extensions view. That sentence had never
  been seen on a real machine before; it read correctly. The installer does not check
  `code --version` before handing the file over — a proposal, not done.
- **A dismissed trust prompt hides the SWCraft panel** — the icon is there with no folder open and
  gone once a folder is. That is VS Code's Restricted Mode, and *Trust* in the status bar brings
  it back without a restart. The guide named the rule; it now names the symptom.

## Known issue found after the release: `swcraft agent chat` needs `SWCRAFT_AGENT_SYSTEM_PROMPT`

Found on 2026-09-08 by the seated Windows gate of the workstation archive, and present in every
archive since 0.7.0: `swcraft agent chat --project PATH` from an **installation** fails with
`SystemPromptNotFoundError` before a prompt appears. The assistant looks for
`docs/agent-system-prompt.md` by walking up from its own module, which finds the file in a checkout
and nothing under `site-packages`, because the wheel does not carry it. The fix — the file packaged
into the wheel, and the assistant falling back to that copy — ships with 0.10.0.

On 0.9.0 the workaround is the variable the error names: take `docs/agent-system-prompt.md` from
the repository at tag `v0.9.0` and point `SWCRAFT_AGENT_SYSTEM_PROMPT` at it.

```sh
set SWCRAFT_AGENT_SYSTEM_PROMPT=<folder>\agent-system-prompt.md   # cmd
export SWCRAFT_AGENT_SYSTEM_PROMPT=<folder>/agent-system-prompt.md    # sh
```

Nothing else is affected: the `swcraft` CLI, `swcraft-mcp` and a Copilot session over the MCP
server never read the prompt.

## Upgrade checklist

1. Install all four artifacts at this version, the extension included.
2. If `swcraft.yaml` carries a `toolchain_version` pin, set it to this release. Until you do,
   every command that writes or gates refuses with the pin sentence and never reaches the model.
3. Write `model/compositions/<Root>.yaml` — `root: true`, `title`, and every component you declare
   as a member. Copy `examples/basic/model/compositions/Root.yaml` and edit the names.
4. Run `swcraft check-model --project swcraft.yaml`. Repeat until it exits 0; each message names the
   element and the fix.
5. Delete `model/containers/`. Nothing will tell you that you forgot — but a script or a moon task
   that ran `swcraft list containers` or `swcraft query containers` now exits 2.
6. Run `swcraft validate --project swcraft.yaml` and diff the generated ARXML against what you had.
   For a flat project the difference is the composition's `SHORT-NAME` and the two paths built from
   it, plus the prototypes re-ordered into your declared member order.
7. **Re-point anything downstream that resolved a path through
   `/ComponentTypes/SwCraftComposition/…`.** That is the one break outside your model.
8. Re-generate the C4 views (`swcraft generate c4`) and commit them if you track them; expect
   reparented ids and one new view.
9. If you re-import a Rhapsody export, expect a hierarchy where you used to get flattened
   leaf-to-leaf connectors — and read the import report's new sections: the external stubs, the
   references skipped because they reach one, and the scaffolded root it replaced.
10. For the C4 **preview** in VS Code, have a Node.js 22.22 or later on `PATH` or named in
    `likec4.node.path` (§ *What two Windows workstations taught the install guide*). Generating the
    `.c4` file needs none.
