# SWCraft 0.10.1

**Released 2026-09-11** (the bump commit; the tag follows the `verify` gate on both self-hosted
runners, Linux and Windows, on this commit, and the tag's own run publishes the release archives to
the NAS). The first patch release of the 0.10 line, made the same day as 0.10.0 for one defect
found when a tool export met the importer. It is cut on `main` rather than on a
release branch, because `main` had not moved since `v0.10.0` and there was nothing to branch away
from. One fix, inside the release-branch criterion: the model's contract, the editing protocol, the
MCP tool surface and the emitted ARXML bytes are unchanged from 0.10.0. A 0.10.0 project upgrades by
installing the archive; nothing else. A 0.9.0 project that has not installed 0.10.0 can skip it and
read `docs/release-notes/0.10.0.md` for what changed there.

## The importer flattens a type chain of any depth, and says so

`swcraft import model` on some tool exports
produced a model that `swcraft generate arxml` refused:

```
Error: Alias '<alias>' base '<base>' must be a primitive type — alias-over-alias is not supported
```

The export is correct. AUTOSAR lets an implementation type of category `TYPE_REFERENCE` reference
another `TYPE_REFERENCE` type, and lets an application type be mapped onto one — a unit type on a
base type, and constrained types on the unit type, is an ordinary way to write a type library. A
SWCraft alias, on the other hand, sits on a primitive and on nothing else, and the importer's job
has always been to flatten such a chain to the primitive at its bottom. It did so for a chain
**one** step deep only: its resolver returned the referenced type's own name, which two steps down
is an alias, and the test that covered the flattening covered a one-step chain. Every deeper chain
was written as an alias on an alias, `check-model` reported `data-type.alias-over-alias` for each,
and the writer refused the project.

Both places the importer mints an alias — an implementation type of category `TYPE_REFERENCE`, and
an application type resolved through a `DATA-TYPE-MAPPING-SET` — now walk the chain the export
declared down to its primitive and write that primitive as the alias's base, at any depth. The
alias keeps its own name, so the ARXML generated back carries every type the export declared.

**What is lost, and where it is written.** The model cannot say that `Volt_n075_to_075_res0_002`
was derived from `Volt` — it says it is an alias of `Float32`, as `Volt` is. That is a loss, so the
import report gains a section of its own for it:

```
Alias chains flattened to their primitive (1; the derived-from link is not written):
  - /Pkg/Types/Volt_n075_to_075_res0_002 -> Volt -> Float32 (base written as Float32)
```

One line per alias whose chain was deeper than one step, rendering the chain as the export spelled
it. The type names in this section are **invented examples** of the shape, and no document SWCraft
ships names an element of a customer's or a vendor's model. A one-step chain records nothing, because nothing
was dropped.

**If you already re-based such aliases by hand** to get past the refusal, the result is exactly what
the importer now writes; a fresh import over the same export is the way to get the report lines.

## The `rhapsody` alias stays through the 0.10 line

`swcraft import rhapsody` is still accepted, as a deprecated alias of `import model`, and its
warning now says it is removed in the release after **0.10.1**: a patch release removes nothing,
so a sentence naming 0.10.0 as the last release would have been false on the release that printed
it. The `--help` text names no release at all, only that the alias is kept for this release and
removed in the next.
