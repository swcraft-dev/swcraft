# SWCraft 0.10.0

**Released 2026-09-11** (the bump commit; the tag follows the `verify` gate on both self-hosted
runners, Linux and Windows, on this commit, and the tag's own run publishes the release archives to
the NAS). This note was written with each change rather than after it, so every figure
below was measured on the host and at the commit that produced it — macOS, CPython 3.11.13,
between 2026-09-07 and 2026-09-11.

## The workstation installer names the compatibility floor before it hands the `.vsix` over

`swcraft_install.cmd` / `swcraft_install.sh` install the toolchain and then give the archive's
`.vsix` to VS Code's `code --install-extension`. Until now a VS Code older than the extension
pack's `engines.vscode` floor learned that from the editor's own dialog, one step later than it
could — and on 2026-09-07 a corporate Windows workstation on VS Code **1.108** did not get even
that far: its `code` died on start with an ICU error (exit `2147483651`) before any compatibility
check ran, and the reader was left with the installer's generic *"the toolchain is installed and
the extension is not"* fallback and no idea that the editor was the cause.

The installer now asks first, in this order:

1. it reads `engines.vscode` out of `extension/package.json` **inside the `.vsix` the archive
   ships** — never a literal in `install.py`, because the floor is the *highest* among the pack's
   members and moves whenever one of them raises its own;
2. only if that answers something does it run `code --version` and compare the first line, using
   VS Code's own `isValidVersion` grammar (`^1.110.0` accepts 1.134.0 and rejects 2.0.0; a bare
   `1.63.0` is an exact requirement, not a floor).

Below the floor, `--install-extension` is **not run at all**. The run stops with one sentence
naming the host version, the declared floor and the `.vsix` to install from the Extensions view
once the editor is updated, and it exits the way every other "the toolchain is installed and the
extension is not" outcome exits.

**Nothing else changes.** A `code` that is absent, will not start, times out, exits non-zero or
prints an unreadable first line is *not comparable*, and the run proceeds exactly as it did before
— which is what keeps the 2026-09-07 ICU host getting the fallback sentence it should get, rather
than a floor refusal quoting a version nobody measured. A range outside the transcribed grammar (a
compound range, a `notBefore` build-date tail) is not comparable either, and never a refusal.
`code --install-extension` run by hand, and the Extensions view, are untouched: VS Code answers
those itself.

**Nothing to do when upgrading.** There is no new flag, no new file in the archive and no change to
what a project holds.

## The Linux CI runner's Rhapsody round-trip gates can no longer report "skipped"

The three machine-local Rhapsody gates — the round trip, the init values and the access-point
import — skip when `SWCRAFT_RHAPSODY_EXPORT` names nothing, which is what keeps `verify` runnable
on a machine with no licensed export. It also made them silent on a machine that is
supposed to hold the variable's file: a file that quietly went missing from that disk
would have left the stage green.

`python scripts/dev.py test-slow` now takes `--require-rhapsody-export`, which turns that skip into
a failure. It is a **flag and not a new stage** — `slow` keeps exactly one stage of its own — and
it reaches the `tools` pytest run alone, because that is the project whose `conftest.py` registers
the option. Every other `dev.py` command **refuses** it rather than ignoring it: a
`verify --require-rhapsody-export` that quietly proved what a plain `verify` proves is the shape
the flag exists to prevent.

The work repository's `verify` workflow passes it on a job whose host is meant to hold the file and not on
one that is not, because turning an intended absence into a failure would make every run of that
job red over a file it is not supposed to have. The licensed AUTOSAR XSDs stay a skip
on both hosts — `test-xsd` is their gate, and it is not a `verify` stage.

**Nothing changes for a developer machine.** A plain `python scripts/dev.py test-slow`, and
therefore `verify`, behaves exactly as before.

## The editor-tooling report names LikeC4's external Node.js

`SWCraft: Check Editor Tooling` reports a pack member as `[ok]` when it is installed, enabled and
within its declared `engines.vscode`. On 2026-09-07 that produced a green line for LikeC4 on a
corporate Windows workstation with no Node.js — and the first *open preview* then failed, because
that extension does not run its language server on VS Code's own Electron: it spawns Node.js from
the `likec4.node.path` setting, or a bare `node` on `PATH`, and needs 22.22 or later.

The report's *What this report cannot see* list now says so, so a reader on a Node-less host is not
left to conclude that a green report cleared it. **It is a stated limit and not a new check**, and
that is a decision rather than an omission: every verdict this surface reaches is read from a
declaration that travels with the thing it describes, and LikeC4's Node floor is declared in no
manifest — it is a string inside that extension's own bundle. A probe would have to carry the floor
as a literal with nothing to check it against, on the one surface whose job is noticing something
missing; and Red Hat XML's Java requirement has the same shape, so one probe would be arbitrary and
two would start a per-member runtime table in the extension's code.

No verdict, marker or problem count changes: the report gains one line.

## The import format is `model`

`swcraft import rhapsody` is now **`swcraft import model`**.

The old name was chosen when the importer was written, and it
named the *source tool*. The reader is a generic AUTOSAR Classic 4.2.2/4.3.0 reader, and the
subcommand has had a sibling — `swcraft import component` — since long before this release, so the
pair now reads as what it actually is, about **what** is imported rather than **who** exported it:

```sh
swcraft import model     --source export.arxml   --project swcraft.yaml   # a whole export, fresh project
swcraft import component --source SpeedSensor.arxml --project swcraft.yaml # one component, existing project
```

**`rhapsody` is kept as a deprecated alias for one release.** It dispatches through exactly the
same path — same report, same exit codes, same `--packages` / `--force` / `--dry-run` semantics —
and prints one line on stderr:

```
Warning: 'rhapsody' is a deprecated alias of 'model' and is removed in the release after 0.10.0.
```

**Migrating** is one word, in whatever runs the command:

```diff
-swcraft import rhapsody --source export.arxml --project swcraft.yaml
+swcraft import model    --source export.arxml --project swcraft.yaml
```

```diff
 # moon.yml
 tasks:
   import:
     command: swcraft
-    args: ['import', 'rhapsody', '--source', 'export.arxml', '--project', 'swcraft.yaml']
+    args: ['import', 'model', '--source', 'export.arxml', '--project', 'swcraft.yaml']
```

**Nothing else moves.** `swcraft import component` is untouched. The machine-local
`SWCRAFT_RHAPSODY_EXPORT` variable, the `--require-rhapsody-export` pytest flag, the round-trip
suites and every dated record keep the old name, because there it is the right one: it names a
variable's file and not a CLI mode.

## `swcraft agent chat` starts from an installation

Until now it did not. The assistant reads its system prompt from `docs/agent-system-prompt.md`,
found by walking up from its own module — which reaches that file in a checkout and reaches nothing
from `site-packages/swcraft_agent/`, because `agent/pyproject.toml` packages `src/swcraft_agent`
alone and the prompt is a repository file. Every installation since the workstation archive of
0.7.0 — 0.7.0, 0.8.0 and 0.9.0 — therefore answered `swcraft agent chat --project PATH` with
`SystemPromptNotFoundError` before a prompt appeared. Every suite that reads the prompt reads it
from a checkout, which is why none of them caught it, and it was found on 2026-09-08 by the first
sitting to run the assistant on Windows from an installation rather than from a checkout.

`python scripts/dev.py artifacts` now copies the file into the agent package as
`swcraft_agent/agent-system-prompt.md` before any wheel is built — the same arrangement as the
guide site in `swcraft_tools`, gitignored and excluded from the generated-source scan — and the
assistant falls back to that copy **after** the checkout walk, so a developer editing `docs/` still
runs the edit. `SWCRAFT_AGENT_SYSTEM_PROMPT` keeps precedence over both, as before.

**On 0.9.0 and earlier the workaround is that variable**: point it at a copy of
`docs/agent-system-prompt.md` taken from the repository at the installed release's tag. Nothing
else of the assistant, and nothing of the MCP server, is affected — a Copilot session over
`swcraft-mcp` never reads the prompt.

## The installer's `.vsix` step rolls back as well as forward

`swcraft_install.cmd` / `swcraft_install.sh` install the toolchain and then the archive's `.vsix`.
Installing release **A** over a newer **B** rolled the toolchain back to A and left the extension
at B, and said nothing: `code --install-extension` refuses to replace a newer extension with an
older one, and refuses it on a run that exits **zero** — *"A newer version … is already installed.
Use '--force' option to downgrade"* — so the installer saw a success and reported one, and only
`SWCraft: Check Editor Tooling` could have noticed the two halves disagreeing. Measured on the
seated Windows gate of 2026-09-08 (§ 3.6 step 4).

The `.vsix` step now carries `--force`. It gives up no check the installer relies on: the
compatibility floor is read out of the `.vsix`'s own manifest and compared by the installer
itself, never delegated to VS Code's dialog. A forward install is unchanged.

**Nothing to do when upgrading.** The flag only matters to a host that later installs an older
archive over this one, and that host runs the older installer — so a rollback *from* 0.10.0 to
0.9.0 still leaves the extension at 0.10.0, and the Extensions view is the way to move it.

## Both archives say what they are

Until now a person who downloaded and unpacked a SWCraft zip found a folder of files and no word
about what they were or what to do with them.

The **workstation archive** now carries a `README.md` at its root, the first file a reader sees
after unpacking. It says what the toolchain is and what each file in the folder does; how to check
the files against `SHA256SUMS` by hand, on Windows with `Get-FileHash` and elsewhere with
`shasum -a 256 -c`; how to run the installer and what it changes on the machine, step by step —
including that the `PATH` edit is Windows-only, and that macOS and Linux get one printed
`export PATH=` line instead; what the VS Code step can do and what each of its four outcomes means;
what to run afterwards (`swcraft docs`, `swcraft init`); and how to update, roll back and
uninstall. It ships because every file in `scripts/workstation/` ships, and the archive's own
`SHA256SUMS` lists it like every other member.

The **guide archive** carries a `README.txt` at its root, beside `swcraft-guide-<version>/`. Its
subject is the one thing the unpacked tree cannot state about itself: the site has to be
**served**, not opened from the file system — over a `file:` URL neither the navigation nor the search
works — and `python -m http.server` from inside the directory is the shortest way to serve it. With
the toolchain installed, `swcraft docs` replaces the zip altogether.

**References to how SWCraft is built are gone from what a user reads.** The installer, the two wrappers, the
files `swcraft init` scaffolds, the assistant's system prompt, the VS Code extension's page in the
Extensions view and the release notes from 0.9.0 on no longer cite development phases, plans or
checklists; a file that can be used without knowing how SWCraft was built now says nothing about
it. The extension's page was rewritten for the person reading it in the editor, and its developer
half moved to a `DEVELOPMENT.md` that the `.vsix` does not carry. A test now scans those
surfaces — and the CLI help, the MCP tool descriptions, the contract's descriptions and the
extension manifest's strings — so the references do not come back. Release notes before 0.9.0 keep
theirs: they are the published record.

**Nothing to do when upgrading.** No flag, no behaviour and no file a project holds changes; both
archives gain one member each.

## The model's contract is `4.6.0`

`contractVersion` moves from `4.3.0` to `4.6.0`, in **three** minor steps and one prose-only patch
between them, one minor per piece of safety work in this release. No identifier is removed and
none is renamed at any step.

**Step one, `4.4.0` — the level on the requirement and on the component.** Three identifiers added.

| Added | What it is |
|---|---|
| `field:requirements.requirement.asil` | the safety integrity level allocated to a requirement |
| `field:swc.swc.asil` | the level a component declares for itself |
| `rule:safety.component-below-requirements` | a component declaring a level **below** the requirements allocated to it |

**Step two, `4.5.0` — the level on the information, and two arguments that answer a finding.**
Eight identifiers added.

| Added | What it is |
|---|---|
| `field:interfaces.data_element.asil` | the level of the information one data element carries |
| `field:swc.port.measures` | per port, the measure that answers a finding about one data element |
| `field:tasks.task.coexistence` | the argument for scheduling components of different levels together |
| `rule:safety.provider-below-element` | a component providing an element rated above its own level |
| `rule:safety.consumer-above-element` | a component consuming an element rated below its own level with no measure declared |
| `rule:safety.measure-unknown-element` | a measure naming no data element of the port's interface |
| `rule:safety.measure-on-provide-port` | a measure on a `provide` port, where no rule reads it |
| `rule:safety.task-mixed-asil` | a task mixing levels with no coexistence argument |

**The patch, `4.5.1` — one description that had not caught up.** No identifier at all: the
description of a sender-receiver interface's data element still listed the three fields it had
before this release and not the `asil` step two declared, so an editor hover, the reference page and
every `discover` answer read it short. Prose only, and the inventory below is unchanged by it.

**Step three, `4.6.0` — the level the hardware is declared able to host.** Four identifiers added.

| Added | What it is |
|---|---|
| `field:hardware.core.asil_capability` | the highest level a core, as the project has configured it, is declared able to host |
| `field:hardware.memory.asil_capability` | the same, for a memory |
| `rule:safety.task-on-unqualified-core` | a task on a core whose declared capability is **below** the level of a component it runs |
| `rule:safety.memory-below-component` | a component charging a non-zero budget to a memory whose declared capability is below its level |

| Inventory | `4.3.0` | `4.4.0` | `4.5.0` | `4.6.0` |
|---|---|---|---|---|
| layers | 10 | 10 | 10 | 10 |
| kinds | 35 | 35 | 35 | 35 |
| fields | 146 | 148 | 151 | **153** |
| rules | 159 | 160 | 165 | **167** (cross-element 99 → 100 → 105 → **107**, element-local 59, `schema-config` 1) |

**What a project gains.** A place to write the level down, and a check that reads it. Both fields
take `QM`, `A`, `B`, `C` or `D`. A requirement carries the level allocated to it; a component that
declares nothing takes the **highest** level of the requirements whose `links` name it, and a
component that declares one may declare it equal to or above that highest level and be right. Only
below it is reported, as one finding naming the component, the level it declares and every
requirement above it. `QM` is **not** the lowest level — it says that no ASIL is allocated — so a
component that writes `asil: QM` under a requirement carrying a level is reported, while a
component that writes nothing is not. `swcraft check-model` and `swcraft validate` report the
finding, and a change the assistant proposes that would create one is refused rather than queried.
The guide's **Safety levels** page — `swcraft docs` serves it — is the page for it.

**What a project must do: nothing.** Both fields are optional and neither has a default, so a model
that allocates no level carries no new key in any file, generates the same ARXML byte for byte at
4.2.2 and 4.3.0, and generates the same LikeC4 document. Nothing is written to or read from ARXML
for either field, by decision: AUTOSAR's component template has no ASIL attribute and the one
spelling that ever existed for one is obsolete with no successor, so the level stays in the model
where the review reads it.

**The one visible change** is in the Sphinx-Needs output: `swcraft generate rst` renders an
`:asil:` option beside `:status:` for a requirement that declares a level **other than `QM`**. A
requirement that declares nothing — or declares `QM` — renders exactly the block it rendered
before, so a project that allocates no level sees no difference in the generated document either.

⚠️ **A project that does allocate one must declare the option in its own `conf.py`.** `:asil:` is
the first option SWCraft emits that Sphinx-Needs does not know built in — `:id:`, `:status:` and
`:links:` are all its own — so the documentation project that builds the generated `.rst` needs

```python
needs_extra_options = ["asil"]
```

Without it Sphinx-Needs warns `Unknown option 'asil'` and drops the value: the level is absent from
the rendered page, and a build run with `-W` fails outright. Adding the line is the whole of the
upgrade step, and it is needed only by a project that declares a level.

### Step two: the level on a signal, and the two arguments

**What a project gains.** A place to rate the *information* rather than only the component, and
three more questions answered from the model's own declarations: may this component **produce**
this rated signal, may it **consume** a lower-rated one, and may these components **share a task**.
A data element takes the same five values a requirement and a component do, and an element that
declares nothing is **unrated** — not `QM` — so nothing is compared against it.

Two of the findings are answered by writing the argument down rather than by switching a check off.
A `require` port's `measures` map names, per data element, the measure that answers a finding about
it; a task's `coexistence` is the free-text argument for scheduling components rated differently.
Both are **declarations and not verifications**: nothing checks either text against anything, and
the model expresses no partition for one to be checked against. A measure's *text* may even be
blank and still answers its finding, because it is the data element's name in the map that the
check reads; a task's `coexistence` is a single field that starts out empty, so an empty one is
simply a task with no argument on it and the finding stands. Two further findings say when an
argument is one nothing can read — on a `require` port, a key naming no element of the port's own
interface; on a `provide` port, a `measures` map at all, where the consumer rule never looks. The
two divide by direction, so a provide port with a misspelt key is one finding and not two: the one
repair for a map that no rule reads is to remove it, and that answers the spelling question too.

**What a project must do: nothing.** All three fields are optional, none has a default that any
file has to carry, and a model that declares none of them generates the same ARXML byte for byte at
4.2.2 and 4.3.0, the same LikeC4 document **and** the same Sphinx-Needs output — none of the three
sits on a requirement, so even the `:asil:` option above is unaffected.

**The one thing to know.** Declaring a measure or a coexistence argument makes a check stop refusing
a model, so the assistant asks about it **separately** before it lands, the way it already asks
about widening a memory's `accessible` list. Approving the edit is not approving the argument, and
the question is asked whether the argument is written into something that already exists or arrives
inside a port, a component or a task created with it already in place. The
same separate question is asked when a **level is taken away** — lowering or clearing the level a
requirement allocates, unlinking a requirement from a component, lowering a level a signal or a
component declares, or deleting the thing that carried it: the requirement, the rated signal, the
interface that declared one, the port that carried the argument, a component that bears a level, or
a task whose coexistence argument answered components at different levels. It is also asked when an argument
you wrote **earlier** becomes live without you writing anything — a measure written on a port ahead
of the rating it answers, once the signal is rated; a coexistence argument on a task, once one of
its components is rated differently — because the standing argument then closes a finding nobody
answered in that change set. Three things it deliberately does *not* ask about: a requirement that
allocates no level allocates nothing, so unlinking or deleting one is not a weakening — nor is
unlinking one where another requirement holds the same level up; a component that stops declaring a
level takes the highest of the requirements allocated to it, so withdrawing a declaration they hold
up is no drop at all; and on a project that has not adopted safety levels, deleting an element of
any of those layers asks nothing, because there was nothing to take away. **Renaming** anything is
not a weakening either, however many files the rename touches: the level and the argument move with
the element.

### Step three: where a level may run

**What a project gains.** A place to say what the hardware is qualified for, and two more questions
answered from the model's own declarations: may this task run on this core, and may this component
use this memory. A core and a memory take the same five values under a different name,
`asil_capability`, because what they carry is a different quantity — not the level something *has*,
but the highest level a core or a memory, as the project has configured it, is declared able to
*host*. A task is reported when its core's capability is below the level of a component among its
runnables, one finding per task and component; a component is reported when it charges a memory
more than nothing and the memory's capability is below its level, one finding per component and
memory. The level compared is the component's own when it declares one, and otherwise the highest of
the requirements allocated to it.

Three things decide what is not reported. A core or a memory that declares no capability is
**unrated** and compared against nothing — it is not `QM`, and one that does declare `QM` hosts no
ASIL, so every rated component placed on it is reported. A budget of `0` is not a use, exactly as it
already is for a memory's `accessible` list, so a component can name a memory it never touches
without a finding. And a component no task runs is never checked against a core — it is not on one
— though its memory budgets still are.

Both checks are **declarations and not verifications**. The capability is the project's statement
about a configured part — one core can carry a different claim in a different configuration, and the
memories of one chip are not always rated alike — and nothing in the model expresses the memory
protection, the partitioning or the safety manual that make the statement true. A capability that was
always too generous is never questioned.

**What a project must do: nothing.** Both fields are optional with no default, `swcraft init` writes
neither into the core it scaffolds, and a model that declares neither carries no new key in any file
and generates the same ARXML byte for byte at 4.2.2 and 4.3.0, the same LikeC4 document and the same
Sphinx-Needs output. `swcraft resource-report` shows neither finding — a level is not a budget — so
`swcraft check-model` is where both appear.

**The one thing to know.** **Raising** a core's or a memory's capability makes both checks stop
reporting the components placed on it, so the assistant asks about it **separately** before it lands,
the way it asks about widening a memory's `accessible` list — and so does **clearing** one that stood
below `D`, because an element that declares nothing is compared against nothing. Declaring a
capability where none stood, and lowering one, make the checks report more and are not asked about;
clearing a `D` is not asked about either, because a `D` capability already refused nothing. Moving
what is placed is not asked about, wherever it moves: a task moved to another core, or a budget moved
to another memory or set to `0`, can close one of these findings without a second question — even
onto a core or a memory that declares no capability, where the component stays placed and is simply
no longer compared. The question is about the hardware's own declaration, and a move leaves it where
it was; `swcraft query hardware --exists asil_capability` lists the cores and memories that declare
one.

**A model that passes these checks is not thereby safe.** They compare a project's own
declarations against each other and say they disagree; they say nothing about whether the
allocation is right, nothing about whether the argument written down is any good, and they are not
a safety analysis.
