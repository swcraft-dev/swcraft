# SWCraft 0.24.0

Released 2026-11-25. The release where SWCraft's source becomes an open repository on GitHub, under the Apache License
2.0, and its archives — a macOS one among them — are downloaded from that repository's Releases
page, with nothing to sign in to. An assistant loads tool descriptions less than half as long, and
reads the detail they no longer carry in the guide; **`swcraft query --form full`** prints every
field of a row; the model guard refuses, under every assistant, a path that names the model folder
or ends like a model file; and `swcraft` reads a `.env` from your project only. The specimen
generator is now the command **`swcraft-specimens`**, at this release's version. *What upgrading
takes* at the end has, beyond the pin, one `.gitignore` line, a `.env` that may have to move, and
what a script may have to spell anew.

## SWCraft's source is an open repository

SWCraft's source is published at `https://github.com/swcraft-dev/swcraft`, licensed under the Apache
License, Version 2.0 (`LICENSE`). `NOTICE` says what that licence does not cover: the name
"SWCraft" itself. The third-party components keep their own licences (`THIRD-PARTY-NOTICES.md`).

- **One commit per release.** The work happens in a separate repository, and each release reaches
  GitHub as one commit, so the repository's history is the list of releases.
- **Issues are open:** a bug (what you ran, what you expected, what happened, `swcraft --version`
  and the platform), a suggestion, or an offer to help, agreed in the Issue before any work starts.
- **Pull requests are off,** because a one-way copy gives one nowhere to land. An agreed change is
  sent as a patch or a branch of your fork, linked from the Issue, applied with you as its author,
  and named in the *Contributors* section of the release note that carries it. `CONTRIBUTING.md`
  has the whole procedure, the gates a change goes through and the test rules.

## The archives are on GitHub's Releases page, macOS among them

- **Where:** the Releases page of `github.com/swcraft-dev/swcraft`. A release carries three
  archives — `swcraft-<version>-linux-x64.zip`, `swcraft-<version>-windows-x64.zip` and
  `swcraft-<version>-macos-arm64.zip` — each with its `SHA256SUMS-<platform>`, and this note as its
  text. The page is public: no e-mail address and no one-time code are asked for.
- **A macOS archive** (Apple silicon) joins the Linux and Windows ones. It is not signed, so macOS
  quarantines what it unpacks; clear the flag on the unpacked folder once, before the installer:
  `xattr -dr com.apple.quarantine <unpacked folder>`. An installer started on a folder that still
  carries the flag installs nothing and says so, naming that command, where the archive's own Python
  would otherwise be stopped by macOS without a word.
- **To check a download,** compute its SHA-256 (`sha256sum`, `shasum -a 256` or PowerShell's
  `Get-FileHash`) and compare it with the file's line in `SHA256SUMS-<platform>`. That proves the
  file arrived whole, not who made it: nothing is signed.
- **Two new pages in the guide.** *An architecture repository* sets up a repository a team keeps
  its architecture in — the build graph, an existing repository, a build machine — and
  *Troubleshooting* lists, symptom by symptom, what goes wrong while installing or building, its
  cause and the fix. *Getting started* gains the installer's options.

## The assistant's tool descriptions are less than half as long

A chat client loads the description of every SWCraft tool into every session. Those descriptions
are cut to what an assistant needs on every call: each opens with what the tool does and when to
use it, then what it answers, its bounds and its refusals. The tool list a client loads went from
about 54,000 bytes to about 25,000. What left a description is in the guide section it points to,
which the assistant reads through `guide` when it needs it: *The read request* (every argument of
`read`, its answers and refusals), *Through the assistant* for `build`, `validate`, `model_diff`
and `architecture_metrics`, `resource_report`'s other answers, and the how-to pages. Five tools
that described their arguments in running text now describe each one on the argument itself. No
tool and no argument was added, removed or renamed. SWCraft's own set of assistant tasks was run
before and after the cut, and no miss was traced to the shorter text.

## `swcraft query --form full` prints every field

- **`--form full`** keeps each row's identity line and adds one indented `field: value` line per
  field the kind declares, in declaration order — a field you did not set as its declared default
  (`false`, `""`, `[]`, `{}`), or as `null` where it declares none. So `swcraft query swc --members
  runnables.calls --form full --project swcraft.yaml` shows each call's operation, timeout and the
  rest: the answer the assistant's `read` gives at `form: "full"`. A request file takes `"form":
  "full"`. Under `--format json` the document is **version 5** (`schemaVersion: 5`, `"form":
  "full"`), each row carrying the whole value. `full` does not combine with `derived` or `join`, and
  `summary` is refused. Without the flag, the output and its JSON versions are unchanged.
- **`--form json` no longer means `--format json`.** The command line used to accept `--form` as an
  abbreviation of `--format`; `--form` is an option of its own now, and `json` is not one of its
  values (`index`, `full`), so `--form json` stops with a usage error (exit 2), and so do the
  shorter abbreviations `--f`, `--fo` and `--for`, which match both options. Spell `--format` in
  full.
- **A `read` of a whole layer at `full` that is too large for one answer** now ends its refusal
  with the command that answers it with no size limit: `swcraft query --request FILE --project PATH`,
  as a too-large `index` read already did. Other refusals are unchanged.

## A missing budget says how to supply it

Both `hardware.missing-budget` findings — in `swcraft check-model`, `swcraft validate`, `swcraft
resource-report` and a refused change set — now name the field, the value's form and an example:

```text
SWC 'Beta' declares no budget for memory 'RAM': add `RAM` to its `memory` map with the bytes it uses, a whole number of at least 0, e.g. `RAM: 1024`.
Task 'T' on core 'CORE0' declares no 'wcet' budget: set its `wcet` to a positive whole number with one of ns, us, ms, s, e.g. `wcet: 500us`.
```

The code, the severity and the element it names are unchanged. A script that matched the end of the
old sentence must match the new one.

## The model guard: the model's path and its names, under every assistant

Two rules join the guard under Copilot, Codex, Claude Code and Kiro, for every path the guard judges
under that assistant, whatever the assistant does with the path afterwards, so an assistant that
resolves a path in a way of its own, or a later release of one, still cannot reach the model
through a path that names it. Under Copilot those are a read's path and a search's folder or
pattern; Copilot's `Edit` and `Write` are not judged, as before. Under Codex, Claude Code and Kiro
an edit's or a write's path is judged too, and under Kiro the folder of `execute_bash`.

- **A path that holds the model folder's path is denied.** A path the guard judges is denied when it
  holds the model folder's path anywhere, whatever its case — for a model folder `model`,
  `zz/yy/model/swc/Engine.yaml` and `notes/MODEL/x.md`; for `arch/model`, both folders in a row — and
  when it is written relative to the project and starts with the model folder's last part
  (`model/x.yaml`).
- **A path that ends like a model file is denied.** While `model/swc/Engine.yaml` exists,
  `elsewhere/swc/Engine.yaml` and the pattern `notes/**/swc/Engine.yaml` are denied: a client that
  looks a file up by its name could find the model's. The guard lists the model folder once per call
  to know those names. When it cannot list it whole — more than 100,000 files and folders, more than
  two seconds, or a folder it may not read — it denies every path of two or more parts until the
  model folder is readable again or holds less.
- **What these rules refuse that they need not:** another folder named like the model folder
  (`notes/model/x.md`), and a file outside the model whose last folder and name are a model
  file's (`notes/interfaces/Foo.yaml` beside `model/interfaces/Foo.yaml`). Rename that folder or
  file, or let the assistant use the SWCraft tools. A shell command's words are judged as the shell
  reads them, as before, not by these two rules.
- **Fixed: on Windows, a search pattern that starts with `~` is judged by the folder it names.** In
  0.23.0 the guard refused every such Kiro or Claude Code pattern on Windows, an allowed one
  included; it now judges them as on macOS and Linux.
- **Fixed: under a home folder whose path holds a pattern character, a `~` pattern is no longer
  allowed by mistake.** When the home folder's path holds a search pattern's character — `{`, `}`,
  `(`, `)`, `[`, `]`, `*`, `?`, `@`, `+`, `!` or `|`, such as a user folder named `John (Admin)` —
  the guard expanded the home folder as a pattern, into folders that missed the real one, so on
  macOS and Linux a `~` search pattern naming the model could be allowed. Under such a home,
  Claude Code's and Kiro's guards now deny every path and pattern that opens with `~`: write the
  path in full.
- **Every rule on one page.** The guide's new page *The model guard's rules* states every rule of
  the guard, for each assistant, and what each one does not reach.
- **Kiro.** The guard now follows how `kiro-cli` 3.3.0 and Kiro 1.4.178 find a file from a written
  path, as well as `kiro-cli` 3.1.0 (0.23.0: 3.1.0 and Kiro 1.4.121). `kiro-cli` 3.5.0's handling of
  paths was read: it tries fewer paths again than 3.3.0 —
  none whose shortened form is rooted at the home folder (`~` alone, or a `~` followed by a slash
  or a backslash) or rooted at a drive (a letter, a colon and then a slash or a backslash), and a file handed
  to a sub-agent under the same rule as a read — so every path it tries is one the guard judges
  already. A shortened form such as `~alice/x`, or `C:x` relative to a drive, is still tried.

## `.env` is read from your project only, and kept out of git

- **Where a `.env` is read:** from the folder you run `swcraft` from and each folder above it up to
  your project's folder, the one holding `swcraft.yaml`; outside a project, from the folder you run
  it from alone. The nearest file wins. A `.env` above the project, or in or above SWCraft's
  installation folder, is no longer read, and an installed SWCraft no longer looks for the AUTOSAR schema in
  a `schemas` folder of its own installation. Set `SWCRAFT_AUTOSAR_XSD_PATH` in your environment or
  in your project's `.env`; `swcraft validate` says *XSD validation is skipped* while the schema is
  not found.
- **Every `swcraft init` leaves `.env` ignored.** The template's `.gitignore` holds `.env`, a plain
  `swcraft init` writes a `.gitignore` holding it, and both forms add the one line `.env` to a
  `.gitignore` you already have that lacks it, keeping every other byte, and print `Updated
  <path> (added .env)`.

## `swcraft resource-report` names the project, not where it is stored

The report `swcraft resource-report` prints is headed by the project's name — *Resource utilization
report: swcraft-basic-example* — as the file `--report` writes already was. Before, the heading was
the model folder as given, so a run given a full path printed where the project is stored. No other
read-only command printed it.

## In VS Code: a selection named once, and the guide one click away

- **Diagrams.** In the diagram tab, a selected element is named once, in the line with **Open in
  model**; the status line under it stays empty until the selection is let go. A page opened in a
  browser shows what it showed before.
- **`guide` above a model element.** The line above an element's name — `references`, `impact`,
  `diagram` — ends with `guide`, which opens the guide's reference page for the file's layer in the
  guide tab, at the section of the element's kind: an interface at *sender_receiver*,
  *client_server* or *external_interface*, and the top of the page when the file's `kind:` cannot be
  read.

## Kiro: SWCraft's questions go to `guide` first

- **The steering file** `.kiro/steering/swcraft.md` that **Onboard Project** writes now tells the
  assistant: *For a question about SWCraft itself — how to do something, or what a refusal, setting
  or command means — call SWCraft's `guide` first, before any file, search, web or documentation tool
  of Kiro's: Kiro's documentation does not describe SWCraft.* Running **Onboard Project** again
  brings it into a project whose steering file it wrote; a file whose first line no longer says so
  is yours and is kept, so add the sentence to it by hand.
- **The guide's *In Kiro* page** says why a change Kiro proposes waits in the SWCraft review tab:
  the server's review mode is `panel`. Keep that value in `.kiro/settings/mcp.json`; `elicit`, the
  mode that asks in the client's own chat, is not the one to use in Kiro.

## Messages give the reason, not a reference

A refusal or a finding that ended with a reference to SWCraft's internal design records, such as a
decision number in parentheses, now ends with its reason, or simply ends: what was refused, why and
what to do are unchanged. `swcraft import model` into a project that already holds a model now says
the import *is refused* and offers `--force`, and an allocation experiment's line for a component
placed more than once says that *a move takes a component placed exactly once*. A script that
matched the end of such a message must match the new one.

**Fixed:** `swcraft experiment trace --labelling` given a number too long for Python's JSON reader
is refused as *a number too long to read*, where it stopped with an internal error.

## Also new in the guide

- *Import a component* says what an `ACCESS-POINTS` marker reading `explicit` means in a component
  export: that the file can state which accesses a runnable has, not that every access in it is
  explicit, so a component with implicit reads and writes carries the same word.
- *In VS Code* says that a Codex `app-server` left running keeps the `swcraft` it found when it
  started: after you change which `swcraft` comes first on your path, quit that process (or restart
  the computer).

## The specimen generator in the delivery

The workstation archive installs `swcraft-specimens` beside `swcraft`, at this release's version.
`swcraft-specimens specimen passport.json --out <dir>` writes a project of the shape a
`swcraft passport` file describes, and `swcraft-specimens generate small --out <dir>` writes one
from a packaged preset; either project's `swcraft.yaml` names this release
(`swcraft-specimens --help` lists the presets and the commands). It is installed into the same
environment as SWCraft and was checked against this release before publication; installing a
newer SWCraft replaces it. Nothing is downloaded separately.

- **The command is renamed.** Up to 0.23.0 the archive installed the generator as `carchetype`, at a
  version of its own; it is now `swcraft-specimens`, built from SWCraft's own source and carrying
  SWCraft's version, and `carchetype` is no longer installed. The commands, presets and options are
  the same.
- **NumPy and SciPy are ranges** in the generator's package (`numpy>=2.4.6,<3`,
  `scipy>=1.17.1,<2`); the archive still installs the exact versions it was checked with.
- **`--toolchain-version`'s help** says what the default is: the installed `swcraft-tools`' version
  when that is an exact release, otherwise none.
- **Five refusals** — four of the small project builder's and the one of a test scale — name what
  is refused, and no longer a stage of the generator's own development.

## The model's contract is `12.7.1`

`contractVersion` moves from `12.7.0` to `12.7.1`, by one patch: two entries of the contract's
development record are removed, and the reason a deprecation gives is one sentence in the present
tense. No layer, kind, field or rule is added, removed or renamed, and no key of the contract moves.
A `12.7.0` model is a valid `12.7.1` one.

## For contributors

The runtime pins did not move: `update-pins` rewrote nothing, so Node.js, CPython, `elkjs` and the
companion extensions are 0.23.0's.

- **The source layout.** The four Python projects live under `packages/`: `packages/tools`,
  `packages/mcp`, `packages/agent` and `packages/specimens`, each with its `pyproject.toml`,
  `src/<package>/` and `tests/`; the scripts' tests are in `scripts/tests/`. The distribution names,
  the import names and the commands are unchanged. A checkout made before the move runs `python
  scripts/dev.py install` once.
- **The development tools are a dependency group,** `dev`, in each project (`pip install -e .
  --group dev`), so no wheel declares a `dev` extra any more.
- **The specimen generator is built from this repository,** like the other projects: `dev.py
  install` fetches nothing for it and needs no key.
- **`.env` in a source checkout.** Run from a checkout, `swcraft` still reads the checkout's own
  `.env` last, after the folders up to the project's.
- **`CONTRIBUTING.md`** says how to build and run the gates, and the test rules a change follows. In
  the open repository `dev.py test-internal` says that its tests are not part of it and exits 0.

## What this release does not reach

- The guard's two new rules judge a path as written. A path that names the model folder with a
  pattern (`mod?l`), splits it with `..` (`arch/x/../model`), spells it in another Unicode form of the
  same letters or as a Windows short name (`INTERF~1`), a single name (`Engine.yaml`), a pattern whose
  last two parts hold a wildcard, a path that ends like a model file only once its `..` is applied,
  and a file added to the model while the guard judges the call are left to the guard's other rules.
- Under a home folder whose path holds a search pattern's character, Claude Code's and Kiro's
  guards deny every path and pattern that opens with `~`: write the path in full.
- The guard follows how `kiro-cli` 3.1.0 and 3.3.0 and Kiro 1.4.178 find a file from a written path,
  and `kiro-cli` 3.5.0 was read and found to try only paths the guard judges. `kiro-cli` updates
  itself; under a later release the guard's protection is not established until it is checked
  again.
- A Codex `app-server` left running keeps the `swcraft` it started with; quit it after changing
  which `swcraft` comes first.
- `swcraft init` recognises only a `.gitignore` line `.env` or `/.env`. A later `!.env`, a broader
  pattern and a global excludes file are not read, and a project that is not passed through
  `swcraft init` again adds the line itself.
- `Generated report: <path>`, which `swcraft metrics --report` and `swcraft resource-report
  --report` print, still names the written file in full, as every written file's announcement does.
- The specimen generator installed by hand, outside the archive, with other NumPy or SciPy versions
  may lay out a generated project differently from the archive's.
- The macOS archive is not signed, and no archive is: the sums file proves a download whole, not
  who made it.
- The requirements import and the linking of requirements in Trace Links are being reworked, so
  this release keeps the needs mapping file and the element picker as they are: the mapping file
  still says nothing of which side of a line is yours, and a port or a runnable still takes two
  picks.

## What upgrading takes

The new archive comes from the Releases page of `github.com/swcraft-dev/swcraft`; on macOS, clear
the quarantine flag on the unpacked folder before you run the installer. The guide's *Upgrading*
page has each step for a project, under *From 0.23.0*:

- **Add a `.env` line to your project's `.gitignore`**, if it has none, and commit it.
- **A setting kept in a `.env` above your project's folder, or in or above SWCraft's installation
  folder**, such as `SWCRAFT_AUTOSAR_XSD_PATH` or a key, is no longer read: set it in your
  environment, or move a setting that is not a secret into a `.env` in your project's folder.
  `swcraft validate` says *XSD validation is skipped* while the schema is not found.
- **An AUTOSAR schema kept in a `schemas` folder of SWCraft's installation** is no longer looked
  for there: where `SWCRAFT_AUTOSAR_XSD_PATH` is not set, `swcraft validate` checks the ARXML by its
  structure alone. Set `SWCRAFT_AUTOSAR_XSD_PATH` to the schema file, in your environment or in a
  `.env` in your project's folder.
- **A project used with Kiro:** run Onboard Project again, so that its steering file sends a
  question about SWCraft to `guide` first, and commit the rewritten file. A steering file whose first
  line no longer says Onboard Project wrote it is yours: Onboard Project leaves it and names it, so
  add the sentence by hand, from the table on the guide's *In Kiro* page.
- **Scripts:** spell `swcraft query … --format` in full where one passed `--form json` or a shorter
  abbreviation; match the new `hardware.missing-budget` sentences, and any refusal whose end named an
  internal reference; read the project's name, not the model folder, from the first line `swcraft
  resource-report` prints; call `swcraft-specimens` where one called `carchetype`.
- Nothing for a model: a `12.7.0` model loads, checks and generates as before.
