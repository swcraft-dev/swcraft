# SWCraft 0.5.0

**The documentation release.** It carries a user guide for the architect, the
integrator and the person upgrading, generated where it can be and gated where it cannot, shipped
as a release artifact — plus the two small pre-release items the first Windows run asked for: a
generated `.vscode/mcp.json` in scaffolded projects, and the extension's own gallery icon. The
model contract's prose moved to `1.4.3`; the YAML model, the editing protocol, the 13-tool MCP
surface and the emitted ARXML bytes are unchanged from 0.4.2.

Upgrade all four artifacts together, as always:

```
swcraft-tools==0.5.0
swcraft-mcp==0.5.0
swcraft-agent==0.5.0
```

plus `swcraft-vscode-0.5.0.vsix`.

---

## A user guide, built from the product and shipped with it

- `docs/guide/` is a MkDocs site: *Getting started*, *Working with the model*, *VS Code*, *The
  assistant*, *Command line*, *Diagrams*, *Upgrading*, and a **reference** section — the model's
  layers and fields, the checks, the CLI, and the MCP tools. It uses an architect's vocabulary; the
  engineering record keeps its own.
- **The reference pages are generated**, never typed: the layer-and-field reference and the page
  of checks come from the model contract (the contract's twelfth total consumer, with the same
  drift gate the editor schemas have), the CLI reference from the `argparse` tree, the tool
  reference from the live MCP registration. `python scripts/dev.py docs-reference` regenerates
  them; a stale page is a failing test.
- **The narrative pages are gated too**: every `swcraft …` command a page quotes exists and its
  quoted invocation runs; every VS Code command id a page names is in `package.json`; the
  vocabulary gate rejects engineering terms on user pages; links and navigation are checked.
- **The guide is a release artifact**: `python scripts/dev.py artifacts` builds it into
  `dist/docs/` as `swcraft-guide-<version>.zip`, listed in `manifest.json` and `SHA256SUMS` beside
  the wheels and the `.vsix`. The rendered site carries its version on every page.
- `README.md` shrank to an entry page pointing both audiences to their tree.
- **Honestly stated:** the eight narrative pages ship as **drafts** — each carries a draft marker
  until the product's author has read it, and `dev.py docs` reports which ones still do. The
  reference pages are not drafts; they are generated.

## The model contract `1.4.3`

Prose only, two patches. `1.4.2` rewrote the one description that still ended in a citation of an internal design record
(`swc.group`) so that the same text serves the editor's hover and the guide's page. `1.4.3`
reworded the `resources` layer's description to be state-neutral: it used to say "present here",
which is true where `discover` probes the project and false on a generated reference page. No
layer, kind, field or rule was added, removed or re-typed; `discover` output is byte-identical
apart from those two descriptions.

## `.vscode/mcp.json` is generated, not committed (scaffolded projects)

`swcraft init` writes two files: `.vscode/mcp.json.example`, the committed reference, and
`.vscode/mcp.json`, generated from it and listed in the scaffolded `.gitignore`. *Onboard
Project* and *Repair MCP Config* rewrite the generated file with the interpreter path the current
host uses, and the working tree stays clean — the first Windows run had shown the rewrite of a
committed file leaving the tree permanently modified.

**For an existing project nothing changes on upgrade, and nothing changes by itself.** SWCraft
does not untrack files in your repository. To adopt the new layout: add `/.vscode/mcp.json` to
the project's `.gitignore`, commit `.vscode/mcp.json.example` (copy it from a fresh `swcraft init`
or from the template), run `git rm --cached .vscode/mcp.json`, and run *Repair MCP Config* once
on each machine. Until you do, the committed file keeps working as before.

A note on the finding that prompted this: the template's `bootstrap.py` provisions a POSIX-style
`.venv/bin/` on Windows too, so the committed POSIX interpreter path was never broken there —
only its rewrite dirtied the tree. Whether VS Code's own process spawn resolves an
extension-less absolute path on Windows remains unmeasured; the change makes the question moot for
scaffolded projects rather than answering it.

## The extension has its own icon

`vscode_extension/package.json` now declares `icon` — a 128×128 PNG rasterised from the colour
mark the product's author designed (`media/icon-128-color.svg`, the committed source). The
Extensions view and a Marketplace listing show it instead of VS Code's placeholder; the
monochrome Activity Bar mark is unchanged. A packaging test pins the PNG signature and dimensions;
the bytes themselves are not pinned, since they depend on the rasteriser build.

## Also in this line since 0.4.0

The 0.4.x patch releases are folded in: `.likec4/` ignored in scaffolded projects (0.4.2);
`moon run :build` on native Windows and the `model_diff` stdin fix under the MCP server (0.4.1).
Their notes remain the record of each.

## Upgrade checklist

1. Install the four artifacts at `0.5.0`.
2. Open `dist/docs/swcraft-guide-0.5.0.zip` (or `dist/docs/site/index.html`) — the guide's
   *Upgrading* page is the reader's version of this file.
3. Optional, for a project that wants the generated `mcp.json`: the four steps above.
4. Nothing else: model, manifest, MCP configuration and generated ARXML are unchanged.

## Known gaps, recorded on purpose

- The guide's narrative pages are drafts until the author's pass; the draft report says which.
- Hosting the guide (Gitea Pages or the corporate site) and linking the walkthrough and the
  schema hovers to published pages are not decided; the artifact is built and hashed either way.
- The Windows half of the clean-host acceptance has still not run; the acceptance of the
  editor work stays open until it does.
