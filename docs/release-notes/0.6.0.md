# SWCraft 0.6.0

**Released 2026-09-01** (the bump commit; the tag follows the Windows sitting on this commit —
the Windows gate and the release acceptance).
Everything stated here was measured on the host that built it, at the commit it describes.

**This is the release that puts the hardware in the model.** Until now a project declared
*budgets* — a `cpu_core` with a number, a memory pool with a size — and the two places where
software meets hardware were matched rather than referenced: a task's `core` was an integer
compared against another integer, and an SWC's `memory:` keys were pool names that nothing
resolved unless the optional `resources/` layer happened to exist. This release replaces that layer
with `hardware/`: one processor, its cores and its memories, declared as model elements, mandatory
in every project. A task names the core it runs on. A component's memory budget names a memory that
exists. The budgets did not go anywhere — they moved onto the hardware that carries them.

**A second step then made the layer earn its place**, and this note is the combined story of the two:
one release, one migration, one contract major to absorb. Three things arrived with it. The
reachability check — a component may not charge a non-zero budget to a memory the core its task
runs on is not allowed to use — which is the first rule the flat pool layer could not have
expressed at all. The three surviving budget rules moved onto `hardware.*` names, so no rule identifier still carries the
retired layer's noun. And widening a memory's `accessible` list joined the acts the assistant must
ask about a second time, because with the check in place it is now a weakening like any other.

**Bounded reads are the third part, and they are on the other side of the product.** On a model of
the real size the assistant could not read the model it was supposed to work on: a `read` of one
layer can answer more bytes than any host lets a tool result carry. `read` and `impact_of` now answer in a declared **form**, every response is measured against
one server budget before it is sent, and an answer that would not fit is refused with the narrower
requests that would. The section *"What the agent sees on a model of the real size"* below has the
measurements. Nothing a project writes in YAML changes because of it.

**This release changes what a project writes in YAML.** It is the first one that does. Read
*"What an existing project must change"* below before you install it; the edits are three files
written and two small ones, and they are written out step by step.

Upgrade all four artifacts together, as always:

```
swcraft-tools==0.6.0
swcraft-mcp==0.6.0
swcraft-agent==0.6.0
```

plus `swcraft-vscode-0.6.0.vsix`.

## What an existing project must change

A model written for 0.5.3 does not load under 0.6.0. Nothing migrates it for you — there is no
compatibility window and no `swcraft migrate` command, by decision. A file the reader cannot parse
at all stops the run on that one file, so those arrive singly; once every file parses, the model
checks report together. The recipe below is the whole of it for a project with one core and one
memory pool; a project with more repeats step 1 per element.

**1. Write the hardware.** Create `model/hardware/` and put one file in it per element. A processor
is required, and exactly one is allowed:

```yaml
# model/hardware/CPU.yaml
name: CPU
kind: processor
description: The example processor — one core and one RAM, which is the smallest honest ECU.
```

Each old `kind: cpu_core` file becomes a `kind: core` file whose **name** is what tasks will use.
`threshold` and `enforcement` carry over unchanged; the old `core:` integer has no successor —
the name replaces it, and the physical core number the vendor prints goes in the new optional,
purely informational `hw_id` if you want it recorded:

```yaml
# model/hardware/CORE0.yaml
name: CORE0
kind: core
threshold: 0.7
enforcement: strict
description: Application core 0 — 70% CPU load budget from the concept document
```

Each old `kind: memory` file becomes a memory of the processor. `size`, `threshold` and
`enforcement` carry over; `type` and `accessible` are new and both are required — the memory's
kind in the AUTOSAR sense, and the cores the project permits to use it. **`accessible` is
checked**, so list every core whose tasks run components that budget this memory, not just the
one you happen to be thinking of:

```yaml
# model/hardware/RAM0.yaml
name: RAM0
kind: memory
type: RAM          # RAM | ROM | EEPROM | Flash
size: 262144
accessible:
- CORE0
threshold: 0.8
enforcement: strict
description: 256 KiB application RAM pool — 80% consumption budget
```

**2. Point each task at a core by name.** `core: 0` becomes `core: CORE0`. The field is a required
string now, with no default; an integer is refused when the file is read:

```
Error: Invalid task YAML in model/tasks/Task_10ms.yaml: 1 validation error for Task
core
  Input should be a valid string [type=string_type, input_value=0, input_type=int]
```

**3. Make each SWC's memory keys name a declared memory.** The `memory:` map keeps its shape — it
is still `{name: bytes}` — but every key must now resolve. If you renamed the pool while writing
step 1, rename the keys with it:

```yaml
memory:
  RAM0: 2048
```

**4. Delete `model/resources/`.** The directory is no longer read at all. Nothing reports it and
nothing cleans it up: a leftover `resources/` directory is silently ignored, which is exactly why
this step is on the list rather than left to be noticed.

**5. Run the gate.** `swcraft check-model --project swcraft.yaml` exits 0 when the four edits above
are done, and names what is missing until then. Running it after each step is the fastest way through:
each message states the element and the fix.

What you will see if you skip a step — every line below is from a real run of the recipe against
the shipped example, taken one step at a time:

```
  ERROR: Project has no hardware/ layer; it is mandatory (a processor, its cores and its memories).
  ERROR: hardware/ declares no 'kind: processor' element; exactly one is required.
  ERROR: Task 'Task_10ms' runs on core 'CORE1', which no hardware element declares (declared cores: CORE0).
  ERROR: Task 'Task_10ms' runs on 'RAM0', which is a memory, not a core.
  ERROR: SWC 'ExampleSWC' budgets memory 'RAM', which no hardware element declares (declared memories: RAM0).
  ERROR: Task 'Task_10ms' runs on core 'CORE1', but SWC 'ExampleConsumerSWC' budgets memory 'RAM0', which is not accessible from 'CORE1'.
```

The last of those is the one a *correct-looking* migration hits: every name resolves, and the
model is still refused because the memory's `accessible` list does not name the core the work was
put on. It has two honest repairs and the check picks neither — add `CORE1` to `RAM0`'s
`accessible`, or move `Task_10ms` back to a core `RAM0` already admits. If a multi-core project
was carrying that mistake before this release, this is where it surfaces.

And if you move the old files into `hardware/` unedited, the loader names the tag it does not
know, one file per run:

```
Error: Invalid hardware YAML in model/hardware/Core0.yaml: 1 validation error for tagged-union[Processor,Core,Memory]
  Input tag 'cpu_core' found using 'kind' does not match any of the expected tags: 'processor', 'core', 'memory'
```

A fresh `swcraft init` writes `hardware/CPU.yaml` and `hardware/CORE0.yaml` for you — a placeholder
core, `advisory` and uncapped — so a scaffolded project passes `check-model` on the first run. No
memory is scaffolded: a `size` is a hardware fact, and inventing one would put a number in the
model that a budget is later checked against.

**Re-running `init` over a project that already has a `hardware/` layer does not disturb it.**
Withholding is by *content*, not only by path: `hardware/CPU.yaml` is not written when the project
already declares a processor under any filename (`hardware/TC397.yaml`, say), and neither element is
written when the name it declares is already taken. Both are rules `check-model` enforces across
files — `hardware.multiple-processors` and `hardware.duplicate-name` — which the never-overwrite
rule alone does not see. A `hardware/` that does not parse withholds both; everything else `init`
writes is written as usual.

## The `hardware/` layer

- **Ten layers, all of them mandatory.** `resources/` was the one optional layer; `hardware/` is
  not optional, so `swcraft init` now creates ten model directories instead of nine.
- **Three kinds in one flat namespace**, discriminated on `kind` exactly as `data_types/` is:
  `processor`, `core`, `memory`, one file each, the filename matching the `name`. A name is unique
  across all three — `hardware.duplicate-name` refuses a repeat — which is what lets a task's
  `core` and an SWC's memory key be plain names.
- **A core is one schedulable, configured core.** A lockstep pair is declared once: it executes one
  instruction stream, and the model has nothing to say about the second. `hw_id` is the vendor's
  physical core number, optional and validated by nothing.
- **`accessible` is the allowed set** — the cores the project permits to use the memory, which the
  integrator configures the MCU's protection to enforce. It is a design statement rather than
  wiring: nothing generated from the model configures a protection unit. It is nevertheless
  **checked** against the work you put on each core — `hardware.unreachable-memory`, below — so
  the statement is one the model holds you to. What that check cannot see is the silicon: it reads
  what the project declared, not a linker script, a protection-unit configuration or a map file,
  none of which the model expresses at all. A memory declared reachable from a core that cannot in
  fact reach it passes every check in this release.
- **The budgets are unchanged arithmetic.** `threshold`, `size` and `enforcement` mean what they
  meant on the old resource elements, and `strict`/`advisory` behave as before.
- **`impact` sees the new edges.** Asking for a core now reports the tasks on it *and* the memories
  that admit it — `hardware RAM0 (accessible from CORE0)` — which a flat pool could not express.

## What `check-model` refuses that it did not before

Eleven cross-element and eight element-local checks, all reported by `check-model` before any
generation runs, all listed on the guide's checks page (`docs/guide/reference/rules.md`):

| Rule | What it refuses |
|---|---|
| `hardware.layer-absent` | The mandatory `hardware/` layer is absent from the project. |
| `hardware.no-processor` | No `processor` element is declared; exactly one is required. |
| `hardware.multiple-processors` | More than one `processor` element is declared; exactly one is allowed. |
| `hardware.duplicate-name` | The same hardware element name declared in more than one file. |
| `hardware.undeclared-core` | A task naming a core no hardware element declares. |
| `hardware.core-not-a-core` | A task's `core` naming a hardware element that is not a `core`. |
| `hardware.undeclared-memory` | An SWC memory budget for a memory no hardware element declares. |
| `hardware.memory-not-a-memory` | An SWC memory budget keyed by a hardware element that is not a `memory`. |
| `hardware.accessible-undeclared-core` | A memory's `accessible` naming a core no hardware element declares. |
| `hardware.accessible-not-a-core` | A memory's `accessible` naming a hardware element that is not a `core`. |
| `hardware.unreachable-memory` | A task on a core not permitted to use a memory its SWC gives a non-zero budget. |

**The last row is the one to plan around**, because it is the only check here that can refuse a
model in which every name resolves. For each task, for the core it runs on, for each component its
runnables belong to, for each memory that component charges more than nothing to: the core has to
appear in that memory's `accessible` list.

```
  ERROR: Task 'Task_10ms' runs on core 'CORE1', but SWC 'ExampleConsumerSWC' budgets memory 'RAM0', which is not accessible from 'CORE1'.
```

It fires once per task, component and memory, so two runnables of the same component on one task
are one finding rather than two, while two components budgeting the same unreachable memory are
two — dropping one component's budget repairs that component alone. It stays quiet where a rule
above it already spoke — a task on a core
nothing declares is reported by `hardware.undeclared-core` and not a second time here, and a task
entry naming a runnable its component does not declare is reported as that broken reference alone. A
single-core project cannot trip it as long as each memory lists that core, which is what the
migration recipe writes.

**A budget of `0` is deliberately not a use.** Under the default `enforcement: strict` a component
that writes no entry for a memory is itself a finding (`hardware.missing-budget`), so `0` is the
only way to say "this component uses none of that memory" — and on a multi-core project every
component that runs elsewhere needs exactly that for a memory private to one core. Reading a zero
as a use would put those two checks in direct conflict, so it does not: a zero-byte budget is not
reachability-checked, and the check starts asking about that memory the moment the number stops
being zero.

The element-local ones are the old resource checks moved across, plus two new ones:
`hardware.memory.accessible.non-empty-unique` (at least one core, no repeats) and
`tasks.task.core.not-blank`, which replaces `tasks.task.core.non-negative` now that the field is a
name.

**Three more checks were renamed rather than added.** The budget arithmetic is unchanged and so is
every message it prints, but the identifiers moved with the layer:

| Was | Is |
|---|---|
| `resource.missing-budget` | `hardware.missing-budget` |
| `resource.threshold-breach` | `hardware.threshold-breach` |
| `resource.rate-monotonic-violation` | `hardware.rate-monotonic-violation` |

After this release no check identifier names the retired layer at all. If you have a script,
a dashboard or a review checklist that matches on one of the three old names, that is the whole of
the change it needs.

**A behaviour was removed, not moved.** In 0.5.3, a task on a core no resource declared was
downgraded from an error to an information line when *every* declared `cpu_core` was `advisory` —
the gradual-adoption escape for a project that had not budgeted all its cores yet. It is gone.
`hardware.undeclared-core` is unconditional: with the layer mandatory and a core an identity rather
than a budget, a task naming a core that does not exist is a broken reference, and `advisory` is a
statement about a budget, not about whether the hardware is real.

**Hardware names are not checked against the AUTOSAR identifier rule.** `hardware/` is declared
`arxmlBound: false` and nothing in it is emitted as a `SHORT-NAME`, so the identifier check does
not read it — a memory named `shared-ram` is accepted, and was measured to be. The recommended
spellings (`CPU`, `CORE0`, `RAM0`, `PFLASH0`) are legal identifiers by convention, not by
enforcement. If a later release exports the layer as an ECU Resource Template, that check arrives
with it and a hyphenated name becomes an error then.

## Generated output that changed, and generated output that did not

**The ARXML did not move.** No `.arxml` golden changed in the whole release; the writer reads no
task, no hardware element and no SWC memory budget, and the reproducibility and XSD-conformance
suites are the oracle rather than an assumption. If your generated ARXML is not byte-identical
after this upgrade, that is a bug worth reporting.

**Three text surfaces changed, because a core is now named rather than numbered.** All three are
human-readable output, none is an interface anything parses:

- `generate c4` — a task's description reads `core CORE0` where it read `core 0`.
- `generate rst` — a core's field list is `:kind: core` with no `:core:` line, where it was
  `:kind: cpu_core` plus `:core: 0`.
- `resource-report` — the heading is `RESOURCE CORE0 (core, strict)`, where it was
  `RESOURCE Core0 (cpu_core, core 0, strict)`; the finding text is `CPU core 'CORE0' utilization …`
  and `Task 'Task_10ms' on core 'CORE0' declares no 'wcet_us' budget.`

**The command is still called `resource-report`**, and the report's section is still `RESOURCE`.
The first step left that question open and the second has decided it: no rename. The budgets are what the
command reports, its frame is its own name rather than the retired layer's noun, and a renamed
command would cost every work instruction and pipeline that quotes it a second migration for a
word.

**`resource-report` gained a section, and it is the part to plan around.** The three structural
checks the analysis used to run itself are contract rules now, reported by `check-model` and
`validate` (see *Python API: removed names* below), and the report does not re-run them. The blocks
are budgets and only budgets, so a task whose `core` names no declared core is still in no core's
arithmetic: it appears in no block and contributes to no total. What changed is that the report no
longer stays silent about it. Above the blocks it now prints one line per model-wide hardware
finding, with the check's name in front of the sentence `check-model` would print:

```
TOPOLOGY 1 finding(s)
  - hardware.undeclared-core: Task 'Task_10ms' runs on core 'CORE9', which no hardware element declares (declared cores: CORE0).
```

Measured on `examples/basic` with `Task_10ms` retargeted to an undeclared `CORE9`: the report exits
0 with that section, a `FINDINGS 0 error(s), 0 informational` summary — the counter is the budget
findings and does not absorb the topology ones — and a `RESOURCE CORE0 … STATUS within budget …
CONSUMERS 0 task(s)` block, while `check-model` on the same model exits 1. In 0.5.3 the same model
produced an `undeclared_core` finding in the report itself, and between the two releases it
produced nothing at all; the section is where that answer now lives.

**`resource-report` is still not a gate.** It exits 0 with a `TOPOLOGY` section in it, because it
reports rather than grades — the section is a reason to run `check-model`, not a verdict this
command has passed. **The assistant's `resource_report` tool renders the same section**, from the
same two calls composed at its own entry point, so the report a person reads and the one the
assistant reads do not answer differently. Where the fix does not reach is the document: **the
budget section of the generated RST renders the same arithmetic and carries no such section**, so a
model with a broken hardware reference produces a document that is silent about it. A build pipeline runs `check-model` before
it generates anything — that is what the command exists for — so the fact is refused upstream of
the document, which is why that gap is recorded here rather than closed. Read the generated
document on a model that passes the checks.

## `check-model` on a model of the real size: one layer read, not one per connector

On a model with many components, ports and
connectors, `swcraft check-model` was slow on 0.5.3 — and with it everything that shares its
composer: `validate` and `build` before generation, the MCP tool `check_connector_consistency`, and the
shadow validation of every assistant `change_set`. One line was the whole cost:
`check_connector_compatibility` opened by reading the entire `swc` layer, and the connector check
called it once per connector — one layer read per connector, all CPU
(the profile is kept in the
repository's engineering record). No example, showcase or test had more than a handful of connectors, so nothing noticed.

The connector check now reads the layer **once** and hands the map to each connector's check, so
its cost no longer multiplies by the connector count. No finding, rule, message or ARXML byte changed; the Python API is
shape-compatible (`check_connector_compatibility(model_root, connector)` still reads the layer
itself when handed no map, which is what `create_connector` relies on), and
`tools/tests/test_validator_scale.py` pins the count — one layer read for a thousand connectors —
so the per-connector re-read cannot come back unnoticed.

## What the agent sees on a model of the real size

A model of the real size has a second cost, on the other side of the product: the assistant cannot
read it at all. On 0.5.3 a `read` of a large `swc` layer answers many times more bytes on the wire
than a host that cuts a tool result at 25 000 tokens by default lets through. The response is correct
and complete, and the model sees a fragment of it that neither side can name. A read of a large
component, and `impact_of` of a hub interface, can be over that limit too.

**This release bounds the read side.** `read` and `impact_of` now answer in a **form**, every answer
is measured before it is sent, and an answer that would not fit is **refused with the narrower
requests that would** — never cut.

- **Three forms of `read`.** `full` is the whole element, exactly what 0.5.3 answered. `summary` is
  the same elements with fewer fields — the identity, the fields that place it, its `kind`
  discriminator, its required scalars, and a **count** for every collection it owns (`"ports": 4`).
  `index` is identities and a count — the projection `swcraft list` has had since 0.4.0 and the
  agent never had. No element is ever omitted from any of the three: what narrows is **width**, not depth.
- **The default depends on the address.** A layer address and a collection address answer `summary`;
  an element, a scalar field, a member and a map entry answer `full`. `index` is never a default.
  The response **echoes the form it answered in**, so a caller never has to know the table.
- **One budget, enforced on the server: 80 000 bytes on the wire** (≈ 20 000 tokens at four bytes a
  token, under Claude Code's 25 000-token default). It is a server constant — not a manifest field
  and not an environment variable, because a budget the model can raise is not a bound — and
  `discover` publishes it so a client can read it.
- **Above it, a refusal.** The eleventh editing-protocol error code, `over-budget`, failure class
  `invalid`, carrying `measured` (`wire_bytes`, `budget`, `elements`) and `hints` — complete,
  narrower `read` requests in the order `full` → `summary` → `index`. The agent replays a hint
  rather than guessing.
- **`impact_of` gains the pair**, `summary` (the count and the identities per layer, no detail
  strings) by default and `full` on request, both measured against the same budget. It is a
  plain-text tool, so its refusal is text and names the same three figures.

### Before and after

Every measurement here is **wire bytes** through an in-memory MCP client, taken by
`scripts/measure_mcp_scale.py` on 2026-08-31. A wire byte is what the host
receives: one tool result goes into the JSON-RPC message twice — as a compact structured document,
and as that document again escaped into a text block — and both halves are counted. The "before" is
a `read` with **no form**, which is the only thing a layer address could mean on 0.5.3; every "after"
names its form, because a before/after comparison that does not is comparing two different
questions. A **refused** answer is measured by the refusal's own `measured.wire_bytes` — a response
that was never sent has no size to count.

Checked against real tool exports the maintainer holds privately, the default forms answer within
the budget where the formless reads were cut, and the demo film's two work-instruction prompts
answered most of their calls and refused the rest, with **no answered response above the budget**.
`discover` has no forms and was not bounded by this part of the release: its size is a function of
the contract and not of the project.

The one comparison that is the release in miniature: the request an agent makes when it says
nothing — `read {"layer": "swc"}` — went from an answer the host cut to one that fits, for the same
call.

### What still does not fit, named rather than implied

Some refusals end a chain that is *exhausted* — every narrower form is over budget too. On a large
model three shapes are over it; they are outcomes, not defects:

- **`impact_of` of a hub interface can be refused in both forms.** The design expected the `detail`
  strings to be the bulk of that report; they are not — the **identities** are, generated ARXML
  names, so dropping the details saves little, not an order of magnitude. On 0.5.3 the same call
  answered and the host cut it; now it refuses and says why. The `full` refusal names the summary, so
  it is the `summary` refusal — and the default, which *is* the summary — that ends the chain.
- **A large `connectors` layer can be refused in all three forms** — its generated names are over
  the budget as an index alone.
- **A large component's `ports` collection summary can be refused** while its `index` answers — so
  the chain is one step longer there, not exhausted.

What answers a request like those is a filter, a page or a bounded traversal depth, and all three are
the model query's — **which is in this release too**, in *Asking for less: the model query surface*
below. The two exhausted chains above are gone: the `connectors` layer answers as a paged index and
the hub interface's `impact_of` answers at depth 1 with a page, each in one further call the refusal
names. This subsection is kept as the record of what the bounded reads alone left.

And one thing the bounded reads deliberately did **not** bound — closed later in this release by the model
query's `discover` forms, and kept here as the record of the state that motivated them: **`discover`**, just
under the budget and, after the bounded reads, the largest single response the agent reads.
Its size is a function of the **contract**, not of the project, so a larger model does not push it
over; the next contract version that adds a layer's worth of declarations would. The `reads` block
the bounded reads added to it costs a few hundred of those bytes. That is the argument the query section answers: `discover`
is now measured against the same budget, its default strips the prose, and the narrower `discover`
that "is a different operation" is exactly what its hints offer.

### What a protocol client sees

The editing protocol's schema gains five keys, two of them **required**, so a client that parses the
closed shapes must know them:

| shape | key | required | what it carries |
|---|---|---|---|
| `readRequest` | `form` | optional | `summary` \| `full` \| `index`; omitted means the default for that address |
| `readResponse` | `form` | **required** | the form actually served |
| `discoverResponse` | `reads` | **required** | `forms`, `default_form` per address shape, `budget_wire_bytes` |
| `errorResult` / `errorDetail` | `hints` | optional | the narrower `readRequest`s, in chain order; absent when the chain is exhausted |
| `errorResult` / `errorDetail` | `measured` | optional | `wire_bytes`, `budget`, `elements` |

`errorCode` gains its eleventh member, `over-budget`, mapped to failure class `invalid`. Neither
`hints` nor `measured` is set by any other code, so every existing rejection is byte-identical. The
editing-protocol vector corpus grows from 43 to **46**: the over-budget refusal, a layer summary and
a collection summary. Nothing about **writing** moved — `change_set`, the shadow validation and the
reviewed-delta guarantee are untouched, and the size of a change set's delta is still unbounded, and
this release does not bound it.

The MCP **tool count is unchanged at 13**: a form is a parameter, never a tool. `swcraft impact`,
`swcraft list` and every other command answer exactly what they answered on 0.5.3 — the budget is
the server's, and the CLI is not a host with a context window.

## Asking for less: the model query surface

The bounded reads made every answer *fit*. It did not make it easy to ask a **small question**: an agent
that wanted the ports using interface A still read a whole layer and filtered in its own head, and
two calls on a large model can have no answer in any form — a large `connectors` layer (over the
budget as an index alone) and `impact_of` of a hub interface (over it as a summary). Both are recorded two sections above as dead ends.
**The model query is the other half: the ways to ask for less.** It adds **no tool** — the count is
still 13 — and no index and no cache; every request is still computed from the files it reads.

- **A filter.** `read` takes `where`: an AND-composed list of `{"field", "equals"}` and
  `{"field", "exists"}` clauses over the fields the **contract declares**, applied at a layer
  address (which elements) or at a collection address (which members), evaluated before the form
  and echoed back in the response. A field no kind at that address declares is refused as
  `unknown-field` — never a silently empty answer, because *I mistyped* and *the model holds none*
  are different facts and one of them is a client bug. `{"exists": false}` and `{"equals": null}`
  are also different questions and answer differently.
- **A page.** `read` takes `limit` and `after` and answers a `page` block —
  `{total, returned, truncated, next?}` — in the order every form already publishes in (kind rank,
  then reader order). It is a **keyset**, not an offset: the model is re-read from the files on
  every request, so an offset silently skips an element when the set moves underneath it, while a
  cursor either continues exactly where it stopped or is refused as `broken-reference`. `total` is
  post-filter and pre-page, so the count is always the whole answer's, and `truncated` is not
  derived from `next` — the last page of a walk is truncated and has no successor.
- **A member slice.** `read` takes `members: "<collection field>"` at a **layer** address and
  answers every member of that collection across the layer, each row carrying the owning element's
  identity beside the member. This is the one question no address could ask — a `path` without an
  `element` is not an address — so it is a request key rather than a new address shape. It composes
  with the filter and the page: *every port on interface A, with its owner*, is one call.
- **A forward direction and a bounded depth.** `impact_of` takes `direction` (`dependents`, the
  default, or `dependencies`), `depth` (a level bound, or the whole transitive walk when omitted)
  and `limit`/`after` over the bounded walk's listing. *What does this component depend on* was not
  expressible before. `depth: null` is served by the same walk 0.5.3 had, in the same emission
  order, so `swcraft impact`'s output is byte-identical — the bounded walk is a second traversal
  beside it, and neither claims a minimal hop count.
- **One CLI subcommand over the same engine.** `swcraft query LAYER [--where FIELD=VALUE]
  [--exists FIELD] [--members FIELD] [--limit N --after ID]` and
  `swcraft query --dependents NAME | --deps NAME [--depth N]`, with `--format text|json`.
  Read-only, and exits 0 on any run that could read the project — the `swcraft list` precedent. The
  three read commands divide deliberately: `list` is identities in reader order, `query` is filtered
  and paged slices in the published read order, and `impact` is the frozen transitive report whose
  bytes nothing here moves.

### `discover` answers a summary now — a behaviour change for every MCP client

This is the one change in this release that an existing client sees **without asking for anything**,
and it lands on the largest single response the agent reads.

`discover` gains a `form`, and its default is **`summary`**: every descriptor `description` is
stripped, at every depth — on layers, kinds, fields and enum members — and **nothing else** is. The
types, enums, units, references, collections, identity and placement facts, the `present` map, the
passport and the `reads` block are all still there, so an element can still be authored off the
default answer. The first call of every session shrinks to well under half its wire bytes, on
every project, since its size is the contract's.

- **The escapes are named, and each is one request.** `form: "full"` is the document `discover` answered before the model query,
  prose included (plus the echoed form and the two new capability keys); a
  `layer` argument answers one layer, in either form. The response echoes the form it served.
- **`discover` is measured and refused against the same 80 000-byte budget as a read**, which makes
  `over-budget` a refusal of both read-only operations rather than of `read` alone. A refused
  discovery is **addressless** — it was not addressed at all — so it carries no `addresses` key, its
  `measured.elements` counts the layer descriptors it did not send, and its `hints` are *discover*
  requests: the project-wide `summary` first, then one discovery per declared layer.
- **Two tripwires, deliberately asymmetric** (`tools/tests/test_discover_budget.py`). The default
  must stay under the budget with a **≥ 50 % margin** (measured 61.4 %); `full` must merely be
  `≤ budget` — it sits at 97.98 % and there is no room to reserve one. Said out loud, because it is
  the regime working rather than a regression: **the first contract growth that pushes `full` over
  the budget makes `full` discover a refusal on every project**, answerable as `summary` or one
  layer at a time. The prose lives on in the editor's hover, in the guide and in the per-layer
  `full`, and the refusal's hints name both routes.
- The response is a function of the **contract**, not of the project.

### Before and after, with the query surface

Measured 2026-08-31 by `scripts/measure_mcp_scale.py` in the same wire unit as the bounded reads'
measurements above, and checked against real tool exports the maintainer holds privately:

- `discover` with no form named answers the `summary`, well under half the bytes it answered before;
  `discover form="full"` is the same document as before, plus the echo and two capability keys.
- A `connectors` layer whose chain was exhausted at `index` is refused and its hint — `index`
  with `limit=50` — **answers**, with a page that says it is truncated: the keyset page and the
  chain's paged step.
- `impact_of` of a hub interface, whose chain was exhausted, is refused and its hint — `depth=1,
  limit=50` — **answers**: the bounded depth and the page.
- Every port on one interface, with its owners, was an element read per component or a refusal; it
  is **one call**, the member slice.
- What a component depends on was not expressible; it is **one call**, the forward direction.
- The film's two prompts, with the exit gate's own calls added, leave **no exhausted chain**.

No answered response is above the budget, and `swcraft impact` is byte-identical on every baseline
taken *after* the replay, so the same measurement also witnesses that its staged change set applied
nothing.

### What a protocol client sees, second half

On top of the bounded reads' five keys the schema gains **nine** more, one of them **required**. Two of the
seven rows below carry a pair, because the keys they name are one decision each:

| shape | key | required | what it carries |
|---|---|---|---|
| `readRequest` | `where` | optional | at least one `{"field", "equals"\|"exists"}` clause; AND-composed |
| `readRequest` | `limit` / `after` | optional | the page size (≥ 1) and the identity to continue past; `after` needs `limit` |
| `readRequest` | `members` | optional | the collection field to slice across the layer |
| `readResponse` | `where` / `members` | optional | echoed when the request carried them |
| `readResponse` | `page` | optional | `{total, returned, truncated, next?}`, present when the request carried a `limit` |
| `discoverRequest` | `form` | optional | `summary` \| `full`; omitted means `summary` |
| `discoverResponse` | `form` | **required** | the form actually served |

`readsCapability` grows two keys of its own — `hint_page_size` (the page size a refusal's hint asks
for, **50**) and a nested `discover` block with that operation's forms and default — so a client
reads both bounds and sets neither. `hints` items are now a `readRequest` **or** a
`discoverRequest`; a `change_set` is refused as a hint by name, on both sides. `errorResult`'s
`addresses` is omitted entirely on a refused discovery. The vector corpus grows from 46 to **50** —
a filtered layer read, a paged one, a filtered member slice, and `discover-project-full.json`, which
is where the shipped-prose oracle now rides. Nothing about **writing** moved.

### What the query surface does not reach

- **Comparison operators and `or`**, by decision: one operator is a vocabulary, three are a query
  language. *Every task with `period` below 10 ms* is served as a bounded projection the caller
  compares client-side, and that is the shipped answer, not a gap waiting on a later release.
- **A `where` across layers** (a join), free-text search, and any index or cache.
- **`impact` as a protocol operation.** `impact_of` stays a plain-text MCP tool, so its refusal is a
  sentence rather than an `errorResult`, and its chain is textual: it names the next request in the
  same sentence shape. There is no `impactRequest` in the schema.
- **A hint never changes the address.** The chain offers a narrower form, a page of the same
  address, or a narrower discovery; *descending into a collection* stays the agent's own move,
  taught by the prompts.
- **A single element or member whose own published value exceeds the budget** still has no answer —
  the refusal's `measured` block is what it gets until one
  exists.
- **The page over a walk is the MCP tool's, not the CLI's.** `swcraft query --dependents` answers
  the whole walk; `--limit`/`--after` window a `LAYER` slice and are refused beside a walk by name.
- **The `swcraft query` figures are not wire figures.** A CLI answer goes to a terminal and is
  bounded by nothing: `--deps` of a large component can be far over the budget and is correct.
- **One host, one date.** `~tokens` is bytes / 4 with no tokenizer, and the VS Code
  agent smoke on a packaged host is deferred to the Windows/showcase sitting.

## The model's contract is `3.0.0`

`contractVersion` moves from `1.4.3` to `3.0.0`, and `SUPPORTED_CONTRACT_MAJORS` becomes `{3}`: a
`1.x` document is refused when it is loaded, with the supported set in the message —
`contractVersion '1.4.3' declares major 1, which this repository cannot read (supported: [3])`.

**Two majors, one migration.** The layer replacement was major 2 and the rule rename is major 3,
and both land in this release: nothing in `2.x` ever reached a user, so there is one document to
move to rather than two. Had `0.6.0` shipped between them, the right answer would have been to keep
the historical identifiers and pay nothing — a cosmetic rename does not earn a second breaking
change on a released product.

The major is not about the meta-schema, whose shape is untouched — six of its prose strings were
reworded and no key was added, removed or made required. It is about identifiers, which the contract's
decision record makes its public surface: this release **removes 29 of them** — `layer:resources`, both
`kind:resources.*`, twelve `field:resources.*` and fourteen rule ids — and adds 43. A consumer
authored against `1.x` that read a `3.0.0` document would find those entries silently missing, and
the version refusal is what turns that into an error instead. The inventory goes from 10 layers,
28 kinds, 109 fields and 101 rules to 10 layers, 29 kinds, 114 fields and 109 rules.

**No rule identifier survives the move.** The three budget rules kept their arithmetic and their
messages but not their names — the table under *What `check-model` refuses* has the three pairs —
and one identifier, `rule:hardware.unreachable-memory`, is new. Renaming an identifier is what makes
this the third major rather than a second patch.

`contractVersion` is deliberately not one of the five product lockstep sites; the product version
and the contract version move independently, and this release happens to move both.

## Python API: removed names

Importers of `swcraft_tools` internals — the packages ship no stability promise for these, but the
list is short and worth having:

- `schema.CpuCoreResource`, `schema.MemoryResource` and the `schema.Resource` union are **deleted**.
  The replacements are `schema.Processor`, `schema.Core`, `schema.Memory` and the discriminated
  union `schema.Hardware`.
- `reader.read_resources` and `reader.find_resource_file` become `reader.read_hardware` and
  `reader.find_hardware_file`, with the same one-line shape over `read_layer`.
- `resource_analysis` keeps its public entry point, `analyze_resource_budgets`, and its arithmetic
  to the last `Fraction`. What went is the layer between it and the model: the first step of this
  release copied each hardware element into a private budget record and computed over that, and the
  second deleted the copy.
  `ResourceUsage.resource` is now the declared `schema.Core` or `schema.Memory` itself, published
  from the module as the alias **`Resource`**; the alias `Budget` is gone with the records it
  named. The discriminator `is_core_budget(resource)` is renamed **`is_core(resource)`** and is
  still the seam a renderer uses, so no consumer of this module has to import a schema class to
  tell a core from a memory.
- `ResourceAnalysis.findings` — the model-wide findings list — is **deleted**, and
  `ResourceAnalysis.all_findings()` now walks one level instead of two. It had no producer left:
  the three
  structural checks that used to fill it (duplicate resources, unresolved memory pools, core
  coverage) are contract rules now, reported by `check-model`. Per-resource findings are unaffected
  and still live on `ResourceUsage.findings`.
- `resource_report.resource_report(model_root)` takes a second, optional argument — the topology
  records to render above the blocks — and `ResourceReport` carries them as `topology`. It defaults
  to empty, so a caller that passes only a model root keeps the report it had. The renderer does
  not fetch the records: each of the two entry points that already imports the validator — the
  command line and the MCP tool — calls the check and hands the result over, so the report module
  still imports nothing from the validator.

## The editor, the assistant and the guide

- **The editor schemas follow the contract**, as designed: `vscode_extension/schemas/` ships
  `hardware.schema.json` in place of `resources.schema.json`, bound to `**/hardware/*.yaml`, with
  completion, hover and enum checking for the three kinds. As before, the editor helps and
  **`swcraft validate` is the gate** — the schemas check neither cross-element references nor
  budgets.
- **The MCP surface is still 13 tools**, with the same names, and all three read-only ones grew
  optional arguments: `read` takes `form`, `where`, `limit`, `after` and `members`; `impact_of`
  takes `form`, `direction`, `depth`, `limit` and `after`; `discover` takes `layer` and now `form`
  (see *"What the agent sees on a model of the real size"* and *"Asking for less"*). No tool was
  added, renamed or removed — the width and the shape of an answer are parameters. What the surface
  *sees* changed with the layer: `discover` reports the `hardware` layer and no longer reports
  `resources`, and its collection inventory goes from 12 to 13 (the memory's `accessible` list). The
  editing-protocol vector corpus grows from 38 to 50 — 43 with the hardware layer, three more with
  the bounded reads, four more with the query surface.
- **The safety review is re-keyed to `hardware`, and it grew a fifth act.** Raising a `threshold`,
  enlarging a `size`, flipping `enforcement` to `advisory` and deleting a core or a memory are
  still four of the acts that make the assistant ask a second question; the prompt still reads
  *"This change set weakens a resource check."* and the rendered line names the element as a
  hardware element now. The fifth is **admitting a core to a memory's `accessible` list**, which is
  a weakening for the same reason the other four are: with `hardware.unreachable-memory` in this
  release, widening the list stops a check firing that the project was relying on. The reviewer is
  shown the cores admitted rather than two nearly identical lists —
  `hardware element 'RAM0': accessible admits CORE1` — and the direction matters: **withdrawing** a
  core is not a weakening and is not asked about, and neither is reordering the list.
- **An approved scope naming the `resources` layer covers nothing any more** — the scope is
  composed per request on a host channel, so there is no stored setting to fix, but a script that
  builds one from a layer name needs `hardware` in it or the change is refused as an unauthorized
  delta.
- **The guide is regenerated.** `docs/guide/reference/model/hardware.md` replaces the resources
  page, the checks page carries the new rules, and the narrative pages describe the layer rather
  than the pools. The guide's *Upgrading* page points at this file for the recipe.

## Known gaps, recorded on purpose

Named here so nobody reads their absence as an oversight. The two gaps the first step recorded — that
`accessible` was declared and enforced by nothing, and that the analysis still ran on an adapter
with the budget rules spelled `resource.*` — are **closed by the second step and are in this release**; what
follows is what is still open at the end of it.

- **The reachability check is a declaration check, not a placement check.** It says whether the
  project *declared* the memory reachable from that core. Nothing in the model expresses a linker
  script, a protection-unit configuration or a map file, so a memory declared reachable from a core
  that cannot in fact reach it passes, and the integrator is still the one who makes the silicon
  agree with the list. This release does not add a way to state the placement.
- **Affinity is out of scope.** A task is pinned to exactly one core. There is no way to say that a
  task may run on any of a set of cores, and the reachability check therefore asks its question of
  one core rather than of a set.
- **The generated RST keeps the blind spot the report lost.** `resource-report` now prints its
  `TOPOLOGY` section; `generate rst` does not, and renders budgets only. Run `check-model` before
  generating and the difference never shows.
- **The hardware layer reaches no diagram.** `generate c4` names a task's core in a description and
  nothing more; whether the processor, its cores and its memories should appear as LikeC4 elements
  is an open question, not a decision already taken.
- **No migration tooling.** The recipe above is the migration, and nothing detects a project that
  has not run it beyond the errors `check-model` reports.
- **A set address no longer dead-ends, but a single value can.** *Refuse, never cut* is the shipped
  behaviour, and the model query's paged step means a layer, a collection or a member slice always has a
  further request to offer: the `connectors` layer and the hub interface's `impact_of` — the
  chains the bounded reads measured as exhausted — both answer now, in one further call each. What can still end
  a chain is **one element or one member whose own published value exceeds the budget**: nothing
  narrower exists for it, and its refusal's `measured` block is the whole answer.
- **`full` discover has no margin.** It sits at 97.98 % of the budget, so the first contract growth
  that pushes it over makes `form: "full"` a refusal on **every** project — by design, with the
  `summary` default and the per-layer discovery as the routes its hints name, and with a tripwire
  that fails the build the day it happens. The default form keeps a 61 % margin.

## Upgrade checklist

1. Read *"What an existing project must change"* above, in full, before installing.
2. Install all four artifacts at `0.6.0`, the extension included.
3. Make the four model edits above, running `swcraft check-model --project swcraft.yaml` after each
   one until it exits 0 — which is step 5 of the recipe. On a project with more than one core,
   expect `hardware.unreachable-memory` to be the last one to go quiet: it is the only check here
   that can refuse a model in which every name already resolves.
4. Run `swcraft validate --project swcraft.yaml` and compare the generated ARXML with what you had:
   it should be byte-identical.
5. If you migrate by re-running `swcraft init` over the project, read the `Skipped` lines: the two
   `model/hardware/` elements are withheld from a layer that already declares a processor or the
   name they carry, so `init` adds only what is missing and never a second processor.
6. Run **SWCraft: Onboard Project** once so the editor picks up the new schema bindings.
7. Note that going back to 0.5.x means taking the model back with it — a `hardware/` model does not
   load under the older version any more than a `resources/` one loads under this one. Keep the
   pre-migration model reachable in version control until you are satisfied.
