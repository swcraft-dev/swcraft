# SWCraft 0.11.0

> **Withdrawn 2026-09-15 — do not install this release.** On a large model and a corporate Windows
> workstation, the two things it was released for did not work: the
> install took over thirty minutes with no output while the anti-virus scanned the 7 535 files of
> the diagram viewer, and a connector from a component to itself made the viewer reject the
> whole diagram set with `generate c4` at exit 0. Use 0.10.1 until the next release. Nothing here
> is patched: the viewer is being replaced, not repaired.

**Released 2026-09-15** (the bump commit; the tag follows the `verify` gate on both self-hosted
runners, Linux and Windows, on this commit, and the tag's own run publishes the release archives to
the NAS). This note was written with each change rather than after it, so every figure below was
measured on the host and at the commit that produced it — macOS, CPython 3.11.13, 2026-09-11 to
2026-09-15.

## Two names that differ only in case are two elements, and now two files

`float32` and `Float32` are two legal, distinct AUTOSAR names, and a type library commonly declares
both. SWCraft wrote each element to a file named after it, and macOS and Windows hold
`float32.yaml` and `Float32.yaml` as **one** file — so the second write replaced the first without
a word. An import could write its data types into **fewer**
files than it has types on macOS; the report counted every type and nothing failed, because nothing referenced the lost
spelling.

From this release every writer — `swcraft import model`, `swcraft import component`, and every edit
the assistant makes — decides a file name the same way, on every operating system:

- **The plain name, unless another file already holds it compared without regard to case**, in
  which case the file takes the nearest free `~1`, `~2`, …: `Float32.yaml` beside
  `float32~1.yaml`. The occupancy question is answered from the directory's own listing and never by
  asking the filesystem, so Linux, macOS and Windows write the same tree.
- **The suffix belongs to the file alone.** The `name:` inside, every reference to the element and
  every generated ARXML, diagram and requirements byte are exactly what they would be without the
  collision.
- **An element already in the model keeps its file.** It is found by the name inside its file —
  never by a file name recomputed from the name — and an edit, or an import that overwrites it,
  writes there. Only an element no file declares is given a file name.
- **Elements are read and written out in an order decided by their names** (components within their
  group) — the order their files always had when each was named after its element — and never by
  what a file is actually called, so renaming a file changes nothing SWCraft generates. You may
  drop a `~1` once no other file holds the plain name; nothing drops one for you.

Now there is **one data-type file per type**, a colliding one suffixed, and
every other layer at one file per imported element as before.

**Both import reports gain a section, *Files suffixed for a case-insensitive collision*,** with one
line per suffixed file naming the element, where it came from, the file written and the file name
that was taken. Both `--dry-run`s list the lines the import itself would report, because each
decides every file name the way the import does without writing one — with one exception: when the
export carries a root composition of its own, `swcraft import model --dry-run` on a freshly
initialised project previews a suffix for an imported composition whose name differs from the
scaffolded `Root` only in case, which the import does not take, because the import removes that
empty scaffolded root before it writes the compositions.

**`swcraft import component` no longer stops on a taken file name.** Until this release it aborted
the whole import when a new element's file name was already held — *"… its derived path … is already
occupied by …"* — or when two new elements of one import differed only in case — *"… would all create
the file …"*. Both are now a success with a report line and a suffixed file. A script that matched
either abort sentence will not see it again. Every other reason the import stops is unchanged —
among them a name the project declares in two or more files, and a shared interface or data type
whose definition diverged.

**`swcraft check-model` reports one new finding**, `rule:storage.filename-case-collision`: two files
of one layer directory whose names differ only in case. Only a case-sensitive filesystem — Linux,
typically — can hold that tree, and a checkout of it on macOS or Windows would silently keep one of
the two, so the finding asks you to rename one file. It fires nowhere else, because on macOS and
Windows the tree cannot exist. While a project holds such a pair the assistant refuses every change
to the model, since its edits are checked against every finding, until the file is renamed by hand.

**The assistant's answers never name a file**, and that has not changed: an element the assistant
creates under a suffixed file is answered exactly as one created under its plain name, and the file
is recorded in the project's audit log.

**Upgrading.** Nothing to do for a project whose files are named after their elements and which
holds no two files differing only in case: it reads, orders and generates exactly as before, and no
key changes. Two cases differ. If a checkout on Linux holds two files of one layer whose names differ
only in case — which an earlier `swcraft import model` wrote there for a type library declaring both
spellings — `swcraft check-model` now fails, and so does `build`, and the assistant refuses every
change until you rename one of the files. And if a file's name differs from the name inside it, the
element keeps its content and takes its place by its name: in the generated files and in
`swcraft list` and `swcraft query` answers it sits where a file named after it would sit.

**What this does not reach.**

- Two names that differ only in how an accented letter is encoded (Unicode normalisation) are not
  compared: macOS treats them as one file name and Windows does not.
- Two component **group** directories that differ only in case are not reported.
- `swcraft import component` plans a file name from the project as it is when you run it; if the
  project changes before the assistant commits that same import, the file it commits may differ,
  and nothing re-checks the two against each other.
- A model file that does not parse is reported under the name its file spells, suffix included,
  because its name cannot be read from inside it.

## A data type is a base type, a value type or a reference type

`primitive` and `alias` are gone. A data type file declares one of six kinds — `base_type`,
`value_type`, `reference_type`, `enum`, `record` or `array` — and the first three are AUTOSAR's own
split:

- a **`base_type`** says how the platform stores a value — its `size`, its `encoding` and its
  `native_declaration`, the C type name — and is written as one `SW-BASE-TYPE`;
- a **`value_type`** is the type an interface uses: its `base` names a base type, and it may carry
  `unit`, `value_min` and `value_max`. It is written as an `IMPLEMENTATION-DATA-TYPE` of category
  `VALUE` that references the base type;
- a **`reference_type`** names a value type or another reference type as its `base` and carries
  nothing else. It is written as an `IMPLEMENTATION-DATA-TYPE` of category `TYPE_REFERENCE`.

A data element, an operation argument, a record field and an array element name a value type, a
reference type, an enum, a record or an array, and **never a base type**. `swcraft check-model`
reports a reference to the wrong kind or to a type that is not declared, the assistant refuses a
change that makes one, and `swcraft generate arxml` refuses to build it. A base type, value type or
reference type file carrying a key its kind does not have — a `base` on a base type, a range on a
reference type — does not load at all, and the file is named.

**Every model that declares a data type generates different ARXML.** SWCraft no longer invents an
`IMPLEMENTATION-DATA-TYPE` named `{name}_impl` beside each primitive: every `SW-BASE-TYPE` and every
`IMPLEMENTATION-DATA-TYPE` in the file is one your model declares, under the name it declares, and the
base types are listed before the value types. After the upgrade below, a data element that pointed at
`/DataTypes/float32_impl` points at `/DataTypes/float32`, and the `SW-BASE-TYPE` is named after the new
base type (`float32_base`). A name ending in `_impl` is no longer reserved.

**`swcraft import model` keeps a type chain as the export declares it.** Each `SW-BASE-TYPE` is
imported as a base type, each `VALUE` implementation type as a value type over it, and each
`TYPE_REFERENCE` implementation type as a reference type naming the type it references — one link,
however deep the chain. Nothing is flattened any more, so the report's *Alias chains flattened to
their primitive* section is gone with the loss it reported.

**One invented type is left, and it is not new.** An application data type that the export maps to
an implementation type of another name is still written as a data type of its own: a reference type
naming that implementation type. The previous release wrote the
same stand-ins as `alias` types and emitted them with category `VALUE`; they are now emitted with category
`TYPE_REFERENCE`. They stay for now because SWCraft has no kind for an application type yet, and
without them every data element, argument, record field or array element typed by one would name
nothing. A later release gives application types a kind of their own and stops writing these
stand-ins.

**`swcraft import component --update` now stops as a conflict when a shared base type declares a
native declaration on one side and none on the other**, naming both values, where it used to reuse
your project's base type without a word — declare `native_declaration` on your project's base type,
or take the incoming value by editing your project to match, and import again.

## Upgrading a project's data types

The eight steps below turn a project's `primitive` and `alias` files into the new kinds. Nothing else
in the project changes, because every declared name stays where it is used.

1. **Split each `kind: primitive` file in two**: the file you have, and one new file beside it.
2. **The file you have keeps its declared `name` and becomes `kind: value_type`.** Keep its
   `description`; move `size`, `encoding` and `native_declaration` out of it.
3. **The new file is `kind: base_type` and carries `size`, `encoding` and `native_declaration`.**
   Always write `native_declaration`: the value the primitive declared, or — if it declared none — the
   primitive's own name, which is the C type name the generated code used until now (§ *A base type's
   native declaration is required, and never derived*).
4. **Name the new file.** Where the declared name is capitalised, use the platform's lowercase
   spelling (`Float32` → `float32`); otherwise append `_base` (`float32` → `float32_base`). Its `name:`
   is the file name without `.yaml`. Every model SWCraft ships is lowercase and takes `_base`, so the
   capitalised branch is written here and exercised by none of them.
5. **Point the value type at it**: `base: float32_base`.
6. **Turn each `kind: alias` file into `kind: value_type`, with its `base` re-pointed to the new
   base type** — or into `kind: reference_type`, keeping `base` on the implementation type it names,
   when you want a `TYPE_REFERENCE` to that type rather than a `VALUE` over the base type. A reference
   type carries no `unit`, `value_min` or `value_max`.
7. **Re-point nothing else.** Interfaces, records, arrays and `init` values keep the names they use,
   because the declared name stayed with the value type.
8. **Run `swcraft check-model --project swcraft.yaml`** and repeat until it exits 0. Every reference
   left unfixed is reported under its rule id — a value type whose base is not a base type, a data
   element naming a base type, a type that is not declared, a base type with no native declaration.

**A component file exported by an earlier release is refused; export it again.** Earlier releases
wrote, beside every base type, an implementation type named after it with `_impl` appended, and used
it for the interfaces, records and arrays that named the base type. This release writes no such type.
Every component file it exports carries a data-types marker beside the access-points one: files from
`swcraft generate arxml --component` or `--all-components`, or from the MCP server's `export_component`
and `export_all_components`. The marker is
`<SD GID="DATA-TYPES">base and implementation types declared, no invented twin</SD>` in the
behaviour's `SWCRAFT` group, and it is a statement about the exporter, never about the component. The
whole-model `swcraft generate arxml` output is unchanged. `swcraft import component` and the MCP
server's `import_component` refuse a file that carries no such marker and declares such a type. They
refuse before comparing anything, change nothing, and say which type they found: *this component file
was written by an earlier SWCraft release (it carries the `float32_impl` implementation-type twin that
release invented and no data-types marker); re-export it with this release*. Export the component
again from the project that owns it, with this release, and import the new file. A project of this
release that itself declares a value type named after a base type with `_impl` appended exports a
marked file, and that file imports unchanged. A file from another tool that happens to declare such a
twin and carries no SWCraft marker is refused with the same sentence.

A component file whose `SWCRAFT` marker group, or the `ADMIN-DATA` block holding it, also carries
anything the exporter did not write — another `SD` or group, an attribute, or text — or whose behaviour
carries a second `ADMIN-DATA` block beside it, or content outside the AUTOSAR namespace, is now refused
as lossy. Earlier releases imported such a file and dropped that content — content outside the AUTOSAR
namespace since 0.7.0, and the rest from 0.8.0 on when the group held the access-points marker.

A known limit, present since 0.7.0: a component import does not yet report every element it leaves
behind; `LONG-NAME` and `INTRODUCTION` are the ones a valid file most often carries.

## A base type's native declaration is required, and never derived

A base type's `native_declaration` is the C type name the generated code declares for it — the
`NATIVE-DECLARATION` of its `SW-BASE-TYPE`. SWCraft used to fill in the base type's own name when a
file left it out. It no longer invents one: the value is written into the ARXML exactly as you
declare it, or not at all.

- **When you split a `primitive` into a base type and a value type, write `native_declaration` on
  the new base type.** Give it the name the primitive emitted: the value it declared, or — if it
  declared none — the primitive's own name (a primitive `float32` with no declaration becomes a base
  type `float32_base` with `native_declaration: float32`). That keeps every generated C type name
  what it was before the upgrade; leaving it out would not silently give you a different one, it
  would stop the build.
- **A base type you write by hand must declare it.** A file without it — or with a blank one — still
  loads, so `swcraft list`, `query`, `diff` and `impact` keep reading the project, but
  `swcraft check-model` reports it under `rule:data-type.base-type-native-declaration-missing`,
  naming the base type, and `swcraft generate arxml` and `swcraft validate` refuse to build until it
  is filled in. The editor marks the field as required while you type.
- **Importing an export that leaves it out.** AUTOSAR permits a `SW-BASE-TYPE` without a
  `NATIVE-DECLARATION`. `swcraft import model` writes such a base type without the field — nothing is
  invented — and its report lists each one under a section of its own, *Base types written without a
  native declaration (check-model reports each)*, with the element's path in the export. Nothing is
  counted as skipped. `swcraft check-model` reports each of them until you declare the C type name.

The description of a layer's storage `filenameFrom` in the contract's meta-schema is reworded as
well: the file name is derived from that field and is equal to its value unless a case-insensitive
collision gives the file a suffix, and an element's identity is read from its content, never from
its file name. No key and no value of the contract changes with it.

The wording patch on top rewords the description of every layer's `name` field (`id` for a
requirement) and of the requirement kind — the text the editor shows when you hover over the key,
and the text of the model reference pages. They said the file is `data_types/{name}.yaml`; they now
say the file is named from the name, or takes a suffixed name when another file collides without
regard to case, and is never what identifies the element. Nothing else in the contract changes, and
nothing in a project needs to change for it.

## `swcraft import rhapsody` is gone; the format is `model`

0.10.0 renamed the whole-export mode from `rhapsody` to `model` and kept the old word as a
deprecated alias for one release, printing one line on stderr each time it was used. 0.10.1 said
that line would be true of the release after it. This is that release, and the alias is removed.

```
$ swcraft import rhapsody --source export.arxml --project swcraft.yaml
usage: swcraft import [-h] [--source FILE] [--project PATH]
                      [--packages P1,P2,...] [--report PATH] [--dry-run]
                      [--force] [--update] [--replace-access-lists]
                      FORMAT
swcraft import: error: argument FORMAT: invalid choice: 'rhapsody' (choose from 'model', 'component')
```

`FORMAT` is now exactly `model` or `component`. A script, a `moon` task or a CI step still saying
`rhapsody` stops with that usage error and exit code 2 rather than drifting on; say `model`
instead, and nothing else about the command changes — the same flags, the same report, the same
exit codes:

```diff
-swcraft import rhapsody --source export.arxml --project swcraft.yaml
+swcraft import model    --source export.arxml --project swcraft.yaml
```

The old name survives everywhere it is about the importer's own tests rather
than about a command: the `SWCRAFT_RHAPSODY_EXPORT` variable a contributor sets, the
`--require-rhapsody-export` test flag, and the import's recorded scope and its
lossiness policy. None of them changes.

## One zip needs nothing on the machine, and the diagrams open in your browser

**An install needs no Python and no access to the VS Code Marketplace.** The workstation archive
now carries everything the installation runs on:

| What | Why it is in the archive | Licence, as its publisher declares it |
|---|---|---|
| Python 3.11 (a CPython build from the python-build-standalone project, as that project publishes the file) | the installer runs on it and the installation is built on it | Python Software Foundation License |
| Node.js 22 LTS (the file nodejs.org publishes) | the diagram viewer and the LikeC4 extension's preview run on it | MIT, with the notices of the parts it bundles |
| the LikeC4 tool and the packages it needs, built for the platform | it is the diagram viewer | MIT for LikeC4; each package under its own terms |
| Red Hat YAML, LikeC4 and Red Hat XML, the three VS Code extensions SWCraft works with | the installer hands them to VS Code before SWCraft's own | MIT, MIT and EPL-2.0 |

`THIRD-PARTY-NOTICES.md` beside the installer lists every one of them with its declared licence and
the licence text it ships. `runtime/RUNTIME.json` names the versions that were packed. **All four
were re-checked at the bump on 2026-09-15 and none of them moved**: the Node.js and CPython
versions, the `likec4` tool and each companion extension are what they were built and measured
against above, and every recorded digest is unchanged — the check is the bump procedure's own, run
every release rather than only when a payload changes, so "they did not move" is an answer here
rather than an omission.

- **Python.** The wrapper you run checks the carried Python against `SHA256SUMS`, unpacks a copy
  beside itself and starts the installer with it; the installation is then built on a second copy
  of its own. A Python already on the machine is neither used nor changed, and a machine whose
  Python moves to another version no longer breaks the installation. `install.py --python PATH`
  still builds on the interpreter you name, and unpacks no Python.
- **The Marketplace.** The three extensions go to VS Code from the archive, so a host with no
  Marketplace access gets completion and checking in the model files, the diagram preview and
  ARXML structure all the same. The copies are a starting point, not a fixed version: a VS Code
  that can reach the Marketplace updates them like any other extension. An extension that will not
  install is one sentence naming it, and the run carries on; `--uninstall` leaves all three in
  place.
- **Node.js.** The installer places `node` beside `swcraft`, so the LikeC4 extension's preview
  works with no `likec4.node.path` setting. Which `node` a window finds depends on the platform:
  on Windows a Node.js you already had on your `PATH` comes first; on macOS and Linux the line the
  installer prints puts SWCraft's first once you add it.
- **Installing from VS Code.** *SWCraft: Install Toolchain* and *Update Toolchain* look for no
  Python either: they open a picked zip with Windows' own `tar`, or with `unzip` on macOS and
  Linux, and run the archive's own wrapper. A Linux machine without `unzip` is refused in one
  sentence; pick the unpacked folder instead. Both stop the window's diagram viewer before the
  installer runs, because the viewer runs on the installation's Node.js. The installer moves each
  unpacked runtime folder aside before putting the new one in place, so a reinstall that cannot
  replace a folder still in use stops with the previous folder intact.

**The archive is about six times larger.** The macOS archive built for this release measured
**170 025 078 bytes**, against 28 794 870 for the same archive without the payloads. The Linux
and Windows archives are built on their own hosts; the ones the `v0.11.0` tag run published
measure **173 616 267 bytes** (`swcraft-0.11.0-linux-x64.zip`) and **180 418 051 bytes**
(`swcraft-0.11.0-windows-x64.zip`), against 27 215 947 and 30 744 628 for 0.10.1's.

**The panel names what you want.** The SWCraft view's *Model* section is now **Build**, **Check
Model**, **Diagrams**, **Diff**, **Impact**, **Resource Report** and **Export Component**. *Validate*,
*Generate C4* and *Open Generated C4* are gone from the panel and the Command Palette; `swcraft
validate` in a terminal is unchanged and is still the gate.

- **Build** runs what `moon run :build` runs, with no moon and no terminal: `swcraft
  clean-outputs`, `check-model`, `generate arxml`, `generate c4`, `generate rst` and `validate`, in
  that order, into the SWCraft output channel. The first step that fails ends the run.
- **Diagrams** generates the diagram file and opens every view in your browser, in LikeC4's own
  viewer, served by the Node.js and LikeC4 tool the installation carries. The viewer — the page and the
  connection that brings the open tab its updates alike — answers only on this machine's loopback
  address (`127.0.0.1`) and only to requests addressed to this machine, so a web page that tries to
  reach it under another name is refused. If another program takes the port the viewer was given
  before the viewer can use it, it is started again on another one; after three tries the press
  ends with a sentence saying so. In the viewer you click between
  views, search, open an element or a relationship for its details, walk
  a scenario as a sequence, and the viewport stays where you put it. While the folder is open, a
  saved model change regenerates the file and the tab updates by itself; pressing *Diagrams* again
  brings the tab forward. A model the generator refuses leaves the last good diagram and shows the
  refusal in the SWCraft output channel. The viewer's own log is a new channel, *SWCraft Diagrams*.
  The viewer stops when the window closes or another folder is opened.
- The walkthrough's fourth step is now *Build — the gate*, and its fifth opens *Diagrams*.

**`swcraft generate c4` leaves a file whose content did not change alone.** It still builds the
whole document first; when the file already holds exactly those bytes it is not opened for writing,
so its modification time stays and a watching viewer does not reload for nothing. A diagram file
that is read-only and already current no longer makes the command fail. The generated bytes are
unchanged, and `generate arxml` and `generate rst` still write their files every time.

**An older installation.** An installation from an earlier archive has no diagram viewer: *Diagrams*
says so in one sentence naming the archive to install with *Update Toolchain*, and starts nothing.
Every other command works as before.

**What this does not reach.**

- *Diagrams* also refuses, starting nothing, when the manifest's `outputs.c4` does not lie inside
  `views_root` — the viewer serves `views_root` and would show an empty page.
- The watch starts with the first *Diagrams* in a window: a change saved before that press
  regenerates nothing. A change to `views_root` in `swcraft.yaml` regenerates into the new directory
  while the running viewer keeps showing the old one until the next press.
- *Build* removes and recreates the diagrams directory, so a tab that is open while it runs shows an
  empty model for a few seconds.
- Within one window, *Build*, *Diagrams* and the regeneration after a save take turns. A second
  window open on the same folder, or a `swcraft` command run in a terminal at the same time, does
  not wait for them, and a *Build* can then fail on the diagrams directory.
- A program already running on this machine can read files through the viewer while it runs, as it
  could read them directly.
- Each viewer keeps its temporary files in a folder of its own in the system temp folder and removes
  it when the viewer stops. A window closed before the viewer has finished stopping leaves that one
  folder behind.
- Nothing ties the LikeC4 extension to the LikeC4 tool the archive carries. VS Code may update the
  extension past the carried copy, so the preview in the editor and the viewer in the browser can
  come to differ, and nothing reports it.
- The diagram viewer, the Node.js it runs on and the three extensions are conveniences outside what
  SWCraft verifies: no diagram, browser view, preview or editor marker is evidence that a model is
  valid. `swcraft validate` is the gate.
- Windows has not been measured for any of this yet: the carried Python's bootstrap, the Node.js
  placed beside `swcraft`, the extensions' installation, the viewer stopping with the window, where
  the viewer keeps its temporary files and whether that folder is removed as it stops, the preview
  finding `node`, and a reinstall of the same version while the LikeC4 extension or the assistant's
  server is running are first exercised by the Windows release build and a seated check.
- No macOS archive is published; one is built from a checkout.

## A fix on Windows: a build graph's parallel generators no longer trip the manifest check

A moon build runs the three generators in parallel, and on Windows one of them could refuse with
"Manifest field `outputs.rst` resolves to `\\?\<drive>:\...`, which is outside the project root". The
path was inside the project; Python had kept Windows' extended-length prefix on an output file
that did not exist yet, because a neighbouring generator created `dist/` between its two probes.
The six declared paths are now compared without that prefix. It happened rarely, only on Windows
and only in a parallel build, and it was the one failure of the `v0.10.1` tag run's Windows job.

## A fix: a model finding no longer says where the project is stored

A `swcraft check-model` finding about an array's undeclared element type or about a name that is not
a legal AUTOSAR Identifier — and the same finding when the MCP server refused a change for it — named
the model folder or the declaring file by its full path on disk, and it now names the element and its
layer instead, and an internal error of the MCP server — such as its change checks and the model
checks disagreeing about a change — no longer names where the project is stored, in the reply or in
the server log: the reply says only that the tool call failed, and the log keeps the rest. Refusing a
change because the model was edited while the change waited for approval named the model folder too,
and no longer does, and neither does the MCP server's answer when a model file cannot be read, which
now names that file only by its place inside the model folder, nor its note that a change was
committed but could not be written to the audit log.

## The MCP server names output locations relative to the project

The MCP server's `build`, `validate`, `export_component` and `export_all_components` tools answered
with the full path of every file they wrote, and `resource_report` headed its report with the model
folder's full path. They now give each location relative to the project — `dist/model.arxml`,
`views/model.c4`, `dist/requirements.rst`, `dist/components/SpeedSensorSWC.arxml`,
`dist/components/export-summary.json` — and name the licensed AUTOSAR schema by its file name and the
AUTOSAR version it validated against, and the resource report by the project's `name` in
`swcraft.yaml`. An output path you pass to an export yourself is answered as you wrote it when it lies
outside the project. **Anything that opened a reported path directly must now join it to the project
folder first.** The per-component errors in `export-summary.json` name each file relative to the
model folder, so a script that opens one must join it to the model folder first.

Their refusals name no location either. A missing manifest is named by its file name, a missing model
folder is *the model root*, a component the model does not declare is *not found in the model*,
`model_diff` at a revision no longer names the temporary folder the revision was read from, and a
component file that cannot be read is named by its place inside the model folder. A refusal of the
ARXML writer or of the diagram generator names the layer folder — *is not declared in data_types/* —
and never the model folder, on the terminal as in a reply; and an error the operating system raises
in `build`, `validate` or a component export or import — `dist` existing as a file, a model file the
server may not read — keeps its error number and reason and names the file inside the model folder
or the project.

A path in `swcraft.yaml` that resolves outside the project, or an output path that lies inside the
model folder, is named by its field alone: *Manifest field 'dist_root' resolves outside the project
root.*, and *Manifest field 'dist_root' overlaps 'model_root'. Generated paths must be outside the
model: generating or cleaning them would otherwise write into, or delete, the model that is the
source of truth.* A component export the ARXML writer refuses names the layer folder inside the
model instead of the temporary folder the export generated in and has already deleted — *Base
type(s) ['float32_base'] in data_types/ declare no native_declaration: …* — in the `export_component`
and `export_all_components` replies, in the batch report and in `export-summary.json`.

The `swcraft` command line still prints full paths on your terminal, with three differences:

- `swcraft generate arxml --all-components` reports a component file that cannot be read with the
  same sentence every other command uses, naming the file by its place inside the model folder, and
  `export-summary.json` records it the same way — it used to write its own sentence with the full
  path, and a file whose component name could not be read was listed under that full path.
- `swcraft import component` refusing a project file that is not YAML at all names it with that same
  sentence, and its full path, instead of *component import aborted: target project file … is not
  valid YAML*.
- `swcraft generate arxml --component` and `--all-components` print a component export the ARXML
  writer refuses by the same layer folder — *Error: Base type(s) ['float32_base'] in data_types/
  declare no native_declaration: …* — and never the full path of the temporary folder the export
  has already deleted, which names nothing you can open.
