# SWCraft 0.19.2

Released 2026-10-25. A patch release of the 0.19 line: four recipes of the assistant profile that
answered with lists sized by the model now answer one page, sized by the question, and *SWCraft:
Onboard Project* no longer creates a project inside another or around one. The four
recipes answered lists that grow with the model in 0.19.1, up to a refusal on a large one; each now answers a small page,
and every recipe of the profile answers under 8 KB, the size past which VS Code's
Copilot writes a tool's answer to a file instead of reading it. A new command, `swcraft passport`,
describes a model's shape without naming anything in it. The MCP server still has twelve tools, and
the ARXML SWCraft generates and the model's format are unchanged from 0.19.1. *What upgrading takes*
at the end has one step beyond the pin: copying the new assistant profile.

## The recipes answer one page

Every request in `index` form in the profile's *Recipes for common questions* now carries a `limit`,
except the two of *Components that no partition runs* (below), and the section says once what such an answer holds: the number the page states as its `total`, the
rows of the page, and that the rest come by the same request with the page's `after`.

- ***The sender-receiver table*** pages at **five** rows. A row names about thirteen things (the
  writer, its runnable, port and data element, the connector and both of its ends, the reader with
  its runnable, port and data element), so a page of twenty would be too large. The whole table is
  still the `swcraft query --request FILE --project PATH` command the section names, which has no
  response budget.
- ***Components by effective level*** is now the number at each level, one `count` for each of `QM`,
  `A`, `B`, `C` and `D`, and then, only when the user asks which, a page of twenty components of one
  level. The recipe used to read every component and group them by hand.
- ***How many components are at a level*** still counts first; its list is a page of twenty.
- ***Who reads or writes a data element*** asks both the readers and the writers as pages of twenty.

The other listing recipes ask for pages of twenty too. The one exception is *Components that no
partition runs*: its answer is every component minus every component a partition runs, which a page
cannot give, so its two requests still read both whole lists. They are small, about 20 bytes a
component, and an answer above the server's bound is refused with
the paged hint as before.

The sender-receiver table grows with the model and could be refused on a large one; its
page is now small. *Components by effective level* is now five numbers, with a page of a
level beside them, and the list of *How many components are at a level* and the readers of a data
element shrank the same way. Every recipe answer is now well under the 8 KB above.

## Onboarding never nests a project

*SWCraft: Onboard Project* now opens its folder picker on the open workspace folder (the first one,
when several are open). *Onboard Project* no longer creates a project inside another or around one: a
chosen folder that lies inside a project, because a folder above it holds a `swcraft.yaml`, is refused
with that project's folder named, and a chosen folder with no `swcraft.yaml` of its own that holds a
project in a folder below it is refused with that project's path named; either way the command runs
nothing. A project's own folder is onboarded again as before, whatever it holds below it. The search upwards stops
at the workspace folder, so a manifest above the workspace refuses nothing; a folder outside the open
workspace is checked up to the root of its drive.

## Reporting a problem without sending the model

`swcraft passport` writes a model passport: a small JSON file that describes the shape of your
model - how many components, ports, interfaces, data types, connectors and the other elements it
holds, and how they are put together - without naming any of them. It carries no element name, no
value and no text from the model, so it can be attached to a problem report when the model itself
cannot leave your machine.

    swcraft passport --project swcraft.yaml --output passport.json

Without `--output` the passport goes to stdout. Run `swcraft passport --help` for its options.

## The model's contract

`contractVersion` stays `12.0.0`. No model file needs an edit. The passport's format is the one
`swcraft passport` writes in this first release of the command; nothing else in this release changes
it.

## The archive

The runtime payloads are 0.19.1's, unchanged: Node.js 22.23.2, CPython 3.11.16 (the
python-build-standalone build of 2026-09-01), `elkjs` 0.12.0 inside the `swcraft-tools` package, and
the two extensions of the pack, Red Hat XML 0.29.3 and Red Hat YAML 2.0.0, which is still the
Marketplace's newest release. The archive carries the same packages as 0.19.1. The Linux archive
measures **198 038 002 bytes** (SHA-256 `cc7566b9…eae8170`) and the Windows archive
**202 097 097 bytes** (`e9e24293…dba775`), as the tag run of 2026-10-25 published them: 37 775 and
37 763 bytes more than 0.19.1's.

## What upgrading takes

1. **Install the 0.19.2 archive, then set `toolchain_version: "0.19.2"`** in each project's
   `swcraft.yaml`. Until you do, every command that writes or gates refuses a project pinned to
   0.19.1 with the pin sentence. The read-only commands (`diff`, `impact`, `list`, `query`,
   `resource-report`) and `swcraft guard` only print a warning, so Copilot keeps working meanwhile.

2. **Run *SWCraft: Onboard Project* again** to copy the new assistant profile, with its paged
   recipes. Onboarding overwrites the profile, the Copilot instructions and the model guard, so keep a
   copy of anything you edited in them. An old profile keeps working; its four recipes only answer the
   long lists they answered before.

Nothing else moves in a project: the model's files, the hook file `.github/hooks/swcraft.json` and the
generated ARXML are unchanged from 0.19.1. A project on 0.19.0 or earlier follows
[0.19.1's note](0.19.1.md) first.
