# SWCraft 0.22.0

Released 2026-11-07. The release where requirements go in and out as Sphinx-Needs: `swcraft import
requirements` reads the requirements team's own `needs.json`, and **`swcraft generate needs`** publishes
the architecture's requirements and links as a `needs.json` of its own, replacing the Sphinx sources
`generate rst` wrote. The model gains three AUTOSAR behaviour elements an RTE generator reads:
**inter-runnable variables**, **exclusive areas** and the **`data` event** that starts a runnable when a
value arrives. A key SWCraft does not declare, in a model file or in `swcraft.yaml`, is now an error
instead of a value dropped without a word. VS Code imports a component in the review tab, puts a malformed
file's errors on its fields and underlines a finding's value. The installation now brings Carchetype, the
generator of synthetic projects. The assistant can now read this guide through a new tool, `guide`, so the
MCP server has thirteen tools. The ARXML SWCraft generates is
unchanged for a model that uses none of the new elements; a component file carries three more lines.
*What upgrading takes* at the end has, beyond the pin, renaming `outputs.rst`, the build task that
generated it, and fixing every key the new check names. The tag run published the archives at
199 835 173 bytes (Linux) and 203 886 601 bytes (Windows).

## Breaking: requirements are published as `needs.json`

`swcraft generate needs` writes `dist/needs.json`, a Sphinx-Needs file the requirements team loads into
its own documentation with `needs_external_needs`. It replaces `swcraft generate rst` and the Sphinx
sources it wrote.

- The file carries your **architecture requirements** and the **architecture elements** that carry a
  link, with both kinds of link: an element satisfies a requirement, an architecture requirement derives
  from an incoming one.
- **Incoming requirements are never copied back.** A link names the team's requirement by its own id,
  unchanged, so the team sees, on its own requirement, which elements satisfy it.
- **A link whose requirement changed since you confirmed it** is published as *unconfirmed*, a link type
  of its own, so the team sees which links still need your decision.
- The file names the requirements delivery the links were set for.
- **Every entry names its file**: `swcraft_path` is the file in your model that declares it, relative
  to the model root (`swc/brake/BrakeCtrl.yaml`; a port or a runnable names its component's file). The
  requirements team's `target_url` can be a template over it, so a click on an architecture element
  opens its YAML — in the repository's file view, as a local `file:` page, or in VS Code through
  `vscode://file/<checkout>/<model_root>/{{need.swcraft_path | urlencode}}`, with no network. The
  guide's lines read the field as text and URL-encode it, so a folder or a file name holding `[[`, `#`
  or a space still links to its file.
- The user guide (*Publishing the architecture to the requirements team*) gives the lines the
  requirements team adds to its `conf.py`: three need types, two fields, four link types and the
  `needs_external_needs` entry, built with Sphinx-Needs 9.2.0 without a warning. The team installs
  nothing of SWCraft's.

What breaks:

- `swcraft generate rst` is gone; use `swcraft generate needs`. `generate rst` now stops with a usage
  error naming the valid formats. The `swcraft-generate-rst` command is removed.
- The manifest's `outputs.rst` is now `outputs.needs`, a file (default `dist/needs.json`). A project
  that still has `outputs.rst` gets a `check-model` error for an unknown manifest key
  (`manifest.unknown-key`, on `outputs`), so `check-model` and `validate` exit 1 and a build stops at
  its `check-model` step until the key is renamed; the project itself still loads, and the read-only
  commands still run.
- A project scaffolded from the template before this release has a `generate-rst` task in its
  `moon.yml`, which fails the build until it is replaced (*What upgrading takes*, step 2).
- Ids are no longer rewritten.
  - **An id holding `.` is not supported in a published link.** Sphinx-Needs 9.2.0 reads every link
    value up to its first `.` as the need's id and the rest as a part of that need, and no setting turns
    that off, so it cannot link such an id, not even inside the team's own documentation. `generate
    needs` refuses a model with such a link, and `check-model` warns about it first
    (`trace.link-unpublishable-id`). Your model can still import and hold such requirements.
  - **An id holding `[` is published as it is.** The guide's lines for the team's `conf.py` set
    `"parse_conditions": False` and `"parse_dynamic_functions": False` on SWCraft's four link types, so
    the team's build reads the whole id, `[[…]]` included.
    The requirements import reads such an id whole where the team's file holds a need of that id.
- **A refused `swcraft generate needs` removes the previous `dist/needs.json`**, so a file that no longer
  describes the model cannot be handed over. The assistant's `build` removes it as soon as the model
  passes its check, before it writes anything, so a build that fails later — the export refused, the
  ARXML refused, a diagram failing — leaves no `needs.json` rather than the previous one beside the new
  ARXML. A model with an error writes and
  removes nothing there: the assistant's previous build's files stay as that build left them, where
  VS Code's *Build* and the template's build graph remove them first.
- **An architecture requirement with an empty title or description is a `check-model` warning**
  (`trace.requirement-blank-text`): it is published as it stands, and the requirements import refuses it.
- The requirements team's import mapping lists the keys SWCraft's declarations add and the import
  does not read (`ignore: [satisfies, satisfies_unconfirmed, derived_from_unconfirmed, swcraft_path]`
  with SWCraft's own names); the user guide gives the line.
- A model whose element is declared by more than one file cannot be published while that element is
  linked: its entry could not name the one file that holds it.
- An `outputs.needs` naming another file the project keeps — the ARXML `outputs.arxml` names, the
  previous ARXML beside it (`model_old.arxml`), the audit log `dist/audit.jsonl`, the build report
  `dist/build-report.md`, `swcraft.yaml` itself, a file directly in `views/` named `report.txt` or
  ending `.svg` or `.html` (the names `generate diagrams` writes there), a path equal to or below
  `dist/metrics/`, `dist/resource-report/` or `dist/change-report/` (where `metrics --report`,
  `resource-report --report` and `change-report` write their reports under fixed names), or one equal to
  `dist/components` or `dist/experiments` — is refused when the project is read, by every command and in
  VS Code: `generate needs` would overwrite that file.
- Outside the command line: the assistant's `build` answers `needs.json generated: <file>` where it
  answered for the RST sources, and refuses before it writes anything when the file cannot be
  published; VS Code's *Build* runs `generate needs` and its Build Report names `needs.json`; the
  Copilot guard allows `swcraft generate needs` where it allowed `generate rst`.

## Breaking: requirements come in as the team's own `needs.json`

`swcraft import requirements` now reads the `needs.json` that `sphinx-build -b needs` writes, as it
is, from Sphinx-Needs 7.0 to 9.2. Sphinx-Needs' own keys are ignored; any other key the model does
not hold is refused, so a misspelt field is never dropped in silence.

- **A parent link to a requirement whose id holds `.`.**
  - If the team's file holds that requirement — the link's whole text, or its text without a
    `[…]` condition — the import refuses it and says that Sphinx-Needs 9.2.0 cannot link such an id. It
    then creates no wrong parent and no stub from the id before the `.`.
  - If the file does not hold it, the link is read as Sphinx-Needs reads it: the id before the first
    `.` names the parent and the rest is a part of it.
  - A parent written in a field that is not a link is always read whole.
- **`--mapping FILE`** maps the team's need types and field names to SWCraft's: a YAML file of your
  own, with completion and checking in VS Code when its name ends in `needs-mapping.yaml`. Without it,
  SWCraft's own names apply, so a file written by an existing converter imports as before. A mapping
  file refuses YAML aliases (`*name`, a merge key's included): write the value out where it is used.
- **Every delivery records its version** in each requirement's `baseline`: `--baseline` (the team's
  commit or baseline) or the file's own `current_version`. An import with neither is refused, and a
  blank `current_version` counts as none. The report's first line names the version, with
  `(from the file)` when it is the file's.
- **A delivery is the complete set.** An imported requirement the new delivery no longer holds is
  removed, and the report names every link that now names no requirement, for `check-model` to show.
- **VS Code:** *Import Requirements* asks for the mapping and remembers it in the workspace folder's
  setting `swcraft.requirementsImport.mapping` (a user-level value is not read), then asks for the
  delivery's version in a box filled with the version the file names: Enter records it. When the file
  names none, the box is empty and a value is required. The report then opens in the import tab with
  **Write** and **Cancel** under it, and the import's report follows in the same tab.

What breaks:

- An import whose file names no version now needs `--baseline`; the report's "no baseline given"
  header is gone, and the header of a version taken from the file ends in `(from the file)`.
- A requirement absent from the file is now removed rather than left as it was. One that a
  requirement still names as a parent becomes a placeholder, and its links need confirming again.
- A requirement that returns after a removal, or a new one, starts above every version at which the
  links the import leaves in the model still name it, so those links stay unconfirmed. A link the
  import rewrites in the same run does not count.
- An import that would write a requirement at a version of more than 640 digits is refused: correct
  the links in the model that name it at such a version.
- A placeholder requirement that nothing names any longer is removed.
- *Rejected, not in the model* is now *Removed by status, not in the model*.

Relaxed: a parent listed twice is read once; an empty `asil`, `document` or `revision` reads as
absent; earlier versions kept in the file are no longer checked.

## Breaking: a key SWCraft does not declare is an error

**In a model file.** `swcraft check-model` and `swcraft validate` report every key in an element file
that no field of its kind declares. Examples are `derived___from:` for `derived_from:` or
`asil_capabilty:` for `asil_capability:`. Each is an error under `model.unknown-key`, on the key's line
in VS Code, naming the nearest declared key where there is one. Until 0.21.0 such a key was dropped
without a word, together with the value it carried. A model holding one fails Check Model and Build
after the upgrade, and until it is fixed the assistant's change sets and the allocation experiment are
refused. The read-only commands keep reading the model.

**In `swcraft.yaml`.** A manifest key SWCraft does not declare, such as `arxml_verison:` for
`arxml_version:`, is an error under `manifest.unknown-key`, on the key's line in VS Code. Until 0.21.0
such a key was dropped, and the setting it was meant to carry was not applied. The project still loads,
so the read-only commands keep working; `swcraft generate` alone and the assistant's validate and build
tools do not check the manifest. A leftover `c4:` line under `outputs:`, ignored since 0.12.0, is now
such an error, and so is `outputs.rst` (above).

**A blank measure is an error.** A `measures` entry whose text is empty or only spaces is an error under
`safety.measure-blank`, on the entry's line in VS Code. Until 0.21.0 such an entry answered a safety
coexistence finding without naming any mechanism. Until it is fixed, the assistant's change sets and the
allocation experiment are refused, as for any error.

## Breaking: smaller changes a script can notice

- **An experiment no longer writes over a report it did not write.** A configured `output` that names a
  directory holding a `report.md` or `result.json` no earlier experiment run wrote is refused, and so is
  any path inside `.git`. The default report directory is unchanged.
- **`swcraft import component` exits 3 for the refusal `--update` resolves.** A run without `--update`
  whose only conflict is the component's own divergence from your project's (*SWC '…' already exists in
  the target project and diverges*) now exits with status **3** instead of 1, with the same message and
  nothing written, so a script can tell the one refusal `--update` resolves from every other. Every other
  refusal still exits 1.
- **`swcraft init` refuses over a `swcraft.yaml` pinned to another release.** `init` keeps a
  `swcraft.yaml` already in the directory and now reads it, so it checks the manifest's
  `toolchain_version` first, like every command that writes: a kept manifest that pins another release
  stops `init` with the pin's sentence and exit status 1, before anything after its *Skipped* line is
  written.
- **The cohesion reason text changed for every model** (below, *Cohesion*).
- **Component files.** Every component file this release writes carries three more lines, and an earlier
  SWCraft release refuses it (below, *Every component file carries three more lines*).
- **A link list naming one target twice is an error**, `trace.duplicate-link`: a `satisfies` list that
  repeats one link or names the requirement at two versions, and a requirement whose `derived_from` names
  one parent twice. Check Model refuses it and so does the assistant's change set; remove the extra
  link.

## Shared state inside a component: inter-runnable variables

A component can now declare the state its runnables share, as `variables`, and each runnable the
variables it reads and writes, as `reads_variables` and `writes_variables`. These are AUTOSAR's
inter-runnable variables: the generated ARXML carries each variable under the component's behaviour,
among the explicit or the implicit ones, and each read and write under its runnable, which is what an
RTE generator reads to give the runnables their inter-runnable variable API.

```yaml
variables:
  - name: FilteredSpeed
    access: implicit
    application_type: VehicleSpeed
    init: 0
runnables:
  - name: FilterSpeed
    events: [{type: timing, period: 0.01}]
    writes_variables:
      - variable: FilteredSpeed
  - name: MonitorSpeed
    events: [{type: timing, period: 0.1}]
    reads_variables:
      - variable: FilteredSpeed
```

`access` is required, `explicit` or `implicit`, because the two give generated code different APIs.
A variable is typed like a data element and may state an `init`, a `description` and a
`sw_calibration_access`. `swcraft check-model` reports an access to a variable the component does
not declare, an undeclared type, a variable typed by a pointer and a variable whose name its
behaviour already uses; `swcraft generate arxml` refuses them and writes nothing.

**A new warning: a variable a runnable reads and that states no `init`.** AUTOSAR leaves such a value
undefined when the read comes before every write, and the model does not say in which order runnables
run, so the warning is given for every such read. It does not check the order. Like every warning it
fails `check-model` and `validate` only under `--warnings-as-errors`.

`swcraft import model` and `swcraft import component` now read a component's inter-runnable variables
and its runnables' reads and writes of them, which earlier releases listed under *Not supported by
SWCraft*. A project imported again gains them, and its `SKIPPED` line counts fewer elements. What
cannot be carried is one line with its reason. In VS Code the new fields complete and validate in the
editor, and a read or write leads to its variable. The assistant edits variables through its existing
tools; no tool was added.

## Runnables that must not interrupt each other: exclusive areas

A component can now declare its exclusive areas, as `exclusive_areas`, and each runnable the areas it
uses: `runs_inside` for an area that guards the whole runnable, and `can_enter` for an area the
runnable enters and leaves by calls in its own code. The generated ARXML writes each area under the
component's behaviour and each use under its runnable, which is what an RTE generator reads to keep
those runnables from interrupting each other.

```yaml
runnables:
  - name: FilterSpeed
    events: [{type: timing, period: 0.01}]
    runs_inside:
      - area: SpeedState
  - name: CalibrateOffsets
    events: [{type: timing, period: 1.0}]
    can_enter:
      - area: OffsetTable
exclusive_areas:
  - name: SpeedState
    description: Guards the filtered speed shared by the 10 ms filter and the 100 ms monitor.
  - name: OffsetTable
```

An area has a `name` and may have a `description`, and a runnable may name only the areas of its own
component. `swcraft check-model` reports an entry naming an area the component does not declare and an
area whose name another name in the component's behaviour already takes; `swcraft generate arxml`
refuses them and writes nothing. No warning was added.

`swcraft import model` and `swcraft import component` now read a component's exclusive areas and its
runnables' references to them, which earlier releases listed under *Not supported by SWCraft*. A project
imported again gains them, and its `SKIPPED` line counts fewer elements. What cannot be carried is one
line with its reason, and `import model`'s report counts the areas and references it imported. In VS
Code the new fields complete and validate in the editor, and an `area:` leads to its area. The assistant
edits areas through its existing tools; no tool was added. `swcraft diff` and the Change Report list an
added, removed or changed area or entry like any other member.

## A runnable started when a value arrives

A runnable can now be started by the reception of a value, with a fourth kind of event, `type: data`,
naming one of its component's own require ports and a data element of that port's sender-receiver
interface. It may name the modes that disable it, like a timing event, and state a `name`. The
generated ARXML writes each one as the event an RTE generator reads to start the runnable when the
data is received.

```yaml
runnables:
  - name: FilterSpeed
    events:
      - type: data
        port: R_WheelSpeed
        element: FrontLeft
    reads:
      - port: R_WheelSpeed
        element: FrontLeft
  - name: MonitorSpeed
    events:
      - type: timing
        period: 0.1
      - type: data
        port: R_WheelSpeed
        element: FrontRight
```

`swcraft check-model` reports a `data` event whose port the component does not declare, whose port is
a provide port, whose port's interface is not sender-receiver, or whose element that interface does not
declare; `swcraft generate arxml` refuses them and writes nothing. No warning was added. A `data` event
beside a timing event, two runnables started by one element, and a runnable started by an element it
does not read are not reported. The generated name of the event is `DRT_{port}_{element}`, so a port
and each element a `data` event names share 123 characters, and the message names both when they are
over.

`swcraft import model` and `swcraft import component` now read these events, which earlier releases
listed as an unrecognized event kind under *Not supported by SWCraft*. A project imported again gains
them, and its `SKIPPED` line counts fewer elements; `import model`'s report counts the events it
imported per component. An event through a port that both provides and requires, which SWCraft does not
model, is one line with its reason. In VS Code the new event completes and validates in the editor, its
`port:` leads to the port and its `element:` to the data element, and the outline shows it; an
`operation` event's `port:` now leads to its port too. The assistant writes and removes the event through
its existing tools; no tool was added. `swcraft diff` and the Change Report list an added or removed one
like any other event.

### Where a received value comes from

A runnable started by a `data` event that is mapped into a task is budgeted as if it ran at most once per
activation of that task, the task's period standing for the shortest interval between two arrivals you
plan for. No check was added for it, and the task budget is summed as before.

`swcraft resource-report` gains an `ARRIVALS` section for a model that has such a runnable. For each
event of each placed occurrence of its component, it follows the connectors and delegations back to the
runnables that write the element and their tasks, and says either *data arrives at most every N ms*,
naming the writer and its task, or why the source is outside the model — no connector reaches the port,
the port is delegated out of the top composition, the sender is an external component, no runnable of
the sender writes the element, or a writer runs in no task. The figure is a bound taken from the
senders' task periods, not a measured rate, and the section says so. It adds no finding and the command
still exits 0. A report on a model without such a runnable is unchanged, with one exception: the command
now reads every component file on every run to find such a runnable, so a component file that does not
parse stops the report with an error even in a project with no `hardware` folder, which used to be
reported alone; with such a runnable, a malformed interface, connector, task or composition file stops it
the same way. The section's header counts lines, one per runnable per placed occurrence. `--format json`
adds `arrivals` and `arrivalsNote`, only when the section has lines; `schemaVersion` stays 1. `--report`'s
file gains an *Arrivals* section, and the assistant's resource report carries at most the first twenty of
the same lines (fewer when they are long), counts the rest and points to `swcraft resource-report` for
them. The Resources view in VS Code does not show them.

## Cohesion and the allocation experiment

`swcraft metrics`' cohesion now counts two runnables of a component that read or write the same
inter-runnable variable as working on the same data, as two runnables using the same port always
counted, and it counts the port of a `data` event among what a runnable works on, as it counts an
`operation` event's. A port and a variable that share a name are not the same thing to it. A model
without variables keeps every figure, but **the text changes for every model**: the cohesion
definitions, four sentences of the conclusions, and the reason of a component whose runnables each use
one single thing, which now reads `one port or variable: every runnable that uses one uses only it`
(it was `one port: every runnable that uses a port uses only it`) in the report and in
`--format json`. A script that matched the old reason text has to match the new one, and a script
that imported the reason from `swcraft_tools.metrics` imports `ONE_PORT_OR_VARIABLE`, which replaces
`ONE_PORT` in the module's `__all__`.

The allocation experiment gives a runnable that only a `data` event starts a class of its own: it is
never moved and never costed, because the model does not hold its rate, and while it runs in a task its
component is not free to move.

## Every component file carries three more lines

Every component file `swcraft generate arxml --component` or `--all-components` writes now carries three
more lines in the behaviour's SWCraft group — `<SD GID="INTER-RUNNABLE-VARIABLES">`,
`<SD GID="EXCLUSIVE-AREAS">` and `<SD GID="DATA-EVENTS">` — a component without the new elements
included. They tell `swcraft import component --update` that the file speaks for the component's
variables, exclusive areas and `data` events: such a file replaces your project's, removing one the file
no longer has. A component file an earlier release wrote leaves your project's as they are, and the
report lists what it kept; a file from another tool that states a `data` event is compared as it stands.
The whole-model ARXML carries none of the three lines and does not change for a model without the new
elements. **An earlier SWCraft release refuses every component file this release writes**, so exchange
component files between projects on this release.

## Trace link proposals made before this release

A trace link search fingerprints each component and runnable it proposes a link to, and this release's
model gives every component and runnable the new, empty variable and exclusive-area lists, so every such
fingerprint moved. Applying a proposals file written before the upgrade marks every row whose target is a
component or a runnable *changed since the search*, and links none of them. Run the search again after
upgrading, then decide and apply as before. Rows whose target is of any other kind — a port, an
interface, a composition, a task or a hardware element — are not affected.

## The assistant reads the guide

The assistant can now read this guide. A new tool, `guide`, searches it by words and headings and
reads a page or a section whole: the same text you read, from the guide your installation carries, so it
always describes the version you run. The search runs inside SWCraft on your machine; no search service
is involved, and the tool reads only the guide the installation brought, never a file of your project.

- **A How-to section** describes the common tasks — connecting two components, adding a component or
  an interface, renaming, removing, moving a runnable to another task, seeing what a change affects,
  linking requirements, checking memory, importing a component, asking the model — each with the step
  in VS Code or on the command line and the step the assistant takes.
- **A Refusals page** says what each refusal of a change means and what to do; the assistant looks a
  refusal code up there, and a check's name on the checks page.
- **The *Upgrading* page lists, release by release, what each upgrade asks of a project** — the old
  spelling, the new one, what to do and how to check it — so an upgrade question is answered from the
  guide of the release you install.
- **An answer drawn from the guide ends with a link to its section.** In VS Code's chat, a click opens
  the guide in a VS Code tab at that section; the first click may ask you to allow SWCraft to open the
  link.
- **A how-do-I question is answered in words**: the steps, what you will see in the review tab and
  the refusals to expect, then an offer to make the change. The request the assistant sends to make
  the change is not pasted into the answer unless you ask for it.
- The agent profile a new project gets is shorter: the how-to answers moved into the guide, and the
  profile lists the guide's How-to pages and each task on them, with the section that answers it.
- The guide now writes your home directory as `$HOME`, which every shell understands, so a command can
  be copied as it is.
- **How well it answers.** Eight questions about SWCraft itself — what a refusal means, how to upgrade
  a project and how to go back to an earlier release, what `swcraft validate` checks, where `needs.json`
  comes from, what a version pin mismatch does, how to import a component, how a change is reviewed —
  were each asked five times in GitHub Copilot, Codex and Claude Code, every time with a small, fast
  model. Answered correctly from the guide: 39, 39 and 40 times of 40; ending with the link to a section
  that answers the question: 40, 39 and 38 times. Each miss was a single run: an answer that stopped
  before the section naming one flag, a fitting section passed over for another, a link written in the
  wrong form.
- **The model tasks did not get worse.** Twenty-four changes to the model and questions about it, each
  run once with the guide in place, passed 24 of 24 in Copilot and in Claude Code and 22 of 24 in Codex,
  as many as Codex passed without the guide.

The MCP server has thirteen tools. Nothing in the model, the ARXML or the checks changes.

## VS Code

**Import Component.** **Model → Import Component** sits directly under Export Component. You pick a
component's `.arxml` file, and the dry run's report opens in the tab *Component Import Report*, shaped
like the tab where you review an assistant's change set: the report, headed by the file's name, with
**Write** and **Cancel** under it. **Write** imports, and the same tab then shows the import's report and
a **Check Model** button; **Cancel** closes the tab and writes nothing. When your project already has the
component and the file changes it, the tab offers **Show Update**, which shows what an update would
replace and what it keeps, and then **Update**, which applies it. The report is never saved. **Import
Requirements** works in the same tab form.

**A malformed model file, one line per field.** A model file that cannot be read is now reported one
line per field, naming the file, the field and what is wrong with it, without the dump of the input value
and without a help link:

    Error: Invalid task YAML in <project>/model/tasks/Task_bad.yaml: period: Input should be a finite number

A line the YAML reader cannot parse is named by its line and column. `swcraft diff`, `swcraft
change-report` and `swcraft metrics`, which report such a file inside a sentence of their own, give the
same lines joined by `; `. In VS Code, **Check Model** and **Build** now put one error per field in the
Problems panel on the file at fault, at the field's line where it can be found, instead of one entry on
the first line of `swcraft.yaml`.

**A finding on a value underlines the value.** In the Problems panel, a finding on a field's value now
underlines the value — `IServer` in `interface: IServer`, with its quotes when it is quoted — and no
longer the key. A value written below its key (a list, a mapping, a `|` block) or no value at all keeps
the key underlined.

**Code Spell Checker leaves the model alone.** `swcraft init` now writes `"cSpell.ignorePaths"` into the
`.vscode/settings.json` it creates, naming the model, `dist` and views folders of the project's
`swcraft.yaml`, so that Code Spell Checker, where it is installed, no longer marks every name in the model
as an unknown word. A misspelling in a model's `description` or a requirement's text is no longer marked
either. `init` never edits a settings file that already exists (*What upgrading takes*, step 6).

## Smaller changes

- **Import reports as Markdown.** `swcraft import component --report PATH` and `swcraft import
  requirements --report PATH` write the report's Markdown form when PATH ends in `.md`, like SWCraft's
  other reports, and the printed text, as before, for any other PATH. `swcraft import model --report`
  always writes the text.
- **A rename through the assistant keeps the file.** The renamed element's file keeps its comments and
  layout, and only its name line changes. A file that cannot be edited line by line is named in the
  review's warning before you approve, as an edited file already is. Rename and edit an element in two
  change sets: a rename bundled with other changes to the same element writes the new file whole, and
  the warning says so.
- **Exporting a component reports an unresolved operation event with its other problems**, all at
  once, before anything is written.
- **The audit log names files relative to the project.** `dist/audit.jsonl` records each file a change
  wrote or removed as `model/swc/Foo.yaml` instead of its full path on your machine, and a path outside
  the project as `(outside the project)`, so the log no longer carries your user name. Entries an
  earlier release wrote stay as they were.
- **A diagram's arrow line ends at its arrowhead.** A sequence message, an activation, a
  self-message and an overview's bundle used to show the line's square end beside the head's point,
  lit or not; every such line now stops inside its head, so the tip is where the line arrives. The
  diagram files change for every model that has one of these lines.

## Carchetype in the delivery

The workstation archive installs Carchetype 0.2.2 beside `swcraft`. `carchetype specimen passport.json
--out <dir>` writes a project of the shape a `swcraft passport` file describes, and `carchetype generate
small --out <dir>` writes one from a packaged preset; either project's `swcraft.yaml` names this release
(`carchetype --help` lists the presets and the commands). It is installed into the same environment as
SWCraft and was checked against this SWCraft release before publication; installing a newer SWCraft
replaces it. Nothing is downloaded separately.

This is the first release that ships it; 0.2.0 and 0.2.1 were never shipped in a release. Since
0.2.1, a project's passport is compared with what SWCraft reports by the major of the contract version,
and exactly in every other field, so a new minor of SWCraft's contract needs no new Carchetype.
Carchetype still writes contract version 12.0.0 into the passports it emits, deliberately, by that rule.
The `swcraft.yaml` of a project it generates names `outputs.needs` (`dist/needs.json`) where it named
`outputs.rst`; the model it writes is unchanged.

## The model's contract is `12.6.0`

`contractVersion` moves from `12.0.0` to `12.6.0`, by six minors and two prose patches: seven
kinds, twenty-six fields and twenty-nine rules are added — the variables, the exclusive areas, the `data`
event, the unknown key, the duplicate link, and the two warnings on what the published `needs.json` cannot
carry — and several earlier rules apply to more fields than before; nothing is removed or renamed. The
inventory goes from 15 layers, 59 kinds, 323 fields and 311 rules to 15 layers, **66** kinds, **349**
fields and **340** rules. The two patches change descriptions only: a requirement's
`baseline`, `source`, `stub` and `version` and the requirement's own description say what the import now
does, and six descriptions say that an architecture requirement is published in `needs.json` as a need of
its own and an imported one only by its id. Three rules are new warnings:
`rule:swc.variable.read-without-init`, `rule:trace.link-unpublishable-id` and
`rule:trace.requirement-blank-text`. A `12.0.0` model is a valid `12.6.0` one, unless it holds a key
its kind does not declare, a blank measure or a link list naming one target twice.

## For contributors

The runtime pins did not move: `update-pins` rewrote nothing, so Node.js, CPython, `elkjs` and the
companion extensions are 0.21.0's.

## What this release does not reach

- **The requirements exchange.** Only Sphinx-Needs 9.2.0 was built against for the published file;
  other releases were not tried. **A requirement id holding `.` is not supported in a published link**:
  Sphinx-Needs 9.2.0 cannot link such an id under any setting, so a model with such a link cannot be
  published until the link or the id changes, and SWCraft offers no other spelling of it. A link to an id
  holding `[` resolves in the team's build only with the guide's `"parse_conditions": False` and `"parse_dynamic_functions": False`; the import
  reads such an id whole only where the team's file holds a need of that whole id, and a team file holding
  both `X` and `X[c]` gives `X[c]`. An unconfirmed link to an id the team does not hold is an
  information line in the team's build only because of the guide's `allow_dead_links`; without it the
  team's `-W` build fails. A confirmed link names a requirement the team still holds only when your
  incoming requirements come from an import of its current delivery; one written by hand, or imported
  before the delivery was recorded, carries no `baseline`, and nothing checks that the team holds it. A
  `derived_from` naming an element your model does not hold is published as unconfirmed.
- **The check on `outputs.needs`** looks only at the manifest outside `dist/` and `views/`, so any other
  project file — what `swcraft init` scaffolds (`moon.yml`, `.vscode/settings.json`),
  `trace-decisions.yaml` — is not reached; nor are, below `dist/`, a file kept there by hand, a component
  export below `components/` and an experiment's report below `experiments/` (their names come from the
  model or the user), a file a later SWCraft release adds, or the same file reached through a link.
- **A `needs.json` write that fails** in `swcraft generate needs` leaves the previous file as it was: the
  new one is written beside it and replaces it whole. The assistant's `build` has removed the previous
  file by then, so it leaves none. Hand over the file a successful build left.
- An architecture requirement with an empty title or description is still published, and the team's
  build shows it; `check-model` only warns about it, and the requirements import refuses such a
  requirement, so it does not come back through SWCraft's own import of the file. A team that already uses `satisfies`, `derived_from` or `asil` with a
  meaning of its own shares the name; SWCraft offers no rename. The team sees an element as a title and
  an id, linking to the file that declares it — a port or a runnable to its whole component's file; a
  component is not shown as the container of its ports and runnables, and an element's kind is a tag,
  not a type. Whether a `file:` or `vscode:` link opens is the reader's browser's and system's. The
  team's next delivery is refused by the import unless its mapping ignores the keys the declarations
  add; with `needimport` it also ignores SWCraft's three need types. How the file reaches the
  requirements team is yours to choose.
- **Inter-runnable variables.** Nothing protects an explicit variable that runnables on different tasks
  share, the implementation policy and an access's scope are not modelled, and no diagram draws a
  variable.
- **Exclusive areas.** SWCraft does not check what an area protects, it models no order in which a
  runnable enters several areas and so finds no deadlock, and it does not say which tasks an area can
  delay, which depends on how the RTE integrator implements the area. No diagram, resource report or
  metric figure is computed from the areas. The order in which areas may be nested and the exclusive
  area API options of AUTOSAR 4.3.0 are still not read by the import.
- **The guide tool** finds the words the guide uses: a question put in quite other words can find
  nothing, or a section that answers something else, and the assistant then reads the list of pages.
  The *Refusals* page explains the refusals of a change; the other tools' own messages are found by
  search, not looked up. The link at the end of an answer opens in VS Code only; in a terminal
  assistant it opens nothing. A project whose agent profile came from an earlier release does not
  mention the tool, though the assistant still sees it among its tools.
- **`data` events.** The model holds no arrival rate, so SWCraft says nothing about how often such a
  runnable runs, its response time or an end-to-end latency, and a clean check says nothing about
  whether an RTE generator accepts the model. Two runnables started by one queued element in two tasks,
  which an RTE generator of a later AUTOSAR release refuses, are not checked. Wait points and activation
  reasons are not modelled. No diagram draws the event. The three other data events of AUTOSAR are still
  not read by the import.

## What upgrading takes

1. **Install the 0.22.0 archive, then set `toolchain_version: "0.22.0"`** in each project's
   `swcraft.yaml`. Until you do, every command that writes or gates refuses a project pinned to
   0.21.0 with the pin sentence. The read-only commands (`diff`, `impact`, `list`, `metrics`,
   `query`, `resource-report`) and `swcraft guard` only print a warning, so an assistant keeps
   working meanwhile.

2. **Rename `outputs.rst` in `swcraft.yaml`**: replace `rst: dist/needs` under `outputs:` with
   `needs: dist/needs.json`, or delete the line to take the default. In a project scaffolded from the
   template, replace the `generate-rst` task in `moon.yml` with the template's `generate-needs` task
   (command `swcraft generate needs`, output `dist/needs.json`), and name `generate-needs` wherever
   `generate-rst` appears in `deps` (the `validate-arxml` task and the `build` task), or the build fails
   at that task. A script that ran `swcraft generate rst` runs `swcraft generate needs`.

3. **Run Check Model, and fix each new error it names.** For each `model.unknown-key` finding, rename
   the key to the field it was meant to be, or delete it; for each `manifest.unknown-key`, rename or
   delete the manifest key (a leftover `c4:` line under `outputs:` included); for each
   `safety.measure-blank`, write the mechanism into the entry, or delete the entry and answer the
   finding that comes back. A pipeline under `--warnings-as-errors` also refuses a model whose runnables
   read a variable without an `init`; give the variable an `init`.

4. **The requirements import.** An import whose file names no version passes `--baseline`. If the
   requirements team's file uses its own need types or field names, write a mapping file and pass it
   with `--mapping` (VS Code asks for it). The team's own import of SWCraft's `needs.json` ignores the
   keys SWCraft adds; the guide gives its `conf.py` lines.

5. **Run *SWCraft: Onboard Project* again.** The assistant profile's model section now names the
   variables, the exclusive areas and the `data` event, and the profile now sends the assistant to the
   guide's How-to pages. It overwrites the profile, so keep a copy of anything you edited in it. An
   earlier profile keeps working: it does not mention `guide`, which the assistant still sees in its
   tool list.

6. **Add `"cSpell.ignorePaths"` by hand to an existing project's `.vscode/settings.json`**, if you want
   it, with your own folders: `"cSpell.ignorePaths": ["model/**", "dist/**", "views/**"]`.

7. **A pending trace-link proposals file:** run the search again before applying it.

8. **Exchange component files only between projects on this release**: an earlier release refuses
   every component file this one writes, so upgrade both sides. A model imported before this release
   gains its variables, exclusive areas and `data` events when it is imported again.

9. **Scripts:** one that reads `swcraft import component`'s exit status treats 3 as the refusal
   `--update` resolves; one that matched the cohesion reason text matches
   `one port or variable: every runnable that uses one uses only it`; and an experiment configuration
   whose `output` is refused points at another directory, or the named file is moved away.

Nothing else moves in a project: the hooks and the generated whole-model ARXML of a model without the
new elements are unchanged from 0.21.0. A project on 0.20.0 or earlier follows [0.21.0's
note](0.21.0.md) first.
