# SWCraft 0.13.0

**Released 2026-09-23** (the bump commit; the tag follows the `verify` gate on both self-hosted
runners, Linux and Windows, on this commit, and the tag's own run publishes the release archives to
the NAS). This note was written with each change rather than after it, so every figure below was
measured on the host and at the commit that produced it.

## An import keeps the elements it used to drop

A real AUTOSAR export rarely stands alone. It references types and interfaces that live in **other
files of the same delivery**, and until now `swcraft import model` answered such a reference by
**dropping the element that made it** — a port whose interface was not in the file, a value type
whose base type was not, an operation argument whose type was not — and then dropping whatever hung
off that element in turn. The import reported a skip line and the project looked complete.

Now the element is **kept**. The reference is written into the field it already has — a port's
`interface`, a data element's or an argument's `type`, a value or reference type's `base`, a record
field's `type`, an array's `element_type` — exactly as the export spelled it, as a full AUTOSAR path
such as `/Delivery/Common/Interfaces/IWheelSpeed`. Nothing guesses, and nothing binds the reference to
some other element that happens to carry the same short name at the end of the path.

Two consequences, and the second is the one to plan for.

- **Elements come back.** The references that used to take their elements
  with them are kept, and the connectors and delegations that had fallen with those elements are
  imported.
- **The project does not generate until you finish it.** `swcraft check-model` reports every kept
  reference — and, **among references**, exactly those: it never reports one the import resolved, and
  never invents one. It is still the model gate it always was, so it also reports anything else your
  project needs finishing for, which an import can leave behind for reasons of its own — a base type
  the export declares with no `NATIVE-DECLARATION` is the one you are most likely to meet, and it is
  listed in the import's own report as well. `swcraft generate arxml` refuses the project and writes
  nothing at all. That is a change of behaviour on exports that generated
  before: 0.12.0 produced a document that was silently missing every element the import had dropped.
  Two repairs, and you choose: **supply the missing file** and import again, or narrow `--packages`
  to a set of packages whose contents reference nothing outside themselves.

The report gains a section for it, one line per target:

```text
UNRESOLVED 6 reference(s) to 2 target(s)

Unresolved references (6 reference(s) to 2 target(s); the element that made each reference is kept, the path is written as the export spelled it, and check-model reports every one):
  - /Common/Interfaces/ILevel (DEST SENDER-RECEIVER-INTERFACE) is declared by no element of this export; 4 referring element(s):
      /Chassis/Components/Reporter/pLevel (P-PORT-PROTOTYPE PROVIDED-INTERFACE-TREF -> swc.port.interface)
      /Chassis/Components/Monitor/rLevel (R-PORT-PROTOTYPE REQUIRED-INTERFACE-TREF -> swc.port.interface)
      /Chassis/Compositions/Root/pLevel (P-PORT-PROTOTYPE PROVIDED-INTERFACE-TREF -> compositions.composition_port.interface)
      … and 1 more
```

Every line names the target you would have to supply, the `DEST` the export gave it, why it did not
resolve, and which of your own elements pointed at it — by its AUTOSAR path, the ARXML attribute
that carried the reference and the model field the path was written into.

`--verbose` lists every referring element instead of the first three. The count on the heading line
is every reference, never a sample.

**Three things this does not cover, deliberately.** A component prototype whose type the export does
not carry is still imported as an *external stub*, as it was before, carrying the reference and its
`DEST` so that a re-export points where the source did. A connector or delegation endpoint on such a
stub's port is still skipped, because SWCraft builds the emitted path out of the member and the port
and there is no port to build it from. And a reference to something the export **does** contain and
SWCraft could not import — an unsupported kind, an element with no name — is not in this section at
all and stays in the skipped list where it was.

## One name declared twice is one element, or none

An export may declare one short name in two packages, and AUTOSAR allows it. SWCraft, which has one
namespace per layer, used to answer that in four different ways, one of which
quietly kept the first declaration and discarded the second.

There is one answer now:

- if the two declarations are the **same in everything SWCraft can read**, they become **one
  element** under the declared name, and every reference to either one resolves to it;
- if they **differ**, **neither** is imported and the name stays taken, so nothing else quietly
  claims it.

A difference in `DESC` alone is not a difference: the declaration that comes first in the export
keeps its text, and the report names the other path and the text that was not carried. A declaration
that references a name which is itself declared twice with different definitions is itself a
conflict, and so is one whose definition would depend on itself through a cycle of references.

**This is SWCraft's own policy, and the report says so.** No AUTOSAR release defines what makes two
declarations of one name "the same" — every constraint in the standard is about two elements being
*compatible*, not identical — so SWCraft states its rule rather than claiming one, and prints every
source path so that you can decide:

```text
Merged declarations (2; one name declared more than once and the declarations identical in everything SWCraft reads -- one element kept, every path resolving to it):
  - data_types/SW-BASE-TYPE/Flag declared at /Left/Types/Flag, /Right/Types/Flag -- kept as one element
  - interfaces/SENDER-RECEIVER-INTERFACE/ILevel declared at /Left/Interfaces/ILevel, /Right/Interfaces/ILevel -- kept as one element
      description not carried, from /Right/Interfaces/ILevel: Level reported by the right-hand subsystem.

Conflicting declarations (2; one name declared more than once with different definitions -- nothing of the group is imported and the name stays claimed):
  - data_types/SW-BASE-TYPE/Word16 declared at /Left/Types/Word16, /Right/Types/Word16 -- not imported: the declarations differ in BASE-TYPE-SIZE
  - data_types/IMPLEMENTATION-DATA-TYPE/Distance declared at /Left/Types/Distance, /Right/Types/Distance -- not imported: it references data_types/SW-BASE-TYPE/Word16, which is itself declared more than once with different definitions
```

**What this can cost you.** An export whose two declarations differ imported **one** of them before
and imports **neither** now, so a project can come out with an element it used to have missing — and
every reference to it in the *Unresolved references* section, which is how you find it. Repair the
export, or select the packages you mean: a `--packages` selection that keeps exactly one of two
conflicting declarations imports that one, and the report says which.

**One shape neither repair reaches, and it is a real loss.** AUTOSAR scopes an assembly connector's
short name to the composition it is drawn inside, so two compositions may each declare a connector
called `Wire` and the export is perfectly valid. SWCraft's `connectors/` layer is **flat** and has
room for one of them. 0.12.0 imported the first and skipped the second with an overwrite reason;
0.13.0 reports the pair as a conflict — the differing property is named `composition` — and imports
**neither**. Nothing about the export is wrong, so there is nothing to repair and no selection that
helps; if you need both connectors, rename one of them in the source model. The rule is deliberate:
importing whichever happened to come first would be a guess about which connector the project means,
and that guess is what this release exists to remove.

**What it compares.** Everything SWCraft's reader carries: sizes, encodings, native declarations,
categories, byte order, memory alignment, every own property, the members of an interface or a record
by name and order, and every reference **after resolution**. It cannot compare a property it does not
read — a vendor extension, a variation point, an `IS-SERVICE` flag — so two declarations differing
only in one of those are merged. What it deliberately ignores is **formatting**: whitespace inside an
element whose value is a token, a number or an enumeration is not a difference, so an exporter that
writes `<CATEGORY>FIXED_LENGTH</CATEGORY>` and one that puts the same word on its own line declare the
same base type. An init value is compared by its **value** for the same reason: `0x0A` and `10` are
one number, and the radix the export wrote is something SWCraft reports rather than compares. A
difference in the *text* of a value it cannot read past still counts, though — `8` and `08` are one
memory alignment to AUTOSAR and two spellings here, and the cautious answer wins. The comparison is
also order-sensitive: two declarations carrying one set of data elements in two orders are treated as
differing. Note what every cautious answer costs: a conflicting group imports **neither** declaration
and leaves every reference into it dangling — not one element, both.

Two smaller rules follow the same line. A `SW-BASE-TYPE` and an `IMPLEMENTATION-DATA-TYPE` that
declare **exactly** one short name are refused as a duplicate — neither is imported and the name stays
taken — because they are two kinds of one SWCraft layer and cannot share an identity; names differing
only in **case** are untouched and stay two elements in two files, exactly as they are today. And
a `--packages` selection is applied **after** the verdict, so narrowing your selection can resolve a
conflict but never create one.

## The physical view of a signal is something the model says

A signal has two descriptions in AUTOSAR. One says what the software stores — eight bits, unsigned.
The other says what it **means**: kilometres per hour, a hundredth of the stored number, between
zero and four hundred. Until now SWCraft's model had only the first, and the exporter papered over
the gap: wherever a record field or an array element named a value type, it **invented** a physical
type called `{name}_AppView` and a mapping called `DataTypeMappingSet` to pair the two, because both
AUTOSAR schemas refuse an implementation type in those positions. Neither name was in your model,
neither could be given a unit, and an import had to undo them again.

Two new things say it properly.

**An `application_type` is a data type kind like any other.** It declares an optional `unit` — free
text such as `km/h` — an optional `conversion`, the two numbers `factor` and `offset` with
`physical = stored × factor + offset`, and an optional `range`, the physical `min` and `max`:

```yaml
# model/data_types/VehicleSpeed_Kph.yaml
kind: application_type
name: VehicleSpeed_Kph
unit: km/h
conversion:
  factor: 0.1
  offset: 0.0
range:
  min: 0.0
  max: 400.0
```

Each of the three is emitted only if you declare it, so a type that declares none of them is a name
and a category and nothing more.

**A mapping set says which implementation type stores it**, and a component names the sets it uses:

```yaml
# model/mapping_sets/PhysicalTypes.yaml
name: PhysicalTypes
maps:
  - application: VehicleSpeed_Kph
    implementation: uint16
```

```yaml
# model/swc/sensing/SpeedSensor.yaml
name: SpeedSensor
data_type_mappings: [PhysicalTypes]
```

`model/mapping_sets/` is a required directory and **may be empty**: a project whose interfaces are
typed by value types and reference types alone needs no set. An **enumeration** on a port does need
one — an enum is a physical type like any other application type, and the pairing is what says what
stores it.

What follows from that:

- **A record field and an array element may no longer name a value type or a reference type.** They
  name an application type, an enumeration, a record or an array. `swcraft check-model` reports
  each offender and `swcraft generate arxml` refuses the project and writes nothing. This is the
  one change that can stop a model that generated before — see *Upgrading a project* below.
- **Every application type *or enumeration* a component's ports speak in has to be paired by one
  of the sets that component names**, because generated code cannot be produced without knowing
  what stores the value. `swcraft check-model` reports the ones that are not, and
  `swcraft generate arxml` refuses the project — and refuses a single component's export
  (`--component`, `--all-components`) whose own ports speak one, where the other components of an
  `--all-components` run are still exported. The enumeration half is the one that reaches a
  project with no composite at all: a project whose interfaces carry an `enum`-typed data element
  or argument needs a set even though nothing about its records or arrays moved.
- **A component stores each physical type one way.** The sets one component names may not pair
  the same application type or enumeration with two different implementation types between them —
  the AUTOSAR software component template allows exactly one per component. `swcraft check-model`
  reports the component and the type, naming every implementation type and the set each comes
  through, and `swcraft generate arxml` refuses the project, and a single component's export, and
  writes nothing. Two sets that pair a type with the **same** implementation type are fine, and two
  different components may store one type differently. The check reads every pair of every set a
  component names, not only the types its ports speak, because every pair ends up in its generated
  file.
- **The exporter invents nothing.** The two generated names are gone, and with them the two checks
  that used to refuse a data type called `Speed_AppView` or `DataTypeMappingSet`. Both are ordinary
  names you may now declare.
- **A mapping set may not take a data type's name**, nor one of the names a data type generates:
  the sets and the types are written side by side into one package, where two elements cannot share
  a name. `swcraft check-model` reports it and `swcraft generate arxml` refuses. `swcraft import
  model` renames such a set to `{name}_app` and says so in its report; `swcraft import component`
  refuses the import and writes nothing.
- **Three new generated names take their place, and only where you ask for them**: a declared `unit`
  becomes a unit element called `{name}_Unit`, a declared `conversion` a computation method called
  `{name}_Compu`, a declared `range` a data constraint called `{name}_Range`. They count against the
  128-character AUTOSAR limit like every other generated form — but only when the field exists, so a
  type with no `unit` is charged for no `_Unit`.
- **A model that declares no application type and no mapping set generates exactly the bytes it
  generated before.** That is asserted file by file, at both AUTOSAR versions, and the diagrams and
  the requirements document of every model are unchanged either way.

## An import brings the physics back, and stops losing enumerations

Two classes of element that used to arrive flattened now arrive whole.

- **Physical types.** An application type the export declared with a unit, a conversion or a range
  used to become a stand-in reference type over whatever implementation type a mapping set paired
  with it, and the three properties were dropped; if no set paired one, the type was skipped
  outright. It is imported as an `application_type` now, with its unit, its conversion and its
  range, whether or not anything maps it.
- **Enumerations declared twice.** Where an export declared an enumeration and an implementation
  type of exactly one name, the import collapsed the pair onto the
  implementation type and **every literal was lost**. The enumeration is kept now, with its
  literals, and the implementation half takes the name `{name}_impl`.

**A same-name pair is still collapsed where it really is one thing said twice**: where the physical
half declares no unit, no conversion, no range and no literals, and nothing composite names it. The
import's report tells the two apart — the collapsed ones under *Type-name reductions*, the kept ones
under the renames section with their `{name}_impl` twin.

**What the `{name}_impl` rename costs, so that it is not a surprise.** It is a rename in the
imported project: every file, every reference and everything SWCraft generates from that project
spells the implementation type `{name}_impl`, so a re-export is not name-identical to the source on
those elements. Nothing undoes it on a later import, and `Speed_impl` is a perfectly legal name you
may declare yourself.

**Mapping sets are imported too**, one model file per set, with each component's references to them.
A pair whose implementation side is a structure or an array implementation type is **dropped with a
line in the report** — those two kinds are not modelled yet — and the rest of the set is written.

Two more report changes. A new section, *Physical properties not imported*, names every type written
without a property it declares and says which property and why; and a computation method SWCraft
will not read rather than guess at — a non-linear one, one with more than one scale, one whose
denominator is not exactly one — imports its type **without** the conversion and is named there. So
is every type whose category changes on the way through, because a later export writes it with the
category of the kind it was written as — `VALUE` for a physical type, `TEXTTABLE` for an enumeration.
That is a category SWCraft has no kind for, such as `BOOLEAN`, and it is also an enumeration the
export declared `VALUE`, the spelling the standard pairs with a table, so the section can have one line per enumeration. One case is not in that section: a physical type that declares nothing but its category and
shares its name with the storage type it is mapped onto is folded into that storage type, so no
physical type is written and its category goes with it; the folding is listed under the type-name
reductions by a whole-model import (a component import does not list it). Both importers print this section, and neither refuses an import because of it. The
import never recomputes physics.

**One class is smaller evidence than the rest, and it is worth saying so.** A conversion with more
than one scale or a denominator other than one is tested only against documents built for the
purpose.

## The diagrams are easier to read, and show where the software runs

`swcraft generate diagrams` draws the same views from the same model, and they read differently.
The first drawings of this release were read on real tool exports the maintainer holds privately before the tag, and what
that reading found was fixed before it — so what follows describes the shipped drawings, not the
first attempt.

- **The port glyphs follow the AUTOSAR port notation, seated as the VFB figure seats them.** A
  sender's port is a pentagon arrow on a short stem out of its square, a receiver's a fork on a
  longer stem opening towards the line, a server's an empty circle on a stem and a client's a half
  circle on one. The direction of the data is in the shape now, not in a fill or a dot, and a line
  ends where the glyph ends.
- **A composition's own ports face outwards.** A boundary port sits astride the frame with its
  glyph outside, pointing away from the composition exactly as a member's port points away from
  its box, and the delegation inside arrives at the back of the square. The port's name is written
  inside the frame, and the frame keeps enough room beside its border for its longest port name,
  so a name never runs over a member.
- **A port's name no longer runs over its square.** A label is anchored at its own port's side, so
  a long name runs into its component's box rather than over the glyph, and a box is sized by an
  estimate per kind of character — a name in capitals is wider than one in lower case — so a member
  whose ports have long capitalised names is drawn wider.
- **An overview's lines are straight.** The bundled lines between components are routed with right
  angles like a block diagram's, so an arrowhead always enters its box square-on, and the head keeps
  its size whatever the line's width.
- **A line can be pointed at, and lights up with its two ends.** Every line has an invisible band a
  few pixels wide around it that the pointer can rest on. Resting on a line lights it black and
  thicker with the two ports it joins, and writes its title — `connector Name: A.p -> B.r` — in a
  status line under the picture at once; a click keeps it lit until a click on empty space. Resting
  on a port lights every line it has and the ports at their far ends. On a sequence view a step
  lights its task and its component.
- **An overview's number square opens the list behind it.** A click on the number between two
  components opens a panel on the page listing that pair's connectors, one line each — the
  connector's name, its sending and receiving port with their components, and the interface, with
  the connector's description under it when one is declared — in natural order and scrolling when
  the list is long; a second click, a click on empty space or the panel's own button closes it.
  Resting on the square shows the head line alone, and the page's search finds a pair by any one of
  its connectors' names.
- **The frame's name leads up.** On a composition placed inside another, the frame's name carries
  an `↑` and opens the containing composition's page of the same kind, which marks the member you
  came from and scrolls to it. The page's header shows the chain from the root composition as
  plain links. A composition placed in several others lists them instead and chooses none.
- **A new view, `deployment`**, for a model that declares tasks: the processor, its cores, the
  tasks on each core and the components each task runs, each core labelled with the safety level it
  is qualified to host and each component with its effective level. It is written as
  `deployment.svg` and `deployment.html`, listed in the index, and a model without tasks gets no such
  file. A task on a core the model does not declare, and a component no task runs, cannot be put in
  a box and are named in `report.txt` — so a project with a component no task runs now lists it
  under *Not drawn*.

The pages are still files and make no request but for the file itself. The drawings grow with what
they now carry — the connector lists behind the number squares most of all: on a large model the SVG files together
are noticeably larger than 0.12.0's, and a whole generation takes as long as before.

## The editor marks what a save made stale, and regenerates nothing

In VS Code, saving a model file no longer regenerates the diagrams. On a large model that took seconds
on every save, and it could block a **Build** pressed right after. Instead, **Build** and **Diagrams**
each show the state of the file they generate — the ARXML and the diagram index: *not generated*, a
yellow dot and *out of date* when the model or `swcraft.yaml` changed after the last successful
generation, and nothing extra when it is current. The number on the SWCraft icon in the activity bar
counts the out-of-date files. Press the item to bring its file up to date; after a new generation the
browser page shows it when you press its *Reload*.

While a command runs, the panel now says so — every command that starts the toolchain, not only
**Build** and **Diagrams**: **Check Model**, **Export Component**, **Diff**, **Impact**, **Resource
Report**, **Onboard Project**, **Check Editor Tooling** and the two toolchain commands alike. A
progress bar under the view's title, the item's text `running…`, and a status-bar text —
`Build — 3/6 generate arxml` for a **Build**, which moves on as each of its six steps starts,
`Check Model — running…` for the others. None can be cancelled from the panel, and a command that
asks you something first asks before it shows itself running.

Two cases read *out of date* on purpose, because the record of the last successful generation is kept
by the VS Code workspace and not by the files: an output written from a terminal, and a branch switched
while the window was closed, both read *out of date* until the item is pressed. A **Build** that fails
at its last step, the ARXML check, leaves the ARXML on disk and reads *out of date* as well.

## Smaller things

- **The release notes are part of the user guide.** The guide that `swcraft docs` serves and
  *Open Guide* opens carries a *Release notes* section — this note and every one since 0.9.0, and
  the 0.6.0 note the upgrading page points to — so a workstation that cannot reach the source
  repository can still read what an upgrade takes. No guide page links into the repository any more.
- **Windows PowerShell 5.1 and a pipeline.** Piped or redirected through Windows PowerShell 5.1, a
  report's `×` or an em dash reads as `├ù` or similar, because that shell decodes a program's output
  with the console's legacy code page; printed straight to the console it is correct, and
  PowerShell 7 decodes it correctly. The guide's command-line page gives the two answers that work:
  the command's own `--report FILE` where it has one, or
  `[Console]::OutputEncoding = [Text.Encoding]::UTF8` before the pipeline.
- **Creating an element refuses a lost race instead of overwriting.** The Python API's `create_*`
  functions open their file exclusively, so if another process writes that file between the moment
  SWCraft picks the name and the moment it writes, the create fails with a sentence naming the layer,
  the element and the file rather than replacing the other process's bytes. The sentence says the
  file *is there and the listing did not name it*, and deliberately not that it *appeared*: a
  filesystem that folds Unicode normalization can answer the listing and the open with two spellings
  of one name, and there the file was there all along. Updates and the `add_*`
  functions are unchanged — each rewrites a file it has just read. This is a guarantee the filesystem
  gives; it has not been measured on Windows or over NFS.
- **A file where a layer directory belongs is a sentence, not a stack trace.** If `model/tasks` is a
  regular file rather than a directory, writing a task now says so, naming the layer and
  `tasks` rather than surfacing the operating system's message about a path on your disk. Reading
  such a project still shows that layer as empty.
- **Both importers name a case-only pair's files the same way.** `swcraft import model` wrote each
  layer in the export's own order while `swcraft import component` planned its files in name order,
  so the two could give the plain file name and the `~1` to opposite elements of one pair. Both use
  the export's order now. This changes nothing about any element's name or any generated file — but
  it does change which element of a case-only pair takes the `~1`, and it changes the **order** in
  which `swcraft import component` lists its created and reused interfaces and data types, for any
  export whose order in the file differs from alphabetical. A script that parses that report should
  not depend on the order of those lists.
- **A pretty-printed `<CATEGORY>` is read as the value it spells.** AUTOSAR gives `CATEGORY`,
  `BASE-TYPE-ENCODING`, `BYTE-ORDER` and `MEM-ALIGNMENT` types that ignore the whitespace around
  them, and SWCraft now does too. An exporter that writes the value on its own line, indented, used
  to have its element refused — *unsupported category* — along with everything typed by it; those
  elements are imported now. It is why two declarations that differ only in how they are laid out
  count as the same declaration, and it also decides which elements are imported at all. So an
  export of that shape imports **more** than it did under 0.12.0, and its report says so.
- **A data type map with one side missing is reported, not lost.** A `DATA-TYPE-MAP` that names an
  application type and no implementation type, or the other way round, pairs nothing, and both
  importers used to drop it without a line. `swcraft import model` now lists it among the skipped
  elements and still writes the mapping set with every whole map it carries; `swcraft import
  component` refuses the file, as it refuses any other part of a component it cannot carry, because
  the component would otherwise arrive without a pairing its exporter declared. SWCraft's own
  component exports never contain such a map.
- **An element may not be named for a device Windows reserves.** Windows holds no file whose name
  before the first `.` is `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9` or `LPT1`–`LPT9`, in any case, so
  a project holding `interfaces/CON.yaml` could not be checked out there — and until this release
  nothing said so. The rule is the same on every platform: `swcraft check-model` reports such a
  stored file, naming the layer and the element; the editing protocol refuses to create such an
  element; and both importers skip it with a reason naming the rule — `swcraft import model` lists
  it among the skipped elements and goes on, `swcraft import component` refuses the file with
  nothing written. **What that skip costs**: an element that refers to the skipped one keeps the
  name it spelled, which now names nothing, so `swcraft check-model` reports that reference and
  `swcraft generate arxml` refuses the project until the name is changed in the export. A near miss
  — `CONSOLE`, `COM10`, `NULL` — is an ordinary name. Windows' own naming page also lists `COM0`,
  `LPT0` and the superscript digits after `COM` and `LPT`, and treats a trailing space before the
  extension as the same device; SWCraft does not refuse those, and how Windows treats them was not
  measured. A stored file of such a name has to be renamed by hand: see *Upgrading a project*. The
  Python API's `create_*` functions accept a reserved name as they always did.
- **The import report no longer names where your project is stored.** When `swcraft import model`
  replaces the empty root composition `swcraft init` scaffolded, its *Replaced scaffolded
  compositions* line used to print that file's full path on your disk. It names the file relative to
  the model folder now, as every other line of the report does: `compositions/Root.yaml: the empty
  root composition 'Root' was removed and replaced by the root this import mapped`. The rarer line
  that says such a root could not be located names `compositions/` the same way.
- **A `--packages` import reports only the renames and collapses of what it writes.** The
  *Type-name reductions* and *Type/prototype/reserved-name renames* sections used to list every
  type of the whole export that was collapsed onto its twin or renamed, whatever the selection kept.
  A one-component selection could print mostly rename lines about types it
  never wrote; it prints only those about an element in the project now. An import without
  `--packages` prints the same lines as before.
- **A data element with no name skips its interface instead of aborting the import.** A
  sender-receiver interface one of whose data elements has an empty `SHORT-NAME` used to stop the
  whole import with *must be an AUTOSAR Identifier* and nothing written, whenever that element's
  type could be found. The interface is skipped now and listed among the skipped elements —
  `SENDER-RECEIVER-INTERFACE: a data element has missing or blank SHORT-NAME` — and the rest of the
  export is imported. Where the nameless element's type could **not** be found, the interface was
  already skipped; the reason it is listed under is now the missing name rather than the missing
  type.

## What this release was measured against

Real tool exports the maintainer holds privately, on macOS: imported, reported, checked, and — over a
selection of packages whose contents are complete on their own — generated at both AUTOSAR versions and
validated against the licensed AUTOSAR schemas at 4.2.2 and at 4.3.0. Windows was
not measured.

The schemas do not check what a category says, and one thing they let through is SWCraft's own: every
enumeration is written with the category `TEXTTABLE`, which is a computation method's category, and
the standard's table of the categories an application data type may take (`[constr_1007]`, at 4.2.2
and at 4.3.0) does not list it. Every earlier release wrote enumerations the same way, and this one
does not change it.

## Upgrading a project

### The model format changed, and two steps of this are for every project

The two sections above are the first change to the model format since `0.11.0`, and unlike the rest
of this release they can stop a project that worked. Step 1 is for **every** project; step 2 for a
project whose records or arrays name a value type or a reference type; step 3 for a project whose
interfaces carry an **enumeration**, which is a much wider set — a project with no composite at all
meets step 3.

1. **Create the new layer directory**, which is required and may be left empty:

   ```sh
   mkdir model/mapping_sets
   ```

   A project scaffolded with `swcraft init` from this release gets it already. Nothing else about
   an existing model has to move for `swcraft check-model` to read it — unless an element is named
   for a device Windows reserves, which *If an element is named for a Windows device* below
   covers.

2. **Give every composite member a physical type.** Run `swcraft check-model`: each offender is
   reported by name, and says which record field or array element names which implementation type.
   For each one:

   a. **Declare the physical view** in `model/data_types/`, with whatever of the three properties
      you actually know. A type with none of them is legal and is exactly what the exporter used to
      invent for you, so the minimum change is three lines:

      ```yaml
      # model/data_types/Distance_M.yaml
      kind: application_type
      name: Distance_M
      ```

      If you know the physics, say it — `unit: m`, a `conversion`, a `range` — and it reaches the
      generated file, where the invented type carried nothing.

   b. **Point the member at it.** In the record or the array, replace the implementation type's name
      with the new one:

      ```yaml
      # model/data_types/Pose_T.yaml
      kind: record
      name: Pose_T
      fields:
        - name: x
          type: Distance_M          # was: float32
      ```

   c. **Pair the two in a mapping set**, so that generated code knows what stores the value:

      ```yaml
      # model/mapping_sets/PhysicalTypes.yaml
      name: PhysicalTypes
      maps:
        - application: Distance_M
          implementation: float32
      ```

      One set for the whole project is fine, and so is one per domain; a component references the
      set as a whole.

   d. **Name the set on every component whose ports speak the new type**, in `data_type_mappings`.
      `swcraft check-model` reports the ones that still need it.

   e. **Re-run `swcraft check-model` until it is clean**, then `swcraft validate`.

3. **Pair every enumeration a port speaks.** An `enum` is a physical type, so the rule in step 2c
   applies to it whether or not the project has a composite: `swcraft check-model` reports each
   component that speaks one and names no set pairing it. The enumeration itself does not move —
   only the pairing is new:

   ```yaml
   # model/mapping_sets/PhysicalTypes.yaml
   name: PhysicalTypes
   maps:
     - application: GearPosition        # the enum, unchanged
       implementation: uint8            # what stores it
   ```

   Then name the set in `data_type_mappings` on every component whose ports speak it, exactly as
   step 2d does, and re-run `swcraft check-model`.

**What the generated file gains.** Where the exporter used to write `Distance_M_AppView` with
nothing in it and a mapping set called `DataTypeMappingSet`, it now writes the type you declared,
under your name, with the unit, the computation method and the data constraint you gave it, and
your own mapping set. A record or array that already named an enumeration, a record or another
array is untouched.

**If you import exports, expect the `{name}_impl` twins.** A re-import of an export whose
enumerations or physical types share a name with an implementation type produces two elements where
`0.12.0` produced one, the implementation half named `{name}_impl`, and every reference inside the
imported project points at the right one. If you have hand-edited a previously imported project,
diff before you overwrite it.

**A component export written by an earlier release still imports.** `swcraft import component` reads
a file `0.12.0` or earlier wrote and imports its `_AppView` types as ordinary application types and
the set that paired them as an ordinary mapping set — no special case and nothing to do. What
changed on the export side is that a component whose ports speak an application type now carries the
mapping sets it names, narrowed to what that component's own ports reach; re-importing such a file
into the project it came from reports the set as *reused*, not as a conflict.

**Components exported from one project assemble in another.** Each export carries the shared set
narrowed to its own component, under the set's one name, so the second component you import usually
brings pairs the first did not. `swcraft import component` adds them to the set it finds and says so
in an `EXTENDED` block naming every added pair and every other component that uses the set — on
`--dry-run` too, before anything is written. It refuses, with nothing written, an import that would
leave one physical type stored as two different implementation types: inside one set, or for any
component — the one you import or one already there — across the sets it names, read as the whole
import leaves them. Two sets that agree on one implementation type are not refused. What it does not
refuse is a type your project already stored two ways before the import, through sets the import
leaves as they were: that ambiguity was there before and the import does not create it, so it is
left to `swcraft check-model`, which reports it, and `swcraft generate arxml`, which refuses the
project until one of the pairs is removed or the component stops naming one of the sets.

**What this release does not claim about the new emission.** It is checked against real tool exports the maintainer holds privately
and the licensed AUTOSAR schemas at 4.2.2 and 4.3.0. Three limits are known and stated rather than
implied: a unit is text on the type, so two types spelling the same physical unit emit two unit
elements where the source had one; an implementation structure or array cannot be paired yet, so a
mapping onto one is dropped with a line in the report; and the compatibility check between two
physical types compares the unit, the conversion and the range and nothing else — a difference in
anything AUTOSAR carries and SWCraft does not is not seen.

### If an element is named for a Windows device

`swcraft check-model` now reports an element stored as `CON.yaml`, `aux.yaml`, `Com3.yaml` or any
other name Windows reserves for a device (*Smaller things* has the list), and a project that passed
on the previous release can fail it for that alone. Rename the element **by hand**: give it a new
name inside its file, rename the file to match, and change every reference to the old name —
`swcraft impact` lists them — then run `swcraft check-model` until the finding is gone. The
assistant cannot do it for you: while such a file stands it refuses every change it is asked to
make to the model, and it cannot change, rename or remove that element itself, because the name is
one it may not write. On Windows such a file could not have been checked out in the first place.

### If you import exports


1. **Re-import and read the report.** Expect more elements than before, and expect a new
   *Unresolved references* section if your export references other files of its delivery.
2. **Expect `swcraft generate arxml` to refuse** where it used to succeed, if that section is not
   empty. Supply the referenced file and re-import, or narrow `--packages` to a self-contained set.
   `swcraft check-model` lists exactly what is missing.
3. **Check the *Conflicting declarations* section** if your export declares one name twice. Those
   elements are not in the project; repair the export or select the package you mean.
   A `--packages` selection that re-admits one member of such a group can leave the *other* member
   referenced by ports you kept. Those references are reported as *outside the selected packages* —
   they are not bound to the member that was re-admitted, because the two declarations differ. Widen
   the selection if you need them. When that happens, nothing you kept references the re-admitted
   member either, so it is dropped as unreferenced and the closure says so; the selection's own
   section names a re-admission only when the import went on to write it.
   **One shape a selection does not narrow as far as it could**, stated rather than implied: where
   a data type map's application type could rest on either of two implementation types of
   **different** names, a `--packages` import keeps both in reach, and if their own base types are
   two declarations of one name that differ, that name stays in *Conflicting declarations* — so the
   implementation type the import writes loses its base type, and `swcraft check-model` reports it
   — although the selection would have needed only one of the two. Where an export has that shape,
   the repair is the duplicate declaration itself.
4. **A script that parsed the import report** should know about three new section headings
   (*Unresolved references*, *Merged declarations*, *Conflicting declarations*) and three new summary
   counts (`UNRESOLVED`, `MERGED`, `CONFLICTING`). Each is printed only when it counts something, so
   an export that declares every name once and dangles no reference gains **none** of the six. That
   is not a promise that its report is byte for byte the one 0.12.0 printed, and two other changes in
   this release can move a line on such an export: one skipped-element **reason** is reworded (the
   one about a port init value whose data element the import mapped nothing under — it now says
   *under that path* and names a merge as a third cause), and an export that pretty-prints a
   `<CATEGORY>` or one of the three properties beside it now imports elements 0.12.0 refused, which
   moves the counts and the skipped list. Match on the headings and the counts, not on the whole
   report.
5. **Three more report lines move** (*Smaller things* above has each): the *Replaced scaffolded
   compositions* line names `compositions/Root.yaml` rather than a full path, a `--packages` import
   lists fewer reductions and renames, and a nameless data element is now a skipped-element line
   where it used to be the import's abort.

### If you script around the diagrams or the editor

- **A project that declares tasks gains two files** in `views_root`, `deployment.svg` and
  `deployment.html`, `swcraft generate diagrams` prints one more `Diagram deployment:` line for it,
  and `report.txt` lists under *Not drawn* every component no task runs. A project without tasks
  gains nothing.
- **Every view's files change**, because the glyphs, the label widths and the new attributes move
  their bytes. A repository that commits `views/` sees every file change once on the first
  generation with this release.
- **Saving in VS Code no longer regenerates the diagrams.** If you relied on it, press **Diagrams**
  after editing, or run `swcraft generate diagrams` from a terminal or your build graph. Only a
  press records a successful generation, so pages a terminal wrote still read *out of date* in the
  panel until the next press.
