# SWCraft 0.2.0

**This release changes the MCP contract, and it changes it without a deprecation
window.** If you drive SWCraft through its MCP server — from the standalone agent, from
VS Code, or from a client of your own — the tool names your prompts and scripts use are
gone in this version and are not aliased to anything.

Upgrade all four artifacts together. They are released in lockstep on one version
string, and the internal pins are exact, so a mixed install is not resolvable:

```
swcraft-tools==0.2.0
swcraft-mcp==0.2.0
swcraft-agent==0.2.0
```

plus the `swcraft-vscode-0.2.0.vsix` extension. `swcraft init` scaffolds a project
whose `requirements-swcraft.txt` already carries these pins.

Nothing in the YAML model changes. A project written for 0.1.0 loads, validates, builds
and exports byte-identically under 0.2.0; `swcraft generate`, `swcraft validate`,
`swcraft check-model`, `swcraft diff`, `swcraft impact`, `swcraft resource-report`,
`swcraft import` and the Python API behave as they did. Everything below is about the
MCP surface and the hosts that speak it.

---

## Why there is no deprecation window

Every client of the SWCraft MCP server lives in this repository or is generated by it:
the `swcraft-agent` MCP client, the VS Code custom-agent profile and the `.vscode/mcp.json`
it is generated with, the onboarding templates, and the scenario scripts. They all move
in the same commit as the server. A compatibility layer would mean keeping the old,
schema-coupled half working — which is the cost this release exists to stop paying — and
it would buy nothing for a caller set that is upgraded atomically. The breaking change is
placed at the minor position because the version is still in `0.x`.

There is also no protocol-version negotiation. One lockstep version already tells a
client exactly which surface it is talking to, and `discover` publishes that version in
its project passport.

## 39 tools became 13

The old server registered a function per supported model field: one `project_info`, nine
layer readers, and nineteen element-bound create/correction wrappers including
`delete_element`. Adding support for a new field meant adding a new tool. Twenty-nine of
those thirty-nine tools are removed:

| Removed | |
|---|---|
| Project and layer readers (10) | `project_info`, `read_swc`, `read_interfaces`, `read_connectors`, `read_requirements`, `read_systems`, `read_containers`, `read_tasks`, `read_sequences`, `read_resources` |
| Mutations (19) | `add_swc`, `add_port`, `add_runnable`, `add_interface`, `add_cs_interface`, `add_connector`, `add_requirement`, `add_trace_link`, `add_task`, `add_sequence`, `add_resource`, `map_runnable_to_task`, `set_task_core`, `set_task_priority`, `set_task_wcet`, `set_swc_memory_budget`, `unset_swc_memory_budget`, `update_resource`, `delete_element` |

What remains is thirteen tools: three generic ones — `discover`, `read`, `change_set` —
plus the ten specialized tools that answer something other than addressable model
content, and are therefore kept as they were:

`build`, `validate`, `model_diff`, `impact_of`, `resource_report`,
`check_port_compatibility`, `check_connector_consistency`, `export_component`,
`export_all_components`, `import_component`.

The removed *MCP tools* are not removed *behaviour*. The `swcraft_tools` writer and
reader functions behind them (`writer.mutations.add_port`, `reader.read_interfaces`, …)
are unchanged and still available to Python callers; only the MCP wrappers are gone.

The per-tool disposition of all thirty-nine was recorded as a machine-readable
mapping from an old tool name to what replaces it.

## The three request shapes

Everything the removed tools did is now reachable through three requests:

- **`discover`** — what this project is and what may be edited in it: the project
  passport (name, the AUTOSAR version the exporter emits, the SWCraft version, the
  baseline token) plus the editable layers, element kinds and fields, derived from the
  schema. A newly supported field shows up here with no new tool.
- **`read`** — the content at an address.
- **`change_set`** — every write, whatever layer it touches. `create`, `update` and
  `remove` exist only inside this envelope, which is what makes atomicity and the
  baseline token unavoidable rather than optional.

Addresses and typed payloads are the only things these requests accept. No operation
takes a file path, raw YAML or raw text.

### A change set is one request with three terminal states

`change_set` is submitted once, with a baseline token, an intent and its operations, and
it answers with a status that is one of:

- **`staged`** — validated and held, nothing written to the model;
- **`committed`** — applied in full;
- **`abandoned`** — discarded in full, with the model byte-identical to what it was.

There is **no commit request and no transaction handle**. A client does not open a
transaction, add to it and close it; there is nothing to leak if the client disappears
mid-turn, and no handle for a later request to reuse. Everything in the set commits
together or nothing does.

## Review mode: `SWCRAFT_REVIEW`

Who reviews a staged change set is a property of the host, so it is read from the
environment at server start, not from any tool argument. The LLM does not spawn the
server process and nothing in a request reaches this value.

- **`stage-only`** — the default. **It stages and commits nothing.** Nothing is asked,
  so nothing can be approved; the delta is validated and held for you to review some
  other way. This is the correct mode for any client with no proven human channel.
- **`elicit`** — the exact staged delta is put to the human through MCP elicitation, and
  a separate second question is asked when a change would weaken a resource constraint.

An unrecognised value is a **startup error, not a silent fallback to the default**. A
host that asked for a review channel the server cannot provide must see that, rather
than keep running in a weaker mode it never chose while believing a human is being
asked. Unset and empty both mean "no channel selected" and give you `stage-only`.

Under `elicit`, **every non-affirmative outcome abandons the change set**: a decline, a
cancellation, an accepted answer of "no", a client that has no elicitation capability at
all, and a failed elicitation transport. The last two are reported distinctly from a
person saying no — they are not something the user did, and the message says so.

There is deliberately no mode in which a host's tool-call confirmation stands in for the
review. VS Code's confirmation dialog shows the `change_set` arguments *before* staging,
while the decision that matters is over the exact semantic delta computed *after* it —
and `Allow in this Session` can suppress later dialogs entirely.

`SWCRAFT_MANIFEST` is unchanged: it still points at the project's `swcraft.yaml` and
must be set before the first tool call.

### What the review prompt does with your text

The prompt a human answers is composed on the server, from your request. Two rules govern
what it does to the strings you send, and both are **rendering** rules — neither rejects a
request:

- **Every code point `str.isprintable()` rejects is shown escaped** — every Unicode
  "Other" or "Separator" code point except the ASCII space, so C0, `DEL`, the C1 range,
  `NEL`, U+2028/U+2029, the bidi format controls and the zero-width characters. They appear
  in JSON's own spelling (`\u001b`), so a `before`/`after` on the prompt is still a value
  you can send back. A client value cannot open a line on that prompt or move a terminal
  cursor across it.
- **Every delta entry is shown, every bound that bites says what it dropped, and the prompt
  never truncates the list its one answer covers.** The `intent` is shown to 200 characters
  and one entry summary to 400, but the **number of entries is not bounded**: the boolean at
  the end of the prompt commits every entry, so every entry is rendered however many a change
  set carries (the same holds for the safety prompt's weakenings). The `before`/`after`
  payloads share a **total** display budget allocated max-min fairly: an ordinary change set —
  a whole-element `create` and the ten-element greenfield seed included — is rendered with
  every value complete. A value that does not fit states the count it dropped and where the
  rest can be read: a `before` half carries `… (N characters elided; read the full value with
  'read')`, while an `after` half and an address step say the text is **not retrievable** and
  that the way to see it is to answer **no** and re-submit a smaller change set — `read`
  answers the real model, and nothing is applied while the prompt is up. Nothing is ever
  silently shortened.

## New refusals `protocol.schema.json` does not describe

These are behavioural refusals added by 0.2.0 that the frozen protocol contract does not
express.

- An **element identity** or a **placement value** (`swc.group`) carrying a non-printable
  code point, or longer than a path component can hold once the composed file name has its
  extension and commit staging suffix (198 UTF-8 bytes for an identity — 255 minus that
  57-byte overhead exactly, nothing reserved beyond it; a placement value becomes a directory
  and gets the whole 255), is a `schema-violation` at the field you
  wrote — refused *before* staging rather than raising an `OSError` in the middle of a
  commit.
- `swcraft-agent` only: a proposed **task scope** carrying more than 100 entries, or an
  address more than five path steps deep (the deepest the model can be addressed), is
  refused terminally rather than shown truncated — a scope prompt showing part of a grant
  would take one `y` for all of it. The same applies to a proposal summary carrying a
  non-printable code point.

## Dependencies: `swcraft-mcp` raises its floor

`swcraft-mcp` declares **two** third-party requirements it did not declare at 0.1.0, and raises
the floor of a third it already had:

```
anyio>=4.0         (new)
mcp>=1.29.0        (new)
fastmcp>=3.4.5     (was fastmcp>=2.0)
```

The `fastmcp` floor moved because the review boundary uses `Context.elicit(message,
response_type)` and the three result types it returns; the old floor could resolve a FastMCP
with no elicitation at all, which would leave `SWCRAFT_REVIEW=elicit` unable to reach a human
while the surface still looked complete. `anyio` and `mcp` were already arriving transitively
through `fastmcp` and are now declared because `swcraft_mcp.server` imports them itself — the
sync/async bridge (`anyio.to_thread.run_sync`) and the `mcp.types.TextContent` block the closed
`changeSetResponse` cannot carry.

If you install from an offline wheelhouse or an internal index, refresh those three
distributions before resolving `0.2.0`. No other package's requirements changed; the internal
`swcraft-*==` pins move to `0.2.0` as usual.

## Approved scope: `SWCRAFT_APPROVED_SCOPE` and `SWCRAFT_SCOPE_ID`

A host that bounds what a turn may touch sets both of these, on the same channel and for
the same reason as the review mode.

- `SWCRAFT_APPROVED_SCOPE` is a JSON array of `{operation, address}` entries.
- `SWCRAFT_SCOPE_ID` is the host's per-turn correlation id, written on every change-set
  lifecycle record so a turn's records can be found by the id that authorized them.

The rules:

- **Both or neither.** Either one alone is a startup configuration error. A scope with
  no correlation id is a run whose records cannot be tied back to the turn that
  authorized them; a correlation id with no scope runs *wider* than the host asked for
  while labelling every record as if it had been bounded.
- **Both absent is an unscoped run** — the scope gate is unrestricted.
- **A present-but-empty scope (`[]`) is not the same as unscoped.** It means nothing is
  approved, and every operation is refused. The two are distinguished end to end and are
  never collapsed. An empty *string* is not a scope document either, and is read as
  absent rather than guessed at.

## `import_component` behaves differently

The MCP `import_component` tool no longer applies the import. It is now **planning-only
and model-neutral**: it reads the export, decides everything the import would do against
your project, and answers with a ready-to-submit `change_set` request. Nothing is
written — no model file, no audit record — until you submit that request yourself.

It also now **requires a `baseline`** argument, which it copies unchanged into the draft.
The workflow is three calls:

1. `discover`, for a baseline token;
2. `import_component` with it, which answers with a draft `change_set`;
3. `change_set` with that draft's `baseline`, `intent` and `operations` — **plus any
   companion operation the model needs to stay valid.** A newly created SWC needs one:
   nothing links to it yet, and the cross-layer rule refuses a model with an unlinked
   component, so the requirement trace link belongs in the same submission. Everything
   commits together or nothing does.

Under the default `stage-only` review mode, that submission **stages**; it does not
commit. That is the intended behaviour, not a failure to import.

The planning decisions themselves are unchanged — an identical shared interface or data
type is reused silently, a divergent shared definition still aborts with no override, and
a divergent target SWC is still replaced only under an explicit `update=True`.

**The CLI is unaffected.** `swcraft import component --source … --project …`, its
`--dry-run`, and the `swcraft_tools.component_exchange` Python API all still plan *and*
apply, exactly as before. The authorization boundary exists to authorize LLM mutations;
a human who typed the command is outside it.

## The `delete_element` confirmation token is gone

Removing an element used to be a two-step flow: a first call returned a confirmation
token, a second call spent it. That protocol no longer exists, along with the tool it
belonged to. A removal is now a `remove` operation inside a change set, reviewed the same
way as every other change — as the **exact staged delta**.

This is a stronger boundary, not a weaker one. The token asked you to confirm a *name*
the agent had already chosen, and it showed nothing else: the referrer updates a removal
drags with it were invisible at the moment of consent, and the same second call that
spent the token applied them. The delta shows that cascade before anything is written.
The requirement itself is unchanged: a destructive operation needs your explicit confirmation,
and it still does — earlier, and over more.

## Upgrade checklist

1. Install all four artifacts at `0.2.0`; update `requirements-swcraft.txt` in existing
   projects (a project scaffolded by `swcraft init` gets the new pins).
2. Rewrite any prompt, script or profile that names one of the twenty-nine removed
   tools, with the replacement operation of each (`docs/guide/reference/tools.md` lists the
   tools that remain).
3. Decide your review mode. If you leave `SWCRAFT_REVIEW` unset you get `stage-only`,
   which will not commit anything — set `elicit` when your client can ask a human.
4. **Regenerate `.vscode/mcp.json` in every existing project.** A 0.1.0 config carries no
   `SWCRAFT_REVIEW` at all, so the server starts in `stage-only` and the agent stages change
   sets that never commit — a silent symptom, not an error. Run **SWCraft: Repair MCP Config**
   from the 0.2.0 extension (it always rewrites the `swcraft` entry's `env`; only a
   project-local `command` survives a repair), or add `"SWCRAFT_REVIEW": "elicit"` by hand.
   **SWCraft: Onboard Project** does the same write and additionally overwrites the two
   bundled assets, `.github/agents/swcraft-architect.agent.md` and
   `.github/copilot-instructions.md`, whose 0.1.0 copies still name the removed tools.
5. If you set an approved scope, set `SWCRAFT_SCOPE_ID` with it.
6. If you call `import_component` over MCP, pass a `baseline` and submit the returned
   draft through `change_set` yourself.
7. Rebuild your project (`swcraft validate`) and confirm the artifacts are unchanged —
   they should be.

## Three `discover` field descriptions are corrected

`0.2.0` also carries a rewrite of the model kernel. **No CLI command, no MCP tool, no request
or response shape and no generated artifact changed** — both reference builds are byte-identical
at AUTOSAR 4.2.2 and 4.3.0, and `git diff` over the MCP server's and the agent's sources is empty.
The one thing a client can observe is text: three field descriptions published by `discover` were
false of the shipped code and now say what it does.

| Field | It used to say | It now says |
|---|---|---|
| `cpu_core.threshold` | the **host** classifies the change | the **server** classifies it, from the staged before/after values |
| `swc.memory` | an unknown pool key is reported by a check, unconditionally | in a project declaring **no** resources, an unknown pool key is reported by **no** check — the analysis returns before reading anything |
| `interfaces.data_elements` | `add_interface` hard-codes one data element | **no operation of this protocol restricts** a sender-receiver interface to one data element |

These strings are shipped to a model as tool documentation, so a plausible-but-wrong sentence is a
defect that no assertion in this repository can catch. All three were found by a human
semantic review and are corrected in the registry, in the model contract and in both
shipped `discover` vectors together. If your prompts or scripts quote these descriptions, requote
them; nothing else about the descriptors moved, and no field, type, enum, `elementKind`,
`immutable` flag, unit or reference target changed.

**`contractVersion` is now `1.4.0`, and it is not the product version.** The model contract gained
six optional declarations across this release. The kernel rewrite added three — `fieldDecl.relation`,
`layerDecl.label` and `layerDecl.displayOrder` (`1.1.0`) — and the coverage work added three more:
`layerDecl.arxmlBound`, which layers carry an AUTOSAR `Identifier` constraint (`1.2.0`);
`fieldDecl.omitAtDefault`, the single-entry exception table beside the writer's derived
omit-at-default rule (`1.3.0`); and `layerDecl.token`, the singular word a layer is called by in
`swcraft impact`'s output, which used to be computed by stripping a trailing `s` (`1.4.0`). All six
are optional, so a `1.0.0` document is still valid and the supported major stays `{1}`. This number
is the *contract's* compatibility number: it moves when the contract's shape changes and it does
**not** move with a release, which is why it is not one of the release's version sites. Nothing in an architecture project pins it.

**The coverage work changed no observable behavior either.** It completed the coverage declarations for
the ten partial consumers, migrated the last historical layer tables onto the contract and deleted
the temporary legacy-parity gate. No CLI command, no MCP tool (still thirteen), no request or
response shape and no generated artifact moved: all ten generated artifacts and all 22 read-only
CLI streams are byte-identical at AUTOSAR 4.2.2 and 4.3.0, and `git diff` over the MCP server's and
the agent's sources is empty. One thing a *hand-edited* model could observe is the `impact` token
above — a layer whose plural is irregular would have been named wrongly before, and no shipped
layer is such a layer, so nothing in an existing project changes.

## `swcraft diff` and `swcraft impact` list requirements first

Both commands group their output by model layer, and that grouping now starts with
**requirements** instead of systems: requirements drive everything else, so they belong at the top
of a listing a person reads. The full order is requirements, systems, containers, SWCs, interfaces,
data types, connectors, tasks, sequences, resources.

This is presentation only. It changes `swcraft diff --format text` section order and
`swcraft diff --format json` **key order** inside `layers` (the key *set* and the schema version
are unchanged, and a JSON consumer that indexes by key sees nothing at all); it changes the order
`swcraft impact` and the MCP `impact_of` tool group dependents in. **No model file, no ARXML, no
LikeC4 and no Sphinx-Needs output changes**, and no element, field or identity moved. If you have a
script that reads diff sections or impact groups by position rather than by name, reindex it.
