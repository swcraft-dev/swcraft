# SWCraft 0.4.1

The first patch release from `release/0.4`. Two fixes, both found on a native Windows host on 2026-08-25 and both inside the
release-branch criterion: the model contract, the editing protocol, the MCP tool surface and the
emitted ARXML bytes are unchanged from 0.4.0. A 0.4.0 project upgrades by installing the four
artifacts — **plus one file it must update itself**, see below.

Neither defect is reproducible on macOS or Linux, and both were found by running the product on
Windows for the first time since the release.

```
swcraft-tools==0.4.1
swcraft-mcp==0.4.1
swcraft-agent==0.4.1
```

plus `swcraft-vscode-0.4.1.vsix`.

## `moon run :build` now runs on native Windows

In a scaffolded architecture project on Windows, the build failed on its first task without ever
reaching Python:

```
architecture:clean-outputs | Unexpected token 'clean_outputs.py' in expression or statement.
Process .venv/bin/python failed: exit code 1
```

moon's `shell` task option defaults to **true on Windows and false everywhere else**, so on Windows
alone moon composed `'.venv/bin/python' clean_outputs.py dist views` and handed it to PowerShell.
PowerShell reads a statement that opens with a string literal as an *expression*, never as a
command, and rejects the following token. macOS and Linux, which never had a shell in that path,
were unaffected — which is why the defect survived every green build on those platforms.

The template's `moon.yml` now declares `options: shell: false` on all six tasks that run a command,
and spells the interpreter `./.venv/bin/python` with the leading `./`. Both halves are needed and
both were measured on the failing host: the quoting is what breaks the parse, so no path spelling
alone is enough, and with the shell gone a bare `.venv/bin/python` does not resolve on Windows
(`WinError 2`) while `./.venv/bin/python` does. That spelling is also the ordinary one on POSIX, so
one committed build graph still serves both platforms — no per-OS fork, no `.exe` suffix and no
backslash in any committed file.

Verified by a real `moon run :build` on native Windows: seven tasks, exit 0, ARXML generated at
AUTOSAR 4.3.0 and structurally validated.

## `model_diff` no longer hangs under the MCP server on Windows

Asked through the assistant to compare two revisions of the architecture, the `model_diff` tool
never returned. The measurement on the host: four `git` processes alive at 0% CPU until they were
killed, while the identical revisions diffed in two seconds from a terminal.

`materialize_revision`'s `git rev-parse` and `git archive` did not say what their stdin was, so
the children inherited the parent's — and under the MCP server that handle is the JSON-RPC pipe
VS Code writes requests into. Both calls now pass `stdin=subprocess.DEVNULL`, which is what
`builder.run_build` had always done for the same reason. Neither git call reads stdin.

The command-line `swcraft diff` was never affected: there stdin is a console.

A guard now requires every `subprocess.run`/`Popen` in the shipped package to declare its stdin —
a declaration rule, because silence is what inherits.

## Upgrading an existing project needs one manual edit

Installing the new wheels is **not** enough. `moon.yml` is committed *into* an architecture project
by `swcraft init`, which is a one-time step; nothing — not `bootstrap.py`, not a setup launcher,
not a newer wheel — ever rewrites it afterwards. The wheel carries the fixed template for the
*next* `swcraft init`, not for a project that already exists.

To pick up the fix in an existing project, copy the template's `moon.yml` over the project's own:

```sh
cp <site-packages>/swcraft_tools/templates/vehicle-architecture/moon.yml ./moon.yml
```

The only differences from the 0.4.0 template are the six `command:` lines, the six `options:`
blocks and their comments, so a project that has not edited its build graph can take the file
whole. A project that *has* edited it should apply the same two changes to each task that runs a
command.

Nothing else in a scaffolded project changes, and macOS/Linux behaviour is identical before and
after: on those platforms `shell: false` pins the default they already had.

## Not in this release

`.vscode/mcp.json` resolves the MCP server as `${workspaceFolder}/.venv/bin/python` — absolute, no
`./`, and VS Code spawns it directly rather than through a shell, so the PowerShell half of this
defect cannot apply to it. Whether that extension-less absolute path resolves on Windows is
untested in either direction; it is recorded as open and deliberately not changed on
speculation.
