# SWCraft 0.16.0

Released 2026-10-13. Every figure below is measured on the host and at the commit that produced it;
the archive's sizes are the tag run's.

## Where could a component move? A new command answers

`swcraft experiment allocation` answers a question an architect asks *themselves*: which
components could move to another partition, and what would each move buy? It runs with its defaults
as it is, or with a small configuration file that narrows the question; the answer is a report, and
the model is never changed.

```yaml
# experiments/rebalance.yaml
name: rebalance
search:
  max_moves: 3
  candidates: 3
constraints:
  locked: [SafetyMonitor]
```

```sh
swcraft experiment allocation --project swcraft.yaml
swcraft experiment allocation --project swcraft.yaml --config experiments/rebalance.yaml
```

Every key of the file is optional, and an unknown one is refused by name. The report goes to
`dist/experiments/<name>/` — `dist/experiments/allocation/` when the file names none, or the run has
no file — or into the directory the file's `output` names, which must lie inside the project and
outside the model. Both files record what they answered: the kind, the configuration file with its
SHA-256 (or that the defaults ran) and every setting used, defaults included. In `report.md` the
names of the components, partitions and tasks a move names, and of the components in the freedom
table, link to their model files.

The command first checks the model as `swcraft check-model` does and refuses a model with findings,
naming how many. Then it reads what the model declares — partitions and their cores, the cores' CPU
limits, the tasks in each partition with their periods and budgets, the runnables each task runs,
the components' safety levels and the connectors between them — and writes two files under
`dist/experiments/rebalance/`: `report.md` to read and `result.json`, the same content for a script.
The report holds:

- **a freedom table**: for every component and every other partition, whether it may move there,
  and if not every reason, each with a class that says what would change the answer — *hard* (the
  hardware forbids it), *needs a safety decision* (a safety rule would break; the experiment never
  proposes a coexistence argument), *removable* (no task of the runnable's period with a budget in
  that partition) or *locked* (the configuration file excludes it);
- **a curve**: the least data exchanged between partitions — the size of each signal times how often
  it is sent, in bytes per second — for 1, 2, … up to `max_moves` moves under every `strict` core's
  CPU limit, each point marked *optimal* (proved), *feasible* (the time limit ran out after a
  solution was found) or *unknown*; among equally good answers a point gives the one with the fewest
  moves, so a move that buys nothing is never part of it;
- **candidates** at one number of moves, best first: the moves, the load of every core they touch
  before and after, the data exchanged before and after, and the `wcet` budget edit each touched
  task would take, exact and in the finest unit among the budgets involved (`2ms -> 1500us`) —
  stated, never applied;
- the move sets it dropped, and every data gap and assumption it made.

A runnable that AUTOSAR lets run outside every task is judged by its kind. An initialization
runnable in no task does not stop its component from moving, and the report lists it among the
assumptions as outside the steady load. A server runnable in no task runs in its callers' tasks, so
its component stays where it is, but the data and calls through the component are still counted.

Every move set is checked before it is reported: the moves are applied to a temporary copy of the
model outside the project and the whole copy is run through `check-model`'s checks; a set they refuse
is listed with the rule, never offered. The command exits 0 whenever it could answer — also when no
move improves anything or no component is free — and exits 1 with one `Error:` line, writing
nothing, when it cannot. Like every command that writes, it refuses a project pinned to another
release; it is not a check, and `swcraft validate` stays the gate. Where you keep configuration
files is your choice — commit them if you want your questions versioned, and keep them out of
`dist/`, which `clean-outputs` removes whole with the reports in it.

**What it does not reach.** A component type placed more than once is not moved; client-server
calls are counted, not weighed; the data exchanged is the logical size of the types, without
alignment, padding or bus overhead; a runnable costs the same on every core; `gross` and `net`
budgets are added alike, so the calls a `net` budget leaves out are counted in no load (the report
lists the `net` budgets it added); a move set whose budget edit would need more than a budget's 18
digits is dropped, never rounded; memory stays where it is; no task is created or re-budgeted; a
component whose initialization or server runnable is mapped to a task is not moved, and one whose
runnables are all initialization or server runnables in no task has no partition the experiment can
tell, so it is not moved and its data and calls are left out; a server's cost in its callers' tasks
is not weighed and a server called from two partitions is not judged — a component that calls such
a server can still move, its call is then counted as crossing partitions and whether it is allowed
there is not judged; and every figure in its tests comes from synthetic models —
nothing yet compares its answers with an architect's own investigation of a real allocation. The
user guide's *Experiments* page is how to write the question and read the answer.

**In VS Code**, the SWCraft panel has a new section, **Experiments**, between *Model* and *Setup*.
Its item **Allocation (CARMA)** runs the experiment on the open project, with the configuration file
the setting `swcraft.experiments.allocation.config` names, or with the defaults when the setting is
empty. The run shows in the SWCraft output channel as every panel command's does, and on success the
report opens in VS Code's Markdown preview, where its tables render and its linked names open the
model files. A refusal stays in the channel and opens nothing. The palette entry is
**SWCraft: Allocation Experiment (CARMA)**.

## An execution-time budget carries its unit, and a runnable's reaches the ARXML

A budget is now written with its unit: a whole number followed by `ns`, `us`, `ms` or `s`. A task's
`wcet_us: 1200` becomes `wcet: 1200us`, and a runnable can declare a budget of its own, **`wcet`**,
together with its **`wcet_type`**:

```yaml
runnables:
  - name: Run_Filter
    events:
      - type: timing
        period: 0.001
    wcet: 850ns
    wcet_type: gross
```

A budget is what the architect allots — an upper bound the model is checked against, never a
measurement. Nanoseconds were out of reach while the field counted microseconds; now a budget is
written in the unit that fits it. No space, no leading zero, no decimal point (`1500us`, never
`1.5ms`: ARXML writes a time as a whole number of a unit), at most 18 digits, and above zero; each
refusal names the spelling to write. `wcet_type` is AUTOSAR's own distinction: `gross` includes the
calls the runnable makes outside itself, `net` leaves them out, and neither counts interruptions.
A runnable declares the two together — either one alone is refused — and through the assistant
both are set in one change to the runnable, never in two changes one field at a time, which would
leave it half-declared in between. Removing a budget is the same: both go in one change. Changing
only the number, the type kept, is a single change to `wcet`.

`check-model` (and therefore `validate`) reports a task whose runnables declare more time between
them than the task's own budget, naming the task, the sum, the budget and each runnable's budget as
written — judged only when the task declares a budget and at least one of its runnables one,
equality silent. `gross` and `net` budgets are added alike; when a `net` one is in the sum the
finding says so, because the calls it leaves out are counted nowhere.

**The generated ARXML carries a runnable's budget.** Each component with a budgeted runnable gets
one `SWC-TIMING`, `<component>_Timing`, beside its `SWC-IMPLEMENTATION`, holding one
`EXECUTION-TIME-CONSTRAINT` `<runnable>_Budget` per budgeted runnable: the runnable it constrains,
the type (`GROSS` or `NET`) and the maximum as the unit's AUTOSAR time code and the number exactly as
written — `850ns` is code 26 with factor 850 — the same at 4.2.2 and 4.3.0. A component or a
composition named like such a `<component>_Timing` is refused, and a runnable whose
`<runnable>_Budget` would pass 128 characters too. A model with no runnable budget produces the
same ARXML as before, byte for byte. A task's budget stays out of the ARXML: AUTOSAR's
execution-time constraint names a runnable, never an operating-system task.

`swcraft import model` and `swcraft import component` read the budget back from an execution-time
requirement of a component they create, when it names one of that component's runnables, states
its type and a maximum, and carries no condition or instance scope that the budget would lose. A
maximum in another AUTOSAR time unit is written in the coarsest of the four units that holds it
exactly (`10 ns × 85` becomes `850ns`) and listed under *Represented in another form*, as is a
factor spelled in hexadecimal, octal or binary, which the model writes in decimal; one no unit
holds exactly, below a nanosecond, is not imported. Anything else — a supplier's timing guarantee,
two requirements on one runnable, a conditional requirement, a minimum, the timing description's
own name or package — is named in the report rather than carried halfway: a requirement that cannot
be kept whole stops the import, and what the model has no place for is listed and the import goes
on. An `import component` compares a runnable's budget like any other field: **the file's budget
wins**, and a runnable the file brings without one — every component file an earlier release
wrote — keeps the budget the project declares for the runnable of the same name before anything is
compared, so such a file whose only difference is the missing budget is reported unchanged, with or
without `--update`. When the import does write the file, the kept budgets are listed on a line
beginning `WCET preserved from the target project`.

**What it does not reach.** A task's budget is not written to the ARXML (above); neither is a
minimum, a condition or an instance scope, which the model does not hold. Response time — the time
including interruptions — and a measured or analysed execution time of existing code are different
AUTOSAR constructs and are not modelled. A budget cannot be authored below a nanosecond or in
AUTOSAR's 10× and 100× units (an import converts the exact ones). Nothing reconciles `gross` and
`net` in a sum. And whether a tool downstream reads a factor as wide as 18 digits — wider than 32
bits — is not checked.

## The model's contract is `10.1.0`

`contractVersion` moves from `9.2.0` — the contract 0.15.0 shipped — to `10.1.0`, a major: a
renamed identifier is a major. Against `9.2.0`, one field is renamed, `field:tasks.task.wcet_us`
to `field:tasks.task.wcet`, and its rule `rule:tasks.task.wcet_us.positive` to
`rule:tasks.task.wcet.positive`; a runnable gains `field:swc.runnable.wcet` and
`field:swc.runnable.wcet_type`; and nine rules are new — the element-local
`rule:swc.runnable.wcet.format`, `rule:swc.runnable.wcet.positive`,
`rule:swc.runnable.wcet.retired-spelling`, `rule:swc.runnable.wcet_type.paired`,
`rule:tasks.task.wcet.format` and `rule:tasks.task.wcet.retired-spelling`, and the cross-element
`rule:task.runnable-cost-exceeds-task`, `rule:name.swc-timing-collision` and
`rule:name.composition-timing-collision` (a component or a composition named like the
`{component}_Timing` the writer now generates beside a component with a budgeted runnable). A project's own tooling that names `wcet_us` has to follow
the rename.

The contract also declares what a runnable's reads, writes and calls name: a field's new optional
`memberReference` says that an access's `port` names a port of its own component and its
`element` or `operation` a data element or an operation of that port's interface — what
`check-model` already enforced, now stated for the editor to follow. It adds no field and no rule,
and a model file needs no change for it.

## The archive

The workstation archive carries a solver for the first time: SciPy 1.17 (BSD 3-Clause), whose
`scipy.optimize.milp` drives the HiGHS solver it bundles. Its wheel is 20 334 032 bytes on macOS
arm64, 35 349 300 bytes on Linux x86_64 and 36 607 512 bytes on Windows x86_64, and it brings one
package more, `numpy`. On Windows it needs nothing beyond what Windows 10 and 11 carry — no
Microsoft C++ runtime to install, and no administrator rights. Nothing new is installed by hand: it
arrives with SWCraft's own packages, and no command other than `swcraft experiment` loads it, so
`generate`, `validate` and every other command are unaffected by it. The Linux archive measures
**197 349 003 bytes** (SHA-256 `1b2f5d3d…09e819d4`) and the Windows archive **201 410 953 bytes**
(`bca184e3…257e1eba`), as the tag run of 2026-10-13 published them: 51 663 950 and 48 825 657 bytes
more than 0.15.0's, the solver and `numpy` with everything they bring.

The runtime payloads are re-checked against the publishers' own digests for this release and none
moved: Node.js 22.23.2, CPython 3.11.16 (the python-build-standalone build of 2026-09-01), `elkjs`
0.12.0 inside the `swcraft-tools` package, and the two extensions of the pack, Red Hat XML 0.29.3 and
Red Hat YAML 1.25.0, each still the newest Marketplace release at the bump (`dev.py update-pins`
rewrote nothing).

The archive's third-party notices list the payloads it carries beside SWCraft — Node.js, CPython,
the two companion extensions and `elkjs` — as before, and do not list Python packages: every wheel
in the archive, SciPy and `numpy` included, carries its own licence file.

## Go to Definition, hover and Find All References on model files

The VS Code extension now follows the references your model files hold. On a port's `interface`,
a data element's type, a connector end's component, a task's partition, a partition's core, a
composition member's type, a unit, a compu method, a data constraint, a base or referenced type,
and every other field the model declares as a reference to another element:

- **Go to Definition** (F12, or Ctrl/Cmd-click) opens the element's file at its `name:` line;
- **hovering** the line shows the element's kind, its name, its `description` and the first lines
  of its file.

On an element's own `name:` line (`id:` in a requirement), **Find All References** (Shift+F12, or
Peek References) lists the elements that refer to it directly, each at its own `name:` line. The
extension asks `swcraft impact` for that answer, so it needs the toolchain installed, and while a
model file does not parse it shows the CLI's message rather than a partial list. A referring element
whose file the extension cannot find (a component stored more than eight folders deep under `swc/`)
is named in a message rather than left out, and an unsaved change to the element's own `name:`
line asks you to save first, because the CLI reads the saved file.

Nothing is indexed and no answer is kept: every answer is computed when you ask, from the **saved**
files — an unsaved edit in another tab is not seen. A line written in a form the extension does not
read (a flow value such as `ports: [ … ]`, a value continued over several lines, a quoted value
with an escape, an anchor or alias, a key written twice) gets no navigation rather than a wrong
jump. Navigation checks nothing: it adds no diagnostic, and `swcraft validate` stays the gate. The
guide's VS Code page, *Following a reference*, has the details.

## The outline, Go to Symbol, CodeLens and links in model files

The extension now does more with the same reading of your model:

- **Go to Definition** also follows a requirement's `links`, a component's `memory` (on the key,
  `RAM:`) and `data_type_mappings`, and a memory's `accessible` cores; the hover shows the target's
  card as for any other reference. On a runnable's `reads`, `writes` and `calls`, F12 on `port:`
  jumps to that port in the same file, and on `element:` or `operation:` to the data element or
  operation inside the port's interface.
- **The Outline** view, the breadcrumbs and Go to Symbol in Editor show the element, its
  collections and their members as the file holds them: a component's ports and runnables with
  each runnable's events, reads, writes and calls; an interface's data elements or operations and
  their arguments; a composition's ports, members and delegations; and so on for every layer.
- **Go to Symbol in Workspace** (Ctrl/Cmd+T) lists every element of the model by name, with the
  folder it is stored in beside it. It reads folder listings, not files, so an element is listed
  under its file's name.
- **A CodeLens** above an element's `name:` line reads *N references* (a click lists exactly
  those N, without the element's own `name:` line),
  *impact* (the element's impact walk in the output channel) and, for a composition or a sequence
  whose diagram page exists, *diagram* (regenerates the diagrams and opens that page). The count
  asks `swcraft impact` and counts the saved files: an unsaved file shows *references (save to
  count)*, and a count the CLI could not give shows *references (unavailable)*.
- **Links**: an element named in a `description` — `interfaces/IBrakeTemperature`, or a bare name
  when only one layer holds an element of exactly that name — and the names in an import report written with
  `--report` become links to the element's file.

As before, nothing is indexed and every answer is computed when you ask; none of this checks your
model or adds a diagnostic, and the *N references* count is evidence of nothing. Find All
References and the count do not yet follow a runnable's reads, writes and calls: *which runnables
write this data element* is not answered.

## The assistant answers short questions, and asks the model through SWCraft alone

A person asking Copilot *"who reads the vehicle speed?"*, *"which components are ASIL D?"* or
*"what crosses a partition?"* now gets the answer the model gives, through SWCraft's tools.

- **Three values SWCraft computes, on request.** A `read` (and `swcraft query --request`) may ask
  for `derived: ["effective_level"]` on components — the level a component runs at: its declared
  `asil`, else the highest level a requirement allocates to it, `QM` for none — for
  `derived: ["partitions"]` on components — each partition whose tasks run one of the component's
  runnables, with that partition's core — and for `derived: ["crossing_ends"]` on connectors — the
  connections whose two ends run in different partitions, followed through compositions, each end
  with its partition. A connector that crosses nothing gives no row, so the answer is exactly the
  crossing set. None is a second calculation: `effective_level` is the level `check-model`'s
  safety rules compute per component and the deployment diagram labels it with, `partitions` is
  the reading `check-model`'s partition rules use, and `crossing_ends` puts that reading beside
  `connection_ends`. Like the partition rules, `partitions` reads component types: two placements
  of one type are not told apart, and a component no partition runs has no row.
- **"Without a description" now finds the elements without one.** A `where` clause
  `{"field": "description", "exists": false}` matched nothing, because a description you do not
  write is stored as an empty string and the empty string counted as a value. Now **an empty
  string** counts as no value, in `read`, in a request file and in `swcraft query --exists`, so
  the request finds every element whose description is missing or empty. `0`, `false` and an
  empty map are still values.
- **An answer too large for one reply names the command that gives it whole.** When a `read` of a
  whole layer table is refused for its size, the refusal now also says that `swcraft query
  --request FILE --project PATH` (`PATH` being the project's `swcraft.yaml`) answers the same
  request with no size limit, and that leaving `limit` and `after` out of the file prints the whole
  answer. A refused `impact_of` names its command the same way: `swcraft impact NAME --project
  PATH` for what depends on an element, `swcraft query --deps NAME --project PATH` for what it
  depends on, with `--depth N` when the question carried a depth. The paging hints are unchanged.
- **The SWCraft Architect agent in every project.** The extension now ships the agent profile and
  Copilot instructions written for a **model project** — the files `swcraft init` writes. Until
  now, *Onboard Project* copied in the instructions written for developing SWCraft itself.
  When a SWCraft project opens without `.github/agents/swcraft-architect.agent.md`, the extension
  offers to **Add the SWCraft Architect agent**: it writes the profile, writes
  `.github/copilot-instructions.md` only if the project has none, never overwrites a file and never
  runs `swcraft init`; **Not for this workspace** stops the offer for that workspace (closing the notice without a
  choice asks again next time). *Check Editor
  Tooling* gains a row, *Copilot agent profile*: missing (run *Onboard Project*), different from
  this release's (a warning, not counted, since you may have edited it — *Onboard Project*
  replaces it), or this release's.
- **The instructions say to ask SWCraft, in every Copilot mode.** The model project's Copilot
  instructions gain a section, *Questions about the model*: answer through the SWCraft tools,
  never read or parse the model's files with a script, the terminal or a file tool, page a large
  answer, give the user the `swcraft query --request` command for a whole layer table, and use the
  SWCraft Architect agent. Instructions are guidance: only the agent's own tool list takes the
  terminal and file edits away, which is why the agent is the place to ask.
- **Recipes in the agent.** The SWCraft Architect profile carries copy-ready requests for the
  common questions — who reads or writes a data element, the sender-receiver table, elements
  without a description, components by level, a component's partitions, the connections that
  cross a partition, the components no partition runs, and what a change affects. Each recipe is
  run against a model built to give known answers before a release ships.

**What it does not reach.** An assistant's answer is not deterministic: a model or a client other
than the one tried may still form a wrong request, and an answer from it is evidence of nothing.
`swcraft validate` stays the gate. A field filter cannot name a computed value, so *the components
no partition runs* is two requests and a subtraction, as its recipe says.

## Copilot reads a large SWCraft answer, and a guard keeps its file tools off the model

Copilot in VS Code hands a tool's answer to the model whole only up to about 8 KB. A larger one —
the project overview, what a change to a much-used interface affects, a long table — is saved to a
temporary file, and the model sees only where it is and its first few hundred characters. The
SWCraft Architect agent had no file tool, so it answered from that preview: on a large model it
gave the number of affected elements but not which ones.

- **The agent reads the saved answer.** The model project's agent profile now grants `view`, a
  read-only file tool, beside SWCraft's tools — still no file editing and no terminal — and tells
  the agent to read a saved SWCraft answer with it, in parts when it is long, and never to view the
  model or any other project file — an instruction; the guard below enforces its model-directory
  half. SWCraft's own limit on an answer's size is unchanged.
- **A guard on the model directory, in every Copilot mode.** A project now carries
  `hooks/swcraft.json` in its `.github` folder, a Copilot hook that runs the new `swcraft guard` before every tool
  call. It denies a file tool's read when any path it names is under the model directory, and a
  search whose folder is the model directory, inside it or above it — a search's file pattern is
  judged by the folders it starts with, and one that could climb back up with `..` after a wildcard
  is denied — and tells the agent to use the SWCraft tools; it allows a saved SWCraft answer and
  everything else. It reads only the `swcraft.yaml` in the folder
  Copilot names, allows everything where there is none, and denies every read and search but the
  saved answer when that file cannot be read. `swcraft init` writes the hook, *Onboard Project*
  writes it, and the *Add the SWCraft Architect agent* notice writes it where it is missing.
- **Check Editor Tooling gains a row, *Copilot model guard*:** missing or different from this
  release's (a warning, not counted; *Onboard Project* writes it), or this release's — and a
  warning in any state when a bare `swcraft` in the window resolves nowhere or is another version,
  because the hook runs that `swcraft`.
- **Ask in the SWCraft Architect agent.** Short model questions were answered reliably there. In
  Copilot's general Agent mode, set the **Auto** model choice to optimize for intelligence: optimized
  for balance it can route a question to a lighter model, and one was seen answering a partition
  question wrong by reading the model's files instead of asking SWCraft.

**What it does not reach.**

- **The terminal.** A command's reads cannot be judged from its text, so a terminal command in the
  general Agent mode is not guarded; Copilot asks you before it runs one.
- **File edits.** The guard judges reads and searches; an edit is not guarded.
- **A guard that does not run:** a project without the hook file; no `swcraft` on the path, or an
  older one with no `guard` command; Copilot hooks switched off (`chat.useHooks`), or a host that
  does not read a project's hook files. What Copilot does with a call when the hook cannot run is
  Copilot's behaviour and has not been measured; a reading of VS Code's source, not an
  observation, suggests it allows the call.
- **Other chat clients** save or cut a large answer in their own way; the hook is Copilot's
  mechanism.
- **A path the guard does not look for.** It knows the file and search tools Copilot named on the
  day this was written, and the fields their paths arrive in; a tool or field it does not know is
  allowed, and the names the general Agent mode's hook sees were never observed. A `Grep`
  pattern is a regular expression and is not judged as a path; a `search` call's pattern is judged
  as a glob, so it can deny a regular expression aimed outside the model. A file pattern's folders after its first
  wildcard are checked only for climbing with `..`, cautiously, so some harmless patterns are
  denied too (`.*`, `!**/x`, `(draft)`, any pattern with a backslash). A path written with `~` or as a
  `file:` URL is taken literally, never expanded. A network path (`//server/share/...`) or a path
  relative to a drive (`C:notes`) is denied wherever it points, so a project kept on a network
  share and opened by its network path has every file read and search denied; on macOS and Linux
  a path that starts with a drive letter is denied too.
- **Another folder.** The guard reads only the `swcraft.yaml` in the folder Copilot names; a
  workspace whose root is a folder above the project is not guarded.
- **A change on Copilot's side.** If Copilot saves a large answer somewhere else or under another
  name, the agent loses the saved answer, and the model stays guarded.
- Whether Copilot honours the hook is observed in a Copilot session only; nothing in SWCraft's own
  tests runs Copilot.

## What upgrading takes

A project whose tasks declare a budget renames it: **write `wcet: 400us` for `wcet_us: 400`** —
the same number, now with its unit. A file still spelling `wcet_us` is refused, never converted,
with the sentence

```text
'wcet_us' was renamed 'wcet' by contract 10.0.0 and now carries its unit: write 'wcet: 400us' for 'wcet_us: 400'
```

carrying the file's own number (a runnable's sentence also asks for its `wcet_type`, and a value
that is not a positive whole number is shown as `<value>`). Every command that reads the model refuses it — `check-model`,
`validate`, `list`, `query` and `impact` among them — and so does `diff` when it reads a revision
committed before the rename, like any revision it cannot read; the editing protocol answers a `wcet_us` key
as an unknown field. A runnable's budget is new: declare it with its `wcet_type`. A project that
declares no budget changes nothing, and its ARXML is the same as before.

Navigation changes no model file, manifest or setting; the extension ships the reference table it
reads inside its own package. The contract's new `memberReference` declaration is optional and
needs no change to a model file, so the outline, Go to Symbol, the CodeLens and the links need
nothing from you.

A request that relied on `exists` counting an empty string as a value now answers differently:
`exists: true` on `description` no longer finds an element whose description is empty, and
`exists: false` finds it. A project the extension onboarded before this release holds SWCraft's own
development instructions in `.github/copilot-instructions.md` and an older agent profile: run
*Onboard Project* again to replace both with the model project's files — it overwrites both, so
keep a copy of anything you edited in them. The extension's offer does not replace them: it
appears only where the agent profile is missing, and never overwrites a file. *Onboard Project*
is also how such a project gets `view` in its agent profile and the model guard, the hook file
`hooks/swcraft.json` in its `.github` folder; *Check Editor Tooling* reports the guard missing until then. The
guard runs the `swcraft` on your path, so that `swcraft` must be this release's: an older one has
no `guard` command.
