# SWCraft 0.18.0

Released 2026-10-21. The release of trace links: SWCraft proposes, for each requirement, the
architecture elements it could be linked to, with the reasons and a band for the strength of the
evidence; you decide in VS Code's new **Trace Links** view or in a file, and one **Apply…** writes
the links into the model. The **Change Report**, in the panel in place of *Diff* and on the command
line as `swcraft change-report`, shows what a model change does before you commit it. The
requirements import now says what changed in each requirement and asks one question in VS Code, and a
component no
longer needs a requirement link — the model's contract moves to `12.0.0`, a major, for that one
removed rule. No model file needs an edit; *What upgrading takes* at the end is the recipe. The
archive's sizes are the tag run's, recorded under *The archive*.

## A new experiment: proposed trace links

`swcraft experiment trace` reads your requirements and every element that can carry `satisfies` —
components, ports, runnables, interfaces, compositions, tasks and hardware elements — and proposes,
for each requirement, a short ranked list of elements it could be linked to, each with the reasons
it was proposed and a band (*strong*, *medium*, *weak*) that names the strength of the evidence and
is not a probability of being right.

The elements linked by the other requirements of the same document count for more as the document
gets more links, at full weight from five: a document with one or two linked requirements no longer
has their elements proposed to every other requirement ahead of what the text names, and such an
element alone is *weak* until three requirements of the document are linked.

It writes `report.md`, `result.json` and `proposals.json` under `dist/experiments/trace/` and nothing
into your model; each search rewrites `proposals.json` whole, unless it holds decisions not yet
applied (below). Each document gets one pass: **review**,
the default, lists every requirement with its candidates; **labelling**, chosen per document in the
configuration file, lists every requirement too, the few to link first on top. Words of the project's
name and of a requirement's baseline, and boilerplate such as *one*, *every* and *provide*, are not
evidence. The search runs on a model
`swcraft check-model` refuses and lists its findings; it refuses only a project it cannot read, two
elements of one kind sharing a name (or two requirements one id), a configuration it refuses, and a
project pinned to another release. A requirement's `document` matters: the links the other
requirements of its document already have are the strongest evidence, and a requirement without one
is ranked from its text alone. The guide's *Experiments* page has the details.

The command's `KIND` now accepts `allocation` and `trace`; the editor's panel runs it too (below).
Nothing changes for `swcraft experiment allocation`.

## Applying the trace links you decided

You decide in `proposals.json`: a candidate's `decision` becomes `"accept"` or `"reject"`, an element
the search did not list can be added to the requirement's `chosen` list, and a link awaiting
confirmation gets `"confirm"`. Then

```sh
swcraft experiment trace --project swcraft.yaml --apply dist/experiments/trace/proposals.json --dry-run
```

prints what would be written — the links, the confirmations, the rejections, the decisions that can
no longer be applied and why, every component whose allocated safety level the new links raise, the
links you must add by hand — and a `Plan:` digest. The same command without
`--dry-run` writes it all or nothing; `--expect-plan` with the digest refuses if anything changed
since the preview. Every decision is checked against your model as it is now: one whose requirement
or element changed since the search is not applied and is listed with its reason. Running it twice
writes nothing the second time.

Accepted links are written as `satisfies` entries `<id>@<version>` on every kind of element that
carries `satisfies`; a confirmed link moves to the requirement's new version. Apply adds only those
lines: every other line of the file — comments, key order, quoting — stays as you wrote it. A
`satisfies` list in a form it does not edit (a list in brackets over several lines, for example) is
left alone and its links are listed for you to add by hand. Every decision applied is
recorded in a new file, `trace-decisions.yaml`, beside `swcraft.yaml` — keep it in version control. A
rejected pair is not proposed again while the requirement stays at that version.

A search now refuses to overwrite a `proposals.json` that holds decisions not yet applied, one it
cannot read as a proposals file, or one that changed while it ran; apply them, or search again with `--discard-pending`. The ARXML a model generates does not change: no ARXML reads
`satisfies`.

## Deciding trace links in VS Code

The SWCraft panel's *Experiments* section gains **Trace Links** with two nodes, **Labelling** and
**Review**. Click one to choose its documents from a list (the ones with no link yet first); a
document is in one mode at a time. The **Trace Links** view below the panel then shows the documents
of the mode you clicked last — document, requirement, proposed elements, with a checkbox on each
element — and each mode counts what is left (*9 of 12 to go*). A
requirement shows its three strongest proposals, then *More candidates* unfolding the rest in place,
then *Any element of the model…*; hovering a requirement shows its whole text and clicking it opens
its file in one preview tab; a requirement already linked shows its links and asks nothing. Labelling shows the
elements alone, as `runnable:Owner.Name`; Review shows each one's band, as `strong·runnable:Owner.Name`
with a dot coloured by the band, and a short reason, and **Mark strong** ticks the strong
ones for you to check. The panel searches only when a chosen document is not in the proposals file in
its mode; if the last search's decisions are not applied yet, it asks first whether to apply them,
discard them or cancel. You tick an element to accept it, reject it with ✕, choose an element the
search did not propose, and confirm a link that awaits confirmation. A click opens the element in one preview tab; the panel never splits the editor. **Apply…** — a row at the top of the view while anything is ticked — asks one
question, *Write N links into M files?*, with *Write* and *Cancel*, and writes exactly what the dry run
showed; the message after it opens the report. Your ticks are saved in
`proposals.json` and nowhere else.

Two command-line additions serve the panel and work on their own: `swcraft experiment trace --documents`
prints each document's links and the pass the configuration gives it and writes nothing, and
`--labelling` (`"all"` or a list of documents, as JSON) chooses the labelled documents for one search
without changing the configuration file; the report says the choice came from the command line. Each
requirement in `proposals.json` now carries its `title`.

The guide's *Importing requirements* section now says why a converter should fill each requirement's
`document`, with what SWCraft measured.

## The Change Report: what a change does, before you commit

The SWCraft panel's **Diff** is replaced by **Change Report** (also in the palette as *SWCraft:
Change Report*). One click compares your uncommitted model with `HEAD`, as `swcraft diff` does by
default, and opens a report in VS Code's Markdown preview:

- a verdict line — the errors and warnings the change introduces, how many changes in how many
  elements and compositions;
- what changed, element by element;
- the requirement links the change gained, lost or re-confirmed, and the links it left needing
  confirmation;
- the `check-model` findings the change introduced — never those the model already had;
- the load of each core and the use of each memory, before and after;
- who uses an interface the change touched;
- the ARXML elements the change adds, removes or changes;
- the overview of each composition the change touches, drawn before and after. The *before* picture
  is unmarked; on the *after* picture an added element has a green outline, a removed one a red dashed
  outline, and a line is green when connectors were added on it, red when removed, blue when both.

Every line is computed from the model at the two revisions; the same change gives the same report,
and nothing in it is written by AI.

The command behind it is `swcraft change-report`. It takes `swcraft diff`'s revisions (none: the
working tree against `HEAD`; one: a revision against the working tree; two: two revisions) and writes
`change-report.md`, `change-report.json` and the pictures into `dist/change-report/`. `--format json`
prints the JSON document, `--no-diagrams` leaves the pictures out (they need Node.js), and `--fail-on
error` or `--fail-on warning` makes the run fail when the change introduces a finding of that level —
the report is written first. The user guide's *Change Report* page has pipeline templates that post the
report as a pull request comment; the posting is your pipeline's, not SWCraft's.

`swcraft diff` now prints a task's or a sequence's runnable entry, and a runnable's read, write or call,
as the model writes it — `Chassis/BrakeSubsystem/BrakeFadeMonitor.DetectFade`, `pSpeed.speed` — where it
printed `(None, Chassis/BrakeSubsystem/BrakeFadeMonitor, DetectFade)`. `swcraft diff --format json` is
unchanged.

## Importing requirements in VS Code asks once

*Model → Import Requirements* now asks one question after its dry run, with the dry run's count —
*Import needs.json: 46 added, 0 changed, 0 removed, …?* — and imports only on **Write**. No report
opens by itself: the message after the import gives its count, with **Show Report** and **Check
Model**, and the report opens in one tab named *Requirements Import Report*, which the next report
replaces. Before, the dry run's report opened in a tab, a notification led to a second question, and
the import's report opened in a second tab. The command line is unchanged.

## The requirements import says what changed

`swcraft import requirements` now prints, under each changed requirement of its report, what changed
in it: the numbers before and after, the words added and removed, the type, the safety level and the
parents. For example:

```text
Changed:
  SR-12 v3 → v4 (description, asil)
    text: numbers 600 → 650; terms added: overheat; terms removed: temperature
    ASIL: B → D
```

A word is named when it carries meaning: a negation or a modal that moved (`shall` → `shall not`,
`shall` → `may`) is named, while common words such as *at*, *for* or *the*, and the *s* of `60 s`,
are not; a text whose terms and numbers did not move reads `wording only`. These lines are what you
check a link against before confirming it. The `Summary:` line and the
other sections are unchanged, so a script reading the summary needs no change.

## A component no longer needs a requirement link

`swcraft check-model` and `swcraft validate` no longer warn about a component that satisfies no
requirement. The line

```text
  WARNING: SWC 'SpeedSensor' satisfies no requirement — add `satisfies: [<id>@<version>]` on the component, one of its ports or one of its runnables.
```

is gone, and with it the rule `cross-layer.swc-without-requirement-link`. No standard asks that
every architecture element trace to a requirement: traceability in both directions means a link
can be followed both ways, not that every element has one. A freshly imported architecture, whose
components link to nothing yet, now checks with no warning at all.

The other direction stays: **a requirement that no element satisfies is still a warning**
(`trace.requirement-unallocated`), so a requirement the architecture does not realize is still
listed by every check.

A pipeline that runs `check-model` or `validate` with `--warnings-as-errors` now accepts a model
whose only findings were components without a link, and `validate` generates its ARXML. A
requirement nothing satisfies is refused under the flag as before. The ARXML a model generates does
not change.

The import report no longer says each imported component is listed as a warning; it says that no
requirement was written, and to link each imported component to the requirements it realizes with
`satisfies`. `swcraft import component` no longer leaves a warning per imported component either.

The assistant instructions `swcraft init` writes — `.github/copilot-instructions.md` and
`.github/agents/swcraft-architect.agent.md` — now describe the requirement's direction only. A
project created before this release keeps its own copies, which still say an unlinked component is
a warning, and nothing overwrites them; replace them from a freshly scaffolded project.

The assistant no longer asks for or adds a requirement link to every new component: it links one
only when you name the requirement the component realizes.

## The model's contract is `12.0.0`

`contractVersion` moves from `11.1.0` to `12.0.0`, a major: one identifier is removed,
`rule:cross-layer.swc-without-requirement-link`. Nothing is added or renamed. Four rules are
warnings now: `rule:trace.requirement-unallocated`, `rule:trace.requirement-stub`,
`rule:trace.link-version-not-stated` and `rule:trace.link-needs-confirmation`. No model file
needs an edit.

## The archive

The runtime payloads are 0.17.1's but one: **Red Hat YAML moves from 1.25.0 to 2.0.0**, the
Marketplace's current release, so VS Code no longer offers to update it right after an install.
2.0.0 raises the extension's own minimum VS Code to 1.91.0, below the 1.110 the SWCraft extension
needs, and changes nothing the SWCraft extension relies on: the schema lens it draws at the top of
each model file is titled as before. Node.js 22.23.2, CPython 3.11.16 (the python-build-standalone
build of 2026-09-01), `elkjs` 0.12.0 inside the `swcraft-tools` package and Red Hat XML 0.29.3 are
unchanged, and the three Python packages and the extension declare the same dependencies as 0.17.1.
The Linux archive measures **197 828 776 bytes** (SHA-256 `bf0bc5c1…c0f6e3f2`) and the Windows
archive **201 890 716 bytes** (`46f0cbec…3aca1e2f`), as the tag run of 2026-10-21 published them:
184 456 and 184 464 bytes more than 0.17.1's.

## What upgrading takes

1. **Install the 0.18.0 archive, then set `toolchain_version: "0.18.0"`** in each project's
   `swcraft.yaml`. Until you do, every command that writes or gates refuses a project pinned to
   0.17.1 with the pin sentence and never reaches the model. The read-only commands (`diff`,
   `impact`, `list`, `query`, `resource-report`) and `swcraft guard` only print a warning, so
   Copilot keeps working meanwhile.

2. **Run *SWCraft: Onboard Project* again** to bring the assistant profile and the Copilot
   instructions to this release: they no longer call a component without a requirement link a
   warning, and the assistant no longer adds a link to every new component. It overwrites both
   files and the model guard, so keep a copy of anything you edited in them.

3. **A pipeline that counted on the removed warning** changes with it. `check-model --format json`
   no longer reports the rule `cross-layer.swc-without-requirement-link`, and
   `--warnings-as-errors` no longer stops a model whose only findings were components without a
   link. A project that wants every component linked keeps that as a review check of its own; a
   requirement nothing satisfies is still a warning, and still refused under the flag.

4. **Once you apply trace links, commit `trace-decisions.yaml`** beside `swcraft.yaml` with the
   model files the apply changed: it records every decision applied, and a pair you rejected is
   not proposed again while the requirement stays at that version.

The model's files, the hook file `.github/hooks/swcraft.json` and the generated ARXML are unchanged
from 0.17.1. A 0.16.x project upgrading straight to 0.18.0 follows [0.17.0's note](0.17.0.md) first:
its requirement files and one line of `swcraft.yaml` need an edit.
