# SWCraft 0.5.2

**The guide gets a door.** A patch release from `release/0.5`, for the demonstration track. The
model contract, the editing protocol, the 13-tool MCP surface and the emitted ARXML bytes are
unchanged from 0.5.1; a 0.5.x project upgrades by installing the four artifacts.

0.5.0 shipped the user guide and hashed it into the release as `swcraft-guide-<version>.zip`. That
is a **serve-it** artifact, and until now the delivery read, in full, as *"download the zip, unpack
it, run `python -m http.server` in the unpacked folder, then open `localhost:8000`"* — because over
`file://` the site's search cannot load its index and every internal link degrades to a directory
listing. Both halves were measured. This
release removes the procedure for anyone who has SWCraft installed.

```
swcraft-tools==0.5.2
swcraft-mcp==0.5.2
swcraft-agent==0.5.2
```

plus `swcraft-vscode-0.5.2.vsix`.

## `swcraft docs` — the guide, from the install, in one command

```sh
swcraft docs                    # serve the installed guide and open a browser
swcraft docs --no-browser       # serve only; the address is printed
swcraft docs --port 8080        # a fixed port instead of an OS-chosen one
```

- **The rendered site ships inside the `swcraft-tools` wheel** as package data at
  `swcraft_tools/guide_site/` — 71 files, 3.25 MiB, measured. One `pip install` brings the guide on
  every platform; there is no second artifact to fetch and no `--project` to point at, because the
  command reads no model.
- **Search and navigation work**, because the site is served rather than opened. That is the whole
  point: the two `file://` breakages are out of reach by construction.
- **The bind is always `127.0.0.1` and is deliberately not a flag.** A documentation server that can
  be exposed to a network is a security decision nobody asked for. `--port` defaults to `0`, so the
  OS picks a free port and a second `swcraft docs` does not fail on a busy one — two concurrent runs
  were measured on two ports, both bound to the loopback interface and nothing else. The URL is
  printed before the browser opens; `Ctrl+C` exits **0**, because a completed serve is a successful
  run.
- **If no guide is installed, the command refuses by name**: exit **1**, naming the directory it
  looked in by absolute path and naming `swcraft-guide-<version>.zip` as the fallback with what to
  do with it. That advice was followed in acceptance and found true. A read-only command exits 0
  when the answer is uninteresting, not when it could not answer.
- **A failed browser launch is not a failure.** On a headless or locked-down host the opener can
  report failure while the URL is perfectly serviceable, so the command says "open this URL
  yourself" and the exit code does not move.
- `swcraft --help` and the guide's own CLI reference document the command; nobody typed that page,
  it is generated from the parser.

## `SWCraft: Open Guide` in the VS Code panel

A thirteenth panel item, last in the **Setup** section under `Check Editor Tooling` — that one is
the narrow question asked when something is already wrong, this one is the general *how does this
work*. It is in the Command Palette as `SWCraft: Open Guide`, and the walkthrough gains a seventh
step that runs it.

It is the first SWCraft command whose child is not expected to exit, so it does not go through the
extension's ordinary CLI spawn (which resolves when the process closes). Instead it runs
`swcraft docs --no-browser`, resolves on the server's **announcement** rather than on its exit, and
hands the announced address to `vscode.env.openExternal` — the API that resolves to the machine the
user is sitting at, which under Remote SSH, WSL or Codespaces is not the extension host.

Lifecycle: **one server per window.** A second invocation re-opens the browser against the server
already running; a child that dies on its own is dropped; the session is disposed when the window
closes. There is deliberately **no `Stop Guide` command** — a documentation server bound to the
loopback interface, tied to the window that started it, is not something a reader should have to
manage.

Each failure path records a status on the item, reveals the output channel and raises a
notification: the CLI cannot be spawned; the CLI exits before announcing (the no-payload refusal,
whose full text — the directory and the archive — reaches the channel); or no address arrives inside
20 s, after which the child is killed. Measured announcement latency on one Linux host: 0.37 s.

## What this does not reach, stated rather than implied

- **It serves what shipped.** The site is the one that came with the installed product, so the
  command **cannot show a newer guide than the release on the machine**. Getting a newer one means
  upgrading SWCraft, or unpacking a newer archive and pointing `SWCRAFT_GUIDE_SITE` at it.
- **It cannot tell you the site is old.** The locator makes one presence check, on `index.html`. It
  compares no version, and a guide rendered from an earlier release reads as perfectly good to it.
- **`SWCRAFT_GUIDE_SITE` overrides the location**, and it is an ordinary environment variable —
  **a project's `.env` reaches it**, because `swcraft`'s entry point loads that file before it
  dispatches to any subcommand. Pointed at an empty directory it produces the refusal above; pointed
  at another release's unpacked archive it serves that release's guide without comment.
- **The archive is still the artifact for everyone without an install** — a machine with no SWCraft
  on it, a review copy, an intranet mirror. `swcraft docs` narrows the case for the mkdocs `offline`
  plugin and for `use_directory_urls: false`; it does not close it, and neither has been tried.
  Central hosting stays an open question for the same reason: it serves the reader who has installed
  nothing.
- **Windows is unmeasured for this command.** Everything above is one Linux host, one platform, one
  date. Firewall behaviour on a first bind to `127.0.0.1` and which browser Windows opens are the
  two specific unknowns, and they are on the standing Windows checklist.
- **No page of the guide is qualification evidence**, and serving a page over HTTP adds nothing to
  what the page is. `swcraft validate` remains the sole authoritative model and ARXML/XSD gate. The
  plausible failures here are "serves nothing" and "serves a stale site"; neither can produce a
  false pass about a model.

## A note for developers of SWCraft itself

`python scripts/dev.py artifacts` now renders the guide into `tools/src/swcraft_tools/guide_site/`
as part of the wheel build — the one write of that run that reaches a Python package source tree.
It is gitignored, rewritten from scratch each time, in no manifest, and removed by no clean step;
it costs about 3.3 MiB in a working tree. `python scripts/dev.py docs` still renders only into
`dist/docs/site/`, and `SWCRAFT_GUIDE_SITE=dist/docs/site swcraft docs` is how a documentation
change is previewed.

## Upgrading

Install the four artifacts and reload VS Code. **Nothing in a project changes**: no manifest key, no
model file, no generated output, no MCP configuration. Getting the guide is an install, not a
migration — the site rides the wheel, so `pip install swcraft-tools==0.5.2` is what brings it, and a
project that keeps its own pinned `requirements-swcraft.txt` raises the three `==` pins.

Then run `swcraft docs`, or click **Open Guide** in the SWCraft panel.
