# SWCraft 0.15.0

**Released 2026-10-10** (the bump commit; the tag follows the `verify` gate on both self-hosted
runners, Linux and Windows, on this commit, and the tag's own run publishes the release archives to
the NAS). This note was written with each change rather than after it, so every figure below was
measured on the host and at the commit that produced it.

## Every task runs in a partition

The hardware layer gains a fourth kind of element, the **partition** — AUTOSAR's OS-Application,
the group of tasks that run together on one core under one memory protection. A task no longer
names a core: it names its **partition**, and takes its core from it. This is the one change of
this release that stops a project from loading, and it reaches every project that declares a task.

```yaml
# model/hardware/PARTITION0.yaml
name: PARTITION0
kind: partition
core: CORE0
```

```yaml
# model/tasks/Task_10ms.yaml
name: Task_10ms
period: 0.01
priority: 5
partition: PARTITION0       # was: core: CORE0
```

A partition has a `name`, its `kind`, the `core` it sits on (required, the name of a declared
core), an optional `asil` — the level the partition *is*, `QM` or `A` to `D` (or a decomposed `X(Y)`, below), like a component's
and unlike a core's `asil_capability` — an optional `coexistence` text, its argument for sharing
its memory between components of different levels, and a `description`. A partition no task names
is legal. A project on one core without memory protection still has every task name a partition:
it declares one without a level on that core — a convention of SWCraft, since AUTOSAR configures
no OS-Application there.

**What breaks.** A task file that still says `core:` does not load. Every command that reads the
model stops at the first such file, naming it, with:

```text
Error: Invalid task YAML in …/model/tasks/Task_10ms.yaml: 1 validation error for Task
partition
  Field required [type=missing, …]
```

A task file carrying both `core:` and `partition:` loads, and its `core:` is ignored like any other
key the model does not know — delete it.

**What upgrading takes**, for a project written by hand:

1. For each core the project's tasks name, write one partition on it into `model/hardware/`. Give
   it as its `asil` the level the components its tasks run share, or no `asil` when they do not
   share one. `swcraft init` names the scaffolded one `PARTITION0` on `CORE0`; any name the
   hardware layer does not already use will do.
2. In every task file, replace `core: <core>` by `partition: <the partition on that core>`.
3. Run `swcraft check-model`.

Nothing else in the model moves. The generated ARXML and the requirements document are byte for
byte what they were — a partition is not written into either — and only the deployment diagram
changes. A project that declares no task is not affected — `swcraft import model` writes none, so
a project built from an export alone needs nothing.

**New checks.** Each names the elements involved and the repairs, and chooses none of them:

- the references: a task naming a partition nothing declares, or naming a hardware element that is
  not a partition; a partition naming a core nothing declares, or a hardware element that is not a
  core. They replace the two checks on a task's core. A partition with a blank name, a name
  holding a path separator, or a blank `core`, and a task with a blank `partition`, are refused
  when the file is read.
- a **rated partition on a core** declared able to host only a lower level — whether or not any task
  runs in it. It replaces the check of a task on such a core, which compared each component the
  task ran with the core's `asil_capability`. That comparison now goes through the partition's
  level: a partition left without an `asil` is compared against nothing, so on a project whose
  cores declare an `asil_capability`, an unrated partition loses a finding the retired check
  reported — a component rated above its core passes `swcraft check-model` once the recipe's
  partition is unrated. To keep the check, rate the partition.
- a component run by a partition's tasks **above** the partition's level; one **below** it, `QM`
  included, unless the partition carries a `coexistence` argument; and a partition whose components
  charge **a memory** declared able to host only less than the partition's level, once per partition
  and memory. A budget belongs to the component type, so two instances of one type in two
  partitions are charged to the same memory.
- a component **occurrence** whose runnables are run by tasks of **two partitions**: two
  occurrences of one component type are judged apart (see *A task can name one occurrence of a
  component* below). A model without exactly one root composition and a cycle among the
  compositions below the root are not judged.

An unrated partition is compared against nothing, so a project that writes no `asil` on its
partitions gains no finding from the four level checks (a `trusted` unrated partition is the one
exception, under *A partition says whether it is trusted* below). The checks that compare a core's time
budget and a memory's reach now find a task's core through its partition; their findings name the
partition, as in *Task 'Task_10ms' runs in partition 'PARTITION1' on core 'CORE1', but …*.

**The assistant** asks you separately before it lowers or clears a partition's level, removes a
rated partition, writes a partition's `coexistence`, or moves a task into an argued partition so
that the argument starts answering. Raising a partition's level is not asked about — a level is a
rating, and raising one never is — and neither is a task moved to an unrated partition or a
partition moved to an unrated core.

**The deployment diagram** draws one more level, processor → core → partition → task → component:
each partition is a box inside its core, headed with its name and, when it declares one, its level;
an empty partition is an empty box. A task whose partition is not declared, and a partition whose
core is not declared, are listed in the report as not drawn.

**`swcraft init`** writes `model/hardware/PARTITION0.yaml` — on `CORE0`, unrated — beside the
processor and the core, so a new project's first task has a partition to name; the template has
sixteen files. It withholds the partition whenever it does not write `CORE0` itself. Deleting
`CORE0.yaml` from a fresh project now fails `swcraft check-model`, because the partition names it.

**For a script that calls SWCraft's Python writer:** `create_task`'s `core` parameter is renamed
`partition`, in the same position, and `set_task_core` is now `set_task_partition`.
`create_hardware_element` creates a partition for `kind="partition"`, with `core=` and, optionally,
`asil=` and `coexistence=`.

**The model's contract is `9.2.0`**: its major, `9.0.0`, because five identifiers are removed:
`field:tasks.task.core`, `rule:tasks.task.core.not-blank`, `rule:hardware.undeclared-core`,
`rule:hardware.core-not-a-core` and `rule:safety.task-on-unqualified-core`. Thirty-two are added: the
partition kind and its six fields, `field:tasks.task.partition`, the four reference checks, the three
checks that refuse a blank name or core, `rule:safety.partition-on-unqualified-core`,
`rule:safety.component-above-partition`, `rule:safety.component-below-partition`,
`rule:safety.partition-memory-below-level` and `rule:task.instance-in-multiple-partitions` —
and the twelve of the occurrence selector below. The minor, `9.1.0`, adds three more and removes
nothing: a partition's `trust` and its two checks (below). The minor `9.2.0` widens four fields'
values (the decomposed levels, below) and adds and removes nothing. The contract declares fifteen layers,
fifty-nine element kinds, 304 fields and 292 checks. Tooling of your own that names a removed
identifier has to follow it.

## A task can name one occurrence of a component

A task's `runnables` entry and a sequence step name their component by **exactly one** of two
keys: `swc`, the component **type**, as before, or the new `instance`, one **occurrence** of it —
the member names from the root composition down, joined by `/`, never starting with the root
composition's own name. A member of the root is its member name alone.

```yaml
# model/tasks/Task_10ms.yaml
name: Task_10ms
period: 0.01
priority: 5
partition: PARTITION0
runnables:
  - swc: SpeedCtrlSWC          # a type placed once: as before
    runnable: Run10ms
  - instance: left/worker      # one of two occurrences of the same type
    runnable: Run10ms
```

Nothing written so far changes meaning: an entry with `swc` alone loads and is checked as it was
whenever its type is placed once below the root composition, or nowhere. A type placed **more than
once** has no one occurrence for `swc` to name, so `swcraft check-model` now refuses such an entry
and asks for `instance`; before, every check read the type and the partition check did not judge
it. An entry with both keys or neither is refused when the file is read.

**What upgrading takes:** nothing where every type a task or a sequence names is placed once below
the root composition, or nowhere. For each entry `swcraft check-model` refuses as naming a type
placed more than once, replace `swc: <type>` by `instance: <path>`, using a path the message lists
(it lists the first 64 and the exact count). To keep running the runnable of every occurrence,
write one entry per path. Do the same in each sequence step that names that type, then run
`swcraft check-model`.

**New checks**, in `swcraft check-model`, each the same for a task and a sequence step: a `swc` on
a type placed more than once (it names every path, up to the first 64, and the exact count); an
`instance` path one of whose names is no member on the way, or that goes on below a component or
into a composition nothing declares; one that ends on a composition rather than a component; and one runnable of one occurrence reached twice in a task or
a sequence, once by `swc` and once by `instance`. Every task, sequence and safety check compares
occurrences, so the two spellings of one occurrence are one. Without exactly one root composition,
or on a composition cycle, an entry is compared as written and none of these is reported.

**What a script that reads SWCraft's output pays.** The identity of a task entry and of a sequence
step is now `{swc, instance, runnable}`, and what the tools return always spells the absent one as
`null`:

- `swcraft diff` prints the key as `(SpeedCtrlSWC, None, Run10ms)` and, in `--format json`, as
  `["SpeedCtrlSWC", null, "Run10ms"]`; the JSON document's `schema_version` is **2**.
- `swcraft query`'s `--members` identities and `--after` cursors carry the three keys; its JSON
  `schemaVersion` is **3**.
- The assistant's editing tools return member addresses with the three keys, and a `full` read
  carries both `swc` and `instance`, one of them `null`; a `summary` row carries only the one set.

What a script **writes** keeps working: an address or a payload that leaves the absent key out
names the same entry. Changing an entry from `swc: A` to `instance: a` is reported as a removal and
an addition, never a change, because no tool resolves an occurrence when it compares two models.

**What it does not reach.** An `instance` is a path, not a reference: `swcraft impact A` and
`swcraft query --dependents A` do not list an entry that names an occurrence of `A` by `instance`.
A component's level and its memory budget still belong to its type, so two occurrences of one type
cannot be rated or charged differently. The diagram of a sequence draws one lifeline per occurrence,
labelled as the step writes it; a data message to a type with two lifelines is not drawn and is
listed in the diagram report. The ARXML and the requirements document do not move: a task mapping
is in neither.

## A partition says whether it is trusted

A partition gains an optional `trust`: the class the operating system gives it. `non_trusted`, the
default, is confined by memory protection; `trusted_with_protection` is trusted but confined for
memory the same way; `trusted` is not restricted for memory at all.

```yaml
# model/hardware/P_Gateway.yaml
name: P_Gateway
kind: partition
core: CORE0
asil: B
trust: trusted
```

**What upgrading takes:** nothing. A partition that writes no `trust` is `non_trusted`, and a file
that declares none is written back byte for byte as it was. The ARXML and the requirements document
do not move.

**New checks**, in `swcraft check-model`, each judging a `trusted` partition alone — the operating
system protects a partition's data only from partitions that are not trusted, so a trusted one can
write into every other partition's memory:

- a trusted partition rated **below** the highest level any partition of the processor declares,
  naming the partition that declares it (a written `QM` counts as a level);
- a trusted partition declaring **no** level while that highest level is above `QM`.

A `trusted_with_protection` or `non_trusted` partition is never reported by either. The class is a
declaration: nothing reads the operating system's configuration, so a partition the configuration
actually trusts and the model leaves `non_trusted` is not reported.

**The assistant** asks you separately before it makes a partition `trusted` or creates one that is,
and before it confines a trusted partition — `trusted` to `trusted_with_protection` or
`non_trusted` — because that makes both checks stop reporting it. Moving between `non_trusted` and
`trusted_with_protection` is not asked about, and neither is removing a trusted partition: a
partition that no longer exists declares nothing to ask about. That includes removing a trusted
partition and creating a confined one under another name in the same change set — that is a
removal and a creation, not a confinement, so the confinement question is not asked; only a rated
partition's level and argument are, as for any removal. The question about a grant opens *This change set
widens a permission.* rather than calling it a weakening. **For a reader of `dist/audit.jsonl`:** a
change set whose only safety change makes a partition `trusted` was asked that second question, so
its `change_set_approved` record carries `safety_decision` `approved` or `declined`, not
`not-applicable` — the same as for a change set that weakens a check.

**The deployment diagram** heads a trusted partition with `trusted` after its level
(`ASIL D · trusted`, or `trusted` alone on a partition without a level); a confined partition shows
no mark.

**For a script that calls SWCraft's Python writer:** `create_hardware_element` takes `trust=` for a
partition.

## A level can be written decomposed

A requirement's, a component's, a data element's and a partition's `asil` take the decomposed
levels as well as the five plain ones: the eighteen values the AUTOSAR Safety Extensions list —
`QM`, `A`, `B`, `C`, `D` and the thirteen `X(Y)` spellings `QM(A)`, `QM(B)`, `QM(C)`, `QM(D)`,
`A(B)`, `A(C)`, `A(D)`, `B(B)`, `B(C)`, `B(D)`, `C(C)`, `C(D)`, `D(D)`. `Y`, in parentheses, is the
level before decomposition. `A(A)` is not one of them, because the standard does not list it.

```yaml
# model/requirements/REQ-BRK-012.yaml
id: REQ-BRK-012
title: Brake request plausibility, channel 1
description: One of the two independent channels the ASIL D brake request is decomposed into.
asil: B(D)
```

**Every check compares by `X`:** `B(D)` is the level `B`, and `QM(D)` declares no ASIL, like `QM`.
`(Y)` is kept as written — in the file, in a finding's message, in the requirements document and on
the deployment diagram — and never compared. A core's and a memory's `asil_capability` keep the five
plain values: a capability is not decomposed.

**What upgrading takes:** nothing. Every value valid before is valid now, and the ARXML does not
move. The editor completes and checks the eighteen spellings, and any other — `A(A)`, `b(d)`,
`B (D)` — is refused when the file is read.

**What this does not check.** Whether a decomposition is valid — that the two `B(D)` requirements
are independent and together realise one `D` requirement — is evidence outside the model, and
nothing checks it. A safety goal taking only a plain level is not checked either: a requirement says
nothing that marks it as a safety goal. `swcraft query --where asil=B` matches the value as written,
so it finds `B` and not `B(D)`, and the same holds for a filter on the requirements document's
`:asil:` option.

## A build keeps the previous ARXML as `model_old.arxml`

Until this release the first step of a build removed everything it had generated before, so after
a model change there was no earlier ARXML left to compare the new one with. Now one previous copy
is kept. `swcraft clean-outputs` — the first task of the scaffolded `moon.yml` — moves
`dist/model.arxml` aside as `dist/model_old.arxml` (replacing an older one) and removes the rest,
`dist/audit.jsonl` still kept as before; `swcraft generate arxml` and `swcraft validate` make the
same move themselves before they write, but only when the new file's content differs, and print
`Previous ARXML kept:` with its path when they do. A `validate` that regenerates exactly what
`generate arxml` just wrote moves nothing, so after a build `model_old.arxml` is the ARXML of the
build before it. The assistant's `validate` and `build` make the same move, and their answers do not
mention it; SWCraft: Build in VS Code runs `clean-outputs` first, so it keeps the copy too.

What you see: from the second build on, `dist/` holds one more file. It is the previous ARXML that
was **written**, not necessarily one that passed — a build whose `validate` refused its ARXML
leaves the refused file at `model.arxml`, and the next build moves that one aside. A build that
fails at `check-model` generates nothing, so it leaves `model_old.arxml` and no `model.arxml`. The
copy is kept only when the ARXML sits directly in `dist_root`: an ARXML the manifest places in a
subdirectory, or directly in `views_root`, is not moved, and when `dist_root` lies inside
`views_root` the copy is removed with it. The per-component exports are never moved aside, and the
content of every generated file is unchanged.

**What upgrading takes:** nothing. A project that ignores `dist/` in version control — the
scaffolded one does — needs no change.

## An infinite physical limit is named in the import report

A range's or a constraint's physical limit that is infinite on its own side — `-INF` below, `INF`
or `+INF` above — was already imported as no bound, which states the same interval, but the
report said nothing of it. A limit marked `INTERVAL-TYPE="INFINITE"` was read as the number it
held. Now both read as no bound, and `swcraft import model` and `swcraft import component` list
each such limit once, *infinite physical limit represented as an absent bound*, under a new block
*Represented in another form* — nothing is lost, so it is neither a skipped line nor a property not
imported, and `import component` never aborts on it. Two declarations of one name that differ only
in the number an `INFINITE` limit holds are now one element, and an `INFINITE` limit no longer
equals a closed limit of its number: the comparison reads every physical limit's interval now, an
omitted one meaning `CLOSED`.

What this does not reach: a value type's bounds (`INTERNAL-CONSTRS`) still read an infinite limit
as absent with no line, and an `INTERVAL-TYPE="OPEN"` physical limit is still carried as its
number. A physical limit that is `NaN`, or the other side's infinity, is still reported as a limit
the import cannot read as a number, under `INTERVAL-TYPE="INFINITE"` too.

**What upgrading takes:** nothing.

## Every external element an import creates is named `<name>_ext<N>`

When an export references an interface, a type or a component it does not contain, `swcraft import
model` creates an **external** element for it, holding the source's path. Until this release such an
element took the path's last segment as its name, and an `_ext` suffix only where that name was
already taken — by another external element whose path ended the same way, for one — so which of
two paths kept the plain name depended on the file. Now every external element the import creates is
named the last segment followed by `_ext` and a number: `_ext0` where no other external element of
its kind has a path ending the same way, and `_ext0`, `_ext1`, `_ext2` … where several do, numbered
in the alphabetical order of their paths. The suffix says the element came from outside the file,
and the name never depends on where in the file a path first appears. Every external element is
listed among the report's renames, `<name> -> <name>_ext<N>`. Where the name with its suffix would be
longer than 128 characters, the last segment is shortened and the suffix kept whole. The generated ARXML is
unchanged, because an external element's name is never written there — its path is.

What this does not reach: when an import keeps only some packages (`--packages`), or a later step
drops the only element that referenced one of several namesakes, the kept element keeps the number
the whole file gave it, so a number can be missing beside it (`IFoo_ext1` with no `IFoo_ext0`), and
importing the written result again numbers it afresh. An external element written by hand keeps the
name its author gave it. `swcraft import component` still refuses an incoming interface or type that
the target project holds as an external element **standing for the same path**: it now finds that
element by its exact `external_ref` as well as by its name, so a target's `IFoo_ext0` for
`/Pkg/IFoo` refuses an incoming `IFoo` declared at `/Pkg/IFoo`, and the refusal names both. An
external element standing for another path (`/Other/IFoo`) is another element, and the incoming
`IFoo` is created beside it — two paths sharing a last segment never identify one element. The
same holds for a component: a target's external `Foo_ext0` for the incoming component's own path
refuses an incoming `Foo`, and `--update` does not replace it, because the component would take the
external element's file while the compositions still name `Foo_ext0`. Rename the external element
and the compositions' references to it to `Foo`, and `--update` replaces it as it always did.

**What upgrading takes:** nothing for a project that does not import. A project built by `swcraft
import model` receives the new names on its next import, and every reference inside the import
follows; anything you wrote yourself that names an imported external element by its old name must
be renamed to match.

## `import component` answers a component's references from your project

Until this release `swcraft import component` resolved every reference a component file makes
against the file alone, and refused the whole import on the first one the file did not answer. A
file whose port names an interface your project already holds, but which the file leaves out — the
usual shape of a component file another tool wrote — was refused, and so was a file whose runnable
reads a data element or serves an operation your project's interface declares and the file's copy
does not. Nothing was written, and the refusal listed the file's lines rather than what was missing.

Now the import answers each reference against the project it would leave: the file's own
definition at exactly the path the reference names first, then your project's interface or mapping
set of the same name — an interface only when it is of the kind the reference names. What the
component **describes** — its ports with their communication
specifications, the interfaces and types the file brings, its description, how it handles
termination and restart, and every mapping set it names that the file or your project declares — is
always written. What it **does** — its runnables — is written only when every reference it makes is
answered; otherwise the component is written without its `runnables` and without each mapping set
found nowhere, and the report lists each missing reference in a block of its own, *References the project does not have*, one line per
reference naming the element that refers and the element that is missing, never a path:

```text
SWC Comp: created
References the project does not have (1; the component's runnables and any mapping set listed below are withheld; its ports, interfaces, description and resolved mapping sets are written):
  - swc 'Comp' runnable 'R' read through port 'rSig' names the data element 'a', which the interfaces element 'ISig' does not declare
```

The same block reaches `--dry-run`, a `--report` file and the assistant's `import_component` answer.

- **A port whose interface neither the file nor your project declares** — or whose interface of
  that name in your project is of another kind — is written on an external interface holding the
  source's path, as `swcraft import model` writes one; where your project already holds an external
  interface for exactly that path and that kind, that one is reused and nothing is created; one for
  exactly that path but another kind refuses the import naming both (one path cannot be two kinds
  of interface). Both are marked *(external interface stub)* in the report's `CREATED` and `REUSED` lists.
  Every read, write, call or event through such a port is a missing reference, so the runnables are
  withheld: what an external interface lists was named by the file, never declared by anyone.
- **An update into a component your project already has** keeps your runnables, events, accesses,
  mapping sets and termination handling when the file's are withheld, and takes the file's ports and
  description over them — but only when nothing your runnables use breaks. A removed port, a changed
  direction, an interface without an element a runnable reads, or a by-value read of an element that
  became queued is a conflict naming the reference, and nothing is written. Without `--update`, a
  component whose described part equals yours is reported unchanged. A component your project holds
  only as an external component has no runnables to keep: `--update` replaces it with the file's, as
  a create would write it.
- **Every value of a port's communication specification that SWCraft does not carry** — an
  attribute, a child, an initial value it cannot read — is now a line under *Not carried from the
  file*, and the port is written without it; in `import component` such a value used to stop the
  import. A data element's own initial value that is not carried still stops it. In `import model`
  nothing written or reported changes.

Unsupported content still stops the import with nothing written, and so does every name that is not
a legal AUTOSAR identifier. SWCraft's own export of a component that reaches an external interface or
type is still refused: such a file could not be imported back whole.

**What this does not reach.** A data type the file names but does not declare is not looked for in
your project; the import still stops on it. The tasks your runnables are mapped to are neither read
nor changed, and whether they still map the component's runnables after an update is
`swcraft check-model`'s question. A component whose ports speak an application type or an
enumeration needs a mapping set that pairs it: a set found nowhere is a missing reference, and
`swcraft check-model` reports the type it would have paired — and `swcraft generate arxml` refuses —
until you declare it; a set the file or your project declares stays named when the runnables are
withheld. A port an update adds whose type your kept sets do not pair is reported the same way.

**What upgrading takes:** nothing. A component file this release refused may now import, with its
runnables withheld and the missing references listed; read the report, add what is missing to your
project or correct the file, and import again with `--update` to take the runnables.

## A query can follow a path, compute two values and join

`swcraft query` and the assistant's `read` tool answer three new kinds of question, and they
answer them alike: the command reads the same request the tool takes.

- **A path of nested lists.** `--members runnables.writes` (and `"members": "runnables.writes"` in
  a read) lists every member of a list nested inside another, each row naming its owners — the
  component as before, and the runnable under `through`.
- **Computed values.** A request may name `derived` values SWCraft computes from the model:
  `connection_ends` on `connectors`, each connection's providing and requiring component and port
  followed through compositions, and `base_type` on the data elements runnables read or write, the
  implementation type the element resolves to and its base type. `discover` lists both, with the
  shape of each value, under `reads.derived`.
- **A join.** `join` combines a read's rows with the rows of further reads where named values are
  equal; a row with no match is dropped.

`swcraft query --request FILE` takes the whole request from a JSON file — the tool's request
without `operation`, addressed to one layer — and is refused beside a layer name or any other
slice or walk option. A request carrying `derived` or `join` must say `"form": "index"` and is
answered as rows; on the command line those print under `rows` in a JSON document whose
`schemaVersion` is **4**, while every other `query` document stays at **3**. The
command-line guide shows the sender-receiver table — writer, runnable, data element, types, reader
and its runnable — as one such file.

**What changes for a request that worked before.** The new keys are additive: a request without
them answers as it did, byte for byte, with exactly five exceptions.

1. A `members` value with an empty step — `"."`, `".ports"`, `"ports."` — was refused as
   `unknown-field` and is now refused as `schema-violation`.
2. The refusal of a `members` name no element declares says *an element kind at that step* where
   it said *top-level element kind*.
3. Every answered `discover` carries the new `reads.derived` and `reads.join`, so the default
   `discover` on the bundled example grows by 474 bytes; with this release's decomposed safety
   levels it measures **34 151** (about 43 % of the response budget). A `discover` that is refused carries no `reads` block, but the size its refusal
   reports grows by the same bytes; its code and hints are unchanged.
4. A `members` value naming a declared path, such as `"runnables.writes"`, was refused as
   `unknown-field` and is now answered. A dotted value that names no declared path is still
   `unknown-field`.
5. `swcraft query --members operations` or `--members data_elements` over `interfaces` used to list
   an external interface stub's members as rows with a `null` member; it now skips the stub, as the
   assistant's `read` always has, so the two answer the same rows.

**What it does not reach.** The rows are per component **type**: a component placed twice in the
compositions joins its rows across both places. A connection to an external component SWCraft
knows only by name has no runnable and drops out of a join through readers. A `null` value matches
nothing in a join, as in a database's inner join: a row that cannot state a joined value drops out.
The assistant's answer is held to the response budget and paged like any other read: a page too
large is refused with a smaller page to try. The further reads a join combines are not measured on
their own, and every page computes the whole join again before it is windowed, so the server caps
the rows a join builds: a join whose rows would number more than **50 000** in total, summed over every further
read it combines — counted exactly before any row is built, and published under `reads.join` — is
refused whatever page size the request asks for, and
offers no page to try instead: narrow either side with `where`. Without that cap, 1 500 rows
meeting 1 500 rows on one shared value made 2 250 000 rows in 31 seconds, measured; at the cap a
page costs about 0.7 seconds. The cap counts only those rows. Each further read is computed in full
before it is consulted, on every page, so one request combines at most **8** further reads
(published as `reads.join.max_entries`): a ninth is refused as `schema-violation` before anything is
read, by the assistant's `read` and by `swcraft query --request` alike. Give each further read its
own `where`. The command line's answer is not capped by rows, and its speed on a large project is
unmeasured.

**What upgrading takes:** nothing, unless a script relied on one of the five exceptions above.

## The build's own checks run less often, and lose less to the network

This changes nothing in what SWCraft does on your machine; it is how the release you install is
checked before it is published. The gate runs on two machines, one Linux and one Windows. A push of
a working branch no longer starts a run there — a branch is checked by starting the gate by hand,
on both machines at once — so a branch no longer costs one run that the next one cancels. When a
branch that already passed on both machines becomes the head of `main` unchanged, the run for
`main` takes that result over instead of repeating it: each machine still checks itself and fetches
the sources, and skips every test. A release tag always runs the whole gate. The download of the
Python, Node.js and editor-extension files the installation archive carries now retries a dropped
connection, a timeout or a server error three times, after 5, 15 and 45 seconds, before it gives
up, and says how many attempts it made; an address the server answers it does not have (a 4xx
answer other than 429) or a file whose checksum differs from the recorded one still fails at once.
Each stage of the gate now has a time limit of its own on both machines (between 10 and 60
minutes, below the job's), so a test session that never returns ends as that stage's failure
within the hour rather than holding the machine for the job's whole ceiling; the check that proves
the per-test timeout works runs its probe in one process, where it is the timeout's alone.

**What upgrading takes:** nothing.

## Every MCP tool result is sent once

Until this release the assistant's server put every tool result into its reply **twice**: once as
structured content and once as a text block holding the same document again. A client read one
copy and paid for both. The default short description of the model (`discover` with no `form`)
measured 60 888 bytes on the bundled example, of which roughly half was the second copy.

Now every one of the 13 tools answers with **one text block** and no structured content, and the
tool list publishes no output schema. A tool that answers with a mapping — `discover`, `read`,
`change_set`, the two checks, `validate`, `build` and the three component tools — sends it as
compact JSON in that block; `model_diff`, `impact_of` and `resource_report` send their text as it
is. A note the server adds to a change set's answer is still its own block after the answer. The
same `discover` measured **33 085** bytes in one copy, about 41 % of the response budget where it was 76 % (34 151 with this release's partition trust, query additions and decomposed safety levels).

The response budget itself did not change: it is still 80 000 bytes, and `discover` still
publishes it. It now counts the one copy that is sent, so every response has nearly twice the room
it had, and a read the server refused before may now answer — the ports of a wide component, say. A read too large for the
budget is still refused with hints, never cut.

**In `swcraft agent chat`** you may notice three things in what the assistant shows of a tool
result. An answer in JSON arrives compact, without spaces, and with non-ASCII characters as they
are rather than as `\uXXXX` escapes. A text tool's answer is no longer wrapped in `{"result": ...}`:
the report arrives as plain text, a refusal starts with `ERROR:`, and an answered port
compatibility check reads `{"ok":true,"reason":""}`. The note after a change set's answer is
unchanged.

**What this does not reach.** A client that reads only a tool result's structured content now
receives nothing. `swcraft agent chat` reads the text block, which is tested; Claude Code and GitHub
Copilot are expected to read it but were not tested by this release. The
command line is unaffected: `swcraft query` writes its own JSON, as before.

**What upgrading takes:** nothing, unless you script around the assistant's server. A script that
read a tool result's `structuredContent` reads the first text block instead and parses it as JSON
where the tool answers a mapping; a script that unwrapped `{"result": ...}` from a text tool takes
the text as it is.

**The four tools whose instructions never reached the host now send them whole.** A tool's
description is what an assistant reads before it calls it. Four tools — `discover`, `read`,
`change_set` and `impact_of` — kept part of their instructions after the argument list, where the
server library does not publish it: the three outcomes of a change set, the refusal codes of a read
and what to do on each, the rule that a reply over the budget is refused rather than cut, and the
sentence that a read consults no scope and writes no audit record. Those paragraphs now come before
the argument list and are published; the reasoning written for developers moved into the source
beside each tool and costs the host nothing. The published descriptions of the thirteen tools
grew from 13 927 to 17 479 characters, and a check holds that no tool's docstring carries text
after its arguments again. `impact_of`'s `name` argument also gained the description it never had.

## Your own component exports import back

A component file SWCraft exported from a project it had imported could be refused when it was
imported back. The project holds an application type with no unit, conversion or range beside an
implementation type of the same name as **two** elements, paired by a mapping set, when a record or
an array of the project names the application type. A component's file carries only what that
component needs, so in the file nothing names the application type any more; `swcraft import
component` then reduced the pair to the one implementation type, as `import model` does, and the
mapping set's row became a type paired with itself, which stopped the import.

Two things change, both in the import:

- **A pair your project holds is kept.** When the project you import into declares both members of
  such a pair — an `application_type` element and an implementation type of its name —
  `import component` keeps the pair as your project keeps it, both elements and the row between
  them, and reads the component against them.
- **The row of a pair the import reduces is a line, not a refusal.** Into a project that holds no
  such pair, the pair is still reduced to the one implementation type, and the mapping set's row that
  paired the two is listed under *Not carried from the file* — *the map row of the same-name pair
  'X' is folded into its collapse: both sides are the one implementation type 'X'* — beside the
  reduction's own line; the set is written without it. A row whose two sides are one type for any
  other reason — the file's own, such as a second row pairing the application type with itself —
  still stops the import. That includes a row pairing a type with itself after the row of a pair
  that is kept: both `swcraft import model` and `swcraft import component` now refuse it, where
  before it was listed as a repeated row and accepted.

Checked against real tool exports the maintainer holds privately: such a file now imports
back, reported unchanged into the project it was exported from and created into an empty project.
No byte of any ARXML SWCraft writes moved, and `swcraft import model` writes the same elements from
every file it accepted before; in its
report the row keeps its line under *Not supported by SWCraft*, in the new wording, and that
section's count does not move.

**What this does not reach.** `swcraft import model` has no project to consult, so it reduces such a
pair as before. A component file whose interface element carries an initial value under such an
application type, where the implementation type references a table, can still stop an import into
a project that does not hold the pair.

**What upgrading takes:** nothing.
