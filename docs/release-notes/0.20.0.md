# SWCraft 0.20.0

Released 2026-10-28. The release where the panel answers in VS Code: a change set an assistant
proposes is reviewed in a **review tab** that works with every client, Copilot, Codex or Claude,
not through Copilot's elicitation alone; Build ends in a **build report**; Impact is a **view**;
Resource Report is a **Resources** view whose fit question has two verdicts; a finding's rule name
in Problems opens the guide at that rule; and `swcraft guard` speaks Codex, so a Codex session is
held to the same model guard as a Copilot one. The MCP server still has twelve tools. The ARXML
SWCraft generates and the model's format are unchanged from 0.19.2; one answer changed its shape
(*The fit question*, below). *What upgrading takes* at the end has three steps beyond the pin:
running *Onboard Project* again, for Codex trusting the new hook, and taking the template's build
task so that a build writes its report.

## The review tab: every client reviews a change set

A change set commits only after a human answers the review question. Until now the server could
ask in one way, MCP elicitation, which Copilot answers and Codex declines, so every change set a
Codex session proposed was abandoned without a human answer. 0.20.0 adds a review mode, `panel`:
the server stages the change set, writes the pending question into your SWCraft home, outside
every workspace, and waits; the SWCraft extension opens a **review tab** with the server's text
and two buttons, **Approve** and **Reject**; one click decides, and the server binds the decision
to the change set and to the exact text that was shown. Only an affirmative answer commits. A
**Pending Change Sets** view in the SWCraft panel lists every waiting question and reopens a tab
closed unanswered; the second, independent question about a weakened check goes through the same
tab; the audit record names the channel. The SWCraft extension registers the server with the
review tab for every client, Copilot included; a server you start yourself, or a chat
configuration you wrote by hand, says `SWCRAFT_REVIEW=panel` (or `elicit`, for a client that answers
a server's question in its own chat), and a server given neither does the work and writes nothing,
as before. Use the review tab only with an assistant that works confined to the project folder: a
process that can write your home could answer in your place. The guide's *Review in VS Code* lists
what the channel does not reach.

## Build ends in a report

`swcraft validate --report` writes `<dist_root>/build-report.md` once it has generated the ARXML,
whether the ARXML check then passes or fails: the verdict with its mode (XSD or structural) stated;
what was built, each output on disk or absent; the findings the run listed; every core and memory
with its use, limit, headroom, physical headroom and status; and the ARXML elements added, removed
or changed against the previous ARXML the build kept aside. The template's build graph and the
panel's Build pass `--report`, so `moon run :build` and Build write the same report. In VS Code,
Build ends in Problems when its model check placed an error there, and otherwise in the report,
opened in the Markdown preview the Change Report uses. The report is computed, never written by an
assistant, and is no qualification evidence: `swcraft validate`'s exit code stays the one verdict.

## Impact is a view

*SWCraft: Impact of This Element* (the id `swcraft.impact` is unchanged; the palette title was
*SWCraft: Impact*) draws what depends on an element in the new **Impact** view of the SWCraft side
bar: the element asked as the root, its dependents grouped by layer with their counts, each with how
the walk reached it; a layer of more than twenty dependents collapsed; a click opens the dependent's
file at its element's line. It is asked from the element's file, from the editor's context menu, the
Command Palette or the *impact* lens, about the element under the cursor. The panel's *Model → Impact*
item and its element picker are gone, and the Output channel keeps the log only; the text answer is
`swcraft impact` in a terminal, whose output and JSON are unchanged.

## The fit question has two verdicts

"Does X fit this core or memory" answered with one verdict, `fits`, measured against the threshold,
and an assistant reading the headroom off the overview compared the numbers itself and got it wrong.
`swcraft resource-report`, the MCP tool `resource_report` and the profile's recipe now answer
with two: `within_threshold` (the limit `size × threshold`, the headroom to it, yes / no / unknown,
what `fits` answered) and `within_size` (the limit `size`, or 100 % for a core, and the headroom
to it). `fits` stays the top-level answer and equals `within_threshold`; a sentence states the case
the two split on, *fits physically, breaks the threshold by N bytes*; the overview rows gain the
physical headroom. A reader of the JSON that took `fits` alone reads the same value as before.

**Resource Report is a view, *Resources***, in the SWCraft side bar: per core and per memory the
budget, the use, the headroom and the status, coloured by state, expandable to the consumers with a
jump to each file, and a *Does It Fit…* question answered by the two verdicts. Its data is a new
versioned JSON form of `swcraft resource-report`; the Output channel keeps only the log.

## Help at the finding

The guide's *Checks* page gives each check's row an anchor named by the check's rule, and in VS Code
a finding's rule name in the Problems panel is a link that opens the page at that row, starting the
guide first when it is not served. A refusal for a window without a folder or without a project, and
a run refused because the project pins another release, carry *Learn more*, which opens the guide's
section on what to do. A rule name, *Learn more* and *Open Guide* share the window's one guide tab.
Known limit: the guide stops with the window, so a guide tab VS Code restores after a reload shows a
page that cannot be reached; the next link opens a new tab.

## The model guard speaks Codex

`swcraft guard --host codex` renders its deny in the one shape Codex's `PreToolUse` hook accepts
(a deny in Copilot's shape is a failed hook to Codex, which then runs the tool anyway), and judges
Codex's own tools: `apply_patch` (any file the patch adds, updates, deletes or moves to inside the
model directory) and the shell (any command whose text names a path at or inside the model
directory, with the readers it allows on the project's manifest alone). The template and *Onboard
Project* write the Codex hook file, `.codex/hooks.json`, beside Copilot's
`.github/hooks/swcraft.json`; the Copilot hook's command, rendering and decisions are unchanged.
It is a guardrail, not an enforcement boundary, in Codex's own words for its hooks, and the guide
lists what it does not reach (*The model guard under Codex*).

## Six small moves in the panel

Check Model moves the focus to Problems when it finishes, and a status-bar item shows the counts
(`SWCraft: 0 errors · 35 warnings`); Export Component opens the exported ARXML in an editor; the
Setup section keeps its three commands and collapses once the toolchain is installed and the
project onboarded; Open Guide and Check Editor Tooling live in the view title's overflow menu and
the Command Palette; Open Guide opens the guide in VS Code's Simple Browser; and the walkthrough
*The first hour with SWCraft* was re-read against the moved places.

## For contributors: one specimen generator

SWCraft's test tree no longer carries a model generator of its own. The synthetic models its
functional scenarios, passport tests, benchmarks and the agent task benchmark's large bench read are
**specimens** written by an external specimen generator, pinned by tag, from eighteen committed
passports, generated on demand into a gitignored cache and held to a pinned digest every time a
test takes them; git holds the passports and the pins, never a generated model. `python
scripts/dev.py install` gains a last step that provisions the pinned generator from the release
store, with the read-only reader key an environment variable names, so a contributor's machine
needs that key and the store reachable for the fast gate; the first fast-gate run on a machine
generates the specimens once (about 11 s), later runs only check digests. Nothing a user's project
reads changes: no product command, no model file format, no passport schema version. Two harness
facts of the release: `pytest` is pinned below 9.2 (9.2.0 broke `pytest-benchmark`'s fixture), and
the runtime pins did not move (`update-pins` rewrote nothing).

## What upgrading takes

1. **Install the 0.20.0 archive, then set `toolchain_version: "0.20.0"`** in each project's
   `swcraft.yaml`. Until you do, every command that writes or gates refuses a project pinned to
   0.19.2 with the pin sentence. The read-only commands (`diff`, `impact`, `list`, `query`,
   `resource-report`) and `swcraft guard` only print a warning, so an assistant keeps working
   meanwhile.

2. **Run *SWCraft: Onboard Project* again.** It brings the assistant profile, the Copilot
   instructions and the model guard up to date, and writes Codex's model guard, `.codex/hooks.json`,
   which a project set up earlier does not have. It overwrites the three, so keep a copy of anything
   you edited in them; a `.codex/hooks.json` that is not SWCraft's is left as it is, and the command
   says so.

3. **If you use Codex**, trust the new hook once with `/hooks`, and set `SWCRAFT_REVIEW=panel` on
   the server you register for it, so its change sets reach the review tab
   (the guide's *The assistant* has the configuration). Make the edits of `swcraft.yaml` this upgrade asks for
   yourself: the guard does not let Codex edit it.

4. **A reader of `swcraft resource-report`'s JSON** that compared the headroom itself reads the two
   verdicts instead; one that read `fits` alone needs no change.

5. **A project with a build graph takes the template's `validate-arxml` task** to get the build
   report from `moon run :build`: the task passes `--report`, depends on `generate-diagrams` and
   `generate-rst` as well as `generate-arxml`, lists `dist/build-report.md` among its outputs and
   runs with `cache: false`, so every build writes a fresh report. A project that keeps its old
   task builds as before and writes no report; nothing else in `moon.yml` moved.

Nothing else moves in a project: the model's files, the Copilot hook file `.github/hooks/swcraft.json`
and the generated ARXML are unchanged from 0.19.2. A project on 0.19.1 or earlier follows
[0.19.2's note](0.19.2.md) first.
